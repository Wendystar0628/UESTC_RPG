# WF-DOC · 文档写法

> **范围**：本文规定 `docs/design/` 里规范文档怎么写、怎么起名、怎么引用、冲突怎么判、新文档怎么加、谁来维护。
> **不在本文**：全员的写作取向（只写现行规则、不抄实现、一份权威）：WF-RULE §12；决策的内容：CORE-DECISIONS；记录类文档（提案、问题、实验）的状态取值：各自文件夹的 README。
> **查阅**：先读 §0；文件头看 §1；标题、范围块、§0 与接入要点看 §2；编码与引用看 §3；正文写法看 §4；待验证节看 §5；冲突看 §6；新增文档看 §7；登记决策看 §8；谁维护、怎么重建索引看 §9。
> **关联**：[WF-INDEX 协作总纲](../WF-INDEX-协作总纲.md)、[WF-RULE 全员守则](WF-RULE-全员守则.md)、[CORE-INDEX 总索引](../../README.md)、[CORE-CONVENTIONS 约定](../../core/CORE-CONVENTIONS-约定.md)、[CORE-DECISIONS 决策登记](../../core/CORE-DECISIONS-决策登记.md)、[ENG-WP 工作包](../../engineering/ENG-WP-工作包派工单.md)、[ENG-GATES 验收门禁](../../engineering/ENG-GATES-验收与门禁.md)、[ENG-ARCH 工程架构](../../engineering/ENG-ARCH-工程架构.md)

## 0 结论

1. **每份规范文档的结构一样**：文件头、标题、范围块、§0 结论、§0 末尾的接入要点（§1、§2，D-178）。
2. **文件名就是编码**：`编码-中文简题.md`，正文按编码引用；改名、拆分、重编号时全局替换，不留对照（§3，D-200、D-208）。
3. **只写现行规则**：数值只有一个家，不抄实现，不写证据、修订说明和用户原话（§4）。
4. **冲突按层级判**：用户决定、CORE-DECISIONS、权威文档、系统自己的文档、其他摘录；判定不了的报主会话（§6）。
5. **改完重建索引**：重跑 `gen_index.py`，再跑 `check_docs.py`，problems 为 0（§9）。

### 0.1 接入要点

- **写或改规范文档**：按 §1–§4；新增文档按 §7，登记决策按 §8。
- **发现文档冲突或与 CORE-DECISIONS 不一致**：施工期间不改 `docs/design/`，写进回报，由主会话定案（§6）。
- **改了编号、文件名或章节结构**：所有引用一次改到新位置，包括 docs 以外的任务单、简报、角色说明（§3）。

## 1 文件头

每份文档以 YAML front matter 开头，放在标题行之前。字段：

| 字段 | 写什么 |
| --- | --- |
| `id` | 文档编码，与文件名的编码部分相同，例如 `SYS-WEATHER`（§3） |
| `title` | 与标题行 `# 编码 · 标题` 的标题部分一致 |
| `category` | 所在文件夹的类别名，见 §3 的表，例如 `systems`、`maps`、`workflow` |
| `status` | 只用于记录类文档（RFC、ISS、EXP、ADR），取值见各自文件夹的 README |
| `summary` | 一句话说清本文规定什么，不超过 60 字 |
| `keywords` | 检索词，10–30 个：本文的核心概念、契约与类型名、数据与着色器文件名、常见的同义说法；只写本文是权威来源的（D-178） |
| `owners` | 主责工作包（实现本文主体的包） |
| `contributors` | 按本文有增量交付的其他包 |
| `depends` | 读懂、实现本文必须先读的文档编码 |
| `related` | 有交叉、需要对齐的文档编码 |
| `contracts` | 本文定义或拥有的契约、类型名（以 ENG-ARCH §3 为准；没有写 `[]`） |
| `data` | 本文规定的数据文件或目录（没有写 `[]`） |
| `gates` | 验收本文内容的门禁（ENG-GATES） |
| `paths` | 可选。这份文档管哪些仓库相对路径，YAML 列表，每项是 glob，只支持 `**`、`*` 和字面量，例如 `[".collab/notes/**", ".collab/requests/**"]`；只给确实管某类路径、又没有工作包归属的文档写（workflow 文档和少数通用文档）。`gen_index.py` 把它收进 `ROUTES.json`，钩子在模型读、改这些路径时注入本文的接入要点 |

- 工作包、契约、门禁要与 ENG-WP、ENG-ARCH §3、ENG-GATES 核对，不能自己编；这些字段供脚本生成总索引和工作包矩阵。
- 示例：

  ```yaml
  ---
  id: SYS-WEATHER
  title: 天气
  category: systems
  summary: 一句话说清本文规定什么
  keywords: [天气, 天气向量, WeatherVec, 降水, 积雪, 湿度, 雨, 雪]
  owners: [WP-45]
  contributors: [WP-03, WP-40]
  depends: [CORE-INDEX, ART-STYLE, ART-SKYLIGHT, ENG-ARCH, SYS-TIME]
  related: [SYS-MOTION, SYS-AUDIO]
  contracts: [IWeatherProcess, WeatherVec, WeatherSel]
  data: ["game/data/weather/"]
  gates: [G12, G13, G21]
  ---
  ```

## 2 标题与范围块

- front matter 之后第一行是 `# 编码 · 标题`，例如 `# SYS-WEATHER · 天气`。
- 紧接一个 3–6 行的引用块：

  ```
  > **范围**：本文规定……（一两句）
  > **不在本文**：……（指向负责的文档编码）
  > **查阅**：先读 §0；……看 §x；……看 §y（3–8 项，说明什么内容在哪一节）
  > **关联**：[编码 简题](相对路径)、……（按 depends 和 related 给相对链接）
  ```

- 有具体分工信息的（例如"X 由 WP-23 负责"），写成正文里的"### 分工"一段或原位的简短列表。
- **§0 与接入要点**（D-178）：
  - 规范文档在范围块（和"### 分工"）之后写 `## 0 结论`：5–12 条，每条一两句，指向细则所在的小节。
  - §0 的最后一个小节是 `### 0.N 接入要点`，写给不负责本文的其他包：碰到本文管的东西时必须遵守的规则。每条一行，写成 `- **<什么时候>**：<必须怎么做或不许怎么做>（§n.m）`；只写对外的约束、接口和数据位置，不写内部实现。没有对外要求的，写一句"本文只约束 <包号>，没有对其他包的要求。"
  - `scripts/docs/gen_index.py` 与钩子都按标题文字"接入要点"找这一节，所以标题文字不改，不认编号。
  - **接入要点自成一体**：它会被单独注入，不超过 1800 字，只写别的包必须守的规则；本文自己的交付说明按"WP-nn 做 yy 时"写，不放进来；不用"同上""见上文"，要指的东西写明 `§n`。
  - 改本文档时钩子还会注入范围块里的"范围"与"不在本文"两行，两行要能独立读懂。
- **便于单独阅读**：标题写清内容，不只写"其他""补充""细则"；正文不用"同上""上文所说"这类要靠上下文才懂的指代，写明 §n.m 或具体名称。
- **超大的节要有 `###` 小标题**，小节目录才能定位到它。

## 3 编码、小节编号与引用

- **文档编码与文件名**：文件名是"编码-中文简题.md"，编码全大写英文加连字符，在全库唯一，是检索键；中文简题让人一看就懂（D-208）。拆分、合并、重组时可以改，改了就全局替换（D-200）。
  - **规范文档**：`<领域>-<主题>`，例如 `SYS-WEATHER`、`UI-VISUAL`。按图的文档再带图名：`MAP-<图>-<主题>`，清水河的图名缩写是 `QSH`，例如 `MAP-QSH-CORE`。
  - **记录类文档**：`<类>-<领域>-<短名>`，类是 `RFC`（提案）、`ISS`（问题）、`EXP`（实验）、`ADR`（重大决策），例如 `ISS-SYS-SAVE-FLUSH`；领域取规范文档的前缀；状态写在文件头的 `status`。结果定下后写回规范文档，规范文档不引用提案和问题。
  - **领域与文件夹**：

    | 领域前缀 | 文件夹 | 放什么 |
    | --- | --- | --- |
    | CORE | `core/`（总索引是根目录的 `README.md`） | 总索引、决策登记、约定、术语 |
    | WF | `workflow/`（下分 `collaboration/`、`process/`、`management/`、`rules/`） | 模型协作、开发流程、项目管理、规则与守则 |
    | ART | `art/` | 风格、天空光照、视觉精度、造型 |
    | WLD | `world/` | 不分图的世界内容：箱庭、植被、水、生活痕迹、外围、室内 |
    | MAP | `maps/<图>/` | 某一张图的分区内容，清水河在 `maps/qingshuihe/` |
    | SYS | `systems/` | 运行时系统 |
    | UI | `ui/` | 界面内容与视觉语言 |
    | ENG | `engineering/` | 门禁、架构、预算、工作包、性能、扩展路线 |
    | REF | `reference/` | 参考材料，不是施工文档 |
    | GAME、NARR、CHAR、CONT、TOOL、QA、OPS、L10N | `gameplay/`、`narrative/`、`characters/`、`content/`、`tools/`、`qa/`、`ops/`、`localization/` | 待用，见各文件夹的 README |
    | RFC、ISS、EXP、ADR | `proposals/`、`issues/`、`experiments/`、`decisions/` | 记录类文档 |

- **小节编号**：小节号只在本文内有效，不带文档前缀，例如 `## 6 自动天气`、`### 6.4 种子`。多数文档的第一节是 `## 0 结论`。编号稳定，别的文档靠它引用。
- **新小节**加在所属一级节的末尾，取下一个空号，不插号、不重排。整节作废或搬走就直接删，所有引用同批改到新位置，不留占位标题。
- **改结构、改编号时全局替换**：文档拆分、合并、重新编号或改名时，所有引用一次改到新位置，不留旧编号对照表、兼容段或"原 §x 现见 §y"；docs 以外引用了它的文件（任务单、简报、角色说明、记忆等）同一批改掉（D-200）。
- **引用写法**：
  - 跨文档写"编码 §小节"，例如 `ENG-ARCH §3`、`SYS-WEATHER §6.4`；范围写 `SYS-WALK §6–§8`；
  - 本文内只写 `§6.4`；
  - 引用整份文档直接写编码，例如"见 SYS-WEATHER"；
  - 全局不变量写"INV-6"，决策写"D-133"，门禁写"G19"；
  - 编号列表里的一条写"ENG-BUDGET §7 第 9 条"。
- 正文里第一次提到别的文档时写"编码 §小节"，不必逐处加链接；链接只放在范围块的"关联"里。回报里引用条目只写编码和小节，不复述内容（WF-ONBOARD §4）。

## 4 正文写法

- **只写现行规则**：不写修订历史、用户原话、"原写 X，改为 Y"这类过程记录，现行规则直接陈述。
- **不写证据**：调研发现、照片与报道、来源链接都不写。解释"为什么这样设计"的一句话理由可以保留，它是施工共识。
- **链接**：只留施工要用的技术文档（Godot 官方文档、API、规范条文）。
- **数值只有一个家**：某个系统的数值以该系统自己的文档为准（门的参数以 WLD-INTERIORS §4.1 为准，天气以 SYS-WEATHER 为准）；别处引用时写指针，必须抄数值时注明出处，改的时候一起改。已在代码或数据里实现的内容不抄，写一句以哪处为准（WF-RULE §12）。
- **写结构与规则，不写实现**：规范文档说清当前结构、要守的规则、设计目标和后续导向；实现做法和实现细节（类型签名、目录明细、文件格式字段、参数表、逐类型的清单、内部流程步骤）以代码和数据为准，不在文档里维护一份（D-215）。
- **观光规则照写**：写死观光模式的规则（不出现人物、没有可以点选的东西、只有一个偶发事件等）照常写成规则；它们怎样成为观光规则集的配置，由 ENG-ROADMAP 统一登记。

## 5 待验证（P0）节

- 文末加一节，标题按本文编号接在最后一节之后，例如 `## 12 待验证（P0）`。
- 收两类项：会影响施工、要在 P0 原型上核实或实测的数值和做法；文中"待定""需要原型看图"的项。
- 每条写三样：待验证的内容；验证方法或负责包；验证前用的初值。正文原位只留初值。
- 没有这类项就不加这一节。

## 6 冲突与决定层级

文档之间、或文档内部有互相矛盾的设计时，按下面的层级判定，从高到低：

1. **用户的决定**（登记在 CORE-DECISIONS）；
2. **CORE-DECISIONS 登记的其他决策**；CORE-DECISIONS 每条只写现行决定，决策有变时改写原行（CORE-DECISIONS §0）；
3. **权威文档**（D-133）：契约以 ENG-ARCH §3 为准，帧顺序以 ENG-ARCH 为准，全局参数以 ENG-PERF §1.5 为准，预算以 ENG-BUDGET 为准，门禁以 ENG-GATES 为准，工作包以 ENG-WP 为准；
4. **系统自己的文档**：某个系统的细则以它自己的文档为准，例如门参数以 WLD-INTERIORS §4.1 为准、天气以 SYS-WEATHER 为准、存档以 SYS-SAVE 为准；
5. 其他文档里的摘录与速查，包括 CORE-CONVENTIONS。

- CORE-DECISIONS 的一句话结论与细则文档有出入时，按细则文档施工，并报主会话（CORE-DECISIONS §0）。
- **能按层级判定的**：改低层的那一处，使之与高层一致。**判定不了的**：不改，报给主会话，由主会话定案并登记进 CORE-DECISIONS。
- 施工期间子代理不改 `docs/design/`，发现冲突写进回报；文档整理由主会话分派时例外，按分派说明改。

## 7 新增文档与小节

- **新文档**：按 §3 取编码，放进对应的文件夹；写 front matter 和范围块，需要时在末尾加待验证节。文档地图 `docs/design/DOCMAP.md` 由脚本生成、不手登（§9）；由主会话同步改受影响的权威位置：工作包与起读（ENG-WP）、新门禁（ENG-GATES）、新契约（`game/contracts/` 源码）、新全局参数（ENG-PERF §1.5）、归属（`ownership.json`）。
- **新小节**：见 §3。
- 新契约、全局参数、着色器文件、程序集引用或 NuGet 包的需求，不在文档里先写成定论，而是在回报里申请，由 Astra 统一处理（WF-BUILD §1、D-134）。

## 8 登记新决策

- 新增或推翻决策时，主会话先登记进 CORE-DECISIONS，再改相关文档（D-154）。编号 D-001 起全文连续，不改、不复用；决策有变时改写原行；每条写一句结论、适用范围、细则所在和状态（生效、待原型验证）（CORE-DECISIONS §0）。
- 改相关文档时，正文只写决定后的现行规则，不写"某某定"。需要留下背景、选项和取舍的重大决策，另写一份 ADR（§3）。
- 子代理只读 CORE-DECISIONS；发现文档与它不一致时报主会话，不自行改动。

## 9 文档维护

- **谁改**：共识层、WF-* 和 ENG-WP、ENG-ARCH 等共享文档由主会话改（或由它分派、按确切文字改）；子代理需要改时在回报里提。
- **改完以后**：重跑 `scripts/docs/gen_index.py`，重新生成文档地图 `docs/design/DOCMAP.md` 和小节目录 `docs/design/SECTIONS.md`，再跑 `scripts/docs/check_docs.py`，problems 为 0。`gen_index.py` 按文件头的 `category` 分类，加新类别要改脚本里的分类表。
- **主会话改文档**：在主检出 `main` 上改，`git add docs/...` 只加文档，`check_docs.py` problems 为 0 后提交并推送；`DOCMAP.md`、`SECTIONS.md` 由改文档的人重跑 `gen_index.py` 一起提交（WF-RULE §7）。
