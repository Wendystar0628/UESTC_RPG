# WF-MODEL · 模型选择与子代理

> **范围**：本文规定每张单按什么选施工模型与推理强度，Opus 与 Sonnet 怎么分，最便宜的两档做什么，各方怎么开子代理，子代理什么时候恢复、什么时候新开，以及派工简报与"接续"段的写法。

## 0 结论

1. **按七问选够用的施工模型**（§1）：先分清未定判断与已定实现；审美相关的不交 GPT。
2. **Opus 只用在观感还没定的地方**（§2，D-193）：观感已由评审或已批样子定下的可见活交 Sonnet。
3. **最便宜的两档做不需要判断的活**（§3）：Gemini 管一件、小、要快的，luna 管量大、重复的。
4. **推理强度按难度选**（§4）：够用就停，Sonnet 只用 medium 与 high，不用 max。
5. **简单少量的活由拿到信息的一方直接做**，不转手（§5）。
6. **子代理默认新开，靠任务单的"接续"段交接**（§7，D-191）。

### 0.1 接入要点

- **写派工简报**：用 §8 的模板，只填本包特有的信息；守则、查资料和回报写在 WF-ONBOARD，不抄。
- **交候选时**：在任务单"状态"里写"接续"段（§8）。
- **开子代理**：按 §6；Codex 侧子代理共用工作目录，简报里必须写明工作树边界。

## 1 按七问选施工模型

依次看还缺什么判断、结果能否验收、错误会传播多远。混合任务先分清未定判断与已定实现，再按下表安排。

| 问题 | 倾向：模型与档位 | 复核或停止信号 |
| --- | --- | --- |
| 1. 要定造型、风格、声音、玩家可见参数或内容取舍，或制作可见构件吗？ | 需要审美判断的（造型、风格、观感取值，地标与重点构件，质感移植）由 Opus 子代理施工，主会话定案；只缺判断时主会话直接定。规格、尺寸、色名都已给全、难度较低的可见活（简单部件、按已定预设填数据、小修）交 Sonnet。审美相关的活一律不交 GPT，非可见部分可拆出继续问 | Opus 审美评审；接口与生命周期部分才加 Astra |
| 2. 必须读图或依赖中文语感判断吗？ | 按检查单读图初筛、中文改写交 Sonnet；可程序测出的数据与截图采集交 Sol。涉及审美回第 1 问 | Sonnet 不定风格；改变原意或含内容取舍时交主会话 |
| 3. 目标、规格和通过条件仍有歧义吗？ | 工程歧义交 Astra，设计与内容歧义交 Opus，定清再派实现 | 契约含义或规范冲突未定，先停相关项；不靠增加推理替代决定 |
| 4. 错误会跨接口、线程、资源寿命或存档扩散吗？ | Astra 定方案、边界与验收条目，施工默认交 Astra 名下的 Sol 子代理（high 或 xhigh）；Sol 两次做不对或方案本身要改时，Astra 才亲自做关键段 | Astra 定向复核调用方、所有权与迁移 |
| 5. 数学或几何很难，但能由不变量、参考结果验证吗？ | 非审美实现由 Astra 名下 Sol 施工；前提不清或全局耦合，先由 Astra 定清前提再交 Sol。可见构件仍回第 1 问 | 按风险核退化边界、真实引擎约定与确定性；数学成立不代替造型评审 |
| 6. 是大量明确执行或事实整理吗？ | Sol 旁路；工程子任务由 Astra 派 Sol。确需语言加工时再用 Sonnet，不因文件是中文就全部给 Claude | 漏条先由原施工者补；前提失效或反复理解错误再升级对应判断方 |
| 7. 是既有批准后的执行，或剩余明确非审美实现吗？ | 合并与状态交值班执行者，其余默认 Sol 实现，由相应负责方派单 | 候选号、批准条件或权限变化，先停相关项；只做改动需要的检查 |

## 2 Opus 与 Sonnet 的分界（D-193）

Opus 贵，只用在观感还没定的地方；观感已经由评审或已批样子定下来的可见活，默认交 Sonnet。

| 默认交 | 活 |
| --- | --- |
| Opus（high；地标与质感移植 xhigh） | 一个包或一类构件的首版造型，还没有已批的样子可照；地标与重点构件；质感移植与新的画面机制；评审里标明"要定""拿不准"的观感取舍 |
| Sonnet high | 评审已经写明怎么改的跟进单；照已批的样子铺到同类（其余的桥、门、楼按已批预设）；摆放规则、数据与覆盖层登记、树种与预设键；截图采集与重拍；素材收集；文档撰写 |
| Sonnet medium | rebase 与解冲突、按条目填数据、按确切文字打文档补丁 |

- 一张单里混着未定的观感和已定的实现时，把已定的部分拆出来交 Sonnet，Opus 只做未定的那块。
- Sonnet 的候选在观感上两次评审不过，再改派 Opus，不先升推理档。
- 换模型就是新开子代理（§7）；靠任务单的"接续"段交接。

## 3 最便宜的两档（D-194、D-202）

只做照清单执行、结果能机械核对、出错也不会扩散的活，不做任何判断。Claude 侧不设这一档，不用 Haiku。

- **简单快速档：Gemini 3.8 Flash High**：一件、小、要快的活，例如只改文档的合并、按确切文字改一处文档、查一处、追加一条状态、跑一次给定命令并报结果。派法与调用见 `.collab/tools/README.md`；它做完在主会话收件箱新建来信（发件方 `gemini`）。Antigravity 没开或发不出去，改派 luna。
- **批量苦力档：gpt-6-luna**：量大、重复、照清单的活，例如成批替换引用、全仓数据核对与盘点、成批截图与拼图、成批状态整理。luna 的花费几乎可以忽略，并发不设上限；默认快速模式。
- **谁开、怎么开**：拿到这件杂活的一方直接开（D-190），不必转手。GPT 侧的新活一律派进 Codex 应用里开着的会话（D-203）：在 Astra 或 Sol 会话里 `spawn_agent` 开 luna 子代理，或往作者开好的 luna 会话发（WF-COMMS §5）；不用 `codex exec` 另起看不见的线程。
- **怎么选**：一件、几分钟能完的交 Gemini；成批的、要跑很久的交 luna；两者都要判断的回到 Sonnet 或 Sol。一次做不对就改派 gpt-6.1-sol medium 或 Sonnet medium，不在原档上重试。等待、轮询和定时重跑索引交脚本做，不占任何模型。

两档能做的类别：

| 类别 | 做什么 | 不做什么 |
| --- | --- | --- |
| 状态与记录 | 照模板追加任务单"状态"行与流水；更新调研索引；依赖能机械判定时把队列条目改"可派" | 不判断依赖是否"算满足"，拿不准就留原样 |
| 文档机械编辑 | 按确切文字打补丁；重跑 `gen_index.py`、`check_docs.py` 并修它报的格式问题；按给定对照表替换用词 | 不改写措辞，不补内容 |
| 门禁执行与结果整理 | 按给定参数跑 `gate.ps1` 或单测，汇总通过与失败、失败的测试名和日志路径 | 不修代码，不判断失败原因 |
| 截图采集与拼图 | 按给定的位姿清单出图，做左右对比拼图，按约定命名存放 | 不评价观感 |
| 数据核对与盘点 | JSON 能否解析、id 是否唯一、引用是否存在、`licenses.json` 是否覆盖每个素材、文件编码；按给定条件 grep 出清单 | 不改数据，只报结果 |
| 机械 git | 没有冲突的 `rebase main`、按清单 cherry-pick、列出落后或已合并的工作树 | 一遇冲突就停下报告，不解冲突 |

## 4 推理强度按难度选

子代理不一律开 xhigh：每张单按难度选一档，写进派单。每升一档，费用和用时都明显上涨，完成度的提升却越来越小，够用就停。

| 难度 | 例子 | Opus | Sonnet | gpt-6.1-sol |
| --- | --- | --- | --- | --- |
| 简单 | 规格已给全，能按条目或程序验收：填数据、按已定预设接线、rebase 与拣选、单文件小修、查资料与整理、按确切文字打文档补丁 | 不派 | medium | medium |
| 一般 | 要自己规划实现，结果能按条目验收：常规部件与建模、普通接线与单测、截图采集 | high（需要审美判断的可见构件） | high | high |
| 难 | 判断重，或错误会扩散：地标与重点构件的造型、质感移植、跨包根因，确定性、并发、资源寿命、存档方案，契约方案 | xhigh | 不派，改派 Opus | xhigh |

- Sonnet 只用 medium 和 high；要 Sonnet 开 xhigh 才做得好的活，改派 Opus high。不用 max，施工不用 low。
- 返工沿用原档；同一档两次做不对，先按 §5"升级先找失败原因"查原因，确实是难度不够才升一档。
- 固定长期会话保持当前有效档：主会话、Astra 主线程 xhigh；Sol 值班 high，旁路 xhigh，都是普通速度。推理强度、速度层与账号容量分别记录。

## 5 升级、派单与直接做

- **升级先找失败原因**：已明确条目漏做，由原施工者补；接口或生命周期无解交 Astra 定边界；观感和内容争议交 Opus；超量或后半段质量下降按 D-184 拆单（WF-FLOW §2），不用升级模型代替拆单。
- **派单最少写**：目标与验收条目、定案与未定项、独占路径、模型/推理档/速度层、必要复核人、升级信号、预计工作量（D-184）。包内实现路径由施工者规划，任务单和简报只给目标、约束（主线优先、依赖、契约、目录归属、预算）和交付标准，不规定步骤。
- **组合只在需要时用**：Sol 实现 → Astra 核工程风险；Sol 程序采集 → Sonnet 读图初筛 → Opus 定观感；Sol 整理事实 → Sonnet 语言加工 → 主会话批准规范。每张单只列具体风险和对应复核人，小修与纯接线默认不叠 Astra 复核。
- **简单少量的活，拿到信息的一方直接做**：每转一次手都要花额度（写简报、对方重读上下文、再回报）。简单又量少的活，由已经拿到全部信息的一方直接做完，不再写单子转给别人；只有量大、要并行、要换模型能力，或者归属不在自己手里时才转派。

## 6 怎么开子代理

**各方都适用**：
- 一个包或子包一个子代理；同一时刻一个文件只有一个代理在写；每个子代理各用一个工作树（WF-MERGE §5）。
- 简报按 §8 的模板写。Claude 侧的子代理由 `CLAUDE.md` 自动载入开工手册与守则；Codex 侧的不会，简报里要写明先读 WF-ONBOARD、WF-RULE、WF-BUILD。
- `dotnet build`、`--import` 和烘焙这类重 CPU 任务，走 `..\UESTC_RPG.wt\.locks\` 下的计数锁（ENG-ARCH §6）。

**Claude 侧**（主会话开）：用 Agent 工具在后台开，指定 `model: "opus"` 或 `"sonnet"`；一个包一个，简报写明工作树绝对路径；子代理的最终回复就是回报。开之前按 WF-QUOTA §2 算并发。评审不通过时能否恢复原子代理见 §7。

**Codex 侧**（Astra 与 Sol 旁路会话）：用 Codex 的 collaboration 工具：`spawn_agent`（`task_name` 写包号，`message` 写完整简报）、`wait_agent`、`list_agents`、`send_input`。并发上限在 `~/.codex/config.toml` 的 `max_concurrent_threads_per_session`，每个会话各算各的；Sol 旁路另按 `side/ROLE.md` 最多 8 个。Codex 的子代理和主线程共用同一个工作目录，所以简报里必须写明：
- 你的工作树是 `E:\Project\UESTC_RPG.wt\<WP-xx>`，所有读写都用这个工作树下的绝对路径，git 一律 `git -C <工作树>`；
- 不碰别的工作树，也不碰主检出 `E:\Project\UESTC_RPG`；不合并、不推送。

## 7 子代理的生命周期：默认新开，靠任务单交接

每次请求都要把整段上下文重读一遍，缓存读也按输入价的约十分之一计，缓存几分钟不用就过期，过期后第一轮要整段重写缓存。恢复一个上下文已经很长的子代理去接新活，往后每一轮都在为旧历史付费，通常比新开一个、只读这次需要的文档和代码更贵。Claude 侧与 Codex 侧同样适用。

- **默认新开**：同包的下一张子单、新一阶段、跟原任务无关的活，一律新开；交接写在任务单的"接续"段（§8）。子代理交回以后就结束，不留着待命，不占并发名额。
- **只在两种情况恢复原子代理**：交回后几分钟内（缓存还在）就要改的小返工，例如评审意见里的几处修改、rebase 后的冲突，预计十几轮以内改完；或原子代理交回时上下文在约 8 万 token 以内，新任务是跟它刚做的事直接相关的小活。其余返工也新开，任务单写明改什么、改哪里。
- **恢复以后先对齐现状**：先看 `logs/merged.log` 和最新 `main`，`git rebase main`，再核对任务涉及的契约、数据与相关包的新提交；记得的旧版本不当现行依据。
- **记录**：任务单的"派出"行写明子代理的名字和类型；回报最后一行的 token 数是交回时的上下文大小，用来判断还能不能恢复。

## 8 简报模板与"接续"段

**简报模板**：主会话（或 Astra）派工时发给子代理，只替换尖括号里的内容；简报只写本包特有的信息，工作树、守则、查资料和回报都在 WF-ONBOARD，不重复。

```
你是《电光年华》的子代理，负责 <WP-xx 名称>。你向 <派你的一方> 回报。
工作树：<绝对路径>；分支：<wp/xx-slug>；任务单：<绝对路径>。
先读 WF-ONBOARD、WF-RULE、WF-BUILD（Claude 侧已自动载入；Codex 侧自己读），ENG-WP §2 主表与 ENG-WP §2.1 里 <WP-xx> 的行，以及任务单。
独占目录：<独占目录>。交付条目：<条目编号>。额度：三角形 <x%>，绘制调用 <y%>。
起读：<按 ENG-WP 起读栏的三档>。其余文档按 WF-ONBOARD §3 查。
<和本包相关的最近 24 小时合入（从 logs/merged.log 挑）；本轮的特别说明，可空>
完成后按 WF-ONBOARD §4 自检、截图并回报。
```

独占目录、交付条目、额度照本包在 ENG-WP §2 主表的对应栏填写；§3 拆出的子包填子包自己的子目录和分到的额度。

**"接续"段**：交候选时，在任务单"状态"里写一段，只填对下一张子单有用的几行，不求填满：
- **源与状态**：源提交，候选还是进行中，沿用了哪些已定约束（评审时间）；
- **接合**：部件装到宿主的哪个面、基点和安装方式；入口接哪一层；唯一的生产方和消费方；
- **重建**：从哪个生成入口、哪份参数或数据重建；有没有本机生成或缓存；
- **证据**：每批截图对应的提交与位姿；是不是沙盒或替身；
- **未完**：下一张子单要接着补的事，需要哪个包配合；
- **文字载体**：有牌面、题字、门牌的部件或楼，写明写什么字、批准留白的原因、在等什么。
