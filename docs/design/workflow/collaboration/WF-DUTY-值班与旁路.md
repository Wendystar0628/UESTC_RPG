# WF-DUTY · 值班与旁路

> **范围**：本文规定值班执行者怎么被叫醒、分派给谁、没回复怎么退回，值班做什么、不许做什么，完成度调研怎么排，以及 Sol 旁路会话怎么按任务单开子代理。

## 0 结论

1. **值班由唤醒脚本叫醒值班执行者**（§1，D-198、D-202）：只改文档的合并交 Gemini（不可用时 luna），其余合并、值班单与巡检交 Grok，没回复退回 Sol（每次新开一个 Codex CLI 会话，D-210）。
2. **批准即合**（§1，D-204）：新批准行一出现就成批合掉当时所有能合的，不攒时间窗。
3. **值班只做执行**（§2）：合并、施工状态、巡检、通知；不改代码和契约，不做审美判断。
4. **完成度调研由 Sol 旁路会话执行**（§3、§4）：一张单一次，按方向开 gpt-6.1-sol 子代理；调研入队流水线见 WF-FLOW §6。
5. **Sol 的边界**：不做审美，不改契约和共享工程文件，设计文档只按任务单给的确切文字打补丁；值班执行者另可维护施工状态。

### 0.1 接入要点

- **派值班执行者的活**：写成值班单 `tasks/sol/<nnn>-<主题>.md`，值班唤醒脚本发现新单就交出（§1）。
- **派旁路活或调研**：写成旁路单或调研单放进 `side/cards/`，旁路唤醒脚本一次交一张（§4）。
- **想让合并立刻发生**：在合并请求或任务单末尾写批准行（WF-COMMS §3），脚本按行首匹配。

## 1 值班执行者、唤醒与退回

值班唤醒脚本 `tools/duty_watch.sh` 与旁路唤醒脚本 `tools/side_runner.sh` 每 20 秒查一次；发进 Codex 会话都用 `tools/duty/codex_app_run.py`（WF-COMMS §5）。启动命令见 `.collab/tools/README.md`，同一个脚本只能有一个在跑；换账号或重启会话后先查进程再重启。

**值班唤醒脚本**按下面的顺序处理，一次只叫醒一轮：

| 发现 | 做什么 |
| --- | --- |
| `requests/*.md` 或 `tasks/<类>/*.md` 里新的行首"批准合入："行 | 立即开一轮合并：把当时所有已批未合、条件已满足的候选成批合掉（含滚动文档分支 `doc/rolling`）；有代码待合交 Grok（high），只有文档交 Gemini（不可用时 luna）。叫醒消息写明这一轮同不同步施工状态（每小时最多一次） |
| 否则：`tasks/sol/` 下新的值班单（`001-值班长期单.md` 除外） | 交 Grok（medium）读单执行 |
| 否则：距上次巡检满 60 分钟 | 交 Grok（medium）巡检；已批未合、条件已满足的顺手合入，到点就同步施工状态 |

**执行者与退回**（D-198）：值班执行者按难度分：只改文档的合并（批准行写了"只跑 check_docs.py"的）这类简单快速的交 Gemini 3.8 Flash High（发进作者开着的 Antigravity 会话，D-202），Gemini 不可用时交 gpt-6-luna（每次新开一个 Codex CLI 会话，D-210）；其余合并、值班单与定时巡检交 Grok 4.7（后台无界面调用，同一会话续用）。Grok 或 luna 没有回复、出错或报额度用尽，就把同一条消息退回 Sol：唤醒脚本用 `tools/duty/codex_cli_run.py` 新开一个 Codex CLI 会话（gpt-6.1-sol，high，完全访问，工作目录主检出），进程退出即本轮结束，不续用旧会话（D-210）；由它先看 `git status`、`logs/merged.log` 和 `logs/tasks/001-值班长期单.log.md` 末尾再接着做，已做完的不重做。各执行者都照 `tasks/sol/001-值班长期单.md` 与 WF-MERGE 做；同一时刻只有一个执行者在主检出上做；通知都写进主会话收件箱（发件方 `duty`，一轮一个文件，开头注明是谁）。值班唤醒脚本不启动调研。

**旁路唤醒脚本**按文件名顺序，从 `side/cards/` 里取一张还没交出的单，叫醒 Sol 旁路会话，消息里写明任务单路径并要求照 `side/ROLE.md` 执行；这一轮结束后再取下一张，一次只交一张。

**记录**：`tools/duty_watch/`（`seen.txt`、`cards.txt` 记已处理的批准行和任务单）、`tools/side_runner/done.txt`；日志在 `logs/duty/`、`logs/side/`。每轮只做被叫醒的事。

## 2 值班做什么、不许做什么

**做什么**：
- **合并执行**：只合有批准行的候选，步骤见 WF-MERGE §2；每一轮合并里 `doc/rolling` 有新提交就整段合入（WF-MERGE §1）。
- **施工状态**：每小时最多同步一次施工状态文件（WF-STATUS §1）与待派工队列，叫醒消息写明这一轮同不同步；依赖已满足的队列条目改成"可派"，并在来信里写"【待审】Q-nnn 可派"。
- **巡检**（每小时一轮，合并轮和任务单轮不做）：
  - 卡死进程：`Get-Process godot*` 里启动超过 15 分钟仍在跑的截图或门禁进程，记下 PID、命令行、所属工作树，通知主会话，不自己杀；
  - 带条件的批准行：当时没合的，每次都复查，条件满足了就合入；
  - 工作树落后：`git -C <工作树> merge-base --is-ancestor main HEAD` 不成立的工作树列一行写进"状态"，不用通知；
  - 完成度调研：按 §3 看有没有在跑超时的调研。
- **通知与流水**：一轮的通知合成一个新文件放进主会话收件箱 `notes/opus/<YYYYMMDD-HHMMSS>-duty-<短词>.md`（WF-COMMS §4）；本轮做了什么写在 `logs/tasks/001-值班长期单.log.md` 末尾，一行一事、带时间，那份是只追加的流水，不用通读。

**不许做**：改代码；改契约与共享工程文件；改设计文档（任务单给出确切文字时除外）；合并没有批准行的候选；强推；删除分支或工作树（合入后用清理脚本删刚合入的那一个除外，WF-MERGE §2 第 7 步）；做任何画面与风格判断。

## 3 完成度调研

完成度调研是调研入队流水线（WF-FLOW §6）的第 1 步，由 Sol 旁路会话执行。是否排调研、排几张，以主会话写在 `tasks/sol/002-完成度调研排期.md` 的"状态"里的要求为准；本节只写怎么写调研单、查什么。

- **调研单**写进 `side/cards/r<nnn>-<主题>.md`，模板是 `research/cards/调研单模板.md`，按当前阶段调整背景、方向（4–6 个，不重复已做过的，每个写明为什么现在值得查）和输出目录 `research/<日期>-r<nnn>-<主题>/`；写新单前先读 `research/INDEX.md` 去重，写完追加一行。
- **执行**：旁路会话按方向开 gpt-6.1-sol 子代理并行调研，各写一份报告；`00-总览.md` 写按优先级去重的建议表，每条标明归哪个包或建议新包、主线版还是细节阶段、工作量、依赖。写完把 INDEX 里这一单标成"待审"，在 `notes/opus/` 新建来信"【待审】调研 r<nnn> 完成：<总览路径>"。
- **超时**：调研单启动超过 3 小时、`logs/side/runner.log` 里仍没有"本单结束"，值班执行者查 `runner.log` 与 `<单号>.stderr.log`，写进"状态"并通知主会话。
- **三个视角**（每张单都覆盖）：制作完整度（内容量与密度、各系统与管线的覆盖、质量保障与测试、性能与稳定性、存档稳健、发布与本地化、无障碍）；优越性（和同类作品比的长短处、差异化卖点、让人记住的时刻与展示画面、同类作品常被批评而本项目可以避开的地方）；玩家体验（首次体验与上手、节奏与情绪曲线、舒适度与可达性、操作与界面的摩擦、加载与等待、反馈与手感、回访与重玩的理由）。
- **不调研的**：任何阶段都不调研、不建议 RPG 内容；本项目是个人实验作品（D-181），不调研商店页、上架、宣传素材、成就、云存档、平台集成等商业发行内容，"发布完整度"只看按 OPS-RELEASE 在 GitHub 发整包时的完整与稳健；GPT 只收集观感方面的事实与做法，不下画面结论。

## 4 Sol 旁路会话

**是什么**：Codex 应用里的固定会话"Sol旁路会话"（gpt-6.1-sol，xhigh，普通速度，D-203），角色说明 `side/ROLE.md`。完成度调研和其他旁路任务都由它一个会话管理，按任务单开子代理并行处理。

**两类任务单**（都放在 `side/cards/`）：
- **调研单 `r<nnn>-<主题>.md`**：做法见 §3。
- **旁路单 `s<nnn>-<主题>.md`**：由主会话写。主会话判断某件事不在主线关键路径上、却会占主线时间，或者要大量补信息、调研、批量核对数据时，写一张旁路单，写明在哪做、交付什么、能改什么、哪些不许做；派不派、派几张、做到什么程度由主会话定。

**怎么执行**：旁路唤醒脚本一次交一张（§1）；旁路会话按方向数用 `spawn_agent` 开 gpt-6.1-sol 子代理，最多 8 个并发，简报按 WF-MODEL §6 写明共用工作目录的边界；做完在单子末尾"状态"写结果，在 `notes/opus/` 新建来信写一两行结果，然后结束本轮；上下文重置后照 `side/cards/` 下各单的"状态"接着做（WF-COMMS §6）。

**边界**：不做任何审美工作（WF-ROLE §3），调研里涉及观感的只收集事实和出处；不改契约和共享工程文件；不改 `docs/design/`，任务单给出确切文字的补丁除外；不合并、不推送；不碰任何包的工作树和主检出。要写代码的旁路活，在单子指定的独立工作树里做，完成后写合并请求，经主会话批准由值班执行者合入（WF-MERGE §1）。
