# WF-FLOW · 开发流程

> **范围**：本文规定一个包从派工到批准的流程：派工与拆单、施工与回报、评审与可调参数、契约申请与共享工程文件、调研入队流水线。
> **不在本文**：包的归属与开工顺序：ENG-WP §1.1、§2；批准、合并与合入以后：WF-MERGE；模型选择与简报：WF-MODEL；交接文件格式：WF-COMMS；队列与状态：WF-STATUS；额度与并发：WF-QUOTA。
> **查阅**：先读 §0；全流程一览看 §1；派工与拆单看 §2；施工与回报看 §3；评审与可调参数看 §4；契约申请看 §5；调研入队看 §6。
> **关联**：[WF-INDEX 协作总纲](../WF-INDEX-协作总纲.md)、[WF-ROLE 参与者与分工](../collaboration/WF-ROLE-参与者与分工.md)、[WF-MODEL 模型选择与子代理](../collaboration/WF-MODEL-模型选择与子代理.md)、[WF-COMMS 交接与通信](../collaboration/WF-COMMS-交接与通信.md)、[WF-DUTY 值班与旁路](../collaboration/WF-DUTY-值班与旁路.md)、[WF-MERGE 批准与合并](WF-MERGE-批准与合并.md)、[WF-STATUS 施工状态与队列](../management/WF-STATUS-施工状态与队列.md)、[WF-QUOTA 账号与额度](../management/WF-QUOTA-账号与额度.md)、[WF-RULE 全员守则](../rules/WF-RULE-全员守则.md)、[ENG-WP 工作包](../../engineering/ENG-WP-工作包派工单.md)、[ENG-ARCH 工程架构](../../engineering/ENG-ARCH-工程架构.md)

## 0 结论

1. **一个包按固定顺序走**（§1）：派工 → 建工作树 → 施工 → 回报 → 评审 → 批准行 → 合并执行 → 施工状态 → rebase 通知；只合有主会话批准行的候选。
2. **一张单约 2–3 个 Opus 小时**（§2，D-184）：超过就拆子单，开工 30 分钟内重估。
3. **审美评审由主会话做，可调参数集中放一处**（§4）。
4. **契约与共享工程文件只由 Astra 改**（§5）：牵涉画面表现的契约，主会话确认后才冻结（D-134）。
5. **调研走入队流水线**（§6）：调研 → 审计 → 并入工作包 → 分配 → 入队。

### 0.1 接入要点

- **要改契约或共享工程文件**：写 `requests/contract-<包号>-<主题>.md`，不自己改，要早提（§5）。
- **结果看得见或听得见的包**：把可调参数集中放一处，回报里列出位置和现值（§4）。
- **发现单子超出预估**：停下报给派单方拆单，不靠压缩细节赶完（§2）。
- **改了别人在用的设计**：同一批里迁完使用方、删旧的，不留新旧并存（§5，D-209）。

## 1 全流程一览

一个包从派工到合入按下表的顺序走，每一步只有一个负责方。

| 步 | 谁做 | 产出 |
| --- | --- | --- |
| 1 派工 | 主会话（Opus 侧的包）；Astra（Astra 侧的包） | 任务单 `tasks/claude/<nnn>-<主题>.md`；或 Astra 给子代理的简报 |
| 2 建工作树 | 派子代理的一方：主会话或 Astra | `E:\Project\UESTC_RPG.wt\<WP-xx>` 与本地分支（WF-MERGE §5） |
| 3 施工 | 施工子代理 | 分支上的候选提交、快检结果、截图 |
| 4 回报与初步核对 | 子代理向派它的一方回报；Astra 审架构 | 任务单"状态"里的待评审行；或合并请求、评审请求 |
| 5 评审 | 主会话管审美与取值；Astra 管契约与架构 | 任务单末尾的"Opus 评审"小节；请求文件末尾的结论或新值 |
| 6 批准 | 主会话 | 批准行（WF-MERGE §1） |
| 7 合并执行 | 值班执行者 | `main` 上的 squash 提交、`logs/merged.log` 一行（WF-MERGE §2） |
| 8 施工状态 | 值班执行者 | 施工状态文件更新（WF-MERGE §4） |
| 9 rebase 通知 | 主会话、Astra 各自通知名下的子代理 | 各工作树 rebase 到新的 `main` |

## 2 派工与拆单

**从待派工队列派**：调研审计采纳或新决定带来的工作，先进待派工队列（§6、WF-STATUS §2）；按 ENG-WP §1.1 的波次开工的包照波次派。主会话按优先级与并发余量（WF-QUOTA），从"可派"条目里派工，派出后在条目里写任务单号。建模完成度是主线（D-183）：先派建筑、部件、分区、植被、街道家具、箱庭与室内包，再派游泳、生物、角色本体等系统新功能。

**Opus 侧的包**：主会话写任务单 `E:\Project\UESTC_RPG.wt\.collab\tasks\claude\<nnn>-<主题>.md`，一张单对应一件完整且工作量受控的事。单子里写：目标；给子代理的简报（照 WF-MODEL §8 的模板，写明工作树绝对路径、先读什么、主线版要做到哪）；用 Opus 还是 Sonnet 与推理档（WF-MODEL §1–§4）；交付标准（截图、快检）；评审方式。随后主会话直接开子代理（WF-MODEL §6）。派单要分批，按 WF-QUOTA 的并发与队列平衡（WF-STATUS §2）。

**Astra 侧的包**：Astra 用 `spawn_agent` 开子代理，简报照 WF-MODEL §8 的模板，并写明共用工作目录的边界（WF-MODEL §6）；施工模型按 WF-ROLE §6。

**Sol 的任务**：交值班执行者的活，主会话写任务单 `tasks/sol/<nnn>-<主题>.md`；旁路活写旁路单 `side/cards/s<nnn>-<主题>.md`（WF-DUTY §1、§4）。

**按工作量拆单（D-184）**：派工前先估工作量，在任务单写明"预计工作量：约 N 个 Opus 小时"。一张单交给一个子代理，上限约 2–3 个 Opus 小时，大致是一栋地标楼、3–5 栋普通楼、一类部件族或一个系统子功能。
- 超过上限就拆成子单，文件名在编号后加 a、b，各自交候选、各自评审。
- 同包的子单共用独占目录、按顺序做；上一张评审通过后，新开一个子代理做下一张，不让一个子代理带长上下文连续做多张（WF-MODEL §7）。不同包照常并行。
- 子代理中途发现超出预估，就停下来报给派单方拆单，不靠压缩细节赶完；评审发现后做的部分比先做的粗，就拆得更细。
- **开工 30 分钟重估**：施工子代理开工后 30 分钟内重估工作量，超过约 3 个 Opus 小时就拆单，只交第一张，回报里写拆法。

**贴近主线（主会话侧，D-199）**：
- 派单或恢复子代理时，从 `logs/merged.log` 里挑出最近 24 小时和这个包相关的合入，附在简报里。
- 评审里定下的通用结论（对不止一个包有效的，例如"栏杆立杆不投影"）当天写回对应的规范文档，不只留在任务单里。
- 多包共用的热点文件按包分片（加载规则由 Astra 定，施工侧写法见 WF-RULE §10）；决策编号 D-nnn 由主会话统一分配。

## 3 施工与回报

**施工**（细则在 WF-ONBOARD、WF-RULE、WF-BUILD）：只在自己的工作树里写，小步提交；主线闸口之前只交主线版（WF-RULE §8）；交候选之前跑快检（WF-ONBOARD §4）；结果看得见或听得见的，可调参数集中放一处（§4）；要改契约或共享工程文件，提契约申请（§5）；开始下一步之前看 `logs/merged.log`，`main` 变了就 rebase。

**回报**：按 WF-ONBOARD §4 的格式，交给派你的一方。

| 施工方 | 回报给 | 对方接着做 |
| --- | --- | --- |
| 主会话的子代理 | 主会话 | 核对交付（工作树干净、与 `main` 无冲突、快检与截图齐），写合并请求或在任务单"状态"写"待评审：候选 <提交>，截图 <路径>，要定的问题 <…>"；主会话看结果和截图，在末尾写评审 |
| Astra 的子代理 | Astra 主线程 | 回答问题、审代码是否符合架构、跑快检，写合并请求 `requests/merge-<WP-xx>-<序号>.md`；有可见或可听的结果，另写评审请求 `requests/review-<WP-xx>-<序号>.md` |
| Sol 旁路会话的代码类旁路单 | 主会话 | 在单子指定的独立工作树里做，写合并请求（WF-DUTY §4） |

## 4 评审：审美与契约的交叉评审

**审美评审由主会话做**，它是风格负责人，评审金样、色板联表、界面样张和全部画面类截图。
- **任务单的评审**：主会话在单子末尾写"Opus 评审（时间）"小节：通过，或逐条修改意见。意见发回同一个子代理在原上下文里改，条件见 WF-MODEL §7（交回几分钟内的小返工），否则新开子代理照单子改；改完在"状态"写"已按评审修改"，回到待评审。
- **请求文件的评审**：主会话在合并请求或评审请求末尾写结论或新值；评审不通过就把意见发回继续改。
- **色值口径**见 ART-STYLE。

**可调参数集中放**：Astra 的包有可见或可听的结果时，把可调参数放在一处（数据文件或集中的常量类），并在评审请求里写明截图或录像路径、参数在哪、各参数现在的值。主会话评审后，在评审文件里写新值，或直接在那个参数文件里改；改动经合并队列进 `main`。

**画面相关的契约**由 Astra 起草、主会话确认后才冻结，见 ENG-ARCH §3。

**Opus 侧的包需要工程支持时**：遇到性能结构、线程、确定性、契约的问题，在 `requests/contract-<包号>-<主题>.md` 或 Astra 的收件箱 `notes/astra/` 里找 Astra。

## 5 契约申请与共享工程文件

- **谁能改**：契约与工程共享件只由 Astra 改，包括 `game/contracts/`、全部 csproj、`Directory.*.props`、`project.godot`、`ownership.json`、`gate.ps1` 和 `scripts/wt/` 下的脚本（完整清单见 CORE-CONVENTIONS §5.1）；WP-00 也由 Astra 做。`docs/design/` 由主会话改。
- **申请**：任何代理要改这些，写 `requests/contract-<包号>-<主题>.md`：要改什么、为什么、影响哪些包。Astra 处理后在文件末尾写结论和对应的提交。
- **提交与合入**：Astra 在自己的工作树（`..\UESTC_RPG.wt\WP-00`，分支 `wp/00-core`）上提交，写合并请求；主会话优先评审和批准，值班执行者合入。
- **冻结**：契约分批冻结：某组契约的真实生产方与使用方在主线上接通、相关核心专项通过后，由主会话宣布冻结这一组，之后只增不改；还没冻结的组按申请修改；各组的冻结状态见 ENG-ARCH §3（D-134）。牵涉画面表现的契约，主会话确认后才冻结（ENG-ARCH §3）。
- **要早**：上游包在开工后头几个小时内就把契约申请提上来，免得下游包写得太深再返工。
- **改架构或实现新设计时一次迁完（D-209）**：改的一方在同一批改动里把所有使用方迁到新设计，删掉旧设计、旧代码、旧测试和旧文档，不留新旧并存；只有下游正在别的工作树施工、一次改不完时，允许一层过渡兼容，它活不过这张单结案，任务单里写明删除条件。契约组已冻结的，按 §5 申请，由 Astra 定迁移范围。

## 6 调研入队流水线

调研入队是一条固定流水线：调研 → 主会话审计 → 更新或新增工作包 → 分配任务 → 入队（待派工队列，WF-STATUS §2）。不经调研、由新决定带来的工作（例如 D-182），从第 3 步进入。

| 步 | 谁做 | 产出 | 写在哪里 |
| --- | --- | --- | --- |
| 1 调研 | 值班执行者写调研单；Sol 旁路会话按方向开 gpt-6.1-sol 子代理执行（WF-DUTY §3） | 各方向的报告与总览：按优先级去重的建议表 | 调研单 `side/cards/r<nnn>-<主题>.md` → `research/<日期>-r<nnn>-<主题>/00-总览.md`；`research/INDEX.md` 标"待审" |
| 2 审计 | 主会话 | 每条建议标采纳（并入 WP-xx，或新增 WP-yy）、暂缓或不采纳 | 总览末尾的"Opus 审计"；`research/INDEX.md` 的"Opus 审计"一列 |
| 3 更新或新增工作包 | 主会话；大段文档撰写可以派子代理 | 采纳的建议写进现有包的条目，或新增包：按归属逻辑定归属（ENG-WP §1.1），排波次 | ENG-WP |
| 4 分配任务 | 主会话（审计时一并定） | 把采纳的工作拆成两侧任务：Astra 侧负责契约、共享接口、引擎与工程机制；Opus 侧负责画面、风格、内容、建模与文档撰写。每项写清做什么、落到哪个包、预计工作量（D-184）与前后依赖 | 总览末尾"Opus 审计"里的"分配"一段 |
| 5 入队 | 主会话 | 每侧各入一条或一组 Q-nnn，状态"排队"；派往必须写 Astra 或 Opus 侧，不写"待定" | 待派工队列（WF-STATUS §2） |

入队以后：Astra 侧条目由主会话写进 `notes/astra/` 通知 Astra 排期，Opus 侧条目由主会话按 §2 派工；依赖满足后由值班执行者改"可派"，派出后在条目里写任务单号，完成后从队列移除。
