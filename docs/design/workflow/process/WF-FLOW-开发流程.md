# WF-FLOW · 开发流程

> **范围**：本文规定一个包从派工到评审的流程：派工与拆单、防打架、施工与回报、评审与可调参数、契约申请与共享工程文件、调研入队流水线。

## 0 结论

1. **一个包按固定顺序走**（§1，D-211）：派工 → 施工 → 自测 → 提交推送 → 回报 → 评审（不合格就回滚或派返工单）→ 施工状态；施工者直接在主检出 `main` 上改。
2. **同一批文件同一时间只有一个写者**（§2.1）：按独占目录分工，简报写明邻居。
3. **一张单约 2–3 个 Opus 小时**（§2，D-184）：超过就拆子单，开工 30 分钟内重估。
4. **审美评审由主会话做，推送后评审；可调参数集中放一处**（§4）。
5. **契约与共享工程文件只由 Astra 改**（§5）：牵涉画面表现的契约，主会话确认后才冻结（D-134）。
6. **调研走入队流水线**（§6）：调研 → 审计 → 并入工作包 → 分配 → 入队。

### 0.1 接入要点

- **开工前和派工前**：`git status` 看谁在改什么，简报写邻居；要改邻居的文件先停下报派单方（§2.1）。
- **要改契约或共享工程文件**：写 `requests/contract-<包号>-<主题>.md`，不自己改，要早提（§5）。
- **结果看得见或听得见的包**：把可调参数集中放一处，回报里列出位置和现值（§4）。
- **发现单子超出预估**：停下报给派单方拆单，不靠压缩细节赶完（§2）。
- **改了别人在用的设计**：同一批里迁完使用方、删旧的，不留新旧并存（§5，D-209）。

## 1 全流程一览

一个包从派工到评审按下表的顺序走，每一步只有一个负责方。

| 步 | 谁做 | 产出 |
| --- | --- | --- |
| 1 派工 | 主会话（Opus 侧的包）；Astra（Astra 侧的包） | 任务单 `tasks/claude/<nnn>-<主题>.md`；或 Astra 给子代理的简报；简报写邻居（§2.1） |
| 2 施工 | 施工子代理，在主检出 `main` 上直接改 | 本包独占目录里的改动、快检结果、截图 |
| 3 自测、提交推送 | 施工子代理 | 快检通过后带路径提交并 `git push origin main`（WF-RULE §7） |
| 4 回报 | 子代理向派它的一方回报；Astra 审架构 | 任务单"状态"里的待评审行；或评审请求 |
| 5 评审 | 主会话管审美与取值；Astra 管契约与架构 | 任务单末尾的"Opus 评审"小节；请求文件末尾的结论或新值；不合格就 `git revert` 或派返工单 |
| 6 施工状态 | 主会话 | 施工状态文件更新（WF-STATUS §1） |

## 2 派工与拆单

**从待派工队列派**：调研审计采纳或新决定带来的工作，先进待派工队列（§6、WF-STATUS §2）；按 ENG-WP §1.1 的波次开工的包照波次派。主会话按优先级与并发余量（WF-QUOTA），从"可派"条目里派工，派出后在条目里写任务单号。建模完成度是主线（D-183）：先派建筑、部件、分区、植被、街道家具、箱庭与室内包，再派游泳、生物、角色本体等系统新功能。

**Opus 侧的包**：主会话写任务单 `E:\Project\UESTC_RPG\.collab\tasks\claude\<nnn>-<主题>.md`，一张单对应一件完整且工作量受控的事。单子里写：目标；给子代理的简报（照 WF-MODEL §8 的模板，写明邻居、先读什么、主线版要做到哪）；用 Opus 还是 Sonnet 与推理档（WF-MODEL §1–§4）；交付标准（截图、快检）；评审方式。随后主会话直接开子代理（WF-MODEL §6）。派单要分批，按 WF-QUOTA 的并发与队列平衡（WF-STATUS §2）。

**Astra 侧的包**：Astra 用 `spawn_agent` 开子代理，简报照 WF-MODEL §8 的模板，并写明邻居（WF-MODEL §6、§8.1）；施工模型按 WF-ROLE §6。

**Sol 会话的任务**：调研、旁路和机械活，主会话写调研单或旁路单放进 `side/cards/`（§6、WF-COMMS §2），用 `codex_app_run.py` 发进 Sol 会话（WF-COMMS §5）。

**按工作量拆单（D-184）**：派工前先估工作量，在任务单写明"预计工作量：约 N 个 Opus 小时"。一张单交给一个子代理，上限约 2–3 个 Opus 小时，大致是一栋地标楼、3–5 栋普通楼、一类部件族或一个系统子功能。
- 超过上限就拆成子单，文件名在编号后加 a、b，各自推送、各自评审。
- 同包的子单共用独占目录、按顺序做；上一张评审通过后，新开一个子代理做下一张，不让一个子代理带长上下文连续做多张（WF-MODEL §7）。不同包照常并行。
- 子代理中途发现超出预估，就停下来报给派单方拆单，不靠压缩细节赶完；评审发现后做的部分比先做的粗，就拆得更细。
- **开工 30 分钟重估**：施工子代理开工后 30 分钟内重估工作量，超过约 3 个 Opus 小时就拆单，只交第一张，回报里写拆法。

**评审结论与共用数据（D-199）**：
- 评审里定下的通用结论（对不止一个包有效的，例如"栏杆立杆不投影"）当天写回对应的规范文档，不只留在任务单里。
- 多包共用的热点文件按包分片（加载规则由 Astra 定，施工侧写法见 WF-RULE §10）；决策编号 D-nnn 由主会话统一分配。

### 2.1 防打架（D-211）

所有人在同一个主检出上写，靠下面几条避免互相覆盖：
- **按独占目录分工**：派前按 ownership.json 的独占目录分，尽量同时派互不冲突的活；同一批文件同一时间只有一个写者。
- **简报写邻居**：每份简报写"同时在干活的邻居：名字、在做什么、改哪些文件或目录"，来源是 WF-STATUS 的活表（模板见 WF-MODEL §8.1）。Claude 子代理派时给 `name`；碰到共用边界先 SendMessage 问邻居，它们不会主动协调；Codex 子代理会互相通信，不另规定。
- **不动别人的文件**：要改邻居的文件，先停下报派单方。编译失败在邻居的文件里，就等一会儿再试或给它发消息。
- **小步、能编译**：自己的改动小步写，每一步都能编译，不长时间留半成品；提交只提交编译通过的东西。
- **排队**：编译、import、烘焙、门禁和截图一次只跑一个（ENG-ARCH §6）。
- **只提交自己的文件**：`git add` 与 `git commit` 都带自己的路径（WF-RULE §7）。

## 3 施工与回报

**施工**（细则在 WF-ONBOARD、WF-RULE、WF-BUILD）：开工先 `git status` 看邻居，只改本包独占目录，小步提交；主线闸口之前只交主线版（WF-RULE §8）；推送之前跑快检（WF-ONBOARD §4）；结果看得见或听得见的，可调参数集中放一处（§4）；要改契约或共享工程文件，提契约申请（§5）。

**回报**：按 WF-ONBOARD §4 的格式，交给派你的一方。

| 施工方 | 回报给 | 对方接着做 |
| --- | --- | --- |
| 主会话的子代理 | 主会话 | 核对交付（已推送、快检与截图齐），在任务单"状态"写"待评审：提交 <短号>，截图 <路径>，要定的问题 <…>"；主会话看结果和截图，在末尾写评审 |
| Astra 的子代理 | Astra 主线程 | 回答问题、审代码是否符合架构、跑快检；有可见或可听的结果，另写评审请求 `requests/review-<WP-xx>-<序号>.md` |
| Sol 会话的代码类旁路单 | 主会话 | 同子代理规则：在主检出上改、自测、提交推送（WF-RULE §7） |

## 4 评审：审美与契约的交叉评审

**评审后置**：施工者自测通过就推送，不设推送前的评审关卡；推送后主会话看截图评审，不合格就 `git revert` 或派返工单（WF-RULE §7）。造型、风格还没定的活，照旧先由 Opus 子代理出样、主会话定案再铺开（WF-MODEL §1），这是派活方式，不算关卡。看画面用固定机位截图看一眼，审美以作者的反馈为准（ENG-GATES §2）。

**审美评审由主会话做**，它是风格负责人，评审金样、色板联表、界面样张和全部画面类截图。
- **任务单的评审**：主会话在单子末尾写"Opus 评审（时间）"小节：通过，或逐条修改意见。意见发回同一个子代理在原上下文里改，条件见 WF-MODEL §7（交回几分钟内的小返工），否则新开子代理照单子改；改完推送，在"状态"写"已按评审修改"，回到待评审。
- **请求文件的评审**：主会话在评审请求末尾写结论或新值；评审不通过就把意见发回继续改。
- **色值口径**见 ART-STYLE。

**可调参数集中放**：Astra 的包有可见或可听的结果时，把可调参数放在一处（数据文件或集中的常量类），并在评审请求里写明截图或录像路径、参数在哪、各参数现在的值。主会话评审后，在评审文件里写新值，或派人在那个参数文件里改，改完推送。

**画面相关的契约**由 Astra 起草、主会话确认后才冻结，见 ENG-ARCH §3。

**Opus 侧的包需要工程支持时**：遇到性能结构、线程、确定性、契约的问题，在 `requests/contract-<包号>-<主题>.md` 或 Astra 的收件箱 `notes/astra/` 里找 Astra。

## 5 契约申请与共享工程文件

- **谁能改**：契约与工程共享件只由 Astra 改，包括 `game/contracts/`、全部 csproj、`Directory.*.props`、`project.godot`、`ownership.json`、`gate.ps1` 和 `scripts/` 下的工程脚本（完整清单见 CORE-CONVENTIONS §5.1）；WP-00 也由 Astra 做。`docs/design/` 由主会话改。
- **申请**：任何代理要改这些，写 `requests/contract-<包号>-<主题>.md`：要改什么、为什么、影响哪些包。Astra 处理后在文件末尾写结论和对应的提交。
- **提交**：Astra 在主检出直接提交推送；改共享件前告知邻居，改完同批迁完使用方（D-209）。
- **冻结**：契约分批冻结：某组契约的真实生产方与使用方在主线上接通、相关核心专项通过后，由主会话宣布冻结这一组，之后只增不改；还没冻结的组按申请修改；各组的冻结状态见 ENG-ARCH §3（D-134）。牵涉画面表现的契约，主会话确认后才冻结（ENG-ARCH §3）。
- **要早**：上游包在开工后头几个小时内就把契约申请提上来，免得下游包写得太深再返工。
- **改架构或实现新设计时一次迁完（D-209）**：改的一方在同一批改动里把所有使用方迁到新设计，删掉旧设计、旧代码、旧测试和旧文档，不留新旧并存；只有下游文件正由另一个子代理在改、一次改不完时，允许一层过渡兼容，它活不过这张单结案，任务单里写明删除条件。契约组已冻结的，按 §5 申请，由 Astra 定迁移范围。

## 6 调研入队流水线

调研入队是一条固定流水线：调研 → 主会话审计 → 更新或新增工作包 → 分配任务 → 入队（待派工队列，WF-STATUS §2）。不经调研、由新决定带来的工作（例如 D-182），从第 3 步进入。

| 步 | 谁做 | 产出 | 写在哪里 |
| --- | --- | --- | --- |
| 1 调研 | 主会话写调研单；Sol 会话按方向开 gpt-6.1-sol 子代理执行（§6.1） | 各方向的报告与总览：按优先级去重的建议表 | 调研单 `side/cards/r<nnn>-<主题>.md` → `research/<日期>-r<nnn>-<主题>/00-总览.md`；`research/INDEX.md` 标"待审" |
| 2 审计 | 主会话 | 每条建议标采纳（并入 WP-xx，或新增 WP-yy）、暂缓或不采纳 | 总览末尾的"Opus 审计"；`research/INDEX.md` 的"Opus 审计"一列 |
| 3 更新或新增工作包 | 主会话；大段文档撰写可以派子代理 | 采纳的建议写进现有包的条目，或新增包：按归属逻辑定归属（ENG-WP §1.1），排波次 | ENG-WP |
| 4 分配任务 | 主会话（审计时一并定） | 把采纳的工作拆成两侧任务：Astra 侧负责契约、共享接口、引擎与工程机制；Opus 侧负责画面、风格、内容、建模与文档撰写。每项写清做什么、落到哪个包、预计工作量（D-184）与前后依赖 | 总览末尾"Opus 审计"里的"分配"一段 |
| 5 入队 | 主会话 | 每侧各入一条或一组 Q-nnn，状态"排队"；派往必须写 Astra 或 Opus 侧，不写"待定" | 待派工队列（WF-STATUS §2） |

入队以后：Astra 侧条目由主会话写进 `notes/astra/` 通知 Astra 排期，Opus 侧条目由主会话按 §2 派工；依赖满足后由主会话改"可派"，派出后在条目里写任务单号，完成后从队列移除。

### 6.1 调研单与旁路单

两类单都放在 `side/cards/`，由主会话写，用 `codex_app_run.py` 发进 Sol 会话（WF-COMMS §5）；Sol 会话的边界见 WF-ENTRY 第 4 节。
- **调研单** `r<nnn>-<主题>.md`：模板是 `research/cards/调研单模板.md`；写背景、方向（4–6 个，不重复已做过的，每个写明为什么现在值得查）和输出目录 `research/<日期>-r<nnn>-<主题>/`。写新单前先读 `research/INDEX.md` 去重，写完追加一行；是否排调研、排几张由主会话定。
- **调研执行**：Sol 会话按方向开 gpt-6.1-sol 子代理并行，各写一份报告；`00-总览.md` 写按优先级去重的建议表，每条标明归哪个包或建议新包、主线版还是细节阶段、工作量、依赖。写完把 INDEX 里这一单标成"待审"，并来信通知主会话。
- **三个视角**（每张调研单都覆盖）：制作完整度（内容量与密度、各系统与管线的覆盖、质量保障与测试、性能与稳定性、存档稳健、发布与本地化、无障碍）；优越性（和同类作品比的长短处、差异化卖点、让人记住的时刻与展示画面、同类作品常被批评而本项目可以避开的地方）；玩家体验（首次体验与上手、节奏与情绪曲线、舒适度与可达性、操作与界面的摩擦、加载与等待、反馈与手感、回访与重玩的理由）。
- **不调研的**：任何阶段都不调研、不建议 RPG 内容；本项目是个人实验作品（D-181），不调研商店页、上架、宣传素材、成就、云存档、平台集成等商业发行内容，"发布完整度"只看按 OPS-RELEASE 在 GitHub 发整包时的完整与稳健；GPT 只收集观感方面的事实与做法，不下画面结论。
- **旁路单** `s<nnn>-<主题>.md`：某件事不在主线关键路径上、却会占主线时间，或者要大量补信息、批量核对数据时，主会话写一张旁路单，写明在哪做、交付什么、能改什么、哪些不许做；派不派、做到什么程度由主会话定。Sol 会话做完在单子末尾"状态"写结果。
