# WF-STATUS · 施工状态与队列

> **范围**：本文规定施工状态文件怎么填、待派工队列怎么管、队列怎么平衡，以及交接单。

## 0 结论

1. **施工状态只记现在，放在 git 之外**（§1）：文件是 `E:\Project\UESTC_RPG.wt\.collab\status\施工状态.md`，所有工作树读同一份；合入流水看 `logs/merged.log` 与 git，不记在里面。
2. **内容由主会话决定，值班执行者每小时最多同步一次**（§1）。
3. **"回报完成"不等于"已集成"**：合进 `main` 并推送才算集成（§1）。
4. **待派工队列**（§2）：审计采纳或新决定带来的工作先排队，依赖满足改"可派"，只有主会话派工。
5. **派工看整条流水线的队列平衡**，不只看额度（§2）。

### 0.1 接入要点

- **想知道自己的包或别的包在施工表里的状态**：只读状态文件，不改；进度、阻塞和完成都经回报交派你的一方（§1）。
- **想知道某组契约能不能改**：看状态文件的"已冻结的契约组"与 ENG-ARCH §3；列在那里的组只增不改（§1）。
- **想知道一项新工作排到哪了、能不能开工**：看队列；只有主会话从"可派"条目里派工，子代理不自己领（§2）。

## 1 施工状态文件怎么填

- **内容**：当前 `main` 的短号和提交首行；最近可运行入口（能启动并走通主线的那条命令和对应提交，还没有写"尚无"）；已冻结的契约组（逐组列出并记冻结时的提交，还没有写"尚无"）；已知问题；活跃工作包表；待派工队列表。
- **何时更新**：派工、合入（每小时最多同步一次，叫醒消息写明）、交接、冻结契约这四个时刻；其余时候不必改。派工加一行，状态写"已派工"；合入后改 `main` 和相关行，删掉做完的包，还要继续的包把候选提交换成新的；交接时把每一行改成此刻的实情；冻结契约时在"已冻结的契约组"里加这一组和提交。
- **活跃工作包表**每列写什么：

| 列 | 写什么 |
| --- | --- |
| 包 | 编号，子包写到子包（`WP-35b`） |
| 目标 | 本轮要交的东西，一句话，引用 ENG-WP 的条目，不复述 |
| 工作树 | `..\UESTC_RPG.wt\<WP-xx>\`；直接在主检出上做的写"主检出" |
| 分支 | `wp/<xx>-<slug>` |
| 候选提交 | 待合入的那个提交的短号；还没有写"—" |
| 状态 | 已派工、施工中、待合入（已回报，等批准与合并）、合入中、阻塞，五选一 |
| 阻塞 | 卡在什么上、等谁；没有写"—" |
| 下一步 | 下一个动作和由谁做 |

- **谁写**：值班执行者维护活表，内容由主会话决定；文件在 git 之外，不跑 `gen_index.py`、不提交。
- **接手时**：先读状态文件，再用 `git worktree list`、`git branch`、`git log --oneline -1 main` 核对；对不上以 Git 为准并改文件。代理在工作树里有、但没写进状态文件的提交，接手人先问清楚再处理，不删。
- **不写**：合入流水、日报周报、讨论过程和评审意见；这些在 git、`logs/` 和会话里（WF-RULE §12）。

## 2 待派工队列与队列平衡

待派工队列是调研入队流水线的出口：审计采纳或新决定带来的工作先在这里排队，依赖满足后由主会话按优先级派工（WF-FLOW §6）。队列表在状态文件里。

**规则**：
- **加条目**：审计完成、采纳的工作写进 ENG-WP 并分配了两侧任务后再加行；每侧各一行，"派往"写 Astra 或 Opus 侧，不写"待定"。编号 Q-nnn，三位递增；状态先写"排队"。
- **改"可派"**：依赖满足就改成"可派"；值班执行者在每次合入后顺带检查，并在来信里写"【待审】Q-nnn 可派"。
- **派工**：主会话按并发余量（WF-QUOTA）与优先级，从"可派"条目里派工，建模包排在系统新功能之前（D-183）；派出后状态写"已派 → <任务单号>"。
- **移除**：条目完成后从表里删掉，历史交给 Git。
- **列**：编号、事项（一句话）、来源（审计或决定）、落到（包）、依赖、派往、优先级（高中低）、状态（排队、可派、已派 → 任务单号）。

**队列平衡：不让一类活积压**。开发是几道工序串起来的：待派（主会话）→ 在施工（子代理）→ 待评审（主会话）→ 已批待合（值班）；另有等契约、接线与工程验收的（Astra）。某一条堆得太多，上游再快也只是在排队，还会让叠在未合候选上的单越叠越深、冲突越来越多。每次派工前看一眼各队列（任务单"状态"、`requests/` 里未合的批准行、`logs/merged.log`）：
- **已批待合超过 6 条**：暂停新开施工单，只派解冲突、rebase 和清积压的活。
- **同一个上游压着 2 张以上下游**（一份契约、一次接线，或一张还没合的基点候选）：不再开依赖它的新单，把这个上游排到最前，必要时催一句。
- **待评审超过 3 条**：主会话先评审，不开新单。
- **某一方空着、它的输入在另一方手里**：把能解开它的那一件排到最前，例如 Astra 等 Opus 侧的验收就先审它。
- **叠单最多一层**：基点候选没合之前，不在它上面再叠第二层新单。
