# ENG-TEAM-QUOTA · 协作分册：账号与额度

> **范围**：本分册规定各账号的额度怎么用：额度排程的口径，Claude 侧子代理的并发公式、记账与节省，Codex 账号与速度层，单 Claude 账户模式，主账号额度见底时怎么办，以及只在两个 Claude 账号都可用时才适用的规则。

> **查阅**：先读 §0；口径与两种模式看 §1；并发公式、记账与怎么省看 §2；Codex 账号与快速模式看 §3；单 Claude 账户模式看 §4；额度见底时冻结看 §5；仅双账号模式看 §6。

## 0 结论

1. **现在是单 Claude 账户模式**（§4）：Claude 侧只有一个账号可用，流程与派工策略不变，Opus 与 Sonnet 子代理都开在主会话下；进入和退出由作者定。
2. **Claude 侧按"剩余额度在恢复前用满"定子代理的并发**（§2）：按 Opus 当量算，5 小时与每周两个窗口取小，1 到 10 个，派单前先看额度；公式只在紧急段用，非紧急段照 ENG-TEAM-FLOW §2.9 的上限慢慢用。
3. **Codex 账号额度充足**（§3）：杂活默认先派 Sol，额度不监控；GPT 侧只有 gpt-6-luna 用快速模式（D-197）。
4. **主账号剩余约 1% 时冻结**（§5）：停止派一切新活，等在跑的做完，由作者手动切换账号；不移交二号会话。
5. **双账号模式的规则单列**（§6）：两个 Claude 账号都可用时，主账号只给总指挥用、不开新的子代理，Claude 侧子代理开在二号会话的账号上；现在不适用。
6. **容量与倍率是项目经验**（§1）：订阅容量、窗口工时与扣额倍率只用于本项目排程，不作 API 官方报价。

### 0.1 接入要点

本文只约束协作各方的工作方式，没有对其他包的接口要求；按角色的接入要点集中在 ENG-TEAM §0.1。

## 1 额度排程口径与两种模式

**项目经验与额度排程**：本文的订阅容量、窗口工时与本地扣额估计用于本项目排程，以作者实数和项目经验为准，不作为 API 官方报价。

**API 官方定价**：接 API 时按对应服务当前官方报价独立核算，不从订阅容量或本地经验倍率换算 API 单价；推理档、速度层与账号容量分别标注。

Claude 侧按账号可用的情况分两种模式：只有一个 Claude 账号可用时是单 Claude 账户模式（§4），两个都可用时是双账号模式（§6）。Codex 账号额度充足，不监控（§3）。

## 2 Claude 侧的并发与额度

本节的公式与做法在两种模式下都用：双账号模式下由二号会话的主模型执行，单 Claude 账户模式下由主会话执行（§4）。

**并发怎么定**：
- 额度按 5 小时窗口计。按作者实数校准：约 13.4 个 Opus 小时用了 42%，一个窗口的全部额度约够 1 个 Opus 连续跑 32 小时。作者给出实际用量时，以实数为准，并按实数校准常数。
- 并发上限按"剩余额度在恢复前用满"来定，按 Opus 当量算：按子代理的模型和推理档记：Opus medium 0.75、high 1、xhigh 2；Sonnet medium 0.3、high 0.5。系数按各档跑同一套评测的花费之比估算，c 照旧按实测校准。公式不写死，按实测消耗自己校准：
  - 每次读用量，和上一次读数比，算出这段时间每个当量小时实际耗了多少额度：5 小时窗口记作 c，每周额度记作 c周。还没有读数时 c 取 1/32，c周 先不算。
  - 5 小时允许 =（5 小时剩余 − 2% 余量）÷（c × 距 5 小时恢复的小时数）；每周允许 =（每周剩余 − 2% 余量）÷（c周 × 距每周恢复的小时数）。允许的当量取两者较小的一个。
  - 在跑的当量合计（按 §2 的推理档系数记）要向允许值靠，不只是不超过它：比允许值少 1 个当量以上，就从队列补开。
  - 照现在的速度到 5 小时恢复时还会剩 8% 以上，就加并发；撑不到恢复，就不开新的，在跑的不中断。
- **派单前先看额度**：二号会话的主模型每次开新子代理、选 Opus 还是 Sonnet、决定拆不拆单之前，都先看最近一次用量读数，读数超过 15 分钟就重读；算出两个窗口恢复时各自还会剩多少，写进 `notes/max-to-opus.md` 的派单行。
- **紧急段与非紧急段**：上面的公式只在 ENG-TEAM-FLOW §2.9 的紧急段用，这一条和下一条就是紧急段的做法；非紧急段不套公式，只照 ENG-TEAM-FLOW §2.9 的上限慢慢用。
- **余量多时往用满靠**：预计 5 小时恢复时还会剩 10% 以上时，两难之间的活可以用 Opus，不必降到 Sonnet；新单可以两个一起开；空缺活清单里 45 分钟以内的短活优先补位，把恢复前的余量用掉。每周恢复临近、每周额度又剩得多时，只按 5 小时公式开满。个数到上限 10 个、当量还没到允许值时，空出的位子优先开 Opus：Sonnet 只占半个当量，却同样占一个名额。
- **5 小时余量封顶**（按当量计）：只在距 5 小时恢复还有 2 小时以上时生效，用来防窗口前段读数不准：剩余 < 30% 时当量最多 4，剩余 < 15% 时当量最多 2。离恢复不到 2 小时，只按公式。降档不中断在跑的子代理，只是不开新的。
- 例（c 取 1/32，每周额度充足）：窗口刚开始（剩 100%，5 小时后恢复）→ 6.3 → 6 个当量；剩 34%、1.1 小时后恢复 → 约 9.3 → 9 个当量；剩 30%、4 小时后恢复 → 封顶 4；剩 10%、4.5 小时后恢复 → 封顶 2，公式约 0.57 → 1。
- 也就是说：快恢复了、余额又用不完时，开到个数上限 10 个；离恢复还早时少开；最少保留 1 个 Opus 在跑。
- 子代理按 §2 的推理档系数计入上式；二号会话名下的 Opus 与 Sonnet 子代理合计不超过 10 个，截图与重 CPU 任务照样排计数锁。难度较低的活优先开 Sonnet，同样的额度能多跑一倍。

**怎么记账**：剩余额度和恢复时间以二号会话自查用量的实测值为准（作者已授权它用本账号凭据读官方用量接口，脚本只打印百分比和重置时间）。查不到时，按上一次校准出的 c 记账，没有校准值时按"1 个 Opus 跑 1 小时约耗窗口额度的三十二分之一，Sonnet 减半"；每次开新子代理前算一遍，写进 `notes/max-to-opus.md`。公式里的 Opus 小时用任务单上按 D-184 写明的预计工作量来算。

**怎么省**：
- 不一次铺开：比允许值少 2 个当量以上时，新单可以两个一起开；其余情况一个一个开，前一个进入施工后再开下一个。重 CPU 与 GPU 任务照样排计数锁。
- 子代理默认新开、靠任务单交接，只有交回后几分钟内的小返工和小上下文的相关小活恢复原子代理（ENG-TEAM-ROLES §3.5）；长上下文接新活，每一轮都在为旧历史付费。

## 3 Codex 账号（Astra 与 Sol）

- **额度充足**：杂活默认先派 Sol（ENG-TEAM-ROLES §3.2）。
- **不监控**：Codex 额度不监控，重置时机由作者自己决定；套餐额度用完会自动使用账户余额。
- **快速模式**：`service_tier="priority"`，速度约 2 倍、额度约按 2.5 倍消耗是本项目经验估计，不是 API 官方定价倍率。gpt-6-luna 默认用快速模式；GPT 侧其余模型（Sol 值班、Sol 旁路、Astra 及它们开的 6.1-sol 子代理）一律用普通速度（D-197）。

## 4 单 Claude 账户模式

Claude 侧只有一个账号可用时（例如一个账号的每周额度用完，作者把主会话切到另一个账号），进入单 Claude 账户模式；两个账号都可用时是双账户模式（§6）。进入和退出都由作者定，主会话在 `HANDOVER.md` 末尾记一行"进入单 Claude 账户模式：<时间>"或"回到双账户模式：<时间>"。

**不变的**：工作流程和派工策略照 ENG-TEAM 各分册执行，包括七问选模型与 Sonnet 优先（ENG-TEAM-ROLES §3.1）、任务单与"接续"的写法（ENG-TEAM-FLOW §2.2、§2.3）、评审与批准行（ENG-TEAM-FLOW §2.4、§2.5）、Sol 值班合并（ENG-TEAM-DUTY §1）、按 Opus 当量的并发公式与上限（§2）、从 `tasks/claude/max-backlog.md` 补位（§2"余量多时往用满靠"）、开工 30 分钟重估（ENG-TEAM-FLOW §2.2）、按 D-184 拆单。

**只改一处：子代理开在主会话下**：
- Opus 与 Sonnet 施工子代理都由主会话用 Agent 工具开（写法同 ENG-TEAM-DUTY §4 的 Claude 侧），附通用简报 `tasks/claude/max-brief-common.md`；子代理的最终回复就是回报。
- 双账户模式下二号会话做的事，改由主会话做：派单、写简报、核对候选（工作树干净、与 main 无冲突、门禁结果）、代记任务单"状态"、按 §2 读额度并定并发、查停滞。
- 评审不通过时，能在原子代理的上下文里改就接着改；原子代理已经结束的，另开子代理接着做。

**额度**：§2 的公式照用，作用在这一个账号上。主会话用 `get_usage` 直接读 5 小时与每周两个窗口，它自己的消耗也在读数里，公式不用改。合计不设下限：非紧急段 Claude 侧在跑的子代理合计不超过 3 个，紧急段按 §2 的公式开到上限（ENG-TEAM-FLOW §2.9）。§6 的双账号规则在本模式下不适用；额度见底照 §5。

**不用的**：二号会话；`notes/opus-to-max.md`、`notes/max-to-opus.md` 两份流水；ENG-TEAM-COMMS §4 里主会话与二号会话之间的消息。

**切换时**：
- 进入本模式时，二号会话在跑的子代理照常做完，候选照常写进任务单，此后不开新的；返工由主会话另开子代理接。
- 回到双账户模式时，主会话名下在跑的子代理做完为止，新单照 ENG-TEAM-FLOW §2.2 交二号会话。
- 换账号时，原会话在后台跑的唤醒脚本会随它一起停掉。接续的会话先查进程，再按 ENG-TEAM-COMMS §5 重启，每个脚本只能有一个在跑。

## 5 额度见底时冻结

**什么时候查**：主会话每次处理事件时，查一次本账号的额度（`get_usage`）。

**冻结**：主账号的任一额度窗口（5 小时或每周）剩余约 1% 时冻结：停止派一切新活，等在跑的做完，由作者手动切换账号；不移交二号会话。冻结时主会话在 `HANDOVER.md` 末尾更新"进行中的事"，供切换后的会话接着做（ENG-TEAM-COMMS §6）。

## 6 仅双账号模式

本节只在两个 Claude 账号都可用时适用。现在是单 Claude 账户模式（§4），本节不适用；回到双账号模式由作者定。双账号模式下，两个 Claude 账号都是 Max 20x：主账号只给总指挥用，二号会话的账号按 §2 的公式算并发。

### 6.1 主账号（主会话）

- 主账号是 Max 20x，但分工不变：主会话仍只做总指挥，额度只花在要判断的事上（ENG-TEAM-ROLES §3.2）。
- 主账号不开新的子代理：所有并发的 Opus 子代理都在二号会话的账号上跑；要子代理做的事，不论长短，都写成任务单交二号会话（ENG-TEAM-FLOW §2.2）；不需要审美的活交 Sol。主会话名下已在施工的子代理，照常做完手上的包。

### 6.2 二号会话的账号

- **合计至少保持 5 个**（只在双账号模式适用）：二号会话在跑的 Opus 与 Sonnet 子代理合计至少保持 5 个；上限与 5 小时余量封顶优先，封顶低于 5 时按封顶。主会话派的单和正在做的子单排在空缺活清单前面，D-183 建模优先照旧。
- **从空缺活清单补位**：少于 5 个时，从主会话维护的 `tasks/claude/max-backlog.md` 自上而下取第一条未被阻塞、也没有人在做的活，二号会话按 D-184 自己写任务单并开工，编号从 `max-101` 起。开单时给主会话发消息，评审与批准照常走。

**向主会话报额度**：二号会话每次给主会话发消息时附一行额度；没有其他事时，也约每小时在 `notes/max-to-opus.md` 记一行。写明 5 小时剩余与恢复时间、每周剩余、在跑的 Opus 与 Sonnet 数，估算值标“估”；主会话据此控制派单节奏。

**撞到 5 小时上限**：撞线时离重置一般不远。主会话发现二号会话调不动了（消息不回，或者半小时以上没有动静、手上的活又没做完），就每隔 15 分钟发一句探测，直到它回话；回话即说明额度恢复。
- 二号会话来得及时，撞线前在 `notes/max-to-opus.md` 记一行“额度到顶”。
- 恢复后，先让被中断的子代理从中断处接着做；接不上的，按原单开新子代理，在原工作树继续。

**怎么省**：
- 主会话派单也分批：同一时刻挂给二号会话、还没开工的单不超过 4 张，其余留在主会话手里或放进空缺活清单，等有空位再发。
- 二号会话本身只做派单、转达和初步核对，不亲自施工大块内容。
- 账号额度快用完时，在流水里写明并通知主会话，由主会话改派。
