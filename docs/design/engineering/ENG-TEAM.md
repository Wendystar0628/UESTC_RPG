## 0 结论

1. **参与者**（§1，D-179）：作者提出要求、最终拍板。协作的会话分属三个账号：
   - 主账号的 Opus **主会话**是总指挥；
   - **二号会话**（第二个 Claude 账号，Max 20x）开 Opus 与 Sonnet 子代理，承担 Opus 侧的施工；
   - **Astra**（GPT-6 Astra，xhigh，本机 Codex）是工程指挥：定契约与工程方案、拆单派工、审查与集成，尽量不亲自施工；施工默认交它开的 gpt-6.1-sol 子代理；
   - **Sol 会话**（gpt-6.1-sol）有两个固定会话：值班会话（快速模式）做执行类的活，旁路会话（普通速度）按任务单开子代理，做完成度调研与旁路活。
2. **主代理只有一个，就是主会话**（§1.1，ENG-ARCH §6，D-166）：合并队列、`main` 的提交与推送、ENG-STATUS、`docs/design/` 的修改、与作者沟通，都由它决定。不需要判断的执行部分交 Sol 值班会话；`main` 同一时刻只有一个执行人。
3. **按模型能力分工，视觉风格只由 Opus 侧做**（§2）：Opus 管审美、判断与变通；Sonnet 做语言与看图；Astra 管架构判断与工程指挥；gpt-6.1-sol 能力接近 Astra、性价比高得多，是工程施工的默认模型。GPT 模型不做任何审美工作；玩家看得见、听得见的结果，参数和取舍都由主会话评审定值。
4. **契约以 Astra 为准**（§5.7）：契约与共享工程文件只由 Astra 改。牵涉画面表现的契约由 Astra 起草，主会话确认后再冻结（§5.4，D-134）。
5. **按难度选模型，总指挥只做判断**（§3）：主会话只做评审定值、设计定案、派工与合入决定、与作者沟通；主账号不开新的子代理，所有并发的 Opus 子代理都在二号会话的账号上跑；不需要审美的活默认先派 Sol。包内的实现路径由施工模型自己规划。
6. **包按擅长归属，主线分段开工，每个包按固定顺序合入**（§4、§5.1–§5.7）：D0 → 第一波 → 第二波 → 主线闸口；一个包走派工 → 建工作树 → 施工 → 回报 → 评审 → 批准行 → 合并执行 → 施工状态 → rebase 通知。只合有主会话批准行的候选，合并由 Sol 值班会话执行。
7. **调研入队流水线**（§5.8）：6.1-sol 调研 → 主会话审计 → 并入现有工作包或新增工作包 → 加入 ENG-STATUS §4 待派工队列，依赖满足后按优先级与二号会话的并发余量派工。
8. **经文件交接，消息只在事件发生时发**（§6）：交接目录是 `E:\Project\UESTC_RPG.wt\.collab\`。任务单和请求文件是交接的唯一依据，任何一方上下文重置，都照它们接着做。两个 Sol 会话各由一个唤醒脚本叫醒：值班会话按批准行、新任务单和定时；旁路会话按 `side/cards/` 下的新任务单，一次一张。下属会话与子代理不向作者出选项或确认框：要确认的事写进任务单或请求文件并通知主会话，主会话能据项目信息判断的直接定，只有属于作者的决定才转问作者（§6.4）。
9. **额度按账号管**（§7）：两个 Claude 账号都是 Max 20x，主账号只给总指挥用、不开新的子代理；二号会话按"剩余额度在恢复前用满"定子代理的并发（按 Opus 当量，5 小时与每周两个窗口取小），1 到 10 个，派单前先看额度；Codex 账号额度充足，杂活默认先派 Sol，额度不监控。主账号任一额度窗口剩余不到 1% 时，主会话移交给二号会话的 Opus 主模型接任，直到作者说交回（§7.4）。Claude 侧只有一个账号可用时进入单 Claude 账户模式：流程与派工策略不变，Opus 与 Sonnet 子代理都开在主会话下（§7.5）。
10. **值班、调研和旁路交给 Sol**（§8）：值班会话长期做合并执行、施工状态与巡检，并按开发阶段持续排完成度调研；调研单和不在关键路径上的旁路活都写成任务单，交固定的 Sol 旁路会话按单开子代理处理；调研结果走调研入队流水线（§5.8）。Sol 不做审美，不改契约和共享工程文件；设计文档只在两种情况下改：值班会话维护 ENG-STATUS，任务单给出确切文字时按文打补丁。

### 0.1 接入要点

- **你是主会话**：先读 §1.1、§3.2、§5；只做判断，不开新的子代理，要 Opus 子代理做的事一律写成任务单交二号会话，杂活交 Sol；下属报来要确认的事，能据项目信息判断的直接定，只有属于作者的决定才转问作者（§6.4）；调研审计采纳后写进 ENG-WP 并加入 ENG-STATUS §4 待派工队列，从"可派"条目里按优先级与二号会话的并发余量派工（§5.8）；评审写在任务单或请求文件末尾，批准行照 §6.3 的格式写；派单按 §7.2 分批。单 Claude 账户模式下，Claude 侧子代理由你直接开，二号会话的职责由你自己做（§7.5）。
- **你是二号会话**：先读 §5.2–§5.6、§6、§7.2；收任务单，按并发公式开子代理施工，做初步核对，原样转达评审意见；画面与风格以主会话的评审为准；不合并、不推送、不改契约与共享工程文件，不自己大块施工；收到"主会话移交"就按 §7.4 接任主会话。
- **你是二号会话开的子代理**：向二号会话回报，不直接找主会话；照任务单和通用简报施工（§5.3）；评审意见回来，在原上下文里接着改（§5.4）。
- **你是 Astra**：先读 §2、§3.3、§5、§8.4；你是工程指挥，施工默认开 gpt-6.1-sol 子代理去做，你负责拆单、写简报、审查与集成（§3.3）；你的包只交机制和集中的可调参数，不做画面观感的决定与调整，观感问题写评审请求（§2.2、§5.4）；契约与共享工程文件只由你改，在 WP-00 工作树提交并写合并请求（§5.7）；看 `merged.log`，通知你的子代理 rebase（§5.6）。
- **你是 Astra 派出的子代理**：向 Astra 主线程回报，不直接找主会话；做完由 Astra 写合并请求（§5.3）；只在简报给的工作树里读写，git 一律 `git -C <工作树>`（§8.4）。
- **你是 Sol 值班会话**：按 `tasks/sol-001.md` 执行；只合有批准行的候选（§5.5）；合入后同步 ENG-STATUS，并顺带把 ENG-STATUS §4 待派工队列里依赖已满足的条目改成"可派"（§5.6、§5.8）；巡检与排调研按 §8.1、§8.2；不做任何画面与风格判断，不改代码。
- **你是 Sol 旁路会话**：按 `side/ROLE.md` 执行唤醒脚本交给你的那一张单（调研单 `r<nnn>` 或旁路单 `s<nnn>`），做完写状态和流水就结束本轮（§8.3）；按单开 gpt-6.1-sol 子代理，最多 8 个并发；调研涉及观感的只收集事实和出处，不调研、不建议 RPG 内容（§8.2）；不做审美判断，不改契约和共享工程文件，设计文档只按任务单给的确切文字打补丁，不合并、不推送，不碰别的工作树与主检出。
- **你是下属会话或子代理**（二号会话、Sol 值班与旁路会话、Astra，以及各自的子代理）：不向作者出选项或确认框；需要确认时写进任务单或请求文件，并通知主会话，子代理交给派你的一方转达（§6.4）。
- **你是任何施工子代理**：
  - 向派你的一方回报（§1 表的"汇报给"一列），做完写合并请求或回报，不自己合 `main`、不推送（§5.3、§5.5）；
  - 开始下一步之前看 `merged.log`，`main` 变了就在自己的工作树里 `git rebase main`（§5.6）；
  - 要改契约或共享工程文件，在 `.collab/requests/` 写契约申请，由 Astra 处理（§5.7）；
  - 要改设计文档，在回报里提出，由主会话定（§1.1）；
  - 结果看得见或听得见的，把可调参数集中放一处，并在回报里列出，供主会话评审定值（§5.4）。

### 1.1 决定权与执行人

**主会话决定**（ENG-ARCH §6，D-166）：
- 合并队列：哪个候选、什么时候合；
- `main` 上的提交和推送；
- ENG-STATUS；
- `docs/design/` 改什么；
- 与作者沟通。

**执行交出去**：
- 上面不需要判断的执行部分，即按批准合入、跑门禁、提交推送、写 `merged.log`、维护 ENG-STATUS、巡检，由 Sol 值班会话做（§8.1）。
- `main` 同一时刻只有一个执行人。值班会话合并时，主会话和其他会话都不碰主检出的暂存区。
- 设计文档的撰写可以派出去：需要 Opus 的撰写交二号会话的 Opus 子代理；Sol 只在任务单给出确切文字时按文打补丁。改动都在工作树里做，经批准合入。

**其他各方定什么**：
- Astra 定契约、共享工程文件和工程上的取舍（§5.7）；
- 画面与声音的取值、风格定案，以主会话的评审为准（§2.2）。

## 2 按模型能力分工

分工按模型的长处来：要审美、判断和变通的给 Opus；要语言质感和看图、但不定风格的给 Sonnet；架构判断与工程指挥给 Astra；工程施工默认给 gpt-6.1-sol，它的能力接近 Astra，性价比高得多，可以高并发。硬规则只有一条：GPT 模型不做任何审美工作（§2.2）。

### 2.1 各模型的长处与短板

| 模型 | 用在哪里 | 长处 | 短板与限制 |
| --- | --- | --- | --- |
| Claude Opus 5.5 | 主会话；二号会话的 Opus 子代理 | 审美、判断、变通：画面、风格、内容，跨系统取舍，需要 Opus 的文档撰写 | 额度最贵：主账号只给总指挥用，二号会话按并发公式开（§7） |
| Claude Sonnet | 二号会话的 Sonnet 子代理 | 价格约为 Opus 的一半。难度较低的施工：规格、尺寸、色名都已给全的简单部件，按已定预设填数据，覆盖层与数据改动，测试与小修，rebase 与拣选；以及中文文档改写、文案、看图初筛、质感做法整理 | 不定风格，画面与风格的定值归主会话；需要审美判断的活交 Opus |
| gpt-6-astra（xhigh） | Astra 主线程；少数 gpt-6-astra 子代理（§3.3） | 架构判断与工程指挥：契约与程序集边界、注册器、依赖方向，以及并发、确定性、本机烘焙与流式、序列化与迁移、物理与碰撞、性能结构的方案定案；拆单、审查与集成 | 最贵的 GPT 档：主线程以指挥为主，尽量不亲自施工；不做任何审美工作，语言质感、看图和审美眼光是 GPT 模型的短板 |
| gpt-6.1-sol | 两个 Sol 会话及旁路会话的子代理；Astra 侧包的默认施工模型（Astra 开的 6.1-sol 子代理） | 能力接近 Astra，性价比高很多；额度充足，可以高并发；复杂工程施工用 high 或 xhigh；值班会话用快速模式，旁路会话用普通速度 | 同属 GPT 模型，不做任何审美工作；契约和共享工程文件不自行改，Astra 定案并授权后可以施工；设计文档只按确切文字打补丁（§8） |

### 2.2 硬规则：GPT 模型不做审美工作

- **视觉风格只由 Opus 侧做**：着色、调色、描线与后期的观感、材质与造型的观感、按参考场景移植质感（ART-STYLE §1），都只由 Opus 侧处理。参考场景里没有对应物的内容，也由 Opus 侧按同一套质感做法统一处理。
- **定值归主会话**：玩家看得见、听得见的结果，参数和取舍都由主会话评审定值（§5.4）。Sonnet 子代理可以按检查单初筛截图、整理质感做法，不定风格。
- **GPT 模型一律不做**：Astra、它的子代理、两个 Sol 会话和它们的子代理，不做画面、配色、质感、构图、造型、界面观感、参数取值和截图评审方面的决定与调整。
  - Astra 的包只交机制和集中的可调参数；遇到画面观感问题，写评审请求交主会话（§5.4）。
  - 调研里涉及观感的，只收集事实、做法和出处，结论由主会话下。
- **采集、读图与定案分开**：程序采集与像素计量、按检查单读图、风格定案是三种不同的工作，GPT 只做第一种。

### 2.3 事归谁

先分审批与施工：主会话定设计、审美、内容取舍、可见参数、优先级与合入；Astra 定工程、契约及高传播风险的方案。实际施工按 §3.1 的七问逐项判断，包归属（§4.1）与目录写权限不因施工模型改变。

可见构件一律由 Opus 施工，哪怕已给全尺寸和截面；GPT 可承担它们的非可见部分，如碰撞、数据、接线和单测。Astra 名下封闭、已定的子任务可单独转给 Sol；不按包号整包改派，工程取舍与必要复核仍归 Astra（§3.3）。

### 2.4 交叉的地方

- **Astra 的包里有可见结果的**：Astra 交机制和参数表，主会话定参数值。这类包有：启动雾幕、镜头手感、跳转、行走手感、过场播放、介质。
- **Opus 侧的包里有重工程的**：遇到架构问题请 Astra 评审。这类包有：建筑生成器的开间与立面规则、描线的计算着色器、材质库。
- **画面相关的契约**：Astra 起草，主会话确认字段够不够用（§5.4）。

## 3 模型等级与任务划分

按 §3.1 的七问选够用的施工模型；主会话保留判断，其余按权限派出去。

### 3.1 按七问选施工模型

依次看还缺什么判断、结果能否验收、错误会传播多远。混合任务先分清未定判断与已定实现，再按下表安排。

| 问题 | 倾向：会话、模型与档位 | 复核或停止信号 |
| --- | --- | --- |
| 1. 要定造型、风格、声音、玩家可见参数或内容取舍，或制作可见构件吗？ | 需要审美判断的（定造型、风格、观感取值，地标与重点构件，质感移植）由二号会话的 Opus 施工，主会话定案；只缺判断时主会话直接定。规格、尺寸、色名都已给全、难度较低的可见活（简单部件、按已定预设填数据、小修）可以交 Sonnet。审美相关的活一律不交 GPT；非可见部分可拆出继续问 | Opus 审美评审；接口与生命周期部分才加 Astra，GPT 不替选值 |
| 2. 必须读图或依赖中文语感判断吗？ | 按检查单读图初筛、中文改写交二号会话或其 Sonnet；可程序测出的数据与截图采集交 Sol。涉及审美回第1问 | Sonnet 不定风格；改变原意或含内容取舍时交主会话 |
| 3. 目标、规格和通过条件仍有歧义吗？ | 工程歧义交 Astra（gpt-6-astra，xhigh），设计与内容歧义交 Opus，定清再派实现 | 契约含义或规范冲突未定，先停相关项；不靠增加推理替代决定 |
| 4. 错误会跨接口、线程、资源寿命或存档扩散吗？ | Astra 定方案、边界与验收条目，施工默认交 Astra 名下的 Sol 子代理（high 或 xhigh）；Sol 两次做不对或方案本身要改时，Astra 才亲自做关键段 | Astra 定向复核调用方、所有权与迁移；共享文件不得由旁路越权改 |
| 5. 数学或几何很难，但能由不变量、参考结果验证吗？ | 非审美实现由 Astra 名下 Sol 施工；前提不清或全局耦合，先由 Astra 定清前提，再交 Sol。可见构件仍回第1问 | 按风险核退化边界、真实引擎约定与确定性；数学成立不代替造型评审 |
| 6. 是大量明确执行或事实整理吗？ | Sol 旁路；工程子任务由 Astra 派 Sol。确需语言加工时再用 Sonnet，不因文件是中文就全部给 Claude | 漏条先由原施工者补；前提失效或反复理解错误再升级对应判断方 |
| 7. 是既有批准后的执行，或剩余明确非审美实现吗？ | 合并与状态交 Sol 值班，其余默认 Sol 实现，由相应负责方派单；主账号不新开施工代理 | 候选号、批准条件或权限变化，先停相关项；只做改动需要的检查 |

**推理强度按难度选**：子代理不一律开 xhigh，每张单按难度选一档，写进派单（见下文"派单最少写"）。每升一档，费用和用时都明显上涨，完成度的提升却越来越小，所以够用就停。

| 难度 | 例子 | Opus | Sonnet | gpt-6.1-sol |
| --- | --- | --- | --- | --- |
| 简单 | 规格已给全，能按条目或程序验收：填数据、按已定预设接线、rebase 与拣选、单文件小修、查资料与整理、按确切文字打文档补丁 | 不派 | medium | medium |
| 一般 | 要自己规划实现，结果能按条目验收：常规部件与建模、普通接线与单测、截图采集 | high（需要审美判断的可见构件） | high | high |
| 难 | 判断重，或错误会扩散：地标与重点构件的造型、质感移植、跨包根因，确定性、并发、资源寿命、存档方案，契约方案 | xhigh | 不派，改派 Opus | xhigh |

- Sonnet 只用 medium 和 high。要 Sonnet 开 xhigh 才做得好的活，改派 Opus high：花费相近，完成度更高。
- 不用 max；施工不用 low。
- 返工沿用原档。同一档两次做不对，先照下文"升级先找失败原因"查原因，确实是难度不够才升一档。
- Astra 给 Sol 子代理定档照上表；gpt-6-astra 子代理只在 §3.3 列的情形开，用 xhigh。
- 固定长期会话保持当前有效档，不做全局降档：主会话、Astra 主线程 xhigh；Sol 值班 xhigh 加快速模式，旁路普通速度（§7.3）。
- 推理强度、速度层与账号容量分别记录。

**组合只在需要时用**：

- Sol 实现 → Astra 核工程风险；
- Sol 程序采集/像素计量 → Sonnet 读图初筛 → Opus 定观感；
- 二号会话 Opus 做内容 → Astra 核工程交界；
- Sol 整理事实 → Sonnet 语言加工 → 主会话批准规范。

每张单只列具体风险和对应复核人；截图初筛不常驻叠在 Opus 评审前。小修与纯接线默认不叠 Astra 复核，涉及共享接口、跨线程、资源寿命或存档时才加，不叠无对应风险的全链复核。

**简单少量的活，拿到信息的一方直接做**：模型之间每转一次手都要花额度：写简报、对方重读上下文、再回报。所以简单又量少的活，由已经拿到全部信息的一方直接做完，不再写单子转给别的会话或子代理。只有量大、要并行、要换模型能力，或者归属不在自己手里时才转派。例如：主会话手上已有确切文字的几处文档修改，主会话直接在工作树里改；子代理在自己独占目录里顺手能补的小处，直接补，不另提单。

**升级先找失败原因**：已明确条目漏做，由原施工者补条目、候选与对应证据；接口或生命周期无解交 Astra 定边界；观感和内容争议交 Opus；超量或后半段质量下降按 D-184 拆单，不用升级模型代替拆单。

**派单最少写**：目标与验收条目、定案与未定项、独占路径、会话/模型/推理档/速度层、必要复核人、升级信号、预计工作量（D-184）。包内实现路径由施工者规划（§3.4）。

### 3.2 总指挥只做什么

**主会话的注意力只花在要判断的事上**：
- 画面与风格的评审和定值，质感移植（实现交二号会话）；
- 设计定案与跨系统取舍、文档冲突裁决；
- 派工、排优先级、合入决定；
- 与作者沟通。

**其余随时派出去，主会话不自己动手**（简单又量少、主会话手上已有全部信息的活例外，直接做，见 §3.1"简单少量的活"）：
- **不需要审美能力的任务和杂活**：默认先派 Sol（Codex 额度充足，§7.3）。执行类交值班会话；调研、补信息、数据转换与核对、按确切文字打文档补丁、批量的旁路工程活写成旁路单交旁路会话（§8.3）。
- **Opus 侧新开的施工任务**（画面、风格、内容类包与需要 Opus 的文档撰写）：写成任务单交二号会话（§5.2）。补 GPT 短板的简单活也交它。
- **细节阶段的小修**：先交对应包的子代理或二号会话、Sol，主会话只看结果。
- **主账号不开新的子代理**：所有并发的 Opus 子代理都在二号会话的账号上跑；要子代理做的事，不论长短，都写成任务单交二号会话（§5.2）。主会话名下已在施工的子代理，照常做完手上的包。

### 3.3 Astra 当指挥，施工默认交 6.1-sol 子代理

**Astra 主线程尽量当指挥官**：
- 做：契约与共享工程文件的定案；Astra 侧包的拆单和派工；写子代理简报，写清目标、约束和验收条目；审查子代理交回的方案与代码，看架构、契约、确定性和资源寿命；跨包的集成取舍；写合并请求；回答主会话。
- 尽量不做：亲自写实现，亲自跑长时间的测试与排查。这些也先拆给 Sol 子代理，Astra 只看结果和关键差异。

**施工默认用 gpt-6.1-sol 子代理**：Astra 名下所有包的施工，默认由 Astra 用 `spawn_agent` 开 gpt-6.1-sol 子代理完成，复杂工程用 high 或 xhigh。这也包括内核、确定性、统计、契约与存档迁移相关的包（WP-01、02、06、07、08、26、32、34、42、43、44、45a、46、49a、50、53a、53c）。包的归属与审查权不变，仍由 Astra 派工、审架构与契约、写合并请求。

**gpt-6-astra 子代理只在下面几种情形开**：
- 契约、共享接口或存档迁移的方案起草；
- 跨包的根因排查，Sol 子代理两次没查出来或没修对；
- 确定性、并发、资源寿命的方案本身要改，需要 Astra 级判断的那一段。

其余一律用 Sol。已有的 gpt-6-astra 包级子代理不再接新活，新任务按本节改派 Sol 子代理。施工范围以 Astra 明确授权的路径为准，不自动取得其他目录权限；固定值班与旁路会话的边界不变。

### 3.4 包内的实现路径由施工模型规划

- 任务单和简报只给目标、约束（主线优先、依赖、契约、目录归属、预算）和交付标准，不规定步骤。
- 施工模型按当前任务自己排实现路径和先后顺序，在回报里说明计划和偏差。

## 5 开发流程

### 5.1 全流程一览

### 5.4 评审：审美与契约的交叉评审

**审美评审由主会话做**，它是风格负责人（ENG-WP §5 第 4 条），评审金样、色板联表、界面样张和全部画面类截图。

- **请求文件的评审**：主会话在合并请求或评审请求末尾写结论或新值。主会话的子代理评审不通过，就把意见发回同一个子代理继续改。

**可调参数集中放**：Astra 的包有可见或可听的结果时，把可调参数放在一处，可以是数据文件，也可以是集中的常量类，并在评审请求里写明截图或录像路径、参数在哪、各参数现在的值。主会话评审后，在评审文件里写新值，或直接在那个参数文件里改；改动经合并队列进 `main`。

### 5.5 批准与合并

**批准**：评审通过后，主会话在合并请求或任务单末尾写批准行（格式见 §6.3）。批准行可以附"门禁：…"（例如 `-D0`、去掉 G3、只改文档只跑 `check_docs.py`）或补充条件（例如"merge-WP-00-4 已合入 `main` 之后再合"）。条件没满足就不合。

**合并执行**：唤醒脚本发现新的批准行，叫醒 Sol 值班会话（§6.5）。值班会话照 `tasks/sol-001.md` 的"合并执行"一节，在主检出 `E:\Project\UESTC_RPG` 上做（ENG-ARCH §6 第 4 步）：
1. `git status --short` 必须为空；不空就停下，写进文件末尾并通知主会话，不动别人的改动。
2. `git merge --squash <候选提交>`；有冲突就 `git reset --merge` 撤回，停下报告。
3. 跑门禁：默认 `scripts\gate.ps1 -Wp <包号> -Only G1,G2,G3,G4,G5`，批准行另写了组合就照写的跑；只改文档的跑 `scripts\docs\check_docs.py`，要求 problems 0。资源有改动时 G1 会在主检出跑 `--headless --import`，同时更新工作树的导入种子。
   - 失败：`git reset --merge` 撤回，把失败项、关键报错行、日志路径写到文件末尾，通知主会话，停下。不修代码。
   - 等 GPU 锁超过 15 分钟：查卡死的进程并报告，不绕过锁。
4. 提交：首行 `WP-xx: <一句话>` 或 `文档：<一句话>`；正文几条要点，只从请求文件或回报里取，末尾写"候选 <提交>。门禁 … 通过。"；结尾加 `Co-Authored-By: GPT-6.1 Sol <noreply@openai.com>` 和 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` 两行。
5. `git push origin main`：只推 `main`，不推分支，不强推。
6. 往 `merged.log` 追加一行（格式见 §6.1）。
7. 该包工作树若干净，`git -C <工作树> switch -C <分支名> main`，从新的 `main` 重建分支。值班会话不删分支和工作树；文档类的临时工作树（`SN-*`、`DOC-*`）合入后保留；包整体做完以后的清理由主会话定。
8. 在文件末尾追加"已合入：main=<短号>，<时间>，Sol 值班会话"，并通知主会话。

**合并的其他规矩**：
- 一次合一个，内核包按 §4.2 的顺序合。
- 交候选之前，施工方先 rebase 到最新的 `main`。squash 冲突时，值班会话撤回并报告，由施工方 rebase 后重交。
- 带条件的批准行，值班会话每次巡检都复查一遍，条件满足了就合入（§8.1）。

### 5.6 合入以后：施工状态与 rebase

### 6.2 命名与写法

- `.collab` 在仓库之外，不进 git。
- 所有文件只追加、不改写；每条带时间；路径一律写绝对路径。唯一的例外是 `research/INDEX.md` 的"Opus 审计"一列：旁路会话做完一单时标"待审"，主会话审计后改写。
- **不预判时间**：模型凭推理感知时间误差很大，所以不估计"已经用了多久""还要多久"，回报和流水里不写预计完成时间，只写做到哪一步。要用时间时以真实读数为准：手边的命令输出、文件时间戳、额度读数；时长和额度消耗速度用两次真实读数相减。读时间不是硬性规定，不为写时间频繁读时钟；手边没有真实时间就只写日期，不凭推理填。任务单按 D-184 写的工作量用来定单子大小，不当作完成时间的预告。
- **请求文件**：序号取现有最大号加一，用不覆盖的写法创建（例如 bash 先 `set -C` 再重定向，或先确认文件不存在）；撞号时改用下一个号，不覆盖别人的文件。
- **任务单**：`max-<nnn>`、`sol-<nnn>`、调研单 `r<nnn>`、旁路单 `s<nnn>` 都是三位编号递增，新建前确认没被占用。

### 6.3 任务单与请求文件的格式

**max 任务单**：正文写 §5.2 列的五项。末尾依次是：
- **"状态"小节**：二号会话追加，一行一事，带时间：派出（子代理名与模型）、受阻（原因、需要谁定）、待评审（候选提交、截图路径、要定的问题）、已按评审修改。
- **"Opus 评审（时间）"小节**：主会话写，通过或逐条修改意见。
- **批准行**。

**sol 任务单**：正文写任务、做法和不许做的事；末尾"状态"小节由值班会话追加，一行一事，带时间。

**旁路单**：正文写在哪做、交付什么、能改什么、哪些不许做；末尾"状态"小节由旁路会话写过程与结果。调研单的写法见 §8.2。

**请求文件**：正文按 §6.1 的"写什么"一列；后续各方只在末尾追加，每条带时间和署名。

**批准行**：
- 格式：`批准合入：<候选提交或说明>，Opus，<时间>`，后面可以接括号里的门禁组合或条件。
- 写在合并请求或任务单的末尾，单独成行，行首就是"批准合入："，前面不加列表符号或空格。唤醒脚本按行首匹配，行首不对就叫不醒值班会话。
- 合入后，值班会话在同一文件末尾追加"已合入：main=<短号>，<时间>，Sol 值班会话"。

### 6.4 消息与流水

**消息只在事件发生时发**，内容一句话，细节都在任务单里：

| 方向 | 什么时候发 |
| --- | --- |
| 主会话 → 二号会话 | 新单、评审已写 |
| 二号会话 → 主会话 | 待评审、受阻需要决定、整单完成 |
| 两个 Sol 会话 → 主会话 | 合入完成、门禁失败、条件未满足、卡死进程、调研完成；写进 `notes/sol-to-opus.md`，一行 `[时间] <事>`，主会话一侧有监视 |
| 主会话 ↔ Astra | 其余通知，例如文档改了、契约冻结了、某个包阻塞了；写进 `notes/opus-to-astra.md`、`notes/astra-to-opus.md` |

- 不发进度汇报，不互相轮询。几张单在 10 分钟内先后到待评审时，合成一条消息。
- **流水**：主会话与二号会话之间的流水是 `notes/opus-to-max.md`、`notes/max-to-opus.md`，一行一事，带时间。二号会话的额度记账也写在 `max-to-opus.md`（§7.2）。

**确认与提问**：
- 所有下属会话与子代理（二号会话、Sol 值班与旁路会话、Astra，以及各自的子代理）都不向作者出选项或确认框。
- 需要确认时，写进任务单或请求文件，并通知主会话：二号会话发跨会话消息，Sol 写 `notes/sol-to-opus.md`，Astra 写 `notes/astra-to-opus.md`；子代理交给派它的一方，由它写进单子并转达。
- 主会话能据项目信息判断的直接定；只有属于作者的决定，才转问作者。

### 6.5 唤醒脚本

两个 Sol 会话各由一个唤醒脚本叫醒。两个脚本都每 20 秒查一次，都用 `codex exec resume` 叫醒同一个固定会话，消息从标准输入传入。

| 脚本 | 启动 | 叫醒谁 | 什么时候叫醒 |
| --- | --- | --- | --- |
| `tools/sol_duty_watch.sh` | `bash sol_duty_watch.sh <值班会话的 thread>` | Sol 值班会话 | 新的批准行、新的 sol 任务单、定时巡检（下表） |
| `tools/sol_side_runner.sh` | `bash sol_side_runner.sh <旁路会话的 thread>` | Sol 旁路会话 | `side/cards/` 下有还没交出的任务单 |

**值班唤醒脚本**按下面的顺序处理，一次只叫醒一轮：

| 发现 | 做什么 |
| --- | --- |
| `requests/*.md` 或 `tasks/*.md` 里新的行首"批准合入："行 | 叫醒值班会话，消息里列出新的批准行（文件和内容），要求照 `sol-001.md` 合并并巡检 |
| 否则：`tasks/` 下新的 `sol-*.md`（`sol-001.md` 除外） | 叫醒值班会话读单执行 |
| 否则：距上次唤醒满 30 分钟 | 叫醒值班会话做定时巡检，不合并任何东西 |

值班唤醒脚本不启动调研：调研单写进 `side/cards/`，由旁路唤醒脚本交出。

**旁路唤醒脚本**按文件名顺序，从 `side/cards/` 里取一张还没交出的单，叫醒旁路会话，消息里写明任务单路径，并要求照 `side/ROLE.md` 执行；这一轮结束后再取下一张。一次只交一张。

- **叫醒的命令**：值班唤醒脚本用 `codex exec -s danger-full-access -C "E:\Project\UESTC_RPG" resume <thread_id> -m gpt-6.1-sol -c model_reasoning_effort=xhigh -c 'service_tier="priority"' --json -o <输出文件> -`；旁路唤醒脚本相同，但不带 `-c 'service_tier="priority"'`，用普通速度。
- **每轮只做被叫醒的事**：值班会话只处理消息里写的事和巡检；旁路会话只做交给它的那一张单，做完写状态和流水就结束本轮。
- **记录**：
  - `tools/sol_duty/`：`watch.log` 记每次唤醒；`seen.txt`、`cards.txt` 记已经处理过的批准行和任务单；`last.md`、`events.jsonl`、`stderr.log` 是值班会话最近一轮的输出。
  - `tools/sol_side/`：`runner.log` 记每张单的唤醒与"本单结束"；`done.txt` 记已经交出的单；`<单号>.last.md`、`<单号>.events.jsonl`、`<单号>.stderr.log` 是每张单的输出。

## 7 账号与额度管理

**项目经验与额度排程**：本节的订阅容量、窗口工时与本地扣额估计用于本项目排程，以作者实数和项目经验为准，不作为 API 官方报价。

**API 官方定价**：接 API 时按对应服务当前官方报价独立核算，不从订阅容量或本地经验倍率换算 API 单价；推理档、速度层与账号容量分别标注。

三个账号各有各的约束：两个 Claude 账号都是 Max 20x，主账号只给总指挥用，二号会话的账号按 5 小时窗口算并发，主账号额度耗尽时由它接任主会话；Codex 账号额度充足，不监控。只有一个 Claude 账号可用时，按 §7.5 的单 Claude 账户模式执行。

### 7.1 主账号（主会话）

- 主账号是 Max 20x，但分工不变：主会话仍只做总指挥，额度只花在要判断的事上（§3.2）。
- 主账号不开新的子代理：所有并发的 Opus 子代理都在二号会话的账号上跑（§3.2、§7.2）；不需要审美的活交 Sol。

### 7.2 二号会话的 Max 20x 账号

**并发怎么定**：
- 额度按 5 小时窗口计。按作者实数校准：约 13.4 个 Opus 小时用了 42%，一个窗口的全部额度约够 1 个 Opus 连续跑 32 小时。作者给出实际用量时，以实数为准，并按实数校准常数。
- 并发上限按"剩余额度在恢复前用满"来定，按 Opus 当量算：按子代理的模型和推理档记：Opus medium 0.75、high 1、xhigh 2；Sonnet medium 0.3、high 0.5。系数按各档跑同一套评测的花费之比估算，c 照旧按实测校准。公式不写死，按实测消耗自己校准：
  - 每次读用量，和上一次读数比，算出这段时间每个当量小时实际耗了多少额度：5 小时窗口记作 c，每周额度记作 c周。还没有读数时 c 取 1/32，c周 先不算。
  - 5 小时允许 =（5 小时剩余 − 2% 余量）÷（c × 距 5 小时恢复的小时数）；每周允许 =（每周剩余 − 2% 余量）÷（c周 × 距每周恢复的小时数）。允许的当量取两者较小的一个。
  - 在跑的当量合计（按 §7.2 的推理档系数记）要向允许值靠，不只是不超过它：比允许值少 1 个当量以上，就从队列补开。
  - 照现在的速度到 5 小时恢复时还会剩 8% 以上，就加并发；撑不到恢复，就不开新的，在跑的不中断。
- **派单前先看额度**：二号会话的主模型每次开新子代理、选 Opus 还是 Sonnet、决定拆不拆单之前，都先看最近一次用量读数，读数超过 15 分钟就重读；算出两个窗口恢复时各自还会剩多少，写进 `notes/max-to-opus.md` 的派单行。
- **余量多时往用满靠**：预计 5 小时恢复时还会剩 10% 以上时，两难之间的活可以用 Opus，不必降到 Sonnet；新单可以两个一起开；空缺活清单里 45 分钟以内的短活优先补位，把恢复前的余量用掉。每周恢复临近、每周额度又剩得多时，只按 5 小时公式开满。个数到上限 10 个、当量还没到允许值时，空出的位子优先开 Opus：Sonnet 只占半个当量，却同样占一个名额。
- **5 小时余量封顶**（按当量计）：只在距 5 小时恢复还有 2 小时以上时生效，用来防窗口前段读数不准：剩余 < 30% 时当量最多 4，剩余 < 15% 时当量最多 2。离恢复不到 2 小时，只按公式。降档不中断在跑的子代理，只是不开新的。
- 例（c 取 1/32，每周额度充足）：窗口刚开始（剩 100%，5 小时后恢复）→ 6.3 → 6 个当量；剩 34%、1.1 小时后恢复 → 约 9.3 → 9 个当量；剩 30%、4 小时后恢复 → 封顶 4；剩 10%、4.5 小时后恢复 → 封顶 2，公式约 0.57 → 1。
- 也就是说：快恢复了、余额又用不完时，开到个数上限 10 个；离恢复还早时少开；最少保留 1 个 Opus 在跑。
- 子代理按 §7.2 的推理档系数计入上式；二号会话名下的 Opus 与 Sonnet 子代理合计不超过 10 个，截图与重 CPU 任务照样排计数锁。难度较低的活优先开 Sonnet，同样的额度能多跑一倍。
- **合计至少保持 5 个**：二号会话在跑的 Opus 与 Sonnet 子代理合计至少保持 5 个；上限与 5 小时余量封顶优先，封顶低于 5 时按封顶。主会话派的单和正在做的子单排在空缺活清单前面，D-183 建模优先照旧。
- **从空缺活清单补位**：少于 5 个时，从主会话维护的 `tasks/max-backlog.md` 自上而下取第一条未被阻塞、也没有人在做的活，二号会话按 D-184 自己写任务单并开工，编号从 `max-101` 起。开单时给主会话发消息，评审与批准照常走。

**怎么记账**：剩余额度和恢复时间以二号会话自查用量的实测值为准（作者已授权它用本账号凭据读官方用量接口，脚本只打印百分比和重置时间）。查不到时，按上一次校准出的 c 记账，没有校准值时按"1 个 Opus 跑 1 小时约耗窗口额度的三十二分之一，Sonnet 减半"；每次开新子代理前算一遍，写进 `notes/max-to-opus.md`。公式里的 Opus 小时用任务单上按 D-184 写明的预计工作量来算。

**向主会话报额度**：二号会话每次给主会话发消息时附一行额度；没有其他事时，也约每小时在 `notes/max-to-opus.md` 记一行。写明 5 小时剩余与恢复时间、每周剩余、在跑的 Opus 与 Sonnet 数，估算值标“估”；主会话据此控制派单节奏。

**撞到 5 小时上限**：撞线时离重置一般不远。主会话发现二号会话调不动了（消息不回，或者半小时以上没有动静、手上的活又没做完），就每隔 15 分钟发一句探测，直到它回话；回话即说明额度恢复。
- 二号会话来得及时，撞线前在 `notes/max-to-opus.md` 记一行“额度到顶”。
- 恢复后，先让被中断的子代理从中断处接着做；接不上的，按原单开新子代理，在原工作树继续。

**怎么省**：
- 不一次铺开：比允许值少 2 个当量以上时，新单可以两个一起开；其余情况一个一个开，前一个进入施工后再开下一个。重 CPU 与 GPU 任务照样排计数锁。
- 主会话派单也分批：同一时刻挂给二号会话、还没开工的单不超过 4 张，其余留在主会话手里或放进空缺活清单，等有空位再发。
- 子代理做完一轮先别结束，评审意见回来在原上下文里改，比新开省。
- 二号会话本身只做派单、转达和初步核对，不亲自施工大块内容。
- 账号额度快用完时，在流水里写明并通知主会话，由主会话改派。

- 双账户模式下二号会话做的事，改由主会话做：派单、写简报、核对候选（工作树干净、与 main 无冲突、门禁结果）、代记任务单"状态"、按 §7.2 读额度并定并发、查停滞。
- 评审不通过时，能在原子代理的上下文里改就接着改；原子代理已经结束的，另开子代理接着做。

**额度**：§7.2 的公式照用，作用在这一个账号上。主会话用 `get_usage` 直接读 5 小时与每周两个窗口，它自己的消耗也在读数里，公式不用改。§7.1"主账号不开新的子代理"和 §7.4 的移交在本模式下不适用；账号任一窗口剩余不到 1% 时，主会话停止派新活，在跑的做完，等作者定下一步。

**不用的**：二号会话；`notes/opus-to-max.md`、`notes/max-to-opus.md` 两份流水；§6.4 里主会话与二号会话之间的消息。

**切换时**：
- 进入本模式时，二号会话在跑的子代理照常做完，候选照常写进任务单，此后不开新的；返工由主会话另开子代理接。
- 回到双账户模式时，主会话名下在跑的子代理做完为止，新单照 §5.2 交二号会话。
- 换账号时，原会话在后台跑的唤醒脚本会随它一起停掉。接续的会话先查进程，再按 §6.5 重启，每个脚本只能有一个在跑。

## 8 旁路任务与长期值班

值班由 Sol 值班会话承担，完成度调研和其他旁路任务由 Sol 旁路会话承担。两个都是固定会话，各由一个唤醒脚本叫醒（§6.5），不占 Astra 和主会话的主线时间。Sol 会话一律不做审美工作（§2.2）。

### 8.1 Sol 值班会话

**是什么**：一个固定的 gpt-6.1-sol 会话（快速模式），thread `01a14132-0184-7ce1-89b8-b3e472a5af73`，长期任务单 `tasks/sol-001.md`。它承担总指挥的执行类杂活，由唤醒脚本叫醒（§6.5），每轮只处理被叫醒的事和巡检。

**做什么**：
- **合并执行**：只合有批准行的候选，步骤见 §5.5。
- **施工状态**：每次合入后同步 ENG-STATUS，并把 ENG-STATUS §4 里依赖已满足的条目改成"可派"（§5.6）。
- **巡检**（每次被叫醒都做）：
  - 卡死进程：`Get-Process godot*` 里启动超过 15 分钟仍在跑的截图或门禁进程，记下 PID、命令行、所属工作树，通知主会话，不自己杀；
  - 带条件的批准行：当时没合的，每次都复查，条件满足了就照 §5.5 合入；
  - 工作树落后：`git -C <工作树> merge-base --is-ancestor main HEAD` 不成立的工作树列一行，写进"状态"，不用通知；
  - 完成度调研：按 §8.2 看要不要写新的调研单，以及在跑的调研有没有超时。
- **通知与流水**：通知写进 `notes/sol-to-opus.md`；本轮做了什么写在 `sol-001.md` 末尾的"状态"，一行一事，带时间。

**不许做**：改代码；改契约与共享工程文件；改 ENG-STATUS 以外的设计文档（任务单给出确切文字时除外）；合并没有批准行的候选；强推；删除分支或工作树；做任何画面与风格判断。

### 8.2 完成度调研

完成度调研是调研入队流水线（§5.8）的第 1 步。调研是持续的，不是一轮就结束：值班会话按开发阶段排调研，阶段不变时也持续找新方向，由 Sol 旁路会话执行。本节只写这一步怎么排、查什么；审计、并入工作包和入队都照 §5.8，这里不重复。

**谁排、什么时候排**（任务单 `tasks/sol-002.md`）：
- **阶段调研**：值班会话按 ENG-STATUS §2 的"当前阶段"排调研。阶段一变，或主会话在 `sol-002.md` 的"状态"里要求新一轮，就写一张调研单 `side/cards/r<nnn>.md`。
- **持续调研**：每次巡检时，下面两条同时满足，就再写一张新方向的调研单：
  - 距上一张调研单启动超过 2 小时；
  - 旁路会话当前空闲（`tools/sol_side/runner.log` 最后一行是"本单结束"）。
- **新方向**：每张 4–6 个方向，不重复已做过的，每个方向写明为什么现在值得查。新方向从这些地方找：
  - 前几轮总览里"未核实""需要 Opus 拍板""建议后续调研"的条目；
  - `merged.log` 里新合入的包带来的新问题；
  - 当前阶段的侧重（见下文"各阶段的侧重"）；
  - 同类作品与主流二次元游戏的新版本、新系统；
  - Godot 4.x 与三渲二相关的新技术与工程做法；
  - 玩家社区对同类作品的新反馈。
- **调研索引** `research/INDEX.md`：一单一行，写单号、启动时间、阶段、方向、总览路径、Opus 审计状态。值班会话写新单前先读它去重，新单写完追加一行；旁路会话做完标"待审"；主会话审计后改最后一列。
- **模板**：调研单以 `research/cards/r002.md` 为模板，写进 `side/cards/`，按当前阶段调整背景、调研方向和输出目录 `research/<日期>-r<nnn>/`。
- **边界**：值班会话和旁路会话只负责让调研持续产出，不改工作包、不派工。

**执行的细则**：
- 旁路唤醒脚本发现新的调研单，按顺序交给 Sol 旁路会话（§6.5）。
- 旁路会话按方向开 gpt-6.1-sol 子代理并行调研，对照同类作品和主流二次元游戏，各写一份报告。
- `00-总览.md` 写按优先级去重的建议表，每条标明归哪个包或建议新包、主线版还是细节阶段、工作量、依赖。
- 写完把 INDEX 里这一单标成"待审"，在 `notes/sol-to-opus.md` 追加一行"[时间] 调研 r<nnn> 完成：<总览路径>"。调研单启动超过 3 小时仍没有完成行，值班会话查 `tools/sol_side/runner.log` 与 `<单号>.stderr.log`，写进"状态"并通知主会话。

**三个视角**（每张调研单都要覆盖）：
- **制作完整度**：内容量与密度、各系统与管线的覆盖、质量保障与测试、性能与稳定性、存档稳健、发布与本地化、无障碍、玩家对同类作品的预期；
- **优越性**：和同类作品比的长处与短处、差异化卖点、让人记住的时刻与展示画面、技术与美术上值得放大的地方、同类作品常被批评而本项目可以避开的地方；
- **玩家体验**：首次体验与上手、一次游玩的节奏与情绪曲线、舒适度（晕动、眼睛疲劳）与可达性、操作与界面的摩擦、加载与等待、反馈与手感、回访与重玩的理由。

**各阶段的侧重**：
- 第一波、第二波：看世界与观光模式缺什么；
- 主线闸口与集中测试：看质量缺口、性能与设置、发布完整度；
- 细节阶段：看细节打磨与交互小物。

**不调研的**：
- 任何阶段都不调研、不建议 RPG 内容；
- 本项目是个人实验性作品（D-181），不调研商店页、上架、宣传素材、成就、云存档、平台集成等商业发行内容；"发布完整度"只看按 OPS-RELEASE 在 GitHub 发整包时的完整与稳健；
- GPT 只收集观感方面的事实与做法，不下画面结论。


### 8.3 Sol 旁路会话

**是什么**：一个固定的 gpt-6.1-sol 会话（普通速度，不开快速模式），thread `01a14176-abbf-7862-98ba-137e2ad1686f`，角色说明 `side/ROLE.md`。完成度调研和其他旁路任务都由它一个会话管理，按任务单开子代理并行处理。

**两类任务单**（都放在 `side/cards/`）：
- **调研单 `r<nnn>.md`**：由值班会话写，做法见 §8.2。
- **旁路单 `s<nnn>.md`**：由主会话写。主会话判断某件事不在主线关键路径上、却会占主线时间，或者要大量补信息、调研、批量核对数据时，就写一张旁路单，写明在哪做、交付什么、能改什么、哪些不许做。派不派、派几张、做到什么程度，由主会话定。

**怎么执行**：
- 旁路唤醒脚本按文件名顺序一次交一张单（§6.5）；旁路会话做完这一张就结束本轮，下一张再叫醒它。
- 按单子的方向数用 `spawn_agent` 开 gpt-6.1-sol 子代理，最多 8 个并发（§8.4）；子代理的简报写明 §8.4 的"共用工作目录"注意事项。
- 旁路单做完，在单子末尾"状态"写结果，在 `notes/sol-to-opus.md` 追加一行；调研单的收尾见 §8.2。
- 上下文重置后，照 `side/cards/` 下各单的"状态"接着做（§6.6）。

**边界**：
- 不做任何审美工作（§2.2）；调研里涉及观感的，只收集事实和出处。
- 不改契约和共享工程文件；不改 `docs/design/`，任务单给出确切文字的补丁除外；不合并，不推送。
- 不碰任何包的工作树和主检出。要写代码的旁路活，在单子指定的独立工作树里做，完成后写合并请求，经主会话批准由值班会话合入（§5.5）。
- 调研报告和旁路产出写进单子指定的位置；主会话读了以后决定怎么改文档、派给谁。

### 8.4 怎么开子代理

**各方都适用**：
- 一个包或子包一个子代理；同一时刻，一个文件只有一个代理在写。
- 每个子代理各用一个工作树（§5.2）。
- 简报按 ENG-WP §4 的模板写。Claude 侧的子代理由 `CLAUDE.md` 自动载入开工手册；Codex 侧的不会，简报里要写明先读 `docs/design/engineering/ENG-ONBOARD.md`。
- `dotnet build`、`--import` 和烘焙这类重 CPU 任务，走 `..\UESTC_RPG.wt\.locks\` 下的计数锁（ENG-ARCH §6）。

**Claude 侧**（只在二号会话；主账号不开新的子代理，§3.2）：
- 用 Agent 工具在后台开，指定模型 `model: "opus"` 或 `"sonnet"`；一个包一个，简报里写明工作树的绝对路径。
- 评审不通过，把意见发回同一个子代理，在原上下文里继续改。
- 单 Claude 账户模式下改由主会话开（§7.5），其余写法相同。

**Codex 侧**（Astra 与 Sol 旁路会话）：用 Codex 的 collaboration 工具。
- **开**：`spawn_agent`。`task_name` 写包号，例如 `wp-02a`；`message` 写完整简报。
- **等**：`wait_agent`，可以设 `timeout_ms`。
- **查**：`list_agents` 列出子代理。
- **追加指示**：`send_input` 给正在运行的子代理发补充说明。
- **并发上限**：`~/.codex/config.toml` 里的 `max_concurrent_threads_per_session`，当前是 36，每个会话各算各的；Sol 旁路会话另按 `side/ROLE.md` 最多 8 个。

Codex 的子代理和主线程共用同一个工作目录，所以简报里必须写明：
- 你的工作树是 `E:\Project\UESTC_RPG.wt\<WP-xx>`；
- 所有读写都用这个工作树下的绝对路径，git 一律用 `git -C <工作树>`；
- 不碰别的工作树，也不碰主检出 `E:\Project\UESTC_RPG`；
- 不合并、不推送。

**Astra 主线程负责**：派工；回答子代理的问题；审代码是否符合架构；跑快检；写合并请求；处理契约申请；看 `merged.log`，通知自己的子代理 rebase。
