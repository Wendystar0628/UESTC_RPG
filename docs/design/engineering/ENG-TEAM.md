## 0 结论

1. **两个主力模型各管一摊**（D-179）。两个模型是：
   - Claude Opus 5.5，下称 **Opus**；
   - GPT-6 Astra，推理强度 xhigh，在本机 Codex CLI 上运行，下称 **Astra**。

   Astra 管架构和复杂工程。Opus 管画面、风格、内容和需要判断与变通的事，同时担任主代理（§1）。
2. **主代理只有一个，就是 Opus**。下面这些事只由 Opus 做（ENG-ARCH §6，D-166）：
   - 合并队列；
   - `main` 上的提交和推送；
   - ENG-STATUS；
   - `docs/design/` 的修改；
   - 与作者沟通。
3. **Astra 是工程负责人**：
   - WP-00 由 Astra 做；
   - 之后契约和共享工程文件只由 Astra 改，包括 `game/contracts/`、全部 csproj、`Directory.*.props`、`project.godot`、`ownership.json`、`gate.ps1` 和 `scripts/wt/` 下的脚本；
   - Astra 在自己的分支上提交，经 Opus 的合并队列进 `main`（§4）。
4. **包按擅长分**（§2）。每个包或子包一个子代理；子代理开多少个，由当时能开工的包数决定，不设固定数目。同时运行的重 CPU 任务受本机计数锁约束（ENG-ARCH §6）。
5. **主线阶段分三段开工**（§3）：
   - D0：Astra 做 WP-00；Opus 同时做不依赖代码骨架的美术基础；
   - 第一波：内核与系统包，两边并行；
   - 第二波：世界数据、烘焙、部件内核和建筑生成器合进 `main` 以后，开内容包。
6. **两边经文件交接**（§4）：交接目录是 `E:\Project\UESTC_RPG.wt\.collab\`，里面放合并请求、契约申请、评审请求和合并日志。
7. **审美以 Opus 为准，视觉风格只由 Opus 做**：
   - 玩家看得见、听得见的结果，参数和取舍都由 Opus 评审定值。
   - 视觉风格与质感的处理只由 Opus 侧做，包括着色、调色、描线与后期的观感、材质与造型的观感、按参考场景移植质感（ART-STYLE §1）。
   - Astra 与它的子代理不做这些决定，也不做这些调整。Astra 的包只交机制和集中的可调参数（§5）；遇到画面观感问题，写评审请求交给 Opus。
8. **契约以 Astra 为准**：牵涉画面表现的契约（材质、调色板、着色器全局参数、界面令牌、过场 JSON），Astra 起草，Opus 确认后再冻结（§5，D-134）。

### 0.1 接入要点

- **你是 Astra 派出的子代理**：向 Astra 主线程回报，不直接找 Opus；做完由 Astra 写合并请求（§4、§6.2）。
- **你是 Opus 派出的子代理**：向 Opus 回报（§6.1）。
- **要改契约或共享工程文件**：在 `.collab/requests/` 写契约申请，由 Astra 处理（§4）。
- **要改设计文档**：在回报里提出，由 Opus 改（§0 第 2 条）。
- **做完要合并**：写合并请求或回报给派你的一方。不自己合 `main`，不推送（§4）。
- **开始下一步之前**：看 `.collab/merged.log`。`main` 变了，就在自己的工作树里 `git rebase main`（§4）。
- **你的包有可见或可听的结果**：把可调参数集中放在一处，并在回报里列出，供 Opus 评审定值（§5）。

## 1 谁擅长什么

| 方面 | Astra | Opus |
| --- | --- | --- |
| 架构与契约 | 设计契约与程序集边界、注册器、桩、依赖方向 | 确认画面相关的契约字段够不够用 |
| 工程难点 | 并发与线程、确定性、本机烘焙与流式、序列化与迁移、物理与碰撞、性能结构、构建与门禁脚本、复杂算法 | 遇到时请 Astra 评审 |
| 画面 | 不定画面取值 | 着色与调色、光照取值、描线与后期的观感、造型与建模、立面与布局、植被与水面、天空、夜景灯光 |
| 界面与过场 | 播放器、流程状态机、输入分发 | 界面视觉与动效、过场的镜头、节奏和字幕 |
| 声音 | 音频内核、混音总线、空间声学 | 声景取舍、环境声床、界面音的方向 |
| 内容 | 数据管线 | 各区建筑、增补、生活痕迹、室内 |
| 判断 | 工程上的取舍 | 跨系统的取舍、风格评审、文档冲突的定案 |

**视觉风格的归属**：画面观感（着色、影色、描线、高光、后期、材质与造型的观感、质感移植）一律归 Opus 侧，Astra 不碰（§0 第 7 条）。参考场景里没有对应物的内容，也由 Opus 侧按同一套质感做法统一处理。

**交叉的地方**：
- Astra 的包里有可见结果的，Astra 交机制和参数表，Opus 定参数值。这类包有：启动雾幕、镜头手感、跳转、行走手感、过场播放、介质。
- Opus 的包里有重工程的，遇到架构问题请 Astra 评审。这类包有：建筑生成器的开间与立面规则、描线的计算着色器、材质库。

## 4 交接文件

交接目录是 `E:\Project\UESTC_RPG.wt\.collab\`，放在仓库之外，不进 git。所有文件只追加、不改写，每条带时间；路径一律写绝对路径。新建请求文件时序号取现有最大号加一，并用不覆盖的写法创建（例如 bash 先 `set -C` 再重定向，或先确认文件不存在）；撞号时改用下一个号，不覆盖别人的文件。

| 文件 | 谁写 | 写什么 |
| --- | --- | --- |
| `requests/merge-<WP-xx>-<序号>.md` | 包的负责方：Astra 主线程，或 Opus 的子代理 | 合并请求。写包号、工作树、分支、候选提交、已跑的检查与结果、关联的契约申请、截图路径，以及要 Opus 看的东西 |
| `requests/contract-<序号>.md` | 任何代理 | 契约或共享工程文件的申请。写要改什么、为什么、影响哪些包。Astra 处理后在末尾写结论和对应的提交 |
| `requests/review-<WP-xx>-<序号>.md` | Astra 主线程 | 请 Opus 做审美评审。写截图或录像路径、可调参数在哪、各参数现在的值。Opus 在末尾写结论或新值 |
| `merged.log` | Opus | 每合入一次追加一行：时间、`main` 的短 SHA、包号、一句话说明 |
| `notes/opus-to-astra.md`、`notes/astra-to-opus.md` | 各自 | 其余通知，例如文档改了、契约冻结了、某个包阻塞了 |

**合并的流程**（ENG-ARCH §6 第 4 步）：
1. 负责方跑 `scripts\gate.ps1 -Wp <WP-xx>`，通过后写合并请求；
2. Opus 在那个工作树里 `git rebase main`，再跑一遍检查；
3. Opus 用 squash 合进 `main`，推送，再往 `merged.log` 里记一行；
4. 包做完了就删掉分支；还要继续做，就从新的 `main` 重建分支；
5. Opus 在主检出跑一次 `--headless --import`，更新导入种子。

**共享工程文件的改动**：Astra 在自己的工作树（`..\UESTC_RPG.wt\WP-00`，分支 `wp/00-core`）上提交，写合并请求，Opus 优先合入。

## 5 审美与契约的交叉评审

- **可调参数集中放**：Astra 的包有可见或可听的结果时，把可调参数放在一处，可以是数据文件，也可以是集中的常量类，并在评审请求里列出来。Opus 评审后，在评审文件里写新值，或直接在那个参数文件里改。改动经合并队列进 `main`。
- **画面相关的契约**：`ToonSpec`、调色板与 `IPaletteProbe`、着色器全局参数、`ui.json` 令牌、过场 JSON 的格式，由 Astra 起草，Opus 确认字段够用、命名与美术文档一致，然后才冻结（D-134）。
- **Opus 的包需要工程支持时**：遇到性能结构、线程、确定性、契约的问题，在 `requests/contract-*.md` 或 `notes/opus-to-astra.md` 里找 Astra。
- **风格负责人**：由 Opus 担任（ENG-WP §5 第 4 条），评审金样、色板联表、界面样张和全部画面类截图。

## 6 怎么开子代理

**两边都适用**：
- 一个包或子包一个子代理；同一时刻，一个文件只有一个代理在写。
- 每个子代理各用一个工作树。D0 合入以后，工作树用 `scripts\wt\new.ps1 -Wp <WP-xx> -Slug <短名>` 建；D0 之前用 `git worktree add ..\UESTC_RPG.wt\<WP-xx> -b wp/<xx>-<短名> main`。
- 简报按 ENG-WP §4 的模板写；开工手册由 `CLAUDE.md` 自动载入。Astra 的子代理不会自动载入它，要在简报里写明先读 `docs/design/engineering/ENG-ONBOARD.md`。
- `dotnet build`、`--import` 和烘焙这类重 CPU 任务，走 `..\UESTC_RPG.wt\.locks\` 下的计数锁（ENG-ARCH §6）。

**按任务难度选模型**（两边都适用）：

| 任务 | Claude 侧 | Codex 侧 |
| --- | --- | --- |
| 简单任务：范围清楚、设计判断少，例如调研、文档整理与补丁、数据转换、机械性的重命名或接线、单文件小修、按既定格式写数据 | Sonnet，推理强度 xhigh | gpt-6.1-sol |
| 难任务：架构、契约、复杂工程（Astra 一侧） | — | gpt-6-astra，xhigh |
| 难任务：画面与风格、跨系统取舍、质感移植（Opus 一侧） | Opus | — |

这两个"简单任务"模型与旗舰差距不大，拿不准时先派它们，结果不够好再换旗舰。

### 6.1 Opus

- 用 Agent 工具在后台开子代理，一个包一个，简报里写明工作树的绝对路径。
- 子代理回报以后，Opus 先看结果和截图，再按 §4 合并。
- 画面类结果由 Opus 评审；评审不通过，就把意见发回同一个子代理继续改。

### 6.2 Astra

Astra 用 Codex 的 collaboration 工具开子代理：

- **开**：`spawn_agent`。`task_name` 写包号，例如 `wp-02a`；`message` 写完整简报。
- **等**：`wait_agent`，可以设 `timeout_ms`。
- **查**：`list_agents` 列出子代理。
- **追加指示**：`send_input` 给正在运行的子代理发补充说明。
- **并发上限**：`~/.codex/config.toml` 里的 `max_concurrent_threads_per_session`，当前是 36。

Codex 的子代理和主线程共用同一个工作目录，所以简报里必须写明：
- 你的工作树是 `E:\Project\UESTC_RPG.wt\<WP-xx>`；
- 所有读写都用这个工作树下的绝对路径，git 一律用 `git -C <工作树>`；
- 不碰别的工作树，也不碰主检出 `E:\Project\UESTC_RPG`；
- 不合并、不推送。

Astra 主线程负责：
- 派工；
- 回答子代理的问题；
- 审代码是否符合架构；
- 跑快检；
- 写合并请求；
- 处理契约申请；
- 看 `merged.log`，通知自己的子代理 rebase。

## 7 待验证（P0）

| 待验证 | 初值 | 验证方法与负责 |
