# ENG-TEAM-ROLES · 协作分册：参与者与分工

## 0 结论

1. **参与者**（§1，D-179）：作者提出要求、最终拍板。协作的会话分属三个账号：
   - 主账号的 Opus **主会话**是总指挥；
   - **二号会话**（第二个 Claude 账号，Max 20x）开 Opus 与 Sonnet 子代理，承担 Opus 侧的施工；
   - **Astra**（GPT-6 Astra，xhigh，Codex 应用里的会话）是工程指挥：定契约与工程方案、拆单派工、审查与集成，尽量不亲自施工；施工默认交它开的 gpt-6.1-sol 子代理；
   - **Sol 会话**（gpt-6.1-sol）有两个固定会话，都开在 Codex 应用里（D-203）：值班会话是值班执行者没回复时的接手者（ENG-TEAM-COMMS §5，D-198），旁路会话按任务单开子代理，两个都用普通速度（GPT 侧只有 gpt-6-luna 用快速模式，D-197），做完成度调研与旁路活。
2. **主代理只有一个，就是主会话**（§1.1，ENG-ARCH §6，D-166）：合并队列、`main` 的提交与推送、ENG-STATUS、`docs/design/` 的修改、与作者沟通，都由它决定。不需要判断的执行部分交值班执行者（ENG-TEAM-COMMS §5，D-198）；`main` 同一时刻只有一个执行人。
3. **按模型能力分工，视觉风格只由 Opus 侧做**（§2）：Opus 管审美、判断与变通；Sonnet 做语言与看图；Astra 管架构判断与工程指挥；gpt-6.1-sol 能力接近 Astra、性价比高得多，是工程施工的默认模型。GPT 模型不做任何审美工作；玩家看得见、听得见的结果，参数和取舍都由主会话评审定值。
4. **按难度选模型，总指挥只做判断**（§3）：主会话只做评审定值、设计定案、派工与合入决定、与作者沟通；主账号不开新的子代理，所有并发的 Opus 子代理都在二号会话的账号上跑（仅双账号模式，ENG-TEAM-QUOTA §6.1）；不需要审美的活默认先派 Sol。包内的实现路径由施工模型自己规划。
5. **子代理默认新开**（§3.5，D-191）：同包下一张子单、新阶段和无关的活一律新开，靠任务单的"接续"段交接；只有交回后几分钟内的小返工、或原上下文在约 8 万 token 以内的相关小活才恢复原子代理；恢复后先对齐最新 `main` 与契约。

### 1.1 决定权与执行人

**主会话决定**（ENG-ARCH §6，D-166）：
- 合并队列：哪个候选、什么时候合；
- `main` 上的提交和推送；
- ENG-STATUS；
- `docs/design/` 改什么；
- 与作者沟通。

**执行交出去**：
- 上面不需要判断的执行部分，即按批准合入、跑门禁、提交推送、写 `merged.log`、维护 ENG-STATUS、巡检，由值班执行者（只改文档的合并交 Gemini，其余与巡检交 Grok，没回复退回 Sol，D-198、D-202）做（ENG-TEAM-COMMS §5、ENG-TEAM-DUTY §1）。
- `main` 同一时刻只有一个执行人。值班执行者合并时，主会话和其他会话都不碰主检出的暂存区。
- 设计文档的撰写可以派出去：需要 Opus 的撰写交二号会话的 Opus 子代理；Sol 只在任务单给出确切文字时按文打补丁。改动都在工作树里做，经批准合入。

**其他各方定什么**：
- Astra 定契约、共享工程文件和工程上的取舍（ENG-TEAM-FLOW §2.7）；
- 画面与声音的取值、风格定案，以主会话的评审为准（§2.2）。

## 2 按模型能力分工

分工按模型的长处来：要审美、判断和变通的给 Opus；要语言质感和看图、但不定风格的给 Sonnet；架构判断与工程指挥给 Astra；工程施工默认给 gpt-6.1-sol，它的能力接近 Astra，性价比高得多，可以高并发。硬规则只有一条：GPT 模型不做任何审美工作（§2.2）。

### 2.2 硬规则：GPT 模型不做审美工作

- **视觉风格只由 Opus 侧做**：着色、调色、描线与后期的观感、材质与造型的观感、按参考场景移植质感（ART-STYLE §1），都只由 Opus 侧处理。参考场景里没有对应物的内容，也由 Opus 侧按同一套质感做法统一处理。
- **定值归主会话**：玩家看得见、听得见的结果，参数和取舍都由主会话评审定值（ENG-TEAM-FLOW §2.4）。Sonnet 子代理可以按检查单初筛截图、整理质感做法，不定风格。
- **GPT 模型一律不做**：Astra、它的子代理、两个 Sol 会话和它们的子代理，不做画面、配色、质感、构图、造型、界面观感、参数取值和截图评审方面的决定与调整。
  - Astra 的包只交机制和集中的可调参数；遇到画面观感问题，写评审请求交主会话（ENG-TEAM-FLOW §2.4）。
  - 调研里涉及观感的，只收集事实、做法和出处，结论由主会话下。
- **采集、读图与定案分开**：程序采集与像素计量、按检查单读图、风格定案是三种不同的工作，GPT 只做第一种。

### 2.2a 不过度工程化（各方都适用，GPT 模型尤其）

本项目是作者的个人实验作品，不是商业交付级项目；作者不看证据链和证明材料，多写的每一行都在白花额度（D-201）。
- **不写**：证据溯源、来源链、哈希或校验和、proof/verification/attest 一类的脚本与报告、handoff 证据目录、逐字节证明、额外的审计报告。
- **不自己加**：门禁、检查脚本、测试脚手架、全量回归、重复构建。只跑任务单要求的检查，默认是 `gate.ps1` 的快检；觉得需要更多检查，先写一条【需定】问主会话。
- **回报从简**：照 ENG-GATES §5 的格式与 ENG-TEAM-COMMS §3 的短头部，证据只给路径。
- **钩子兜底**：Codex 侧在本项目目录里运行时，由 `E:\Project\UESTC_RPG.wt\.collab\tools\hooks\uestc-guard.cjs` 每条提示前用文字提醒一次上面这几条，只提醒、不拦任何操作（登记在 `C:\Users\Administrator\.codex\hooks.json`）。构建和生产代码里本来就要用的摘要照常写。

### 2.3 事归谁

先分审批与施工：主会话定设计、审美、内容取舍、可见参数、优先级与合入；Astra 定工程、契约及高传播风险的方案。实际施工按 §3.1 的七问逐项判断，包归属（ENG-TEAM-FLOW §1.1）与目录写权限不因施工模型改变。

可见构件一律由 Opus 施工，哪怕已给全尺寸和截面；GPT 可承担它们的非可见部分，如碰撞、数据、接线和单测。Astra 名下封闭、已定的子任务可单独转给 Sol；不按包号整包改派，工程取舍与必要复核仍归 Astra（§3.3）。

### 2.4 交叉的地方

- **Astra 的包里有可见结果的**：Astra 交机制和参数表，主会话定参数值。这类包有：启动雾幕、镜头手感、跳转、行走手感、过场播放、介质。
- **Opus 侧的包里有重工程的**：遇到架构问题请 Astra 评审。这类包有：建筑生成器的开间与立面规则、描线的计算着色器、材质库。
- **画面相关的契约**：Astra 起草，主会话确认字段够不够用（ENG-TEAM-FLOW §2.4）。

## 3 模型等级与任务划分

按 §3.1 的七问选够用的施工模型；主会话保留判断，其余按权限派出去。

### 3.1 按七问选施工模型

依次看还缺什么判断、结果能否验收、错误会传播多远。混合任务先分清未定判断与已定实现，再按下表安排。

| 问题 | 倾向：会话、模型与档位 | 复核或停止信号 |
| --- | --- | --- |
| 1. 要定造型、风格、声音、玩家可见参数或内容取舍，或制作可见构件吗？ | 需要审美判断的（定造型、风格、观感取值，地标与重点构件，质感移植）由二号会话的 Opus 施工，主会话定案；只缺判断时主会话直接定。规格、尺寸、色名都已给全、难度较低的可见活（简单部件、按已定预设填数据、小修）可以交 Sonnet。审美相关的活一律不交 GPT；非可见部分可拆出继续问 | Opus 审美评审；接口与生命周期部分才加 Astra，GPT 不替选值 |
| 2. 必须读图或依赖中文语感判断吗？ | 按检查单读图初筛、中文改写交二号会话或其 Sonnet；可程序测出的数据与截图采集交 Sol。涉及审美回第1问 | Sonnet 不定风格；改变原意或含内容取舍时交主会话 |
| 3. 目标、规格和通过条件仍有歧义吗？ | 工程歧义交 Astra（gpt-6-astra，xhigh），设计与内容歧义交 Opus，定清再派实现 | 契约含义或规范冲突未定，先停相关项；不靠增加推理替代决定 |
| 4. 错误会跨接口、线程、资源寿命或存档扩散吗？ | Astra 定方案、边界与验收条目，施工默认交 Astra 名下的 Sol 子代理（high 或 xhigh）；Sol 两次做不对或方案本身要改时，Astra 才亲自做关键段 | Astra 定向复核调用方、所有权与迁移；共享文件不得由旁路越权改 |
| 5. 数学或几何很难，但能由不变量、参考结果验证吗？ | 非审美实现由 Astra 名下 Sol 施工；前提不清或全局耦合，先由 Astra 定清前提，再交 Sol。可见构件仍回第1问 | 按风险核退化边界、真实引擎约定与确定性；数学成立不代替造型评审 |

| 7. 是既有批准后的执行，或剩余明确非审美实现吗？ | 合并与状态交 Sol 值班，其余默认 Sol 实现，由相应负责方派单；主账号不新开施工代理 | 候选号、批准条件或权限变化，先停相关项；只做改动需要的检查 |

**Opus 与 Sonnet 的分界**（D-193）：Opus 贵，只用在观感还没定的地方；观感已经由评审或已批样子定下来的可见活，默认交 Sonnet。

| 默认交 | 活 |
| --- | --- |
| Opus（high；地标与质感移植 xhigh） | 一个包或一类构件的首版造型，还没有已批的样子可照；地标与重点构件；质感移植与新的画面机制；评审里标明"要定""拿不准"的观感取舍 |
| Sonnet high | 评审已经写明怎么改的跟进单（例如车轮改 24 段、自建绿篱改成登记、长椅换位置、桥身加檐口线）；照已批的样子铺到同类（其余的桥、门、楼按已批预设）；摆放规则、数据与覆盖层登记、树种与预设键；截图采集与重拍；素材收集；文档撰写 |
| Sonnet medium | rebase 与解冲突、按条目填数据、按确切文字打文档补丁 |

- 一张单里混着未定的观感和已定的实现时，把已定的部分拆出来交 Sonnet，Opus 只做未定的那块。
- Sonnet 的候选在观感上两次评审不过，再改派 Opus，不先升推理档。
- 换模型就是新开子代理（§3.5）。下一单改用 Sonnet 时，靠任务单的"接续"段交接，不恢复原来的 Opus 子代理。

**最便宜的两档**（D-194、D-202）：只做照清单执行、结果能机械核对、出错也不会扩散的活，不做任何判断。Claude 侧不设这一档，不用 Haiku。
- **简单快速档：Gemini 3.8 Flash High**（作者的 Antigravity）：一件、小、要快的活。例如只改文档的合并、按确切文字改一处文档、查一处、追加一条状态、跑一次给定命令并报结果。派法：把任务写成 UTF-8 提示文件，用 `python -I E:\Project\UESTC_RPG.wt\.collab\tools\duty\gemini_run.py <会话号> <提示文件>` 发进作者开着的 Antigravity 会话并等它做完；结果它写进 `notes/gemini-to-opus.md`。Antigravity 没开或发不出去，就改派 luna。
- **批量苦力档：gpt-6-luna**：量大、重复、照清单的活。例如成批替换引用、全仓数据核对与盘点、成批截图与拼图、成批状态整理。luna 的花费几乎可以忽略，并发不设上限。

两档能做的类别：

| 类别 | 做什么 | 不做什么 |
| --- | --- | --- |
| 状态与记录 | 照模板追加任务单"状态"行与流水；更新调研索引；依赖能机械判定时把队列条目改"可派" | 不判断依赖是否"算满足"，拿不准就留原样 |
| 文档机械编辑 | 按确切文字打补丁；重跑 `gen_index.py`、`check_docs.py`，修它报的链接、编码、换行这类格式问题；按给定对照表替换用词 | 不改写措辞，不补内容 |
| 门禁执行与结果整理 | 按给定参数跑 `gate.ps1` 或单测，汇总通过与失败、失败的测试名和日志路径 | 不修代码，不判断失败原因 |
| 截图采集与拼图 | 按给定的位姿清单出图，做左右对比拼图，按约定命名存放 | 不评价观感 |
| 数据核对与盘点 | JSON 能否解析、id 是否唯一、引用是否存在、`licenses.json` 是否覆盖每个素材、文件编码；按给定条件 grep 出清单 | 不改数据，只报结果 |
| 机械 git | 没有冲突的 `rebase main`、按清单 cherry-pick、合入后重建工作树分支、列出落后或已合并的工作树 | 一遇冲突就停下报告，不解冲突 |

- **谁开、怎么开**：拿到这件杂活的一方直接开（D-190），不必经 Astra 转手。GPT 侧的新活一律派进 Codex 应用里开着的会话，作者在应用里能看到（D-203）：在 Astra 或 Sol 会话里用 `spawn_agent` 开 luna 子代理；或者往作者开好的 luna 会话里发，`codex queue --thread <会话号> --message <内容>`，会话号记在 `E:\Project\UESTC_RPG.wt\.collab\tools\duty\luna_thread.txt`。不用 `codex exec` 在后台另起看不见的线程。
- **速度**：luna 默认用快速模式，命令里加 `-c 'service_tier="priority"'`（D-197）。
- **怎么选**：一件、几分钟能完的交 Gemini；成批的、要跑很久的交 luna；两者都要判断的，回到 Sonnet 或 Sol。
- 派单写清清单、模板和完成标准，以及能写哪些文件；一次做不对就改派 gpt-6.1-sol medium 或 Sonnet medium，不在原档上重试。
- 等待、轮询和定时重跑索引这类活，交脚本做，不占任何模型。
- 试用阶段：Gemini 先接只改文档的合并和主会话派的小活；luna 先接截图采集与拼图、数据核对与盘点。跑顺了再按上表放开其余几类。

**推理强度按难度选**：子代理不一律开 xhigh，每张单按难度选一档，写进派单（见下文"派单最少写"）。每升一档，费用和用时都明显上涨，完成度的提升却越来越小，所以够用就停。

| 难度 | 例子 | Opus | Sonnet | gpt-6.1-sol |
| --- | --- | --- | --- | --- |
| 简单 | 规格已给全，能按条目或程序验收：填数据、按已定预设接线、rebase 与拣选、单文件小修、查资料与整理、按确切文字打文档补丁 | 不派 | medium | medium |
| 一般 | 要自己规划实现，结果能按条目验收：常规部件与建模、普通接线与单测、截图采集 | high（需要审美判断的可见构件） | high | high |
| 难 | 判断重，或错误会扩散：地标与重点构件的造型、质感移植、跨包根因，确定性、并发、资源寿命、存档方案，契约方案 | xhigh | 不派，改派 Opus | xhigh |

- Sonnet 只用 medium 和 high。要 Sonnet 开 xhigh 才做得好的活，改派 Opus high：花费相近，完成度更高。
- 不用 max；施工不用 low。
- 返工沿用原档。同一档两次做不对，先照下文"升级先找失败原因"查原因，确实是难度不够才升一档。
- Astra 给 Sol 子代理定档照上表；gpt-6-astra 子代理只在 §3.3 列的情形开，用 xhigh。
- 固定长期会话保持当前有效档，不做全局降档：主会话、Astra 主线程 xhigh；Sol 值班 high、普通速度，旁路普通速度（ENG-TEAM-QUOTA §3，D-197）。
- 推理强度、速度层与账号容量分别记录。

**组合只在需要时用**：

- Sol 实现 → Astra 核工程风险；
- Sol 程序采集/像素计量 → Sonnet 读图初筛 → Opus 定观感；
- 二号会话 Opus 做内容 → Astra 核工程交界；
- Sol 整理事实 → Sonnet 语言加工 → 主会话批准规范。

每张单只列具体风险和对应复核人；截图初筛不常驻叠在 Opus 评审前。小修与纯接线默认不叠 Astra 复核，涉及共享接口、跨线程、资源寿命或存档时才加，不叠无对应风险的全链复核。

**简单少量的活，拿到信息的一方直接做**：模型之间每转一次手都要花额度：写简报、对方重读上下文、再回报。所以简单又量少的活，由已经拿到全部信息的一方直接做完，不再写单子转给别的会话或子代理。只有量大、要并行、要换模型能力，或者归属不在自己手里时才转派。例如：主会话手上已有确切文字的几处文档修改，主会话直接在工作树里改；子代理在自己独占目录里顺手能补的小处，直接补，不另提单。

**升级先找失败原因**：已明确条目漏做，由原施工者补条目、候选与对应证据；接口或生命周期无解交 Astra 定边界；观感和内容争议交 Opus；超量或后半段质量下降按 D-184 拆单，不用升级模型代替拆单。

**派单最少写**：目标与验收条目、定案与未定项、独占路径、会话/模型/推理档/速度层、必要复核人、升级信号、预计工作量（D-184）。包内实现路径由施工者规划（§3.4）。

### 3.2 总指挥只做什么

**主会话的注意力只花在要判断的事上**：
- 画面与风格的评审和定值，质感移植（实现交二号会话）；
- 设计定案与跨系统取舍、文档冲突裁决；
- 派工、排优先级、合入决定；
- 与作者沟通。

**其余随时派出去，主会话不自己动手**（简单又量少、主会话手上已有全部信息的活例外，直接做，见 §3.1"简单少量的活"）：
- **不需要审美能力的任务和杂活**：默认先派 Sol（Codex 额度充足，ENG-TEAM-QUOTA §3）。执行类交值班执行者；调研、补信息、数据转换与核对、按确切文字打文档补丁、批量的旁路工程活写成旁路单交旁路会话（ENG-TEAM-DUTY §3）。
- **Opus 侧新开的施工任务**（画面、风格、内容类包与需要 Opus 的文档撰写）：写成任务单交二号会话（ENG-TEAM-FLOW §2.2）。补 GPT 短板的简单活也交它。
- **细节阶段的小修**：先交对应包的子代理或二号会话、Sol，主会话只看结果。
- **双账号模式下主账号不开新的子代理**：见 ENG-TEAM-QUOTA §6.1。

### 3.3 Astra 当指挥，施工默认交 6.1-sol 子代理

**Astra 主线程尽量当指挥官**：
- 做：契约与共享工程文件的定案；Astra 侧包的拆单和派工；写子代理简报，写清目标、约束和验收条目；审查子代理交回的方案与代码，看架构、契约、确定性和资源寿命；跨包的集成取舍；写合并请求；回答主会话。
- 尽量不做：亲自写实现，亲自跑长时间的测试与排查。这些也先拆给 Sol 子代理，Astra 只看结果和关键差异。

**施工默认用 gpt-6.1-sol 子代理**：Astra 名下所有包的施工，默认由 Astra 用 `spawn_agent` 开 gpt-6.1-sol 子代理完成，复杂工程用 high 或 xhigh。这也包括内核、确定性、统计、契约与存档迁移相关的包（WP-01、02、06、07、08、26、32、34、42、43、44、45a、46、49a、50、53a、53c）。包的归属与审查权不变，仍由 Astra 派工、审架构与契约、写合并请求。

**gpt-6-astra 子代理只在下面几种情形开**：
- 契约、共享接口或存档迁移的方案起草；
- 跨包的根因排查，Sol 子代理两次没查出来或没修对；
- 确定性、并发、资源寿命的方案本身要改，需要 Astra 级判断的那一段。

其余一律用 Sol。已有的 gpt-6-astra 包级子代理不再接新活，新任务按本节改派 Sol 子代理。施工范围以 Astra 明确授权的路径为准，不自动取得其他目录权限；固定值班与旁路会话的边界不变。

### 3.4 包内的实现路径由施工模型规划

- 任务单和简报只给目标、约束（主线优先、依赖、契约、目录归属、预算）和交付标准，不规定步骤。
- 施工模型按当前任务自己排实现路径和先后顺序，在回报里说明计划和偏差。

### 3.5 子代理的生命周期：默认新开，靠任务单交接

每次请求都要把整段上下文重读一遍，缓存读也按输入价的约十分之一计，上下文越长每一轮越贵；缓存几分钟不用就过期，过期后第一轮要整段重写缓存。恢复一个上下文已经很长的子代理去接新活，往后每一轮都在为旧历史付费，通常比新开一个、只读这次需要的文档和代码更贵。所以子代理默认新开，交接靠任务单。Claude 侧（Agent 工具）与 Codex 侧（Astra 的 6.1-sol 子代理）同样适用。

**默认新开**：
- 同包的下一张子单、新一阶段、跟原任务无关的活，一律新开。
- 交接写在任务单的"接续"段：已完成的部分、已定的取值与约定、下一步、要先读的文件和最近相关的合入。新子代理照它开工，不靠旧会话的历史。
- 子代理交回以后就结束，不留着待命，不占并发名额。

**只在两种情况恢复原子代理**：
- 交回后几分钟内（缓存还在）就要改的小返工，例如评审意见里的几处修改、rebase 后的冲突，预计十几轮以内改完；
- 原子代理交回时上下文在约 8 万 token 以内，新任务是跟它刚做的事直接相关的小活。

其余返工也新开，任务单写明改什么、改哪里。

**恢复以后先对齐现状**：接到任务先看 `merged.log` 和最新 `main`，`git rebase main`，再核对任务涉及的契约、数据与相关包的新提交；记得的旧版本不当现行依据。

**记录**：任务单的"派出"行写明子代理的名字和类型；回报里的 token 数是交回时的上下文大小，用来判断还能不能恢复。
