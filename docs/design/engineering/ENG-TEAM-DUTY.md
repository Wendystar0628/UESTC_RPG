# ENG-TEAM-DUTY · 协作分册：值班与旁路

> **范围**：本分册规定值班执行者与 Sol 值班会话做什么、完成度调研怎么排、Sol 旁路会话怎么按任务单开子代理处理旁路活，各方怎么开子代理，以及 Codex 侧怎么省。
> **不在本文**：合并的步骤：ENG-TEAM-FLOW §2.5；唤醒脚本与值班执行者：ENG-TEAM-COMMS §5；调研的审计与入队：ENG-TEAM-FLOW §2.8；GPT 不做审美的硬规则：ENG-TEAM-ROLES §2.2。
> **查阅**：先读 §0；值班做什么、不许做什么看 §1；完成度调研怎么排、查什么看 §2；旁路会话看 §3；各方怎么开子代理看 §4；Codex 侧怎么省看 §5；待验证的初值看 §6。
> **关联**：[ENG-TEAM 协作规程总纲](ENG-TEAM.md)、[ENG-TEAM-ROLES 参与者与分工](ENG-TEAM-ROLES.md)、[ENG-TEAM-FLOW 包的归属与开发流程](ENG-TEAM-FLOW.md)、[ENG-TEAM-COMMS 交接与通信](ENG-TEAM-COMMS.md)、[ENG-STATUS 施工状态](ENG-STATUS.md)、[ENG-GATES 验收门禁](ENG-GATES.md)、[ENG-WP 工作包](ENG-WP.md)、[REF-SPEND-AUDIT 消耗审计](../reference/REF-SPEND-AUDIT.md)

## 0 结论

值班由值班执行者（只改文档的合并交 Gemini，其余与巡检交 Grok，没回复退回 Sol，D-198、D-202）承担，完成度调研和其他旁路任务由 Sol 旁路会话承担。值班与旁路各由一个唤醒脚本叫醒（ENG-TEAM-COMMS §5），不占 Astra 和主会话的主线时间。Sol 会话一律不做审美工作（ENG-TEAM-ROLES §2.2）。

1. **值班交给值班执行者**（§1）：长期做合并执行、施工状态与巡检；Sol 值班会话是退回时的接手者。
2. **完成度调研持续排**（§2）：值班执行者在巡检时按开发阶段持续排完成度调研，调研结果走调研入队流水线（ENG-TEAM-FLOW §2.8）。
3. **旁路交给 Sol 旁路会话**（§3）：调研单和不在关键路径上的旁路活都写成任务单，交固定的 Sol 旁路会话按单开子代理处理。
4. **Sol 的边界**（§1、§3）：Sol 不做审美，不改契约和共享工程文件；设计文档只在两种情况下改：值班执行者维护 ENG-STATUS，任务单给出确切文字时按文打补丁。
5. **开子代理**（§4）：一个包或子包一个子代理，各用一个工作树；Codex 侧子代理与主线程共用工作目录，简报里写明只在自己的工作树里读写。
6. **Codex 侧不浪费在等待和重复上**（§5，D-192）：不短轮询；已批准、已合入、已复核的事项没有新输入不再复核；同一组合的公共门禁只跑一次。

### 0.1 接入要点

本文只约束协作各方的工作方式，没有对其他包的接口要求；按角色的接入要点集中在 ENG-TEAM §0.1。

## 1 值班执行者与 Sol 值班会话

**是什么**：值班承担总指挥的执行类杂活，由值班执行者照长期任务单 `tasks/sol/sol-001.md` 做：只改文档的合并交 Gemini 3.8 Flash High（不可用时 gpt-6-luna），其余合并、sol 任务单与巡检交 Grok 4.7，没回复退回 Sol 值班会话（ENG-TEAM-COMMS §5，D-198）。Sol 值班会话是 Codex 应用里的一个固定 gpt-6.1-sol 会话"Sol值班会话"（high，普通速度，D-203），thread `01a14634-61f1-7622-be49-c63705d46a3a`。执行者都由唤醒脚本叫醒，每轮只处理被叫醒的事和巡检。

**做什么**：
- **合并执行**：只合有批准行的候选，步骤见 ENG-TEAM-FLOW §2.5。
- **施工状态**：每小时最多同步一次 ENG-STATUS 与待派工队列，叫醒消息写明这一轮同不同步（ENG-TEAM-FLOW §2.6，D-204）。
- **滚动文档分支**：每一轮合并里 `doc/rolling` 有新提交就整段合入，做法见 ENG-TEAM-FLOW §2.5。
- **巡检**（每小时一轮做；合并轮和任务单轮不做）：
  - 卡死进程：`Get-Process godot*` 里启动超过 15 分钟仍在跑的截图或门禁进程，记下 PID、命令行、所属工作树，通知主会话，不自己杀；
  - 带条件的批准行：当时没合的，每次都复查，条件满足了就照 ENG-TEAM-FLOW §2.5 合入；
  - 工作树落后：`git -C <工作树> merge-base --is-ancestor main HEAD` 不成立的工作树列一行，写进"状态"，不用通知；
  - 完成度调研：按 §2 看要不要写新的调研单，以及在跑的调研有没有超时。
- **通知与流水**：通知写进 `notes/sol-to-opus.md`；本轮做了什么写在 `logs/tasks/sol-001.log.md` 末尾，一行一事，带时间；那份是只追加的流水，执行者不用通读。

**不许做**：改代码；改契约与共享工程文件；改 ENG-STATUS 以外的设计文档（任务单给出确切文字时除外）；合并没有批准行的候选；强推；删除分支或工作树；做任何画面与风格判断。

## 2 完成度调研

完成度调研是调研入队流水线（ENG-TEAM-FLOW §2.8）的第 1 步。调研是持续的，不是一轮就结束：值班执行者按开发阶段排调研，阶段不变时也持续找新方向，由 Sol 旁路会话执行。本节只写这一步怎么排、查什么；审计、并入工作包和入队都照 ENG-TEAM-FLOW §2.8，这里不重复。

**谁排、什么时候排**（任务单 `tasks/sol/sol-002.md`）：
- **阶段调研**：值班执行者按 ENG-STATUS §2 的"当前阶段"排调研。阶段一变，或主会话在 `sol-002.md` 的"状态"里要求新一轮，就写一张调研单 `side/cards/r<nnn>.md`。
- **持续调研**：每次巡检时，下面两条同时满足，就再写一张新方向的调研单：
  - 距上一张调研单启动超过 2 小时；
  - 旁路会话当前空闲（`logs/side/runner.log` 最后一行是"本单结束"）。
- **新方向**：每张 4–6 个方向，不重复已做过的，每个方向写明为什么现在值得查。新方向从这些地方找：
  - 前几轮总览里"未核实""需要 Opus 拍板""建议后续调研"的条目；
  - `logs/merged.log` 里新合入的包带来的新问题；
  - 当前阶段的侧重（见下文"各阶段的侧重"）；
  - 同类作品与主流二次元游戏的新版本、新系统；
  - Godot 4.x 与三渲二相关的新技术与工程做法；
  - 玩家社区对同类作品的新反馈。
- **调研索引** `research/INDEX.md`：一单一行，写单号、启动时间、阶段、方向、总览路径、Opus 审计状态。值班执行者写新单前先读它去重，新单写完追加一行；旁路会话做完标"待审"；主会话审计后改最后一列。
- **模板**：调研单以 `research/cards/r002.md` 为模板，写进 `side/cards/`，按当前阶段调整背景、调研方向和输出目录 `research/<日期>-r<nnn>/`。
- **边界**：值班执行者和旁路会话只负责让调研持续产出，不改工作包、不派工。

**执行的细则**：
- 旁路唤醒脚本发现新的调研单，按顺序交给 Sol 旁路会话（ENG-TEAM-COMMS §5）。
- 旁路会话按方向开 gpt-6.1-sol 子代理并行调研，对照同类作品和主流二次元游戏，各写一份报告。
- `00-总览.md` 写按优先级去重的建议表，每条标明归哪个包或建议新包、主线版还是细节阶段、工作量、依赖。
- 写完把 INDEX 里这一单标成"待审"，在 `notes/sol-to-opus.md` 追加一行"[时间] 调研 r<nnn> 完成：<总览路径>"。调研单启动超过 3 小时仍没有完成行，值班执行者查 `logs/side/runner.log` 与 `<单号>.stderr.log`，写进"状态"并通知主会话。

**三个视角**（每张调研单都要覆盖）：
- **制作完整度**：内容量与密度、各系统与管线的覆盖、质量保障与测试、性能与稳定性、存档稳健、发布与本地化、无障碍、玩家对同类作品的预期；
- **优越性**：和同类作品比的长处与短处、差异化卖点、让人记住的时刻与展示画面、技术与美术上值得放大的地方、同类作品常被批评而本项目可以避开的地方；
- **玩家体验**：首次体验与上手、一次游玩的节奏与情绪曲线、舒适度（晕动、眼睛疲劳）与可达性、操作与界面的摩擦、加载与等待、反馈与手感、回访与重玩的理由。

**各阶段的侧重**：
- 第一波、第二波：看世界与观光模式缺什么；
- 主线闸口与集中测试：看质量缺口、性能与设置、发布完整度；
- 细节阶段：看细节打磨与交互小物。

**不调研的**：
- 任何阶段都不调研、不建议 RPG 内容；
- 本项目是个人实验性作品（D-181），不调研商店页、上架、宣传素材、成就、云存档、平台集成等商业发行内容；"发布完整度"只看按 OPS-RELEASE 在 GitHub 发整包时的完整与稳健；
- GPT 只收集观感方面的事实与做法，不下画面结论。

## 3 Sol 旁路会话

**是什么**：Codex 应用里的一个固定 gpt-6.1-sol 会话"Sol旁路会话"（xhigh，普通速度，不开快速模式，D-203），thread `01a14633-e0a8-78c0-a508-1d9b7904ac14`，角色说明 `side/ROLE.md`。完成度调研和其他旁路任务都由它一个会话管理，按任务单开子代理并行处理。

**两类任务单**（都放在 `side/cards/`）：
- **调研单 `r<nnn>.md`**：由值班执行者写，做法见 §2。
- **旁路单 `s<nnn>.md`**：由主会话写。主会话判断某件事不在主线关键路径上、却会占主线时间，或者要大量补信息、调研、批量核对数据时，就写一张旁路单，写明在哪做、交付什么、能改什么、哪些不许做。派不派、派几张、做到什么程度，由主会话定。

**怎么执行**：
- 旁路唤醒脚本按文件名顺序一次交一张单（ENG-TEAM-COMMS §5）；旁路会话做完这一张就结束本轮，下一张再叫醒它。
- 按单子的方向数用 `spawn_agent` 开 gpt-6.1-sol 子代理，最多 8 个并发（§4）；子代理的简报写明 §4 的"共用工作目录"注意事项。
- 旁路单做完，在单子末尾"状态"写结果，在 `notes/sol-to-opus.md` 追加一行；调研单的收尾见 §2。
- 上下文重置后，照 `side/cards/` 下各单的"状态"接着做（ENG-TEAM-COMMS §6）。

**边界**：
- 不做任何审美工作（ENG-TEAM-ROLES §2.2）；调研里涉及观感的，只收集事实和出处。
- 不改契约和共享工程文件；不改 `docs/design/`，任务单给出确切文字的补丁除外；不合并，不推送。
- 不碰任何包的工作树和主检出。要写代码的旁路活，在单子指定的独立工作树里做，完成后写合并请求，经主会话批准由值班执行者合入（ENG-TEAM-FLOW §2.5）。
- 调研报告和旁路产出写进单子指定的位置；主会话读了以后决定怎么改文档、派给谁。

## 4 怎么开子代理

**各方都适用**：
- 一个包或子包一个子代理；同一时刻，一个文件只有一个代理在写。
- 每个子代理各用一个工作树（ENG-TEAM-FLOW §2.2）。
- 简报按 ENG-WP §4 的模板写。Claude 侧的子代理由 `CLAUDE.md` 自动载入开工手册；Codex 侧的不会，简报里要写明先读 `docs/design/engineering/ENG-ONBOARD.md`。
- `dotnet build`、`--import` 和烘焙这类重 CPU 任务，走 `..\UESTC_RPG.wt\.locks\` 下的计数锁（ENG-ARCH §6）。

**Claude 侧**（只在二号会话；主账号不开新的子代理，ENG-TEAM-QUOTA §6.1）：
- 用 Agent 工具在后台开，指定模型 `model: "opus"` 或 `"sonnet"`；一个包一个，简报里写明工作树的绝对路径。
- 评审不通过：交回后几分钟内的小返工恢复原子代理，其余新开子代理照任务单改（ENG-TEAM-ROLES §3.5）。
- 单 Claude 账户模式下改由主会话开（ENG-TEAM-QUOTA §4），其余写法相同。

**Codex 侧**（Astra 与 Sol 旁路会话）：用 Codex 的 collaboration 工具。
- **开**：`spawn_agent`。`task_name` 写包号，例如 `wp-02a`；`message` 写完整简报。
- **等**：`wait_agent`，可以设 `timeout_ms`。
- **查**：`list_agents` 列出子代理。
- **追加指示**：`send_input` 给正在运行的子代理发补充说明。
- **并发上限**：`~/.codex/config.toml` 里的 `max_concurrent_threads_per_session`，当前是 36，每个会话各算各的；Sol 旁路会话另按 `side/ROLE.md` 最多 8 个。

Codex 的子代理和主线程共用同一个工作目录，所以简报里必须写明：
- 你的工作树是 `E:\Project\UESTC_RPG.wt\<WP-xx>`；
- 所有读写都用这个工作树下的绝对路径，git 一律用 `git -C <工作树>`；
- 不碰别的工作树，也不碰主检出 `E:\Project\UESTC_RPG`；
- 不合并、不推送。

**Astra 主线程负责**：派工；回答子代理的问题；审代码是否符合架构；跑快检；写合并请求；处理契约申请；看 `logs/merged.log`，通知自己的子代理 rebase。

## 5 Codex 侧怎么省

消耗审计（REF-SPEND-AUDIT）显示，Codex 侧的协调开销比实现还高，主要浪费在三处。值班执行者、Sol 旁路会话、Astra 主线程，以及它们开的子代理，都照下面三条做。

1. **不短轮询**：照 ENG-TEAM-COMMS §4"等待不短轮询"。
2. **不重复复核**：
   - 已经批准、已经合入或已经复核通过的事项，没有新的输入（新提交、新基线、新条件）就不再复核，也不再回"已核""复核通过"。
   - 收到提醒时先看有没有新输入：没有就一行写明"无新输入，沿用 <时间> 的结论"，不重跑检查。
3. **同一组合的门禁只跑一次**：
   - 成批合入时，整批的公共门禁只跑一次，做法见 ENG-TEAM-FLOW §2.5"成批合入"与 ENG-GATES §2。
   - `-NoCache` 只在批准行写明或缓存结果可疑时用，同一组合不重复用。
   - 失败后改了东西才重跑；没改就不重跑同一组合。

必要的检查照做：新组合的集成门禁、抓到问题后的复验、批准行写明的专项都不省。
