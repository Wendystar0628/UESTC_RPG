# STD-CODE · 代码结构准则

> **范围**：本文规定写代码时的结构规矩：依赖方向怎么落地、规则值与数据各留一份、先用原生再复用、失败交到底、不留死代码、控制文件规模、测试代码怎么写、异步与线程，以及写 Godot 代码时怎么查 API、怎么处理场景与路径。
> **不在本文**：分层、依赖方向、禁用写法与架构导向见 ENG-ARCH §1、§2、§6；测多少、什么时候跑见 WF-RULE §9 与 ENG-GATES §1；命名与目录见 STD-CONVENTIONS §3、§5。
> **查阅**：先读 §0；Godot API 与场景写法看 §0.1；依赖看 §1；规则值与数据看 §2；先用原生与复用看 §3；失败与死代码看 §4；规模看 §5；测试代码看 §6；异步与线程看 §7。

## 0 结论

1. 依赖只朝一个方向：运行时只读契约里的数据，全局流程遍历所有内容模块，不点名某一个（§1）。
2. 同一含义的数只定义一次，别处引用；坐标、实体 ID、尺寸、名称写数据，Tune 只放规则值（§2）。
3. 先用原生，不重复造轮子：写功能前按次序判断 Godot 原生、.NET 自带、已引用的成熟库、公共层能不能做，原生做得到且更简单就用原生，都不行才自写并写明理由；出现第二份相同代码或机制就收进公共层（§3，DECISION-237、DECISION-297）。
4. 失败带原异常交到文档写明的接收方；被取代的代码同批删；不为测试开单实现接口；不留过时兜底（§4）。
5. 文件、方法、构造参数超限就拆；多人常改的清单文件拆小，能生成的不手写（§5）。
6. 测试只为守契约、守核心体验、守回归而写，测行为不钉实现；容差、夹具、临时目录各一份（§6，DECISION-246）。
7. 每个任务都有持有者等它，跨帧操作一个对象收口，工作线程不碰场景树（§7）。

### 0.1 接入要点

- **写 Godot 代码前**：用到的类、方法、属性先在 `docs/godot-api/signatures.txt` 查到签名再写，着色语言查 `docs/godot-api/shaders/README.md`（DECISION-145）；游戏代码只用 C#（编辑器与构建期工具外壳除外，DECISION-005）；路径只用 `res://`，不手写 `uid://`；场景由代码生成，不在编辑器里重存。
- **加 `using` 或项目引用时**：照 ENG-ARCH §2 的依赖方向；运行时代码不用生成层的实现类，内核不用系统层（§1）。原生资源的创建权与 `user://` 的读写权见 ENG-ARCH §0.1。
- **碰渲染、材质、着色器、逐帧代码、烘焙或存档时**：先读 ENG-BUDGET-RULES §0.1。
- **要用碰撞顶、台阶、门高、预算这类规则数时**：找到它的定义处引用；没有就加进对应的规则类，不写字面量（§2）。
- **要写坐标、实体 ID、尺寸、名称时**：写进按图的数据（世界文件等），不写进 Tune 或 Site 代码（§2）。
- **要写功能、算法或基础设施前**：按 §3 的次序先查 Godot 原生（`signatures.txt`）、.NET 自带与已引用库、公共层；原生做得到且更简单就用原生，自写的在类注释里写明原生为什么不行（§3）。
- **出错时**：失败带原异常交给文档写明的接收方，任务与 TCS 的故障要有人读，不写文档没定的回退（§4）。
- **开后台任务、跨帧操作或订阅事件时**：读 §7。
- **写日志时**：只经诊断服务 `IDiagnosticLog`，不直接调引擎日志（G4 拦）。
- **写测试前**：读 §6，测多少见 WF-RULE §9；补回归时夹具先断言原缺陷的触发条件确实出现，再只断言看得见的结果。
- **注释或数据里提到文档时**：只写文档编码，不写节号（STD-DOC §3）。
- **写或改脚本时**（`scripts/`、`dashboard/tools/`、`pipeline/`、`.collab/tools/` 与双击入口）：开头第一段写一句话作用（Python 用模块文档字符串），怎么跑另起一行"用法："，观察台读这两处。

## 1 依赖方向

依赖方向以 ENG-ARCH §2 为准，本节只列落地时常犯的写法和改法：

- **内核引用系统层**：kernel 不用 systems 的类型。系统要在启动时参与，就实现内核给的接口，接口和数据类型放 Contracts。
- **运行时用生成层的实现类**：systems、style、camera 只读 Contracts 里的数据类型，不用 Planner、Params 这类生成层内部类；生成层改实现不应连带运行时。
- **全局流程点名某个模块**：烘焙、碰撞、发现这类面向整张图的流程，经 `IContentModule` 遍历全部模块，不 `new` 某一个区的模块。
- **命名空间成环**：两个命名空间互相引用时，把共用的常量或类型挪到被依赖的一方。

## 2 规则值与数据各一份

- **规则值**：同一含义的数只定义一次，其他地方引用它，不复制字面量。
  - **定义点按使用范围定**（DECISION-244）：跨程序集用的规则值与基础常量放 Contracts；只在一个模块里用的放该模块的规则类；建筑的通用默认值放建筑生成的默认规则，各区只写与默认不同的项。数值以代码为准，文档只写设计目标并指向定义处。
  - 预算常量在代码里只留一处，各模块按名字读。
- **数据**：坐标、实体 ID、尺寸、朝向、中文名写在按图的数据（世界文件等，STD-CONVENTIONS §5）；Tune 只放规则值和风格参数。同一个 ID 只在一处出现，代码按 ID 读数据，不在 Tune、Site 和数据文件各写一份。
- **ID 目录**：每区一个 ID 目录类，同一个要素号在这里一次给出实体、部件、源轮廓三种 ID；跨区引用经所属区的目录，不再手写字面量。取要素的一段按 DECISION-243 用选段。
- **默认值只在数据**：新游戏的模式、出生点、开局时刻季节天气，设置与画质的默认值和取值范围，只在按图数据、规则集或设置数据里定义一次；服务的内存初值不写业务默认，界面与存储共用同一个设置定义。
- **派生值不手写**：缓存是否过期从输入本身判断，规则值从定义处读，不手写版本串、改规则时再手动加一。

## 3 先用现成，再复用，不复制

- **先用原生，不重复造轮子**（DECISION-237、DECISION-297）：写功能前按次序判断，前一级做得到就停：① Godot 原生——节点、服务器与资源，以及 Jolt、导航、本地化、Image、Geometry2D/3D、SurfaceTool、MultiMesh、可见范围与网格 LOD、线程加载、WorkerThreadPool、Tween、AnimationPlayer、Control 容器与 Theme、InputMap 这类内建能力，签名以 `docs/godot-api/signatures.txt` 为准；② .NET 自带；③ 已引用的成熟库（NetTopologySuite 等）；④ 仍在维护、许可允许的新库（引入按下条）；⑤ 公共层已有的；⑥ 都不行才自写。"原生更简单"按要写和要维护的代码量、接入面与效果判断，效果不能比原生差。只在原生做不到，或违反硬约束（生成层是纯 .NET、同机同输入同输出、画风底线与材质白名单、许可）时自写，在类注释里一句话写明原生为什么不行。改到已有的自写实现时同样先判能否换成原生：量小当批换，量大开队列行（CORE-INDEX §2「顺手清掉死代码与旧设计」）。
- **引入库**：许可与登记见 ENG-LICENSE §2；NuGet 包和程序集引用按 WF-BUILD §3 申请；生成层只用纯 .NET 的库。
- **公共层分层**（DECISION-244）：标量与向量数学、角度与方位换算放 Contracts 的数学底座（各层都够得着）；平面几何、部件几何底座、分区工具与按 ID 读数据在 `gen/` 下各有公共目录（平面几何能用 NetTopologySuite 的直接用）；运行时各模块共用的引擎侧工具（如跨帧等待）放 `Campus.Contracts.Runtime`，不放内核再给门禁开例外（DECISION-304）；测试夹具放共用测试夹具目录。新写类或工具函数前先查这几处。
- **盒体、视锥与图层只有一个入口**：盒体与外向平面体相交、点到盒体距离只经 `Box3`；从正式或合成相机投影填六个视锥平面只经 `CameraFrustum`；3D 渲染层只用 `RenderLayers` 命名位掩码，`NonCasters` 由这些名称组合。
- **公共函数清单由 G4 守**：清单上的函数（点到线段距离、点在多边形内、质心、平滑、插值、方位换算、角度包裹之类）只能在登记的公共类型里定义，别处定义同名函数即不过；清单以 `scripts/gates/arch` 的规则为准。
- **新文件放哪**：按模块分层（ENG-ARCH §1）和文档文件头的 `paths` 找家，找不到先改结构并报主会话，不用补丁式命名（WF-RULE §16）。
- **测试放哪**：各模块的行为测试放自己目录的 `tests/`，编进 `Campus.Gen.Tests` 或 `Campus.Tests`；夹具统一放 `game/testing`（共用的在 `Support`，只给生成或运行时宿主的在 `Gen`、`Runtime`）。
- **`.uid` 与 `.gdignore`**：纯 .NET 的 `game/contracts`、`game/gen`、`game/testing` 和运行时各 `tests` 目录用 `.gdignore` 排除 Godot 导入，不登记其中 C# 的 `.uid`；运行时资源的 `.uid` 由 Godot 生成维护。
- 第二份相同或只差参数的代码、或同一机制（失败聚合、判码、插值、转角政策这类）的第二份实现出现时，就收进公共层，原处改引用；不复制整个模块或框架类再改。
- 各区的差异写成数据或参数，不靠每区一套同构的类来表达。
- **部件按 ID 编目**：共享部件的 ID 与参数在 `game/contracts/Parts/`；各区按 ID 放置部件，特有部件建在自己目录、ID 加区名前缀，证明能复用再申请提升为共享部件。

## 4 不留死代码，不写补丁

- 桩或旧实现被真实实现取代时，同一批删掉，连同只为它存在的测试（DECISION-209）。
- 临时诊断用完就删，包括环境变量开关、日志前缀和诊断类；要长期保留的诊断参数写进 ENG-GATES-SHOTS §1。
- 只有一个生产实现的接口不为测试而开，测试用真实对象加临时目录；真要换实现时再抽接口。
- **失败交到底**：失败沿结果载体（返回值、Task、结果对象）交给文档写明的接收方，由它处置；包装与聚合保留原异常（带 inner 构造或 `ExceptionDispatchInfo`），同一异常不重复嵌套；失败码在产生处定一次，下游原样传递，不按异常类型、阶段或文字重判；有结果的任务与 TCS 进了故障就要有人读；改失败流先列全生产者与消费者，同批迁完（CORE-INDEX §6「失败带原异常交到底」）。
- **补丁式代码由 G4 硬拦**（DECISION-270、DECISION-271）：判据是有没有设计依据，不看用词。下面四种形态出现在自有手写源码里，快检即失败，不设名单。设计上要的默认、降级与回退（例如存档里的图已不存在时回到默认图、设置文件读坏时用默认值）按含义命名，写进管它的文档，并在代码处标出出处（`[FailureHandler("文档码")]` 等声明）；文档没写的回退就是补丁，删掉，缺数据就报错。
  1. **吞掉失败**（`game/`、`scripts/` 的 C# 生产代码，下同）：catch 要么重新抛出，要么把异常对象交给文档写明的失败处理方（流程恢复、阶段失败、存档坏段记录这类）；只打日志、返回空值或默认值、continue 都算吞，取消不算失败。确实可缺的服务在调用处明确按可缺处理，不靠 catch。
  2. **按编号特判**：不拿实体、物种、区域、存档段这类 ID 的字符串字面量做比较或 switch；行为差异写成数据字段或类型自己的声明，ID 从目录、数据或声明处取。
  3. **按版本分读法**：数据与存档只认当前版本号，别的版本按坏数据报错（SYS-SAVE-FORMAT §1.4）；不按版本号分几条读法，不留旧格式转换。
  4. **留旧与开关**：不用 `[Obsolete]` 留着旧接口，`#if` 只用引擎与 .NET 自带的符号，测试不用 Skip、Ignore 跳过。
- **补丁词只作提醒**：fallback、legacy、compat、workaround、hack、shim、temporary 以及兜底、绕过、临时方案、先凑合这类词，写代码时由钩子提醒先查根因，不算失败；同样的补丁换个名字就能过，正当的用法（临时文件、与引擎版本兼容的说明）又会被误伤。
- **机器查不出的补丁**由另一方的收口审计查（WF-FLOW §3.1）：在使用方加特判或校验掩盖上游的错，新旧两条路并存，为凑结果加的偏移与魔数，为通过而放宽的测试与容差，复制一份的数据，绕开已有服务直接调引擎。

## 5 规模

- 同一类型（partial 各部分合计）超过约 600 行、方法或构造器超过约 80 个真实语法行（字符串内容换行不算）、构造参数超过 8 个，就按职责拆开；partial 不能分摊，拆分本身不改行为。生成代码、第三方与测试不计入前两项的行数；但测试同样不用 partial 把一个类切到多个文件，按测的行为拆成独立测试类。
- 多人常改的清单文件（登记表、调参表）按程序集或按区拆开；能从代码生成的不手写。
- 不足约 1000 行、又没有独立依赖边界的程序集，并进相邻程序集；边界靠依赖规则立，不靠多建程序集。

## 6 测试代码怎么写

测多少、什么时候跑、时间与增长预算见 ENG-GATES §1.1；本节只管写法（DECISION-246）。

- **只有三种理由**：守契约（公共接口、数据格式、同输入同输出）、守核心体验（启动、行走、存档的主线冒烟）、守出现过的 bug（回归）。每个测试用类别标签声明是哪一种（`Contract`、`Smoke`、`Regression`），说不出理由的不写。画面和手感不写自动测试，靠固定机位截图与试玩。
- **判据只有一份**：位置、角度、时间的容差和样本量上限都引用共用测试夹具里的测试规则常量（按 demo 阶段取几厘米、度、几帧这一量级：游玩中看不出的误差不判失败；看得出漏光、深度闪烁的缝隙与共面例外，照生产几何容差），断言里不写容差字面量；要求逐位一致的确定性测试是唯一例外，另标 `Determinism`。
- **读权威，不抄权威**：期望值从数据、规则常量和生产代码读；断言里不写坐标、ID、数量、哈希的副本；异常只断言类型，不断言文案。
- **测性质，不钉实现**：断言"同一输入两次一致、不重叠、不出界、走得到"这类性质；内容一调就红的断言不写；已知缺陷不写成期望值，输出暂不能变的在队列行里记下，不用测试锁住（DECISION-314）。
- **能在生产里自检的不写测试**：数据与规则的合法性在加载时直接报错，判据同样按看得出的量级（WF-RULE §15）；测试只守跨边界的行为。
- **夹具与临时文件只有一份**：契约的假实现、找仓库根、读真实地图、用完即删的临时目录都在共用测试夹具里，测试不往 `output/` 写东西。
- **清理只释放，不判定**：断言写在用例正文，`Dispose`、`finally` 与组级钩子只释放，免得清理里的失败顶掉原失败；自建引擎资源（主题、字体、纹理等）的测试组在 `[After]` 里经共用夹具回收，单跑一组也不把泄漏留到引擎退出；组级钩子跟着用例所在的进程走，这类组的用例全部标运行时（DECISION-314）。
- **跟着代码走**：被测代码删了同批删测试；行为改了就改断言，不另加一份并存；一个测试文件过 300 行，先删再拆。
- **新增测试**：修 bug 时补一个回归或在原有测试里加一条断言；补的回归要能在修前失败：夹具先断言原缺陷的触发条件确实出现（复现不出不算回归），再断言修后看得见的结果，不钉句柄复用、调用次数、时序这类内部做法（DECISION-316）；其余新增见 WF-RULE §9。

## 7 异步与线程

- **任务有主**：每个 Task 由启动它的作用域等待，或交给文档写明的失败通道；不写 `async void`（引擎回调入口包一层，把异常交给失败通道），不用 `_ =` 丢弃任务；作用域结束时先取消、再等自己的任务排空，迟到的结果核对代际后丢弃（ENG-ARCH §2「生命周期与发布」）。
- **跨帧操作一个对象**：一次进入、读档、传送这类跨帧操作，把标志、令牌与结果放进同一个操作对象，成功、失败、取消三个出口都结束它；流程阶段只认一个状态机，不另留旁挂的标志，重入时随作用域重建。
- **线程边界**：工作线程只做纯计算与缓存读写，不碰场景树、物理 body 与渲染实例；内核服务回主线程沿用所属服务已有的帧回调入口（如存档服务的 `OnFrame`），不各自另拼一套（ENG-BUDGET-RULES §1）。
- **事件解绑**：订阅寿命可能长于订阅者的普通 C# 事件，在 `_ExitTree` 或作用域释放时解绑。
