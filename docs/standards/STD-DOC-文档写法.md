# STD-DOC · 文档写法

> **范围**：本文规定 `docs/` 的文档怎么分层、文档树怎么分级，每份文档长什么样、写什么不写什么、多长，编码与引用、冲突怎么判、新文档怎么加、谁维护。
> **不在本文**：顶层规则本身在 CORE-INDEX §0、§2–§5；决策的内容在 REG-DECISIONS；钩子怎么注入在 `.collab/tools/README.md`。
> **查阅**：先读 §0；分层与文档树看 §1；文档形状看 §2；编码与引用看 §3；写什么、怎么写看 §4；体量上限与怎么拆看 §5；冲突与规则放哪看 §6；新增文档看 §7；登记决策看 §8；维护看 §9

## 0 结论

1. **分层自上而下查，文档树四级**：顶层规则 → 信息地图与角色入口 → 域总纲与各文档的 §0、接入要点 → 正文小节 → 登记与生成物；上两层由钩子注入，下面按需查。文档树是顶层 → 域总纲 → 主题文档 → 子文档，到子文档为止（§1，D-216）。
2. **每份文档形状一样**：文件头、简题标题、三行范围块、§0 结论、§0.1 接入要点、正文、可选的待验证（§2）。
3. **只写结构、规则、设计目标和导向**：实现做法与细节以代码和数据为准，不写分工块、交付验收和横切副本；只写删了会出错的，要点在前，一个概念一个词（§4，D-215、D-220）。
4. **有上限，按内容拆**：上限见 §5 的表；超了先删；管着几个分开用的子主题就拆成主题文档加子文档，没到上限也可以；文档树到子文档为止（§1）；新内容先找家（§5，D-217、D-222）。
5. **一条规则一个家**：按它回答的问题放进对应文档，别处只给指向；冲突按层级判（§6）。
6. **改完同批更新索引**：生成的索引重跑 `gen-index.py`；增删改名文档或小节时，同批改手写的导航；跑 `check-docs.py` 到 problems 为 0，和文档改动同一次提交（§9）。

### 0.1 接入要点

- **写或改文档**：照 §2 的形状、§4 的取舍与写法、§5 的上限；能一句说清不写一段，代码和数据里有的写一句以哪处为准。
- **改一条规则或设计**：先按文档索引查出讲同一主题的文档，同批改到一致（§4.2"先查再写"）。
- **文档冲突或与 REG-DECISIONS 不一致**：施工期间不改 `docs/`，写进回报，由主会话定案（§6）。
- **改了编号、文件名或结构**：所有引用一次改到新位置，包括任务单、简报和记忆（§3）。
- **提交后钩子提示文档或小节超限**：推送前删掉实现细节和重复，或拆分（§5）。

## 1 分层与文档树

### 1.1 上下文分层

| 层 | 是什么 | 在哪 | 进上下文的方式 |
| --- | --- | --- | --- |
| L0 顶层规则 | 项目与约束、工作原则、协作与分工、文档规范、代码规范，一条一句；按内容分节，一节写满就按主题拆出新的一节 | CORE-INDEX §0、§2–§5 | 钩子按节注入：会话开始、压缩后、子代理启动、作者每条消息；巡逻与通知平时不注入，距上次超过 30 分钟才补一次；子代理距上次超过 20 分钟或 40 次工具调用再送一遍；一次放不下的节下次补（D-272） |
| L1 信息地图与角色入口 | 各类信息在哪、仓库目录、各域总纲入口；本角色独有的必守与"做 X 前读 Y" | CORE-INDEX §1；WF-ENTRY 各节 | 会话开始、压缩后、子代理启动注入 |
| L2 文档要点 | 每份文档的 §0 结论与 §0.1 接入要点 | 各文档 | 读写路由到的路径、派工、看截图、写渲染与存档代码、改这份文档本身时注入接入要点；同一份 90 分钟内不重送，降级送出的下次补全文（D-272） |
| L3 正文 | 小节 | 各文档 | 不注入；grep `SECTIONS.md` 后按行号读 |
| L4 登记与生成物 | 决策、术语；小节目录与钩子路由 | REG-DECISIONS、REG-GLOSSARY；`SECTIONS.md`、`ROUTES.json` | 不注入；grep |

- 只有一个顶层（CORE-INDEX）。下层只向下指或平级指，不把上层的规则抄一遍。
- **顶层只给全局**：一次开发要掌握的是全局，细节按需读。顶层只放每次开发都要的：这是什么、工作方法与作者要求、写文档写代码与做成什么样的规则、各类信息在哪；作品取舍（PRD-SCOPE）、不变量全文（PRD-INVARIANTS）和一切具体内容下放，顶层至多列一个标题或一句话加指向。

### 1.2 文档树

- **文档树四级**：顶层 CORE-INDEX → 域总纲（每个文件夹一份 `<前缀>-INDEX`，写本域通用原则和文档树）→ 主题文档 → 子文档，不再往下套。除顶层和域总纲外，每份文档文件头写 `parent` 指上一级，上一级的文档要列出它（§5.1）。
- 导航只有三套：CORE-INDEX §1 与各域总纲（按功能）、`SECTIONS.md`（按小节）、`ROUTES.json`（钩子按路径）。每份文档范围块的"查阅"行是它自己的目录。

## 2 文档形状

```
---
文件头
---
# 编码 · 标题

> **范围**：本文规定什么（一两句）。
> **不在本文**：……（指向负责的文档编码）
> **查阅**：先读 §0；……看 §n

## 0 结论
### 0.1 接入要点
## 1 … ## n 正文
## n+1 待验证（可选）
```

- **文件头**字段：`id`（编码）、`title`（简题，见下条）、`category`（所在文件夹的类别）、`parent`（上一级文档的编码，域总纲不写）、`summary`（一句话，≤80 字）、`keywords`（主题文档 10–30 个，域总纲与登记类 5 个以上即可；检索词只写本文是权威的）、`owners`、`contributors`（工作包）、`depends`、`related`（文档编码）、`contracts`（本文拥有的契约名，没有写 `[]`）、`data`（本文规定的数据文件）、`gates`（验收门禁）、可选 `paths`（本文管的仓库路径 glob，钩子据此注入接入要点，只给确实管某类路径又没有工作包归属的文档写：顶层写 `docs/README.md`，域总纲写本文件夹，改到那里时注入它的接入要点）。工作包、契约、门禁要与 PLAN-WP、源码、ENG-GATES 核对。
- **标题用简题**：文件头 `title` 与 `# 编码 · 标题` 写同一个简题，不带"：副题"；副题里有用的内容并进 `summary`。标题要准确概括正文。
- **范围块**三行：范围、不在本文、查阅（钩子只认"范围"与"不在本文"这两个字样）。改文档时钩子会注入前两行，两行要能独立读懂。不写"关联"行，关系在文件头。
- **§0 结论**：5–10 条，每条一两句，指向本文小节；登记类文档的第一节可写 `## 0 用法`。
- **§0.1 接入要点**：写给别的包：碰到本文管的东西必须守什么。每条一行，`- **<什么时候>**：<必须怎么做或不许怎么做>（§n）`；自成一体，会被单独注入，不用"同上""见上文"。没有对外要求的写一句"本文只约束本包，对其他包没有要求"。脚本和钩子按标题文字"接入要点"找它，标题文字不改。
- **域总纲**：文件头与范围块照常；§0 只写本域所有文档都要守的几条，不抄 INV；§0.1 写本域新增文档怎么登记（主题文档写 `parent: <域总纲编码>` 并列进 §1；子文档写 `parent: <主题文档编码>`，列进主题文档 §0 和本总纲 §1 对应主题下）；§1 文档树只列编码与标题，主题文档在前，子文档缩进在它下面。
- **正文**：标题写清内容，不只写"其他""补充"；超过一屏的节分 `###` 小标题。
- **待验证**：只收仍未决、仍影响施工的项，每条写内容、验证方法与负责方、验证前用的初值；没有就不写。
- **主线之后**：标题带"（主线之后）"的节现在不施工，试玩流程打通后再做（D-233）；只推迟一部分的节，推迟的内容放在节末"主线之后："一段。

## 3 编码、小节编号与引用

- **文件名就是编码**：`编码-中文简题.md`，编码全大写英文加连字符，全库唯一（D-208）。规范文档 `<领域>-<主题>`，按图的再带图名，例如 `MAP-QSH-CORE`。

  | 前缀 | 文件夹 | 放什么 |
  | --- | --- | --- |
  | CORE | 根目录 `README.md` | 总纲 CORE-INDEX，只此一份 |
  | PRD | `product/` | 作品与范围、全局不变量 |
  | ART | `art/` | 视觉语言：风格、明暗与描线、视觉精度、造型、天空与光照、色彩脚本 |
  | WLD | `world/` | 不分图的世界内容规则，含日式街景与老楼翻新 |
  | MAP | `maps/<图>/` | 某张图的具体内容，清水河在 `maps/qingshuihe/`，总纲是 `MAP-QSH-INDEX`（按图带图名） |
  | SYS | `systems/` | 运行时系统 |
  | UI | `ui/` | 界面 |
  | ENG | `engineering/` | 架构、性能与预算、验收、发布、开发工具（内容预览）、扩展路线 |
  | PLAN | `plan/` | 工作包与阶段 |
  | WF | `workflow/` | 协作、流程、守则 |
  | STD | `standards/` | 文档写法、代码准则、约定 |
  | REG | `registry/` | 决策登记、术语 |

  每个文件夹一份域总纲 `<前缀>-INDEX`；开一个新域（新文件夹）时同批建域总纲、改本表、改 `gen-index.py` 的类别，并列进 CORE-INDEX §1。

- **小节编号**只在本文内有效；第一节是 `## 0 结论`（CORE-INDEX 是 `## 0 项目与约束`，登记类是 `## 0 用法`）。新小节加在所属一级节末尾。
- **改结构时全局替换**：拆分、合并、重编号或改名时，所有引用一次改到新位置，不留旧编号对照、兼容段或"原 §x 现见 §y"；docs 以外引用它的任务单、简报、角色说明、记忆同一批改（D-200）。
- **引用写法**：跨文档写"编码 §小节"（`SYS-WEATHER-PROCESS §1.4`，范围写 `SYS-WALK-BOUNDS §2–§4`）；本文内只写 `§6.4`；整份写编码；不变量写 `INV-6`，决策写 `D-133`，门禁写 `G15`；顶层规则按节名与条目标题引用，不写条号；编号列表里的一条写"ENG-BUDGET-RULES §1 第 9 条"。正文不加链接。代码与数据里提到文档只写编码，不写节号：节号随拆分和改写会变，代码里的引用没人核对（D-227）。

## 4 写什么，怎么写

### 4.1 取舍

- **写**：设计意图与目标（做成什么样、为什么，一句话理由可留）；规则与边界；还没实现的设计目标数值；对其他系统的约束。
- **不写实现**（D-215）：类名、文件树、类型签名、格式字段、命令行全表、参数表、内部流程步骤、"Godot 实现"节。代码或数据里已有的数值和清单（实体 ID、坐标、点位、参数），写一句"以 `路径` 为准"；改成这句前先确认那里有代码在读、值与现行决定一致，对不上的留在文档并报主会话。
- **不写横切副本**：分工块、"WP-xx 交付验收"、工作包节、契约节、帧顺序表、命令行节、预算副本、截图默认串副本。它们的家是 `ownership.json` 与 PLAN-WP、ENG-GATES、`game/contracts/` 源码、ENG-BUDGET、ENG-GATES-SHOTS §1。
- **不写过程**：修订历史、"原写 X 改为 Y"、用户原话、调研证据与出处、工期估计、已完成的待验证项。现行规则直接陈述。
- **数值只有一个家**：某个系统的数值以它自己的文档为准；别处写指针，必须抄的注明出处。
- **观光规则照写**：写死观光模式的规则（不出现人物、没有可以点选的东西等）照常写成规则，怎样成为规则集的配置由 ENG-ROADMAP 登记。

### 4.2 写法（D-220）

- **读者是旗舰大模型**：读者按字面执行、能读懂长文；写规则本身和适用范围，不写给人看的铺垫和成堆的例子；要推广的规则写"适用于所有……"，只限所列的写"只有这些"。
- **只写删了会出错的**：每一句都问"删掉它，读者会做错吗"，不会就删。规则总被无视，多半是文档太长把它淹没了。
- **精度按 demo 阶段**：写阈值、精度、样本量和验收条件前先问现在的画面看得出差别吗，看不出就放宽（WF-RULE §15）。
- **先写最小版**：按已经出过的错补写，不凭想象预先写全。
- **先查再写，同批改齐**：落笔前按文档索引找出讲同一主题的所有文档：CORE-INDEX §1 找到域，域总纲找到主题文档和子文档，再 grep `docs/SECTIONS.md` 和 `INV-n`、`D-nnn` 这类编号；有冲突先定哪边为准，同一批改到一致，不让两种说法并存。
- **一个概念一个词，一个主题一个默认做法**：前后用同一个词；不列几种并列做法让读者挑，确需例外只给一个出口。
- **要点放前面**：每节第一句就是结论；文档被截断注入时也能保住开头。
- **工作包号带名**：正文里提到工作包写成 `WP-21（中部与东区）`，名取 PLAN-WP-LIST 的包名或子包名；每节第一次带名，同一节再提可只写号；表格同一行已有包名的、文件头 `owners` 这类机器读的字段只写号。队列行、任务单和来信同此。
- **指针一层到底**：写到具体的"编码 §小节"，不经第二个入口转指。
- **规则句式**：默认做法加一句理由，例外至多一个出口；写"做到哪算完"，不只列"不要做什么"；"必须""禁止"只给硬约束；加粗只给最常被漏掉的那一句。
- **不写会过期的**：不写日期、进度和"目前""暂时"；顶层与不变量不写会随开发频繁变的清单（比如界面有哪些件），只写约束并指向管它的文档；状态在 WF-STATUS 与 `.collab/`。
- **必须执行的交给钩子**：文档是说明，要保证每次都守的规则放进顶层规则（CORE-INDEX）或接入要点，由钩子注入。

## 5 体量上限

| 部分 | 上限 |
| --- | --- |
| CORE-INDEX 除 §1 外的各节 | 2,700 字 |
| CORE-INDEX §1 信息地图 | 2,300 字 |
| WF-ENTRY 每个角色一节 | 1,200 字 |
| 每份文档的 §0 结论 | 1,000 字 |
| §0.1 接入要点 | 900 字 |
| 单节（从一个标题到下一个标题） | 2,000 字 |
| 单份规格文档 | 12,000 字 |
| 单份地图文档（MAP-QSH-*，按楼写外观） | 16,000 字 |

- 登记类（REG-DECISIONS 及其各卷、REG-GLOSSARY、PLAN-WP 的包表及 PLAN-WP-LIST）不受单份上限约束，但每条只写一行。
- 超了先在整份里挑最该删的删：实现细节、横切副本、重复、过程记录（§4），已写进细则或会由钩子注入的只留指向；不只压缩新加的那几句，也不为腾字数把整份重写一遍。删完仍超，按主题拆成两份，新文档按 §7 登记进域总纲。
- **压不下去就放宽上限**：判断再压会丢信息或引起误解时，稍微提高本表这一项，不硬塞。上限的数字只写在本表：`doc-size.py` 每次从本表读，`check-docs.py`、提交后钩子和巡逻都调用它，所以改了本表就全局生效；别处提到上限只写"见 STD-DOC §5"，不抄数字。例外：CORE-INDEX 各节和 WF-ENTRY 各节要整节注入 Codex，它单次注入最多 3,000 字（钩子留 2,800），这几项放宽后连同注入的标题行也不能超过 2,800 字。
- **量法**：`python -I -X utf8 scripts/docs/doc-size.py` 按本表量（正文不含文件头，一节从一个标题到下一个标题），`--over` 只列超限项。

### 5.1 长大了怎么拆（D-222）

- **按内容拆，不按字数和批次拆**：一份文档管着几个读者分开用的子主题，就按子主题拆出子文档，没到上限也可以拆；快超上限是必须拆的情形之一。不另开"补充""增补二""新版"这类文档。
- **子文档到此为止**：原文档留作主题文档：§0 列出子文档（编码、简题、什么时候读），§0.1 只留跨子文档的接入要点，正文只留各子文档都要用的共同部分或这份文档的核心主题；分开用的子主题整节搬进子文档。子文档在文件头写 `parent: <主题文档编码>`，编码是主题文档编码加子主题（例如 `SYS-AUDIO-AMBIENCE`），放在同一个文件夹。子文档再超，就拆成平级的子文档，不往下套。
- **逐级登记**：CORE-INDEX §1 只列域总纲；域总纲 §1 列本域的主题文档和子文档；主题文档 §0 列它的子文档。`check-docs.py` 查每份文档都被它的 `parent` 列出，没有 `parent` 的只能是域总纲（顶层 CORE-INDEX 除外），且列在 CORE-INDEX §1。
- **拆完全局改引用**：搬走的小节写一张映射表，用 `scripts/docs/remap-refs.py` 一次改完 docs 与脚本里的引用，用法见脚本开头（§3）。

### 5.2 新内容放哪

- 先按 §6 的表、CORE-INDEX §1 和域总纲找到它的家；已有文档管这个主题，就写进那一份或它的子文档，不新开平行文档。
- 是新主题就新开一份，照 §2 的形状，按 §7 登记；不塞进只是沾边的文档。
- 实现细节进代码，数据进数据文件，决策进 REG-DECISIONS，进度与过程进 git 和 `.collab/`；只有结构、规则、设计目标和导向进文档（§4）。
- 写之前先量：会让目标文档或小节超限的，先拆（§5.1）再写。
- 找不到家、要新开文档或改层级，先报主会话；改完同批维护文档树，看到的重复与放错层当批处理或进队列（WF-RULE §16）。

## 6 冲突与规则放哪

**冲突的层级**，从高到低：
1. 作者的决定（登记在 REG-DECISIONS）；
2. REG-DECISIONS 登记的其他决策；
3. 已实现的代码与数据（契约以 `game/contracts/` 源码为准，帧顺序以契约 `FramePriority` 为准）；
4. 负责该主题的文档（预算 ENG-BUDGET，门禁 ENG-GATES，工作包 PLAN-WP，各系统以自己的文档为准）；
5. 别处的摘录与指针。

- 决策与细则文档有出入时以决策为准，发现者报主会话，由主会话同批改细则。能按层级判定的，改低层的那一处；判定不了的不改，报主会话定案。
- 施工期间子代理不改 `docs/`，发现冲突写进回报；主会话分派的文档整理例外。

**一条规则放哪份**，按它回答的问题：

| 回答的问题 | 放哪 |
| --- | --- |
| 每个会话都要守的顶层规则 | CORE-INDEX 对应的一节（一句），细则在下面各家 |
| 观光规则集长期不变的硬约束 | PRD-INVARIANTS（只写约束，会随开发改的设计与数值写在它指向的文档） |
| 某个角色的入口与独有必守 | WF-ENTRY |
| 谁做什么、谁定 | WF-ROLE |
| 选哪个模型、怎么开子代理、怎么写简报、额度与并发 | WF-MODEL |
| 文件怎么命名、来信与回报怎么写 | WF-COMMS |
| 一件事怎么走（派工到评审）、防打架 | WF-FLOW |
| 全员的必须与禁止、git 与回滚 | WF-RULE |
| 改哪里、共享文件、契约申请与构建排队 | WF-BUILD |
| 此刻的状态与队列、调研入队与旁路 | WF-STATUS |
| 文档怎么写 | 本文 |
| 坐标、单位、命名与 ID、文件与编号格式 | STD-CONVENTIONS |
| 专有说法的统一解释 | REG-GLOSSARY |
| 架构、代码结构 | ENG-ARCH、STD-CODE |
| 决策记录 | REG-DECISIONS，一句加落点 |

## 7 新增文档

- 按 §3 取编码，放进对应的文件夹，照 §2 写形状。主题文档写 `parent: <前缀>-INDEX` 并列进域总纲 §1；子文档写 `parent: <主题文档编码>`，列进主题文档 §0 和域总纲 §1 里那个主题下；开新域时同批建域总纲并列进 CORE-INDEX §1（本文 §3、§5.1）。
- 由主会话同步改受影响的权威位置：工作包（PLAN-WP）、新门禁（ENG-GATES）、归属（`ownership.json`）。
- 新契约、全局参数、着色器文件、程序集引用或 NuGet 包，不在文档里先写成定论，在回报里申请，由 Codex 主线处理（WF-BUILD §1）。

## 8 登记新决策

- 新增或推翻决策时，主会话先登记进 REG-DECISIONS，再改相关文档（D-154）。编号从 D-001 起连续，不复用；决策有变时改写原行；每条写一句结论、适用范围、细则所在和状态。
- 正文只写决定后的现行规则，不写"某某定"。
- 子代理读 REG-DECISIONS 及各卷；发现文档与它不一致时报主会话。

## 9 维护

- **谁改**：`docs/` 由主会话改，或由它分派、写明范围；子代理需要改时在回报里提。
- **改完以后，同批更新索引**：
  - 生成的：重跑 `scripts/docs/gen-index.py`（重新生成 `SECTIONS.md` 与 `ROUTES.json`），不手改；
  - 手写的：新增、改名、删除文档或小节时，同批改域总纲的文档树、主题文档 §0 的子文档表（增删域时改 CORE-INDEX §1）、范围块的"查阅"行和文件头的 `related`；
  - 再跑 `scripts/docs/check-docs.py`，problems 为 0。提交后钩子会查索引是否过期，过期就提醒补交。`gen-index.py` 按文件头的 `category` 分类，加新类别要改脚本里的分类表。
- **提交**：在主检出 `main` 上只 `git add docs/...`，文档改动、生成的索引与手写导航放在同一次提交里推送（WF-RULE §7）。
- **任务结束时**：跑一遍 `scripts/docs/doc-size.py --over`，超限的先按 §4、§5 处理再交回。
- **核查**：模型换代、一批文档收口时，派子代理把文档集核查一遍：互相矛盾、过时、重复、断链和为旧模型写的过细流程；新增规则前先 grep 同主题的规则。
