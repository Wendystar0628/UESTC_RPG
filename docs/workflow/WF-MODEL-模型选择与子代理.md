# WF-MODEL · 模型选择与子代理

> **范围**：本文规定每张单按什么选施工模型与推理强度，Opus 与 Sonnet 怎么分，机械活交谁，各方怎么开子代理，子代理什么时候恢复、什么时候新开，以及派工简报与"接续"段的写法。
> **不在本文**：各模型的长短板与"GPT 不做审美"：WF-ROLE；额度与并发数量：WF-QUOTA；派工、拆单与评审流程：WF-FLOW。
> **查阅**：先读 WF-MODEL §0；七问看 WF-MODEL §1；Opus 与 Sonnet 的分界看 WF-MODEL §2；机械活看 WF-MODEL §3；推理强度看 WF-MODEL §4；升级、派单与直接做看 WF-MODEL §5；开子代理看 WF-MODEL §6；恢复还是新开看 WF-MODEL §7；简报模板与接续看 WF-MODEL §8。

## 0 结论

1. **按七问选够用的施工模型**（WF-MODEL §1）：先分清未定判断与已定实现；审美相关的不交 GPT。
2. **Opus 只用在观感还没定的地方**（WF-MODEL §2，D-193）：观感已由评审或已批样子定下的可见活交 Sonnet。
3. **机械活交便宜模型**（WF-MODEL §3）：不需要判断的量大、重复的活，交 Sol 会话或它开的 gpt-6-luna 子代理（medium），Claude 侧用 Sonnet medium。
4. **推理强度按难度选**（WF-MODEL §4）：够用就停，Sonnet 只用 medium 与 high，不用 max。
5. **简单少量的活由拿到信息的一方直接做**，不转手（WF-MODEL §5）。
6. **子代理一律新开，靠任务单的"接续"段交接；单子在上下文约 40 万 token 或 150 次请求前交回**（WF-MODEL §7，D-191）。

### 0.1 接入要点

- **写派工简报**：用 WF-MODEL §8 的模板，只填本包特有的信息；入口、守则、回报写在 WF-ENTRY、WF-RULE、WF-COMMS，不抄。
- **交回时**：在任务单"状态"里写"接续"段（WF-MODEL §8.2）。
- **开子代理**：按 WF-MODEL §6；Codex 侧子代理共用工作目录，简报里必须写明邻居（WF-MODEL §8.1）。

## 1 按七问选施工模型

依次看还缺什么判断、结果能否验收、错误会传播多远。混合任务先分清未定判断与已定实现。

| 问题 | 倾向：模型与档位 |
| --- | --- |
| 1. 要定造型、风格、声音、玩家可见参数或内容取舍，或制作可见构件吗？ | 需要审美判断的（造型、风格、观感取值，地标与重点构件，质感移植）由 Opus 子代理施工，主会话定案；只缺判断时主会话直接定。规格、尺寸、色名都已给全的可见活（简单部件、按已定预设填数据、小修）交 Sonnet。审美相关的活不交 GPT，非可见部分可拆出继续问 |
| 2. 必须读图或依赖中文语感判断吗？ | 按检查单读图初筛、中文改写交 Sonnet；可程序测出的数据与截图采集交 Sol。涉及审美回第 1 问；改变原意或含内容取舍时交主会话 |
| 3. 目标、规格和通过条件仍有歧义吗？ | 工程歧义交 Astra，设计与内容歧义交 Opus，定清再派实现；不靠增加推理替代决定 |
| 4. 错误会跨接口、线程、资源寿命或存档扩散吗？ | Astra 定方案、边界与验收条目，施工默认交 Astra 名下的 gpt-6.1-sol 子代理（high 或 xhigh）；它两次做不对或方案本身要改时，Astra 才亲自做关键段 |
| 5. 数学或几何很难，但能由不变量、参考结果验证吗？ | 非审美实现由 Astra 名下 Sol 施工；前提不清或全局耦合，先由 Astra 定清前提。可见构件回第 1 问 |
| 6. 是大量明确执行或事实整理吗？ | Sol 会话；工程子任务由 Astra 派 Sol。确需语言加工时再用 Sonnet |
| 7. 是剩余明确的非审美实现吗？ | 默认 Sol 实现，由相应负责方派单 |

## 2 Opus 与 Sonnet 的分界（D-193）

Opus 贵，只用在观感还没定的地方。

| 默认交 | 活 |
| --- | --- |
| Opus（high；地标与质感移植 xhigh） | 一个包或一类构件的首版造型，还没有已批的样子可照；地标与重点构件；质感移植与新的画面机制；评审里标明"要定""拿不准"的观感取舍 |
| Sonnet high | 调研（业界做法加本项目建议，WF-FLOW §6）；评审已写明怎么改的跟进单；照已批的样子铺到同类；摆放规则、数据与覆盖层登记、树种与预设键；截图采集与重拍；素材收集；文档撰写 |
| Sonnet medium | 按条目填数据、按确切文字打文档补丁 |

- 一张单里混着未定的观感和已定的实现时，把已定的拆出来交 Sonnet，Opus 只做未定的那块。
- Sonnet 的成果在观感上两次评审不过，改派 Opus，不先升推理档。换模型就是新开子代理（WF-MODEL §7）。

## 3 机械活交谁

只做照清单执行、结果能机械核对、出错也不会扩散的活，不做任何判断。Claude 侧不用 Haiku。

- **交谁**：量大、重复、照清单的活（成批替换引用、全仓数据核对与盘点、成批截图与拼图、成批状态整理、按确切文字打文档补丁、重跑 `gen_index.py` 与 `check_docs.py`、按给定参数跑门禁并汇总结果），交 gpt-6-luna 子代理（medium），由 Astra 或 Sol 会话在 Codex 应用里 `spawn_agent` 开（D-212）；主会话手上的这类活写成旁路单派给 Sol 会话（WF-COMMS §5）。Claude 侧要做的交 Sonnet medium。
- **边界**：不判断依赖是否"算满足"，不改写措辞、不补内容，不修代码、不判断失败原因，不评价观感，不改数据只报结果；拿不准就留原样。
- **谁开**：拿到这件杂活的一方直接开（D-190），不转手。GPT 侧的新活一律派进 Codex 应用里开着的会话（D-203）。
- **怎么选**：一次做不对就改派 gpt-6.1-sol medium 或 Sonnet medium，不在原档上重试。等待、轮询、定时重跑交脚本，不占模型。

## 4 推理强度按难度选

每张单按难度选一档，写进派单；每升一档费用和用时都明显上涨，提升越来越小，够用就停。

| 难度 | 例子 | Opus | Sonnet | gpt-6.1-sol |
| --- | --- | --- | --- | --- |
| 简单 | 规格已给全，能按条目验收：填数据、按已定预设接线、单文件小修、查资料与整理、打文档补丁 | 不派 | medium | medium |
| 一般 | 要自己规划实现，能按条目验收：常规部件与建模、普通接线与单测、截图采集 | high（需审美判断的可见构件） | high | high |
| 难 | 判断重，或错误会扩散：地标与重点构件的造型、质感移植、跨包根因，确定性、并发、资源寿命、存档方案，契约方案 | xhigh | 不派，改派 Opus | xhigh |

- 要 Sonnet 开 xhigh 才做得好的活，改派 Opus high。不用 max，施工不用 low。
- 返工沿用原档；同一档两次做不对，先按 WF-MODEL §5 查原因，确实是难度不够才升一档。
- 固定长期会话保持当前有效档：主会话、Astra 主线程、Sol 会话 xhigh，GPT 侧都是普通速度。

## 5 升级、派单与直接做

- **升级先找失败原因**：已明确条目漏做，由原施工者补；接口或生命周期无解交 Astra 定边界；观感和内容争议交 Opus；超量或后半段质量下降按 D-184 拆单（WF-FLOW §2），不用升级模型代替拆单。
- **派单最少写**：目标与验收条目、定案与未定项、独占路径、模型/推理档、必要复核人、升级信号、预计工作量。包内实现路径由施工者规划，只给目标、约束（主线优先、依赖、契约、目录归属、预算）和交付标准，不规定步骤。
- **复核只在需要时叠**：Sol 实现 → Astra 核工程风险；Sol 程序采集 → Sonnet 读图初筛 → Opus 定观感。每张单只列具体风险和对应复核人，小修与纯接线默认不叠。
- **简单少量的活，拿到信息的一方直接做**：每转一次手都要花额度（写简报、对方重读上下文、再回报）；只有量大、要并行、要换模型能力，或归属不在自己手里时才转派。

## 6 怎么开子代理

**各方都适用**：一个包或子包一个子代理；同一时刻一个文件只有一个代理在写，简报写明邻居（WF-FLOW §2.1）；简报按 WF-MODEL §8 模板写，入口由钩子注入（WF-ENTRY §2）；构建、import、烘焙、门禁和截图排队，一次一个（ENG-ARCH §6）。

**Claude 侧**（主会话开）：用 Agent 工具在后台开，指定 `model: "opus"` 或 `"sonnet"` 并给 `name`；子代理的最终回复就是回报。开几个按任务量定，额度紧时少开（WF-QUOTA §2）。

**Codex 侧**（Astra 与 Sol 会话）：用 `spawn_agent`（`task_name` 写包号，`message` 写完整简报）、`wait_agent`、`list_agents`、`send_input`。开几个按任务量定（WF-QUOTA §2）；`~/.codex/config.toml` 里的上限是软件自身的硬限制，照它办。Codex 子代理和主线程共用工作目录，简报里必须写明：只改点名的文件，读写用绝对路径，不碰邻居的文件，提交推送同 WF-RULE §7。

## 7 子代理的生命周期：默认新开，靠任务单交接

每次请求都要重读整段上下文，恢复一个已经很长的子代理去接新活，每一轮都在为旧历史付费，通常比新开一个只读这次需要的文档更贵。

- **默认新开**：同包的下一张子单、新一阶段、无关的活一律新开；交接写在任务单"接续"段（WF-MODEL §8.2）。子代理交回就结束，不待命，不占并发名额。
- **返工也新开**：任务单写明改什么、改哪里。唯一例外是交回几分钟内、原子代理上下文在约 8 万 token 以内的几处小改。
- **上下文封顶**：做到上下文约 40 万 token 或 150 次请求时，把已完成的部分提交推送，余下写进"接续"交回，由新子代理接着做；派单时按这个量拆单。
- **恢复以后先对齐现状**：`git status`、`git log -5`，再核对任务涉及的契约、数据与相关包的新提交，不以记得的旧版本为准。
- **记录**：任务单"派出"行写子代理的名字和类型；回报最后一行的 token 数是交回时的上下文大小。

## 8 简报模板与"接续"段

### 8.1 简报模板

只替换尖括号里的内容，只写本包特有的信息；入口与必守在 WF-ENTRY，守则在 WF-RULE，回报在 WF-COMMS §3.4。

```
你是《电光年华》的子代理，负责 <WP-xx 名称>。你向 <派你的一方> 回报。
主检出 E:\Project\UESTC_RPG，直接改 main；任务单：<绝对路径>；允许改：<路径>。
读 ENG-WP §2 主表里 <WP-xx> 的行，以及任务单。
独占目录：<独占目录>。交付条目：<条目编号>。额度：三角形 <x%>，绘制调用 <y%>。
起读：<按 ENG-WP 起读栏的三档>。
同时在干活的邻居：<名字：在做什么：改哪些路径>（没有写"无"；来源是施工状态活表）。碰到共用边界先发消息问邻居，要改它的文件先停下报派单方。
<本轮的特别说明，可空>
完成后按 WF-ENTRY §2 收尾：自检、截图、提交推送并回报。
```

独占目录、交付条目、额度照本包在 ENG-WP §2 主表的对应栏填写；子包填子包自己的子目录和分到的额度（ENG-WP §3）。

### 8.2 "接续"段

交回时在任务单"状态"里写，只填对下一张子单有用的几行：
- **源与状态**：源提交，已推送还是进行中，沿用了哪些已定约束（评审时间）；
- **接合**：部件装到宿主的哪个面、基点和安装方式；入口接哪一层；唯一的生产方和消费方；
- **重建**：从哪个生成入口、哪份参数或数据重建；有没有本机生成或缓存；
- **证据**：每批截图对应的提交与位姿；是不是沙盒或替身；
- **未完**：下一张子单要补的事，需要哪个包配合；
- **文字载体**：有牌面、题字、门牌的部件或楼，写明写什么字、批准留白的原因、在等什么。
