# WF-COMMS · 交接与通信

> **范围**：本文规定会话之间经哪些文件交接、`.collab` 里文件怎么放、怎么命名和写、任务单与请求文件的格式、契约申请与完成回报的格式、来信怎么发、Codex 会话怎么派活。
> **不在本文**：一个包从派工到评审的各步：WF-FLOW；git 与推送：WF-RULE §7；全员的来信与等待规则：WF-RULE §2–§5；命令行与会话号：`.collab/tools/README.md`。
> **查阅**：先读 §0；三种渠道怎么选看 §4.4；目录与文件看 §1；命名与写法看 §2；任务单、请求文件、契约申请与完成回报看 §3；来信与消息看 §4；Codex 会话与引导信箱看 §5；向作者发通知、挂审计项看 §6。

## 0 结论

1. **经文件交接，消息只在事件发生时发**（§1、§4）：交接目录是 `E:\Project\UESTC_RPG\.collab\`；任务单和请求文件放细节，做到哪只看施工队列（WF-STATUS §2），上下文重置后照队列接着做，对不上以 Git 为准。
2. **任务单与请求文件只追加、不改写，来信一条一个新文件**（§2、§4）。
3. **结案即删**（§1，D-228）：`tasks/<类>/`、`requests/`、`notes/<收件方>/` 下只有在用的；结案的单子、处理完的请求与来信直接删，不归档，不写流水日志。
4. **来信按收件方分收件箱，一条一个文件**（§4，D-207）：开头标【需定】【待审】【知会】，一件事、5 行以内。
5. **来信留档，消息送达**（§4.4）：给 Codex 会话发话先写来信，再发一句消息；不急的排队，要当轮改变对方手上的事才走引导信箱。
6. **完成回报只有一种短头部样式，不超过 8 行**（§3.4）。
7. **作者看项目只看观察台，改了高层信息的人当场用 `post.py` 更新**（§6）。

### 0.1 接入要点

- **写契约申请**：开头用 §3.3 的六行短头部，正文不贴证据。
- **做完交回**：回报照 §3.4，条目只写编号，证据只给路径。
- **给主会话或 Codex 主线发话**：在对方收件箱 `notes/<收件方>/` 新建一个文件；给 Codex 主线的再按 §4.4 发一句消息（排队或引导信箱）。
- **新建任务单或请求文件**：按 §2 命名，确认编号没被占用，不覆盖别人的文件。

## 1 交接目录与文件

**结案即删**（D-228）：

## 2 命名与写法

- 任务单与请求文件只追加、不改写，每条带时间，路径一律写绝对路径；唯一的例外是 `research/INDEX.md` 的"主会话审计"一列（调研子代理标"待审"，主会话审计后改写）。
- **文件名一看就懂**（D-208）：任务单、旁路单、调研、来信、请求文件、截图、提交与子代理名的格式只在 STD-CONVENTIONS §3.8，规范文档的文件名见 STD-DOC §3。
- **编号**：单内步骤写"第 n 步"，不另起字母编号。旁路单与调研的编号各自递增，取 `status/施工状态.md` 开头记的下一个号，用掉就改；调研号看 `research/INDEX.md` 末行；子单在编号后加 a、b。
- **请求文件**：类型是 `contract`、`review`；先确认文件不存在再创建，已有同名时末尾加 `-2`、`-3`。

## 3 任务单、请求文件、契约申请与完成回报

### 3.1 施工单与旁路单

- **施工单**：开头写对应的施工队列行号，正文写 WF-FLOW §2 列的各项，末尾"主会话评审（时间）"由主会话写，通过或逐条修改意见。**状态只在施工队列**（WF-STATUS §2，D-235），任务单不写状态行；给下一张子单的交接写在末尾"接续"段（WF-MODEL §8.2）。
- **旁路单**：正文写在哪做、交付什么、能改什么、不许做什么；末尾"结果"由做这张单的子代理写过程与结果；状态在施工队列的 S 行。

### 3.2 请求文件

正文按 §1 的"写什么"；后续各方只在末尾追加，每条带时间和署名。

### 3.3 契约申请的短头部（D-201）

开头六行写完要主会话或 Codex 主线看的东西，正文不贴证据：
1. 申请什么：改哪份契约或共享件；
2. 为什么：3 行以内，说结果不说过程；
3. 影响哪些包；
4. 要主会话定的事：逐条，没有写"无"；
5. 依赖与时机：没有写"无"；
6. 证据：日志、截图的路径，一行列完。

### 3.4 完成回报

中文，交给派你的一方，不超过 8 行；条目只写编号，不复述内容，证据只给路径：

```
工作包：WP-18（南区）· 提交 <短号>或"未提交"
改动：game/gen/zones/south/**
完成：MAP-QSH-SOUTH §1–§5；未完成：MAP-QSH-SOUTH §6（可选），未做
检查：跑了什么、结果；没跑写"未跑"
截图或可调参数：路径与现值（结果看得见或听得见时）
假设与申请：做过的假设；契约修改申请 <路径>或"无"；需其他包配合的事
```

- 截图存 `output/render-review/`（不进 git），命名格式见 STD-CONVENTIONS §3.8。
- 门禁运行方式与判据见 ENG-GATES-SHOTS §1、ENG-GATES §1。

## 4 来信与消息

### 4.1 什么时候发

**消息只在事件发生时发**，内容一句话，细节都在任务单里；不发进度汇报，不互相轮询；几张单在 10 分钟内先后到待评审时，合成一条消息。

| 方向 | 什么时候发 |
| --- | --- |
| Codex 主线 → 主会话 | 门禁失败、旁路单完成、待评审、受阻需要决定；写进 `notes/claude/` |
| 主会话 → Codex 主线 | 文档改了、契约冻结了、某个包阻塞了、新任务；写进 `notes/codex/`，再按 §4.4 发一句消息 |

### 4.2 一条来信一个新文件（D-207）

- **收件箱只由来信监视清**：带回的信移到 `.collab/tools/state/inbox_wait/delivered/`（留最近 50 封备查），会话不手删收件箱，读过也不删。

写给谁，就在谁的收件箱 `notes/<收件方>/` 新建一个文件，文件名格式见 STD-CONVENTIONS §3.8；时间取真实读数。写完不改，不往别的文件里追加。收件方处理完就删掉这封信，收件箱里只剩没处理的（D-228）。主会话的收件箱由事件等待脚本带回全文后自动删掉。

### 4.3 三级标记与写法

- **三级标记**（D-201）：写给主会话的来信第一行开头标一种：【需定】要主会话拍板（观感、跨两侧的取舍、作者级的事）；【待审】有推送、申请或报告等主会话审；【知会】只是告诉一声。事件等待只为【需定】【待审】和失败、冲突叫醒，【知会】攒着下次一并看。
- **一条只讲一件事，5 行以内**：要点写全，细节放在任务单或请求文件里给路径。
- **太长就精简，不硬塞**：来信、通知、巡逻输出、钩子注入和观察台的字段超过字数或版面时，先删正常项、合并同类、细节改成给路径，换更短的写法；不靠截断把内容塞进去。上限要装得下一件事，明显不够的（如 40 字）放宽到能写全，写的时候照样短。
- **纯工程判断自己定**：Codex 侧能按契约、架构和现有规则判断的工程事，自己定，记一条【知会】，不写成"请主会话决定"。
- **不向作者出选项**：需要确认的事写进任务单或请求文件并通知主会话（WF-RULE §2）。

### 4.4 来信、排队消息与引导信箱

| 渠道 | 是什么 | 什么时候用 |
| --- | --- | --- |
| 来信 `notes/<收件方>/` | 全文，收件方开工时读，处理完删掉 | 每次发话都写，细节都在这里 |
| 排队消息（`codex queue`） | 一句话指向来信，等对方这一轮结束后送到；对方空闲时直接开新一轮 | 不急、不用打断的事；对方空闲时叫醒 |
| 引导信箱（`codex_app_steer.py`） | 一句话，对方下一次调用工具时送进当前这一轮，只送一次 | 要马上改变对方手上的事：方向错了、卡在问题上、新规则要当轮生效（WF-FLOW §3） |

- Codex 主线发给主会话只写来信，由主会话的事件等待脚本带回（§4.2、§4.3）。
- **Codex 主线在跑时**，派活和要它当轮知道的事一律走引导信箱，排队只在它空闲时用。
- 只写了信没发消息的，巡逻会在信超过 15 分钟没处理时提醒主会话补发。

## 5 Codex 会话与引导信箱

**Codex 侧只有 Codex 主线一个会话**（WF-ROLE §1），不用 `codex exec` 另起后台线程。派活和通知都是来信加一句消息（§4.4），用 `tools/agents/codex_app_steer.py`：它在跑就进引导信箱，空闲就排队开新一轮。模型、推理档和速度跟着会话走，在应用里设；会话号见 `.collab/tools/README.md`。

**引导信箱**什么时候用见 §4.4，机制与用法见 `.collab/tools/README.md`。

## 6 作者观察台

**观察台是作者了解项目的唯一入口**（`dashboard/`，架构见其 README，工具见 `.collab/tools/README.md`）。

- **谁改了高层信息，谁在同一个任务里用 `dashboard/tools/post.py` 更新**：主会话、Codex 主线与各方的子代理一视同仁；`--from` 写自己是谁。
- **高层信息是**：需要作者审或定的事（挂审计项）；给作者的通知：阶段变化、重要合入、能试玩的新东西、风险；作者该知道的删除。
- **能由程序读出的一律自动采集，模型不写**：谁在干活（会话、子代理、型号与推理档）、在做的工作、后台脚本与构建锁、健康检查、队列、文档、决策和最近提交，都由采集脚本从权威来源读出；健康检查与巡逻共用一份实现，不另写。模型让观察台"更新"的方式，就是把下面这些结构化位置写对：施工队列表与状态头部的"当前阶段""当前优先级"两行（WF-STATUS §2）、子代理名开头的队列行号（WF-MODEL §6）、任务单开头的行号（§3.1）、来信第一行的标记（§4.3）。post.py 只用来发需要判断才写得出的通知和审计项。
- **写法**：标题与通知一两句、120 字内，理由 200 字内，写全一件事、不凑字；能直接读出的时刻、份数、个数写确切值，测量出来的大量值（代码行、体积）报数量级；细节用 `--link` 指向文件，不抄进来。
- **不用了就结项**：作者看过、定过或失效的审计项用 `post.py done <id>`，通知同理；过期的由工具删。
- **底层细节不进观察台**：代码改动、测试用例、局部 bug 留在任务单和回报里。
