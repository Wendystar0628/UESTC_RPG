# WF-COMMS · 交接与通信

> **范围**：本文规定会话之间经哪些文件交接、`.collab` 里文件怎么放、怎么命名和写、任务单与请求文件的格式、契约申请与完成回报的格式、来信怎么发、Codex 会话怎么派活、向作者的观察台发通知与挂审计项。
> **不在本文**：一项任务从派工到评审的各步：WF-FLOW；git 与推送：WF-RULE §7；全员的来信与等待规则：WF-RULE §4、§5；命令行与会话号：`.collab/tools/README.md`。
> **查阅**：先读 §0；三种渠道怎么选看 §4.4；目录与文件看 §1；命名与写法看 §2；任务单、请求文件、契约申请与完成回报看 §3；来信与消息看 §4；Codex 会话与引导信箱看 §5；向作者发通知、挂审计项看 §6。

## 0 结论

1. **经文件交接，消息只在事件发生时发**（§1、§4）：交接目录是 `E:\Project\UESTC_RPG\.collab\`；任务单和请求文件放细节，做到哪只看施工队列（WF-STATUS §2），上下文重置后照队列接着做，对不上以 Git 为准。
2. **任务单与请求文件只追加、不改写，来信一条一个新文件**（§2、§4）。
3. **结案即删**（§1，DECISION-228）：`tasks/<类>/`、`requests/`、`notes/<收件方>/` 下只有在用的；结案的单子、处理完的请求与来信直接删，不归档，不写流水日志。
4. **来信按收件方分收件箱，一条一个文件**（§4，DECISION-207）：开头标【需定】【待审】【知会】，一件事、5 行以内。
5. **来信留档，消息送达**（§4.4）：给 Codex 会话发话先写来信，由钩子送达；它空闲时再叫醒，要当轮改变它手上的事才走引导信箱。
6. **完成回报只有一种短头部样式，不超过 8 行**（§3.4）。
7. **作者看项目只看观察台，改了高层信息的人当场用 `post.py` 更新**（§6）。

### 0.1 接入要点

- **写契约申请**：开头用 §3.3 的六行短头部，正文不贴证据。
- **做完交回**：回报照 §3.4，条目只写编号，证据只给路径。
- **给主会话或 Codex 主线发话**：在对方收件箱 `notes/<收件方>/` 新建一个文件；Codex 主线空闲时再按 §4.4 叫醒。
- **新建任务单或请求文件**：按 §2 命名，确认编号没被占用，不覆盖别人的文件。

## 1 交接目录与文件

各方经协作目录 `E:\Project\UESTC_RPG\.collab\` 交接。它在主检出里，但登记在本机的 `.git/info/exclude`，不进 git、不推送。

| 路径（相对 `.collab\`） | 谁写 | 写什么 |

**结案即删**（DECISION-228）：
- 单子对应的施工队列行都删了、没有未了的事，派单的一方就删掉这张单：Claude 侧由主会话删，Codex 侧由 Codex 主线删；巡逻会列出对应行都已删的单和没进队列的单。结果在提交、代码、文档和决策登记里；还有后续的，先写进施工队列（WF-STATUS §2）再删。
- 处理完的请求、来信、交出结果的旁路单同样直接删；调研见 WF-STATUS §4.1。
- 任务单只放目标、范围、已定取值、交付标准和评审结论，不记状态和过程流水。

## 2 命名与写法

- 任务单与请求文件只追加、不改写，每条带时间，路径一律写绝对路径；唯一的例外是 `research/INDEX.md` 的"主会话审计"一列（调研子代理标"待审"，主会话审计后改写）。
- **文件名一看就懂**（DECISION-208）：任务单、旁路单、调研、来信、请求文件、截图、提交与子代理名的格式只在 STD-CONVENTIONS §3.8，规范文档的文件名见 STD-DOC §3。
- **编号**：单内步骤写"第 n 步"，不另起字母编号。旁路单与调研的编号各自递增，取 `status/施工状态.md` 开头记的下一个号，用掉就改；调研号看 `research/INDEX.md` 末行；子单在编号后加 a、b。
- **请求文件**：类型是 `contract`、`review`；先确认文件不存在再创建，已有同名时末尾加 `-2`、`-3`。

## 3 任务单、请求文件、契约申请与完成回报

### 3.1 施工单与旁路单

- **施工单**：开头写对应的施工队列行号，正文写 WF-FLOW §2 列的各项，末尾"主会话评审（时间）"由主会话写，通过或逐条修改意见。**状态只在施工队列**（WF-STATUS §2，DECISION-235），任务单不写状态行；给下一张子单的交接写在末尾"接续"段（WF-MODEL §8.2）。
- **旁路单**：正文写在哪做、交付什么、能改什么、不许做什么；末尾"结果"由做这张单的子代理写过程与结果；状态在施工队列的 BATCH 行。

### 3.2 请求文件

正文按 §1 的"写什么"；后续各方只在末尾追加，每条带时间和署名。

### 3.3 契约申请的短头部（DECISION-201）

开头六行写完要主会话或 Codex 主线看的东西，正文不贴证据：
1. 申请什么：改哪份契约或共享件；
2. 为什么：3 行以内，说结果不说过程；
3. 影响哪些模块；
4. 要主会话定的事：逐条，没有写"无"；
5. 依赖与时机：没有写"无"；
6. 证据：日志、截图的路径，一行列完。

### 3.4 完成回报

中文，交给派你的一方，不超过 8 行；条目只写编号，不复述内容，证据只给路径：

```
任务：<施工队列行号与标题>· 提交 <短号>或"未提交"
改动：game/gen/maps/qingshuihe/south/**
新文件：进项目结构的新文件路径与归属（目录或文档树的哪一级），或"无"
完成：MAP-QSH-SOUTH §1–§5；未完成：MAP-QSH-SOUTH §6（可选），未做
检查：跑了什么、结果；没跑写"未跑"
根因：撞到的架构问题与去向（本批已修，或新开的行号），或"无"
截图或可调参数：路径与现值（结果看得见或听得见时）
假设与申请：做过的假设；契约修改申请 <路径>或"无"；需其他施工方配合的事
```

- 截图存 `output/render-review/`（不进 git），命名格式见 STD-CONVENTIONS §3.8。
- 门禁运行方式与判据见 ENG-GATES-SHOTS §1、ENG-GATES §1。

## 4 来信与消息

### 4.1 什么时候发

**消息只在事件发生时发**，内容一句话，细节都在任务单里；不发进度汇报，不互相轮询；几张单在 10 分钟内先后到待评审时，合成一条消息。

| 方向 | 什么时候发 |
| --- | --- |
| Codex 主线 → 主会话 | 门禁失败、旁路单完成、待评审、受阻需要决定；写进 `notes/claude/` |
| 主会话 → Codex 主线 | 文档改了、契约冻结了、某项任务阻塞了、新任务；写进 `notes/codex/`；Codex 空闲时再按 §4.4 叫醒 |

### 4.2 一条来信一个新文件（DECISION-207）

- **两个收件箱都由送达机制清，箱内即未送达**：主会话的信由来信监视带回，Codex 的信由 uestc-steer 钩子在它下一次工具调用后把全文送进当前一轮；送达后移走，各留最近 50 封备查。收件方不手删，读过也不删。子代理不取主线的信；超大的信留在箱里并提示。

写给谁，就在谁的收件箱 `notes/<收件方>/` 新建一个文件，文件名格式见 STD-CONVENTIONS §3.8；时间取真实读数。写完不改，不往别的文件里追加（DECISION-228）。

### 4.3 三级标记与写法

- **三级标记**（DECISION-201）：写给主会话的来信第一行开头标一种：【需定】要主会话拍板（观感、跨两侧的取舍、作者级的事）；【待审】有推送、申请或报告等主会话审；【知会】只是告诉一声。每封信都即时送达、即时读（DECISION-278），标记只说明要不要回，不决定送达快慢。
- **一条只讲一件事，5 行以内**：要点写全，细节放在任务单或请求文件里给路径。
- **太长就精简，不硬塞**：来信、通知、巡逻输出、钩子注入和观察台的字段超过字数或版面时，先删正常项、合并同类、细节改成给路径，换更短的写法；不靠截断把内容塞进去。上限要装得下一件事，明显不够的（如 40 字）放宽到能写全，写的时候照样短。
- **纯工程判断自己定**：Codex 侧能按契约、架构和现有规则判断的工程事，自己定，记一条【知会】，不写成"请主会话决定"。
- **不向作者出选项**：需要确认的事写进任务单或请求文件并通知主会话（WF-RULE §2）。

### 4.4 来信与即时送达

**每封信都即时送达，不排到对方这一轮结束**（DECISION-278）：与对方手上的事无关，读完接着做；有关，正好一起处理，免得做完才发现和新消息对不上。

| 渠道 | 是什么 | 什么时候用 |
| --- | --- | --- |
| 来信 `notes/<收件方>/` | 全文，由送达机制送给收件方（§4.2） | 每次发话都写，细节都在这里 |
| 引导信箱（`codex_app_steer.py`） | 一句话指向来信；Codex 在跑就放进信箱、它下一次调用工具时送进当前这一轮，空闲就直接开新一轮；不等、不撤回改排队 | Codex 空闲时叫醒；在跑但要它当轮就看到的事（插队、方向错了、新规则） |

- Codex 主线发给主会话只写来信；来信监视见到就叫醒主会话，同一阵连发的几封合成一次带回（§4.2）。
- **Codex 主线在跑时**，来信由钩子在它下一次工具调用后送进当前一轮，不用再发提醒。
- **Codex 空闲时**没有工具调用，钩子不会触发，信留在箱里；用 `codex_app_steer.py` 叫醒。
- Codex 空闲而箱里有未送达的信，巡逻会提醒主会话叫醒。

## 5 Codex 会话与引导信箱

**Codex 侧只有 Codex 主线一个会话**（WF-ROLE §1），不用 `codex exec` 另起后台线程。派活和通知都是来信加一句消息（§4.4），用 `tools/agents/codex_app_steer.py`：它在跑就进引导信箱，空闲就直接开新一轮。模型、推理档和速度跟着会话走，在应用里设；会话号见 `.collab/tools/README.md`。

**引导信箱**什么时候用见 §4.4，机制与用法见 `.collab/tools/README.md`。

## 6 作者观察台

**观察台是作者了解项目的唯一入口**（`dashboard/`，架构见其 README，工具见 `.collab/tools/README.md`）。

- **谁改了高层信息，谁在同一个任务里用 `dashboard/tools/post.py` 更新**：主会话、Codex 主线与各方的子代理一视同仁；`--from` 写自己是谁。
- **高层信息是**：请作者过目的审美取向（挂审计项：画面风格、配色、观感取舍这类），已按主会话的判断在做、不挡推进（WF-RULE §2，DECISION-274）；架构、实现、流程与排期不挂给作者；给作者的通知：阶段变化、重要合入、能试玩的新东西、风险；作者该知道的删除。
- **能由程序读出的一律自动采集，模型不写**：谁在干活（会话、子代理、型号与推理档）、在做的工作、后台脚本与构建锁、健康检查、队列、文档、决策和最近提交，都由采集脚本从权威来源读出；健康检查与巡逻共用一份实现，不另写。模型让观察台"更新"的方式，就是把下面这些结构化位置写对：施工队列表与状态头部的"当前阶段""当前优先级"两行（WF-STATUS §2）、子代理名开头的队列行号（WF-MODEL §6）、任务单开头的行号（§3.1）、来信第一行的标记（§4.3）。post.py 只用来发需要判断才写得出的通知和审计项。
- **写法**：写给人看——标题与通知一两句、120 字内，说做成了什么、对作者有什么影响，不写快检、提交哈希、路径、内部环节这类细节；理由 200 字内，写全一件事、不凑字；时刻、份数、个数、代码行与体积一律写确切值；细节用 `--link` 指向文件，不抄进来。
- **作者留言只到主会话**（TOOL-249）：观察台首页的留言框把作者的话写成 `notes/claude/` 里发件方为 `author` 的来信；来信监视见到就立刻叫醒主会话，钩子也在主会话下一次事件整封送到。主会话当轮读、当轮回应，要改什么照常排进施工队列，不转给 Codex 原文，需要它做的写成新来信。
- **不用了就结项**：作者看过、定过或失效的审计项用 `post.py done <id>`，通知同理；过期的由工具删。
- **底层细节不进观察台**：代码改动、测试用例、局部 bug 留在任务单和回报里。
