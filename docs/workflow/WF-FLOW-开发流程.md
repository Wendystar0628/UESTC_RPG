# WF-FLOW · 开发流程

> **范围**：本文规定一个包从派工到评审的流程：派工与拆单、防打架、施工与回报、评审与可调参数、契约申请与共享工程文件、调研入队流水线。
> **不在本文**：包的归属与开工顺序：ENG-WP §1.1、§2；git、推送与回滚：WF-RULE §7；构建与测试排队：ENG-ARCH §6；模型选择与简报：WF-MODEL；文件格式与回报格式：WF-COMMS；队列与状态：WF-STATUS；额度与并发：WF-QUOTA。
> **查阅**：先读 WF-FLOW §0；全流程一览看 WF-FLOW §1；派工、拆单与防打架看 WF-FLOW §2；施工与回报看 WF-FLOW §3；评审与可调参数看 WF-FLOW §4；契约申请看 WF-FLOW §5；调研入队看 WF-FLOW §6。

## 0 结论

1. **一个包按固定顺序走**（WF-FLOW §1，D-211、D-219）：派工 → 施工（只写不编译）→ 回报 → 指挥统一编译、修错、快检 → 提交推送 → 评审（不合格就回滚或派返工单）→ 施工状态；都在主检出 `main` 上。
2. **同一批文件同一时间只有一个写者**（WF-FLOW §2.1）：按独占目录分工，简报写明邻居。
3. **一张单约 2–3 个 Opus 小时**（WF-FLOW §2，D-184）：超过就拆子单，开工 30 分钟内重估。
4. **审美评审由主会话做，推送后评审；可调参数集中放一处**（WF-FLOW §4）。
5. **契约与共享工程文件只由 Astra 改**（WF-FLOW §5）：牵涉画面表现的契约，主会话确认后才冻结（D-134）。
6. **调研走入队流水线**（WF-FLOW §6，D-224）：主会话派 Sonnet 子代理调研 → 审计 → 并入工作包 → 分配 → 入队；Sol 会话只接旁路单。

### 0.1 接入要点

- **开工前和派工前**：`git status` 看谁在改什么，简报写邻居；要改邻居的文件先停下报派单方（WF-FLOW §2.1）。
- **要改契约或共享工程文件**：写 `requests/contract-<包号>-<主题>.md`，不自己改，要早提（WF-FLOW §5）。
- **结果看得见或听得见的包**：可调参数集中放一处，回报里列出位置和现值（WF-FLOW §4）。
- **发现单子超出预估**：停下报给派单方拆单，不靠压缩细节赶完（WF-FLOW §2）。

## 1 全流程一览

| 步 | 谁做 | 产出 |
| --- | --- | --- |
| 1 派工 | 主会话（Opus 侧的包）；Astra（Astra 侧的包） | 任务单 `tasks/claude/<nnn>-<主题>.md`，或 Astra 给子代理的简报；简报写邻居（WF-FLOW §2.1） |
| 2 施工 | 施工子代理，在主检出 `main` 上直接改 | 本包独占目录里的改动；默认不编译、不跑测试、不提交（WF-FLOW §3.1） |
| 3 回报 | 子代理向派它的一方回报（WF-FLOW §3） | 改动路径与要点（WF-COMMS §3.4）；任务单"状态"写待编译 |
| 4 统一编译、提交推送 | 指挥：Astra 管 Astra 侧的包，主会话管 Opus 侧的包 | 一批交回后编译一次、修错、跑快检，按子代理分路径提交并推送（WF-FLOW §3.1、WF-RULE §7） |
| 5 评审 | 主会话管审美与取值；Astra 管契约与架构 | 任务单末尾的"Opus 评审"小节，或请求文件末尾的结论；不合格就 `git revert` 或派返工单 |
| 6 施工状态 | 主会话 | 更新施工状态（WF-STATUS §1） |

## 2 派工与拆单

**从待派工队列派**：调研审计采纳或新决定带来的工作先进待派工队列（WF-FLOW §6、WF-STATUS §2）；按 ENG-WP §1.1 波次开工的包照波次派。主会话按优先级与并发余量（WF-QUOTA）从"可派"条目里派，派出后在条目里写任务单号。建模完成度是主线（D-183）：先派建筑、部件、分区、植被、街道家具、箱庭与室内包，再派游泳、生物、角色本体等系统新功能。

**Opus 侧的包**：主会话写任务单 `.collab/tasks/claude/<nnn>-<主题>.md`，一张单对应一件完整且工作量受控的事。单子写：目标；给子代理的简报（WF-MODEL §8 模板）；Opus 还是 Sonnet 与推理档（WF-MODEL §1–§4）；交付标准（截图、快检）；评审方式；然后直接开子代理（WF-MODEL §6）。派单分批，按 WF-QUOTA 的并发与队列平衡（WF-STATUS §2）。

**Astra 侧的包**：Astra 用 `spawn_agent` 开子代理，简报照 WF-MODEL §8，写明邻居；施工模型按 WF-ROLE §6。

**Sol 会话的任务**：旁路和机械活，主会话写旁路单放进 `side/cards/`，发进 Sol 会话（WF-FLOW §6.1、WF-COMMS §5）；调研由主会话派 Sonnet 子代理做（WF-FLOW §6）。

**按工作量拆单（D-184）**：派工前估工作量，任务单写"预计工作量：约 N 个 Opus 小时"。一张单交给一个子代理，上限约 2–3 个 Opus 小时，大致是一栋地标楼、3–5 栋普通楼、一类部件族或一个系统子功能。
- 超过上限就拆子单，文件名在编号后加 a、b，各自推送、各自评审。同包的子单共用独占目录、按顺序做，上一张评审通过后新开子代理做下一张（WF-MODEL §7）；不同包照常并行。
- **开工 30 分钟重估**：施工子代理开工后 30 分钟内重估，超过约 3 个 Opus 小时就拆单，只交第一张，回报里写拆法。中途发现超出预估同样停下报派单方，不靠压缩细节赶完。

**评审里定下的通用结论（D-199）**：对不止一个包有效的（例如"栏杆立杆不投影"），当天写回对应的规范文档，不只留在任务单里。多包共用的热点文件按包分片（写法见 WF-RULE §10）。

### 2.1 防打架（D-211）

所有人在同一个主检出上写：
- **按独占目录分工**：派前按 `ownership.json` 分，尽量同时派互不冲突的活。
- **简报写邻居**：写"同时在干活的邻居：名字、在做什么、改哪些路径"，来源是 WF-STATUS 活表（模板见 WF-MODEL §8.1）。Claude 子代理派时给 `name`，碰到共用边界先 SendMessage 问邻居；Codex 子代理会互相通信。
- **不动别人的文件**：要改邻居的文件，先停下报派单方。
- **同一批写完再编译**：施工子代理只写不编译，指挥等这一批都交回后统一编译，不会编到别人改了一半的文件（WF-FLOW §3.1）。
- **排队**：编译、import、烘焙、门禁和截图一次只跑一个（ENG-ARCH §6）。

## 3 施工与回报

施工的硬规则在 WF-RULE、WF-BUILD：只改本包独占目录，主线闸口之前只交主线版（WF-RULE §8），推送前由指挥统一编译并跑快检（WF-FLOW §3.1）。回报格式见 WF-COMMS §3.4，交给派你的一方：

| 施工方 | 回报给 | 对方接着做 |
| --- | --- | --- |
| 主会话的子代理 | 主会话 | 核对改动，统一编译、快检、提交推送（WF-FLOW §3.1）；任务单"状态"写"待评审"；主会话看结果和截图，在末尾写评审 |
| Astra 的子代理 | Astra 主线程 | 审代码是否符合架构，统一编译、快检、提交推送（WF-FLOW §3.1）；有可见或可听的结果，另写评审请求 `requests/review-<WP-xx>-<序号>.md` |
| Sol 会话的代码类旁路单 | 主会话 | 同子代理：只写不编译，由主会话统一编译、提交推送（WF-FLOW §3.1） |

### 3.1 统一编译（D-219）

- **子代理只写**：默认不编译、不跑测试、不提交。写完对照 `docs/godot-api/signatures.txt` 和用到的契约源码自查一遍，回报改动路径与要点。
- **例外**：调试类任务（要复现问题、看运行结果、调手感）和简报写明要编译的，子代理自己编译运行，排构建锁（ENG-ARCH §6）。
- **指挥统一编译**：一批子代理交回后，指挥（Astra 或主会话）编译一次，跑本批涉及的包的快检，碰启动、行走、存档加核心专项（WF-RULE §9）。
- **错误谁修**：小的编译错误指挥直接修；某一处错误多或要改设计，派一个修复子代理，简报给出错误清单和涉及的文件。
- **提交**：通过后按子代理分路径提交，`Co-Authored-By` 写实际写代码的模型，然后推送（WF-RULE §7）。

## 4 评审：审美与契约的交叉评审

**评审后置**：统一编译、快检通过就推送，不设推送前的关卡；推送后主会话看截图评审，不合格就 `git revert` 或派返工单。造型、风格还没定的活，先由 Opus 子代理出样、主会话定案再铺开（WF-MODEL §1），这是派活方式，不算关卡。看画面用固定机位截图看一眼，审美以作者的反馈为准（ENG-GATES §2）。

**审美评审由主会话做**，它是风格负责人，评审金样、色板、界面样张和全部画面类截图。
- **任务单的评审**：主会话在单子末尾写"Opus 评审（时间）"：通过，或逐条修改意见。小返工回原子代理的条件见 WF-MODEL §7，否则新开子代理照单子改；改完推送，在"状态"写"已按评审修改"，回到待评审。
- **请求文件的评审**：主会话在评审请求末尾写结论或新值。
- 色值口径见 ART-STYLE。

**可调参数集中放**：Astra 的包有可见或可听的结果时，把可调参数放在一处（数据文件或集中的常量类），评审请求里写明截图或录像路径、参数在哪、现值。主会话评审后在评审文件里写新值，或派人在参数文件里改，改完推送。

**画面相关的契约**由 Astra 起草、主会话确认后才冻结（ENG-ARCH §3）。**Opus 侧的包需要工程支持时**（性能结构、线程、确定性、契约），在 `requests/contract-<包号>-<主题>.md` 或 Astra 的收件箱 `notes/astra/` 里找 Astra。

## 5 契约申请与共享工程文件

- **谁能改**：契约与工程共享件只由 Astra 改，清单见 WF-BUILD §1；WP-00 也由 Astra 做。`docs/` 由主会话改。
- **申请**：任何代理要改这些，写 `requests/contract-<包号>-<主题>.md`（短头部见 WF-COMMS §3.3）。Astra 处理后在文件末尾写结论和对应的提交。
- **提交**：Astra 在主检出直接提交推送；改共享件前告知邻居，改完同批迁完使用方（WF-RULE §10）。
- **冻结**：契约分批冻结：某组契约的真实生产方与使用方在主线上接通、相关核心专项通过后，由主会话宣布冻结这一组，之后只增不改；没冻结的组按申请修改；冻结状态见 WF-STATUS（D-134）。
- **要早**：上游包开工后头几个小时内就把契约申请提上来，免得下游写得太深再返工。

## 6 调研入队流水线

作者给出新任务、要先弄清怎么做时走这条流水线：调研 → 主会话审计 → 更新或新增工作包 → 分配任务 → 入队（WF-STATUS §2），再派子代理施工（D-224）。不经调研、由新决定带来的工作从第 3 步进入。

| 步 | 谁做 | 产出与落点 |
| --- | --- | --- |
| 1 调研 | 主会话按方向派 Sonnet 子代理（high），一个方向一个；每个方向既查业界的成熟做法，也结合本项目现状给建议 | `research/<日期>-r<nnn>-<主题>/` 下各方向报告与 `00-总览.md`（按优先级去重的建议表）；`research/INDEX.md` 标"待审" |
| 2 审计 | 主会话 | 每条建议标采纳（并入 WP-xx 或新增）、暂缓或不采纳，写在总览末尾"Opus 审计"和 INDEX 对应列 |
| 3 更新或新增工作包 | 主会话；大段撰写可派子代理 | 写进 ENG-WP：按归属逻辑定归属（ENG-WP §1.1），排波次 |
| 4 分配任务 | 主会话（审计时一并定） | 拆成两侧任务：Astra 侧管契约、共享接口、引擎与工程机制；Opus 侧管画面、风格、内容、建模与文档；每项写做什么、落哪个包、预计工作量（D-184）、依赖 |
| 5 入队 | 主会话 | 每侧各入一条或一组 Q-nnn，状态"排队"，派往写 Astra 或 Opus 侧，不写"待定" |

入队以后：Astra 侧条目由主会话写进 `notes/astra/` 通知排期，Opus 侧条目按 WF-FLOW §2 派工；依赖满足后改"可派"，派出后写任务单号，完成后移除。

### 6.1 调研与旁路单

- **调研**：主会话直接派 Sonnet 子代理（high），按方向分，一个方向一个，同时跑。简报写背景、方向（每个写为什么现在值得查）和输出目录；派之前先读 `research/INDEX.md` 去重。每个方向的报告都要有两部分：业界的成熟做法（带出处），以及结合本项目现状的建议（归哪个包或建议新包、主线版还是细节阶段、工作量、依赖）。总览写完把 INDEX 标"待审"。
- **三个视角**：制作完整度（内容量、系统与管线覆盖、测试、性能与稳定、存档稳健、本地化、无障碍）；优越性（与同类作品比的长短处、差异化、让人记住的时刻）；玩家体验（上手、节奏、舒适度、操作摩擦、加载等待、手感反馈、重玩理由）。
- **不调研**：本项目是个人实验作品（D-181），不查商店页、上架、宣传、成就、云存档、平台集成；"发布完整度"只看按 OPS-RELEASE 在 GitHub 发整包时的完整与稳健。调研只给建议，观感取舍由主会话定。
- **旁路单** `side/cards/s<nnn>-<主题>.md`：某件事不在主线关键路径上却会占主线时间，或要大量补信息、批量核对数据时，由主会话写，发进 Sol 会话（WF-COMMS §5）；写明在哪做、交付什么、能改什么、不许做什么。Sol 会话做完在末尾"状态"写结果。
