# WF-FLOW · 开发流程

> **范围**：本文规定一项任务从派工到评审的流程：派工与拆单、防打架、施工与回报、评审与可调参数。
> **不在本文**：路径归属：各文档文件头的 paths；阶段：WF-STATUS §1；git 与推送：WF-RULE §7；构建与测试排队：WF-BUILD §4；模型选择与简报：WF-MODEL；文件格式与回报格式：WF-COMMS；队列、状态与调研入队：WF-STATUS；额度与并发：WF-MODEL §9；契约申请与共享工程文件：WF-BUILD。
> **查阅**：先读 §0；全流程一览看 §1；派工、拆单与防打架看 §2；施工与回报看 §3；评审与可调参数看 §4。

## 0 结论

1. **一项任务按固定顺序走**（§1，DECISION-211、DECISION-219）：派工 → 施工（只写；工作树里交回前自编一次）→ 回报 → 指挥统一编译、修错、快检 → 提交推送 → 评审（不合格就派返工单向前修）→ 施工状态；写在哪以简报给的路径为准（§3.1）。
2. **同一批文件同一时间只有一个写者**（§2.1）：按独占目录分工，简报写明邻居。
3. **按范围拆单，不估工时**（§2，DECISION-184、DECISION-232）：一张子单只管一件完整的小功能、一组文件；子代理做到上下文封顶先交已做好的部分，拆后续子单。
4. **审美评审由主会话做，推送后评审；可调参数集中放一处**（§4）。

### 0.1 接入要点

- **开工前和派工前**：`git status` 看谁在改什么，简报写邻居；要改邻居的文件先停下报派单方（§2.1）。
- **结果看得见或听得见的包**：可调参数集中放一处，回报里列出位置和现值（§4）。
- **发现单子比预想的大**（要碰简报外的文件，或做到上下文封顶）：先交已做好的部分，报给派单方拆单，不靠压缩细节赶完（§2）。

## 1 全流程一览

| 步 | 谁做 | 产出 |
| --- | --- | --- |
| 1 派工 | 主会话（Claude 侧的活）；Codex 主线（Codex 侧的活） | 任务单（命名见 STD-CONVENTIONS §3.8，内容格式见 WF-COMMS §3.1），或 Codex 主线给子代理的简报；简报写邻居（§2.1） |
| 2 施工 | 施工子代理，在简报给的路径上写 | 简报允许路径里的改动；默认不编译、不跑测试、不提交（§3.1） |
| 3 回报 | 子代理向派它的一方回报 | 改动路径与要点（WF-COMMS §3.4）；指挥把施工队列对应行改待集成；代码类旁路单同样交 Codex 主线 |
| 4 统一编译、提交推送 | 指挥：Codex 主线管 Codex 侧的活，主会话管 Claude 侧的活 | 核对改动；一批交回后编译一次、修错、跑快检，按子代理分路径提交并推送，提交后删队列行（§3.1、WF-RULE §7） |
| 5 评审 | 主会话管审美与取值；Codex 主线管契约与架构 | 任务单末尾的"主会话评审"小节；Codex 侧有可见或可听的结果，另写评审请求 `requests/review-<队列行号>-<主题>.md`，结论写在其末尾；不合格就派返工单，在最新版本上改 |
| 6 施工状态 | 主会话 | 更新施工状态（WF-STATUS §1） |

## 2 派工与拆单

**从施工队列派**：要做的活先进施工队列（WF-STATUS §2；调研审计采纳的见 WF-STATUS §4）。主会话与 Codex 主线按优先级与并发余量（WF-MODEL §9）从"就绪"的行里派，派出后改进行中、写上谁。

**Claude 侧的活**：主会话写任务单 `.collab/tasks/claude/`（命名见 STD-CONVENTIONS §3.8，内容格式见 WF-COMMS §3.1），一张单对应一件完整、范围受控的事。单子写：目标；给子代理的简报（WF-MODEL §8 模板）；Opus 还是 Sonnet 与推理档（WF-MODEL §1–§4）；交付标准（截图、快检）；评审方式；然后直接开子代理（WF-MODEL §6）。派单分批，按 WF-MODEL §9 的并发与队列平衡（WF-STATUS §2）。

**Codex 侧的活**：Codex 主线用 `spawn_agent` 开子代理，简报照 WF-MODEL §8，写明邻居；施工模型按 WF-ROLE §6。

**旁路单**：旁路和量大的机械活，主会话写旁路单放进 `side/cards/`，交 Codex 主线开子代理做（WF-STATUS §4.1、WF-COMMS §5）；调研由主会话派 Sonnet 子代理做（WF-STATUS §4）。

**按范围拆单（DECISION-184）**：一张单交给一个子代理，只管一件完整的小功能、一组文件，大致是一栋地标楼、1–2 栋普通楼、一类部件族的一部分或一个系统子功能的一块。任务单、简报、回报都不写工时或完成时间估计（WF-RULE §3）。
- 范围大就拆子单，文件名在编号后加 a、b，各自推送、各自评审。改同一批文件的子单按顺序做，上一张评审通过后新开子代理做下一张（WF-MODEL §7）；互不干扰的子单照常并行。
- **做不完先交一半**：施工中发现要碰简报外的文件，或做到上下文封顶（WF-MODEL §7），就先交已做好的部分，回报里写拆法，不靠压缩细节赶完。

**评审里定下的通用结论（DECISION-199）**：对不止一项任务有效的（例如"栏杆立杆不投影"），当天写回对应的规范文档，不只留在任务单里。多个模块共用的热点文件按模块分片（写法见 WF-RULE §10）。

### 2.1 防打架（DECISION-211）

所有人在同一个主检出上写：
- **按独占目录分工**：派前按施工队列的目录和派工简报划定写入边界，尽量同时派互不冲突的活。
- **简报写邻居**：写"同时在干活的邻居：名字、在做什么、改哪些路径"，来源是施工队列的目录与谁两列和巡逻的"正被改着的目录"（模板见 WF-MODEL §8.1）。Claude 子代理派时给 `name`，碰到共用边界先 SendMessage 问邻居；Codex 子代理会互相通信。
- **不动别人的文件**：要改邻居的文件，先停下报派单方。
- **同一批写完再编译**：主检出里的施工子代理只写不编译，指挥等这一批都交回后统一编译，不会编到别人改了一半的文件；工作树里的子代理只编自己那棵树（§3.1）。
- **排队**：见 WF-BUILD §4。

## 3 施工与回报

施工的硬规则在 WF-RULE、WF-BUILD：只改简报允许的路径，主线闸口之前只交主线版（WF-RULE §8），推送前由指挥统一编译并跑快检（§3.1）。回报格式见 WF-COMMS §3.4，交给派你的一方，指挥接着做 §1 的第 4–5 步。

**规则变了马上转向**（DECISION-236）：施工中规则或设计改了（作者新定、评审改值），指挥当轮通知在做的子代理照新规则改：Codex 走引导信箱（WF-COMMS §4.4），Claude 子代理用 SendMessage；已交回的同批返工，不等这批做完再统一改。

### 3.1 统一编译（DECISION-219）

- **子代理只写**：默认不跑测试、不提交；在临时工作树里写代码的交回前在本树普通编译一次（不导入，排构建锁），把编译错误留在交回前；在主检出写的不编译，由指挥统一编译——只把 obj/bin 改到别处挡不住编译往源码目录写生成物（DECISION-313）。交回前对删改符号与签名的自查按 WF-ENTRY 子代理一节的收尾（DECISION-311）。回报改动路径与要点。
- **主会话派的施工写在临时工作树里**：主检出由 Codex 主线编译，Claude 侧写到一半的文件会挂掉它的门禁；主会话派施工前先开 `E:\Project\UESTC_RPG.wt\<队列行号>`（WF-RULE §13），子代理只在那里写，交回后主会话在同一棵工作树编译、快检，就在工作树里提交，`git rebase origin/main` 后推到 `origin main`，不把文件拷回主检出、不手工合并；主检出那一侧推送前照常 `git pull --rebase`，两边改到同一文件由 git 三方合并，冲突当场看见当场解。Codex 主线集成正等着用的数据文件（地形、世界文件的 json）例外：在主检出原地一次写完、校验能解析，不挂编译，也不用等推送。
- **例外**：调试类任务（要复现问题、看运行结果、调手感）和简报写明要编译的，子代理自己编译运行，排构建锁（WF-BUILD §4）。
- **指挥统一编译**：一批子代理交回后，指挥（Codex 主线或主会话）编译一次，按本批改动路径选域跑快检，碰启动、行走、存档加核心专项（WF-RULE §9）。
- **错误谁修**：编译错误、小的断言修正和改引用，指挥自己改；错误多（超过 5 个文件）或要改设计才派修复子代理，简报给出错误清单和涉及的文件。同一问题试了两轮没修好就停（WF-RULE §14）。
- **快检过就推**（DECISION-232）：专项失败怎么分级、阻断的才先修，见 WF-RULE §14。
- **提交**：通过后按完整改动提交，契约改签与使用方同一提交，再推送（WF-RULE §7）。
- **收口结构审计**（DECISION-271）：一批推送完，由另一方派只读子代理审这一批，不自己审自己：Codex 推的由主会话派 Sonnet，主会话推的由 Codex 主线派 gpt-6.1-sol，重难的才派 gpt-6-astra（WF-ROLE §6）。先看这批的改动里有没有机器查不出的补丁（STD-CODE §4 末条）、Godot 原生或已引用库能做却自写的实现（CORE-INDEX §5「先用原生，不重复造轮子」）、后台任务没人等或退出不排空、失败没交到真实接收方（CORE-INDEX §6），再看改到的目录与文档：重复、放错层、孤儿文件、超长文件，以及搬走或删掉目录后文档文件头的 `paths` 里已匹配不到文件的规则。只报有实际后果的问题（会出错、看得见、会误导后来的人），完备性、措辞、风格与只在理论上可能的情形不开行；同一族问题的后续行派生两轮后，再查到的只登记不开行，由主会话判是否收口（DECISION-291）。查实的补丁当场开 TOOL 行插队，归原施工方，修完之前同一模块不开新功能行；破坏架构或数据权威的同样开行，排在队列最前，在最新版本上改，不回滚。结果只进施工队列，不出报告（WF-RULE §16）；派审的一方收到结论时用 `history.py audits` 按行号记一条（查实数与不计数，用法见 `.collab/tools/README.md`），巡逻据此判这批审过没有（DECISION-312）。
- **收口预烘**（DECISION-315）：一批推送完、要改烘焙输入的行都已推送时，主会话按巡逻提醒从 `origin/main` 开干净临时工作树，`UESTC_BAKE_CACHE` 指向主检出的共享缓存，后台跑 `scripts/build/prebake-game.ps1`，附带改动的数据当批收口后删工作树（说明见 ENG-ARCH §4）。缓存没烘就启动，游戏会边玩边整图补烘、明显卡顿；主检出的在途改动不挡预烘。
- **同类失败看规律**（DECISION-296）：一批收口时主会话看失败登记的同类累计，达到条件就开整类排查行（ENG-FAILS §0 第 7 条）。

## 4 评审：审美与契约的交叉评审

**评审后置**：统一编译、快检通过就推送，不设推送前的关卡；推送后主会话看截图评审，不合格就派返工单向前修。造型、风格还没定的活，先由 Opus 子代理出样、主会话定案再铺开（WF-MODEL §1），这是派活方式，不算关卡。看画面用固定机位截图看一眼，审美以作者的反馈为准（ENG-GATES §1）。

**审美评审由主会话做**，它是风格负责人，评审金样、色板、界面样张和全部画面类截图。
- **任务单的评审**：主会话在单子末尾写"主会话评审（时间）"：通过，或逐条修改意见。小返工回原子代理的条件见 WF-MODEL §7，否则新开子代理照单子改；返工在施工队列加一行，改完推送后删行。
- **请求文件的评审**：主会话在评审请求末尾写结论或新值。
- 色值口径见 ART-STYLE。

**可调参数集中放**：Codex 主线的包有可见或可听的结果时，把可调参数放在一处（数据文件或集中的常量类），评审请求里写明截图或录像路径、参数在哪、现值。主会话评审后在评审文件里写新值，或派人在参数文件里改，改完推送。

**契约与共享工程文件**谁改、怎么申请与冻结见 WF-BUILD §3；**画面相关的契约**由 Codex 主线起草、主会话确认后才冻结（ENG-ARCH §3，DECISION-134）。**Claude 侧的活需要工程支持时**（性能结构、线程、确定性、契约），在 `requests/contract-<队列行号>-<主题>.md` 或 Codex 主线的收件箱 `notes/codex/` 里找 Codex 主线。
