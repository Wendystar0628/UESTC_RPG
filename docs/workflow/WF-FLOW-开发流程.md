# WF-FLOW · 开发流程

> **范围**：本文规定一个包从派工到评审的流程：派工与拆单、防打架、施工与回报、评审与可调参数。
> **不在本文**：包的归属与开工顺序：ENG-WP §1.1、ENG-WP-LIST §1；git、推送与回滚：WF-RULE §7；构建与测试排队：WF-BUILD §4；模型选择与简报：WF-MODEL；文件格式与回报格式：WF-COMMS；队列、状态与调研入队：WF-STATUS；额度与并发：WF-MODEL §9；契约申请与共享工程文件：WF-BUILD。
> **查阅**：先读 §0；全流程一览看 §1；派工、拆单与防打架看 §2；施工与回报看 §3；评审与可调参数看 §4。

## 0 结论

1. **一个包按固定顺序走**（§1，D-211、D-219）：派工 → 施工（只写不编译）→ 回报 → 指挥统一编译、修错、快检 → 提交推送 → 评审（不合格就回滚或派返工单）→ 施工状态；都在主检出 `main` 上。
2. **同一批文件同一时间只有一个写者**（§2.1）：按独占目录分工，简报写明邻居。
3. **一张子单 1 小时内做完**（§2，D-184、D-232）：超了先交已做好的部分，拆后续子单。
4. **审美评审由主会话做，推送后评审；可调参数集中放一处**（§4）。

### 0.1 接入要点

- **开工前和派工前**：`git status` 看谁在改什么，简报写邻居；要改邻居的文件先停下报派单方（§2.1）。
- **结果看得见或听得见的包**：可调参数集中放一处，回报里列出位置和现值（§4）。
- **发现单子超出 1 小时**：先交已做好的部分，报给派单方拆单，不靠压缩细节赶完（§2）。

## 1 全流程一览

| 步 | 谁做 | 产出 |
| --- | --- | --- |
| 1 派工 | 主会话（Opus 侧的包）；Codex 主线（Codex 侧的包） | 任务单 `tasks/claude/<nnn>-<主题>.md`，或 Codex 主线给子代理的简报；简报写邻居（§2.1） |
| 2 施工 | 施工子代理，在主检出 `main` 上直接改 | 本包独占目录里的改动；默认不编译、不跑测试、不提交（§3.1） |
| 3 回报 | 子代理向派它的一方回报（§3） | 改动路径与要点（WF-COMMS §3.4）；指挥把施工队列对应行改待编译 |
| 4 统一编译、提交推送 | 指挥：Codex 主线管 Codex 侧的包，主会话管 Opus 侧的包 | 一批交回后编译一次、修错、跑快检，按子代理分路径提交并推送（§3.1、WF-RULE §7） |
| 5 评审 | 主会话管审美与取值；Codex 主线管契约与架构 | 任务单末尾的"Opus 评审"小节，或请求文件末尾的结论；不合格就 `git revert` 或派返工单 |
| 6 施工状态 | 主会话 | 更新施工状态（WF-STATUS §1） |

## 2 派工与拆单

**从施工队列派**：要做的活先进施工队列（WF-STATUS §2；调研审计采纳的见 WF-STATUS §4）；按 ENG-WP §1.1 波次开工的包照波次派。主会话与 Codex 主线按优先级与并发余量（WF-MODEL §9）从"可派"的行里派，派出后改进行中、写上谁。建模完成度是主线（D-183）：先派建筑、部件、分区、植被、街道家具、箱庭与室内包，再派游泳、生物、角色本体等系统新功能。

**Opus 侧的包**：主会话写任务单 `.collab/tasks/claude/<nnn>-<主题>.md`，一张单对应一件完整且工作量受控的事。单子写：目标；给子代理的简报（WF-MODEL §8 模板）；Opus 还是 Sonnet 与推理档（WF-MODEL §1–§4）；交付标准（截图、快检）；评审方式；然后直接开子代理（WF-MODEL §6）。派单分批，按 WF-MODEL §9 的并发与队列平衡（WF-STATUS §2）。

**Codex 侧的包**：Codex 主线用 `spawn_agent` 开子代理，简报照 WF-MODEL §8，写明邻居；施工模型按 WF-ROLE §6。

**旁路单**：旁路和量大的机械活，主会话写旁路单放进 `side/cards/`，交 Codex 主线开子代理做（WF-STATUS §4.1、WF-COMMS §5）；调研由主会话派 Sonnet 子代理做（WF-STATUS §4）。

**按工作量拆单（D-184）**：派工前估工作量，任务单写"预计工作量：约 N 小时"。一张单交给一个子代理，上限 1 小时，大致是一栋地标楼、1–2 栋普通楼、一类部件族的一部分或一个系统子功能的一块。
- 超过上限就拆子单，文件名在编号后加 a、b，各自推送、各自评审。同包的子单共用独占目录、按顺序做，上一张评审通过后新开子代理做下一张（WF-MODEL §7）；不同包照常并行。
- **超过 1 小时先交一半**：施工子代理开工后 30 分钟内重估，预计超过 1 小时就只做第一块，回报里写拆法；做到 1 小时还没完，先交已做好的部分。中途发现超出预估同样停下报派单方，不靠压缩细节赶完。

**评审里定下的通用结论（D-199）**：对不止一个包有效的（例如"栏杆立杆不投影"），当天写回对应的规范文档，不只留在任务单里。多包共用的热点文件按包分片（写法见 WF-RULE §10）。

### 2.1 防打架（D-211）

所有人在同一个主检出上写：
- **按独占目录分工**：派前按 `ownership.json` 分，尽量同时派互不冲突的活。
- **简报写邻居**：写"同时在干活的邻居：名字、在做什么、改哪些路径"，来源是施工队列的目录与谁两列和巡逻的"正被改着的目录"（模板见 WF-MODEL §8.1）。Claude 子代理派时给 `name`，碰到共用边界先 SendMessage 问邻居；Codex 子代理会互相通信。
- **不动别人的文件**：要改邻居的文件，先停下报派单方。
- **同一批写完再编译**：施工子代理只写不编译，指挥等这一批都交回后统一编译，不会编到别人改了一半的文件（§3.1）。
- **排队**：编译、import、烘焙、门禁和截图一次只跑一个（WF-BUILD §4）。

## 3 施工与回报

施工的硬规则在 WF-RULE、WF-BUILD：只改本包独占目录，主线闸口之前只交主线版（WF-RULE §8），推送前由指挥统一编译并跑快检（§3.1）。回报格式见 WF-COMMS §3.4，交给派你的一方：

| 施工方 | 回报给 | 对方接着做 |
| --- | --- | --- |
| 主会话的子代理 | 主会话 | 核对改动，统一编译、快检、提交推送（§3.1），提交后删队列行；主会话看结果和截图，在任务单末尾写评审 |
| Codex 主线的子代理 | Codex 主线 | 审代码是否符合架构，统一编译、快检、提交推送（§3.1）；有可见或可听的结果，另写评审请求 `requests/review-<WP-xx>-<序号>.md` |
| 代码类旁路单 | Codex 主线 | 同子代理：只写不编译，由 Codex 主线统一编译、提交推送（§3.1） |

**规则变了马上转向**（D-236）：施工中规则或设计改了（作者新定、评审改值），指挥当轮通知在做的子代理照新规则改：Codex 走引导信箱（WF-COMMS §4.4），Claude 子代理用 SendMessage；已交回的同批返工，不等这批做完再统一改。

### 3.1 统一编译（D-219）

- **子代理只写**：默认不编译、不跑测试、不提交。写完对照 `docs/godot-api/signatures.txt` 和用到的契约源码自查一遍，回报改动路径与要点。
- **例外**：调试类任务（要复现问题、看运行结果、调手感）和简报写明要编译的，子代理自己编译运行，排构建锁（WF-BUILD §4）。
- **指挥统一编译**：一批子代理交回后，指挥（Codex 主线或主会话）编译一次，跑本批涉及的包的快检，碰启动、行走、存档加核心专项（WF-RULE §9）。
- **错误谁修**：编译错误、小的断言修正和改引用，指挥自己改；错误多（超过 5 个文件）或要改设计才派修复子代理，简报给出错误清单和涉及的文件。同一问题试了两轮没修好就停（WF-RULE §14）。
- **快检过就推**（D-232）：专项失败怎么分级、阻断的才先修，见 WF-RULE §7。
- **提交**：通过后按子代理分路径提交，`Co-Authored-By` 写实际写代码的模型，然后推送；超过 2 小时没推送，先推已通过的部分（WF-RULE §7）。

## 4 评审：审美与契约的交叉评审

**评审后置**：统一编译、快检通过就推送，不设推送前的关卡；推送后主会话看截图评审，不合格就 `git revert` 或派返工单。造型、风格还没定的活，先由 Opus 子代理出样、主会话定案再铺开（WF-MODEL §1），这是派活方式，不算关卡。看画面用固定机位截图看一眼，审美以作者的反馈为准（ENG-GATES §1）。

**审美评审由主会话做**，它是风格负责人，评审金样、色板、界面样张和全部画面类截图。
- **任务单的评审**：主会话在单子末尾写"Opus 评审（时间）"：通过，或逐条修改意见。小返工回原子代理的条件见 WF-MODEL §7，否则新开子代理照单子改；返工在施工队列加一行，改完推送后删行。
- **请求文件的评审**：主会话在评审请求末尾写结论或新值。
- 色值口径见 ART-STYLE。

**可调参数集中放**：Codex 主线的包有可见或可听的结果时，把可调参数放在一处（数据文件或集中的常量类），评审请求里写明截图或录像路径、参数在哪、现值。主会话评审后在评审文件里写新值，或派人在参数文件里改，改完推送。

**契约与共享工程文件只由 Codex 主线改**，申请与冻结见 WF-BUILD §3；**画面相关的契约**由 Codex 主线起草、主会话确认后才冻结（ENG-ARCH §3，D-134）。**Opus 侧的包需要工程支持时**（性能结构、线程、确定性、契约），在 `requests/contract-<包号>-<主题>.md` 或 Codex 主线的收件箱 `notes/codex/` 里找 Codex 主线。
