# WF-RULE · 全员守则

> **范围**：本文是所有会话和子代理共同遵守的规则，每条只在这里写一份；其他文档和入口只写"见 §n"。
> **不在本文**：角色分工与决定权：WF-ROLE；来信与任务单的格式：WF-COMMS；改哪里：WF-BUILD；文档怎么写：STD-DOC；派工一侧的防打架（独占目录、邻居栏）：WF-FLOW §2.1，执行者一侧的防打架见本文 §10；构建与测试排队：WF-BUILD §4；角色独有的必守：WF-ENTRY。
> **查阅**：先读 §0；每节自成一条：不过度工程化看 §1，不向作者出选项看 §2，不预判时间看 §3，不干等与不重复复核看 §4，来信看 §5，文件操作看 §6，git 与推送看 §7，主线优先看 §8，测试最小看 §9，少和别人打架看 §10，拿不准就问看 §11，写文档与记忆看 §12，一次性产物看 §13，bug 怎么分级看 §14，精度、数值和检查的分寸看 §15。

## 0 结论

守则共 16 节，每节一条，节标题就是条目名；顶层规则 CORE-INDEX §2、§3 的细则在这里，其余各节的细则在各条括号所指的文档。

### 0.1 接入要点

- **派任何单、写任何简报**：不抄本文，只写"见 §n"；简报里的规则副本会漂移。

## 1 不过度工程化（DECISION-201）

本项目是作者的个人实验作品，不是商业交付级项目；作者不看证据链，多写的每一行都在白花额度。
- **不写**：证据溯源、来源链、哈希或校验和、proof、verification、attest 一类的脚本与报告，handoff 证据目录，逐字节证明，额外的审计报告。构建和生产代码里本来就要用的摘要照常写。
- **不自己加**：门禁、检查脚本、测试脚手架、全量回归、重复构建；指挥给门禁新加规则，也要有 fail.py 登记过的逃逸失败作依据（DECISION-291）。只跑任务单要求的检查，默认是 `gate.ps1` 的快检；觉得需要更多检查，先写一条【需定】问主会话。
- **为看不出的差别换算法也是过度工程化**（DECISION-289）：例如为消灭看不见的浮点缝，把扫掠构造改成大数、有理数的精确运算。这类方案不立项，已有的候选与记录删净。
- **回报从简**：照 WF-COMMS §3.3、§3.4 的短头部，证据只给路径。

## 2 不向作者出选项

主会话以外的所有会话和子代理，都不给作者出选项或确认框，不用 AskUserQuestion 一类的工具，也不在终端里停下等作者选择。
- 需要确认、拿不准、要拍板的事，写进来信或请求文件并通知主会话（Codex 主线在 `notes/claude/` 新建来信，格式见 WF-COMMS §4；子代理交给派它的一方转达）。
- 主会话能据项目信息判断的直接定；只有属于作者的决定才转问作者。只有主会话转达"作者已定"的，才算作者的决定。
- **属于作者的只有审美取向**（DECISION-274）：画面风格、配色、观感与氛围的取舍；架构、实现方法、流程、排期与工程取舍都由两位指挥定，不转问作者。转给作者的也不挡推进：主会话先按自己的判断定下、照常施工，挂成观察台的审计项请作者过目，作者看过再按反馈调；没看也照常往下做。

## 3 不预判时间

模型凭推理感知时间，误差很大：不估"已经用了多久""还要多久"，回报、评审和流水里不写预计完成时间，只写做到哪一步。
- 要用时间时以真实读数为准：命令输出、文件时间戳、额度读数；时长用两次真实读数相减。手边没有真实时间就只写日期，不凭推理填，也不为写时间戳频繁读时钟。
- 任务单、简报、调研报告、来信与对作者的回复都不写工时或完成时间估计；单子大小按范围定（WF-FLOW §2，DECISION-184）。
- **定期的事按开发节点触发**：集中测试、全图预烘、复拍、阶段评审这类定期做的事，按一批收口、阶段收尾这样的开发节点触发，不写每天、每周；作者的开发时间不固定。

## 4 不短轮询、不干等、不重复复核

- **等命令**：能前台一次跑完的前台跑（单次最长 10 分钟）；必须放后台的，隔几分钟查一次日志或进程，进程没了就直接读结果往下做，不等完成通知，通知可能送不到。轮询间隔不短于 2 分钟，不连续反复读同一份日志。
- **每次被叫醒只读与这次事件有关的文件**，不重读已完成的任务单。
- **不重复复核**：已推送、已复核通过的事项，没有新输入（新提交、新基线、新条件）就不再复核，也不再回"已核"；收到提醒时先看有没有新输入，没有就一行写"无新输入，沿用 <时间> 的结论"。门禁同一组合只跑一次（ENG-GATES §1）。

## 5 来信

来信的写法、三级标记和收件箱只在 WF-COMMS §4。

## 6 文件操作

对所有会话和子代理都适用（DECISION-149–DECISION-152）：
1. **下载**：需要的引擎、SDK、素材、文档直接下载，不必请示；只用官方或可信来源，下完说明下了什么、多大、放在哪。第三方代码与插件、音频素材的许可与登记见 ENG-LICENSE §2。
2. **临时文件**：放会话临时目录或不进 git 的 `output/`，不放进源码和文档目录。
3. **删除**：能不删就不删；要删只用绝对路径、只删具体文件，不用通配符或相对路径，不写 `cd X; … rm …`（`cd` 失败后删除会落到当前目录）。复制文件时复制来的 `.uid` 也按绝对路径逐个删。
4. **路径与格式**：一律用绝对路径，命令行参数里的也一样；新建文本文件用 UTF-8 和 LF，保持原有换行风格。
5. **只改分派给自己的文件**：别的代理正在改的不碰。
6. **含反斜杠的文本与脚本**：Windows 路径、正则和含反斜杠的 Python、JS，先用 Write 写成文件再用（往 `.collab` 追加时 `cat 临时文件 >> 目标`），不内联在 heredoc、printf 或 `-c`、`-e` 里，反斜杠会被转义吃掉；写完用 grep 核一下确实落进去了。

## 7 git 与直接改主线（DECISION-211）

- **写在哪以派单简报的路径为准**：Codex 侧在主检出 `E:\Project\UESTC_RPG` 的 `main` 上改，Claude 侧的施工在简报指定的临时工作树（WF-FLOW §3.1，工作树见 §13）；都不另开本地分支。
- **只提交自己的文件**：`git add <自己改的文件>`，不用 `-A` 和 `.`；提交带路径 `git commit -- <路径>`，以免带走别人暂存的东西；碰到 `index.lock` 就等几秒重试。
- **提交按完整改动切**（DECISION-268）：队列行只是派工单位，何时提交、切成几次由施工方按工作状态定；每次提交是一个完整的改动，单独编得过、一句话说得清；一行可以分几次提交，几行合成一个改动就提交一次，首行写全部涉及的行号（`GAME-209/GAME-210 …`）；契约改签与它的全部使用方在同一个提交里。
- **只推自己的提交**：主检出由两侧共用，`git push` 会把别人已提交、还没推的提交一起推出去，对方就没了推前补测和修正的机会。推前跑 `git log --oneline origin/main..main`，只有自己的提交才推；有别人的，先来信问对方能否一起推，或等它推完再推。
- **编译与快检通过才推送**：流程见 WF-FLOW §3.1，快检和专项见 §9；只提交编译通过的东西，专项失败按 §14 分级，只是一般或轻微的 bug 时照样先推送，阻断的先修。超过 2 小时没推送，先推已通过的部分，其余留在工作区。提交首行的格式见 STD-CONVENTIONS §3.8（行号取自施工队列，WF-STATUS §2），结尾 `Co-Authored-By` 写实际执行的模型。
- **不动别人的文件**：要改邻居的文件，先停下报派单方（WF-FLOW §2.1）。
- **出了问题向前修，不回滚**（DECISION-279）：主线上同时有两位指挥和多个子代理在改，回滚一个提交会打乱别人基于它的在途改动、各方难以对齐；推送后发现问题，就开行插队、在最新版本上改。也不用 `reset --hard`、`checkout .`、`clean`、`git stash`，它们会毁掉或卷走别人还没提交的改动。
- **推送被拒就停下**，报派单方；不强推，不改写历史。
- **远端**：`origin` 是 GitHub 上的 `Wendystar0628/UESTC_RPG`，只有 `main` 和里程碑标签；不开 PR，不推别的分支。

## 8 主线优先（DECISION-168）

- 主线的定义见 PRD-SCOPE §3。主线闸口（WF-STATUS §1）通过之前，每项活只交主线版：能接进主线、跑得通、不崩、不挡路。
- **主线版可以**：用简化几何或体块、默认参数、占位贴图与占位声音；只做默认状态和最常见的组合；跳过边角情况。
- **主线版不可以**：改动或绕开契约、数据格式和目录归属；留临时接口；违反 INV（PRD-INVARIANTS）；只有 INV-11 的细节密度和 INV-12 的性能数值留到主线闸口之后验收。
- **不为细节阻塞推送**：细节问题写进回报，留到主线闸口之后统一处理；核心体验（主线流程、行走、存档、画面没有明显卡顿）的问题优先修。

## 9 测试最小（DECISION-167）

- **只做认为最有必要的测试**：时间花在实现上，不按上架游戏的标准测。经常跑、几乎从不失败的检查不该每次跑；不为一批改动堆测试。
- 推送前由指挥统一编译后跑几分钟的快检（WF-FLOW §3.1）；改动碰到启动、行走、存档时加跑对应的核心专项；其余测试全部留到大量开发之后集中测一次，由主会话发起。排队规则见 WF-BUILD §4，判据与命令见 ENG-GATES §1。
- **不重跑**：同一组改动上次门禁全过、之后没改相关文件，不再原样重跑。
- **没用的测试直接删**（DECISION-290）：不守契约、核心体验或回归的测试，比如只查内部形态（闭合、流形）、精度高过看得出的那一级、断言永远为真或钉死实现的，见到就删，不放宽了留着。
- **新增测试有门槛**：测试只为守契约、守核心体验、守回归三种理由而写，派单默认写"不新增测试"；预算与写法见 ENG-GATES §1.1、STD-CODE §6（DECISION-246）。
- 开发中用 `--pose` 截图看效果不算门禁；只改文档的不跑门禁，跑 `check-docs.py`。测试代码怎么写见 STD-CODE §6。

## 10 少和别人打架（DECISION-199）

大家在同一个主检出上写，碰的公共文件越多，互相覆盖和返工越多。
- **开工和被恢复时先看谁动了什么**：先 `git status`、`git log -5`，再读简报里的邻居栏；之后每开始下一步之前，别人动了你要碰的文件就先停下问。
- **动可能撞车的事之前先看一眼对方**（DECISION-275）：两位指挥与各自的子代理在同一个主检出与同一套协作文件上并行，下面这些动作先看对方最近的来信、在做的行、未提交与未推送的改动和构建锁（`python -I -X utf8 .collab/tools/watch/peek.py` 一次列出，钩子在动手时提醒），撞上了先写信约定先后：
  - **改施工队列**：在同一次读改写里现读"下一个编号"和对方在做的行，断言要用的号没被占用，替换编号失败就报错（WF-STATUS §2）。
  - **改共享文件**（`scripts/gates/shader-whitelist.json`、`third_party.json`、`docs/ROUTES.json` 与 `SECTIONS.md` 的生成、钩子与巡逻脚本、观察台数据契约、契约源码）：先看对方的未提交改动和最近来信里有没有它；有就约定谁先改，另一方等对方推送后再动。
  - **在主检出提交、推送、变基、合并或检出**：先看 `git status` 里对方的暂存与未提交改动、`git log origin/main..main` 里对方未推送的提交；只带自己的路径，对方有在途改动时不变基、不检出、不用暂存（stash）（§7）。
  - **跑重活**（收口预烘、固定机位截图、门禁、编译）：先看构建锁和主检出 `game/` 下有没有对方的在途改动；对方在集成就等它推送（WF-BUILD §4）。
  - **起停后台进程**（常驻采集、本地服务、来信监视）：先看是谁起的、对方是否在依赖；只停自己起的，按进程号停，不按窗口标题或进程名成批结束。
  - **删文件、目录与工作树**（一次性产物、任务单、交接文件）：先看对方的任务单和来信有没有引用它（§6、§13）。
  - **改对方在用的接口或数据格式**：先写信，等回信或同批改，不先改后通知。
- **只往自己的文件里加**：多个模块共用的数据只加本模块条目，世界文件按区、按内容分文件（STD-CONVENTIONS §3.1）；改动只落在简报允许的路径。
- **测试只锁本模块自己的输出**，以及"原有条目的字节与顺序不变"；不锁别的模块会合法增减的全局集合与指纹。
- **改架构或实现新设计时，一次迁完、不留旧的（DECISION-209）**：改的一方在同一批改动里把所有使用方迁到新设计，删掉旧设计、旧代码、旧测试和旧文档，禁止新旧多套并存；推送前跑全仓 G2，回报里列出迁了哪些使用方。下游文件正被别人改着时也不写过渡兼容层：等对方交回后一次迁完，或把迁移并给同一个人；牵涉下游包归属的先找 Codex 主线定迁移方案。已冻结的契约组按 WF-BUILD §3 申请。
- **小步交付**：小步提交，测完就推；一块能独立成立的先推，不攒大批。
- **评审定下的通用规则以规范文档为准**：开工时按文档做；决策编号（DECISION-nnn）由主会话统一分配，需要新决策在回报里提。

## 11 拿不准就问

- 会改动契约、数据格式或目录归属的，停下来问主会话；不影响这些的，按最保守的理解做，并在回报里写明假设。
- 文档之间冲突，或文档与 REG-DECISIONS 不一致：按 STD-DOC §6 的层级判定；判定不了的报主会话，不自己改文档。

## 12 写文档与记忆

文档怎么写见 STD-DOC §4；记忆只留偏好与原因和指向，不抄规则。写文档也费输出额度：先列要点，再展开。

## 13 一次性产物（DECISION-221）

- **用完就删**：日志、测试输出、临时脚本、调试截图都是一次性产物；回报要引用的留到评审结束，其余在交回前删掉自己的。
- **放对地方**：临时脚本和中间结果放系统临时目录（Claude 用会话的 scratchpad），测试写的临时文件也放系统临时目录并在结束时删；必须落在仓库里的生成物只进 `output/`。
- **长期保留的目录**以 `scripts/build/clean-artifacts.py` 为准；给作者看的页面做成观察台的面板，不另出报告页。
- **会一直增长的由产出方封顶**：日志、状态与存档类文件由写它的工具自己限大小或按时间删，不靠人清。
- **临时工作树**：主会话派的施工、统一编译、快检和要边改边看画面的视觉样板用（WF-FLOW §3.1），一律由主会话开在 `E:\Project\UESTC_RPG.wt\<行号或用途>`，把路径写进简报，不用 Agent 工具自带的独立工作树（它开在别处）；开好后可从主检出拷入导入缓存 `game/.godot`，省掉完整导入；用完就 `git worktree remove`。巡逻和观察台列出全部登记着的工作树，不在这个目录的、失效的、久没动的都会提醒。
- **统一清理**：`python -I -X utf8 scripts/build/clean-artifacts.py` 列出可删项（范围与过期口径见脚本开头），加 `--delete` 删除；主会话和 Codex 主线每个任务结束时跑一次，巡逻发现可删项会提醒。

## 14 按严重程度修 bug（DECISION-223）

- **修之前先登记**：交回或集成之后抓到的游戏本体失败，先按 ENG-FAILS 登记类别再动手；登记不算修复，也不替代下面的分级。
- **设计和修问题都先参考同类主流游戏**：设计新机制或系统，先查相关同类主流游戏的做法再定；流式加载、LOD 跳变、浮点精度、z-fighting、碰撞穿透这类经典问题，先查引擎文档、Godot 的现成机制和同类主流游戏的通行做法，有标准做法就借鉴，回报里写一句借鉴了什么；不自己发明一套补丁。
- **先查架构再动手**：工程问题先找它在架构里的根因——职责放错了层、同一数据有两份权威、依赖方向反了、接口不合用、生命周期或数据流不对——在根上改；不加特例、开关、兼容层、兜底或绕过，修法以后续开发更省事为准。根因在别人的包里就写清问题、改法和影响，派单修掉（WF-ROLE §6），不在自己这边糊过去。
- **问题越大越要根治（DECISION-209）**：职责放错层、设计有根本缺陷这类大问题，越大越必须按正确方案改到底；工作量大不是打补丁、加过渡层、先凑合或往后推的理由。一次做不完就报主会话拆成队列行，按顺序做完；每一步合入的都是新设计本身，不合入为过渡而写、以后要删的代码。
- **撞到架构问题先治理，不带补丁推送**（DECISION-271）：施工中发现本单的正确做法要先改架构，量小就当批在根上改；量大就停下本行，报指挥开 TOOL 行排在本行之前，本行改成等前置，不先绕过去把本行做完。可以带着登记过的缺陷推送（下面的分级），不能带着掩盖缺陷的代码推送；补丁的各种形态见 STD-CODE §4。回报、提交信息和来信里写到的遗留问题都带施工队列里的行号，开不出行的当批修掉。
- **先查是不是全局问题**：动手前先问同样的写法、同类数据或同一机制在别处有没有——grep 同类代码与数据，文档按索引查同主题的各份（STD-DOC §4.2）；有就同一批修齐，修不到的同批登记派单；回报写一句查了哪些、共修几处（DECISION-257）。跨单反复出现的同类失败由主会话按失败登记开整类排查（ENG-FAILS §0，DECISION-296）。
- **先分级**：
  - **阻断**：挡住启动、进出、行走、存档等核心体验，或破坏核心架构与数据（契约、存档格式、确定性）；当场修，修好再推送。
  - **一般**：局部出错、少数位置表现不对、非核心功能不可用；先提交推送，回报里写明，由指挥登记待修，另派子代理或排到后面。
  - **轻微**：观感小瑕疵、罕见的边界情况；只登记，集中测试时一起修。
- **不让小 bug 挡住大家**：一批改动只差一般或轻微的 bug 时先提交推送，提交信息和回报里写明已知问题及其行号；编译不过和阻断的不在此列。核心专项失败同样先分级，不设"某项全过才交"的关卡（DECISION-232）。
- **修不收敛就停**：同一个问题试了两轮还没修好，就停下写清现象和试过的办法；阻断的交派单方，非阻断的登记后去做别的。指挥和子代理都一样。

## 15 精度按 demo 阶段定（DECISION-225、DECISION-231、DECISION-290）

- **现在处于 demo 阶段**：精度、容差、样本量、测试和验收按这个阶段的需要定，不照上线大型游戏的标准；画面和玩法的追求不因此降低。定阈值、精度或检查之前先问：现在的画面看得出差别吗？看不出就放宽到看得出的那一级。碰撞和画面差几厘米、远处一处小瑕疵、偶尔掉一帧都可以接受；不为精度写整图预算、复杂机制或长时间检查，一次专项几分钟内跑完。
- **不要求全局高精度**（DECISION-290）：建模细节决定观感，照画面要求做，不在这里简化。简化的是精度处理方式：拼接、交会与接缝用最简单的合理做法，互相穿插、略有重叠、几厘米误差都行，不求精确交点、处处闭合。看不见的部分（被挡住的面、实体内部）和行走很少走到或走不到处的碰撞极简处理，一个平面、一道空气墙就够；看得见的外观照 INV-11 处处达标，旁观能飞到的地方也算。外面看着基本没问题、做法不引入技术债务也不破坏架构的建模，不管内部形态（闭合、流形、内部穿插）：看不见的建模、够不到的内容不挡推进，门禁不以内部形态判失败，只查内部形态的测试直接删（§9）。已做好的精度实现不删、不返工。代码处注 DECISION-290 作出处，不算补丁（STD-CODE §4）。不写要求整图处处精确的算法、测试与门禁，例如全图每个实体闭合、每处拼接无缝；见到可见缺陷只修那一处（DECISION-289）。

- **主观设定的数值看数量级**：预算百分比、面数与绘制调用、形状与实例数量、绝对精度与容差、项目自己定的上限常量，都是设定出来的目标，不是要逐位达到的数。实测和阈值在同一个数量级（相差不到 10 倍）、又不挡核心体验，就算合理：照常推送，必要时把阈值调到实测附近，回报里写一句；不为压到某个具体数字另做优化。
- **判据挡路就放宽或删**：数学等价式的判据（1e-6 一类的容差、“去掉这一项结果不变”、为判定再做二分或加密采样）不进生成与加载路径；毫米级的差挡住启动或集成时，放宽到厘米级或删掉这条判据，不加量化、二分、更多采样去“修精度”，也不为它另写校验器。几何退化判断这类数值稳定用的 epsilon 不算。
- **硬约束照真实上限办**：格式或接口的真实容量、引擎限制、存档与契约的版本、确定性要求的同机同输入同输出，不适用数量级判断。
- **体验优先**：差在同一量级内却明显影响玩家体验（卡顿、穿模、加载等待），按 §14 的 bug 处理。

## 16 改文件即维护体系（DECISION-264）

新建文件、往文件里加一块新内容、改动文件，都同时在维护整个代码与文档体系；只把单点需求写对、却随手落在某个位置，就是在给结构打补丁。
- **管哪些文件**：只管进仓库、属于项目结构的文件：`game/`、`pipeline/`、`scripts/`、`docs/`、`dashboard/`、`tools/`、`.collab/tools/`。为改文件、查数据临时写的脚本和中间文件是一次性产物，放会话临时目录或 `output/`（§6、§13），不查结构、不登记；来信、任务单这类协作文件按 WF-COMMS §1 放。
- **结构图**：文档是文档树（CORE-INDEX §1 → 域总纲 → 主题文档 → 子文档，STD-DOC §1、§7）；代码是模块分层（ENG-ARCH §1）加文档文件头的 `paths` 路径归属；脚本按 `scripts/` 现有的子目录。
- **先定位再动笔**：动笔前先回答"它在结构图里归哪"。已有家就写进去，先复用再新写（STD-CODE §3），文档放哪见 STD-DOC §5.2；只是沾边的不算家。
- **找不到家先改结构**：要新目录、新文档、新模块或新的公共层，先报主会话定，再在相关文档文件头的 `paths` 或文档树里登记，最后写内容；不为一次需求开平行文件，不随手找路径生成。
- **不用补丁式命名**：文件和目录名不用 misc、util、utils、helper、helpers、temp、tmp、new、v2、old、backup、legacy、compat、patch、fix 这类词；文档不开"补充""增补""新版"；名字说职责（STD-CONVENTIONS §3）。
- **改完同批维护**：新东西登记进索引与文档文件头的 paths；被它取代的、和它重复的同批删掉或合并，引用改到新位置。
- **看到的死代码、旧设计和混乱**（DECISION-273）：工作中看到的没有使用方的代码、测试、数据、脚本与文档段落，已被取代的旧设计、旧路径、旧说法，以及重复、放错层，量小当批删掉或理顺、同批改引用，量大登记成队列行。删前按名字 grep 全仓，再看路由表、文档文件头的 paths 与钩子，确认真没有使用方；在别人正在改的目录里的，写信给负责方，不自己动。不视而不见，也不借机改本单以外的行为。
- **派单与回报**：简报的"新文件"栏写放哪、为什么（WF-MODEL §8.1），子代理只在列出的路径新建，要另建先写申请；回报列出新文件及其归属（WF-COMMS §3.4）。
- **守门**：快检的 G4 查新文件是否落在已登记的路径、名字是否补丁式（ENG-GATES §1）；文档登记由 `check-docs.py` 查；每批收口做一次只读结构审计（WF-FLOW §3.1）。
