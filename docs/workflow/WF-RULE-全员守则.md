# WF-RULE · 全员守则

> **范围**：本文是所有会话和子代理共同遵守的规则，每条只在这里写一份；其他文档和入口只写"见 §n"。
> **不在本文**：角色分工与决定权：WF-ROLE；来信与任务单的格式：WF-COMMS；改哪里：WF-BUILD；文档怎么写：WF-DOC；防打架与派工：WF-FLOW §2.1；构建与测试排队：WF-BUILD §4；角色独有的必守：WF-ENTRY。
> **查阅**：bug 怎么分级看 §14；数值按数量级判断看 §15；一次性产物看 §13；先读 §0；每节自成一条。

## 0 结论

守则共 15 条，各占一节：§1 不过度工程化；§2 不向作者出选项；§3 不预判时间；§4 不短轮询、不干等、不重复复核；§5 来信；§6 文件操作；§7 git 与直接改主线；§8 主线优先；§9 测试最小；§10 少和别人打架；§11 拿不准就问；§12 写文档与记忆；§13 一次性产物；§14 按严重程度修 bug；§15 数值按数量级判断。

### 0.1 接入要点

- **派任何单、写任何简报**：不抄本文，只写"见 §n"；简报里的规则副本会漂移。

## 1 不过度工程化（D-201）

本项目是作者的个人实验作品，不是商业交付级项目；作者不看证据链，多写的每一行都在白花额度。
- **不写**：证据溯源、来源链、哈希或校验和、proof、verification、attest 一类的脚本与报告，handoff 证据目录，逐字节证明，额外的审计报告。构建和生产代码里本来就要用的摘要照常写。
- **不自己加**：门禁、检查脚本、测试脚手架、全量回归、重复构建。只跑任务单要求的检查，默认是 `gate.ps1` 的快检；觉得需要更多检查，先写一条【需定】问主会话。
- **回报从简**：照 WF-COMMS §3.3、§3.4 的短头部，证据只给路径。

## 2 不向作者出选项

主会话以外的所有会话和子代理，都不给作者出选项或确认框，不用 AskUserQuestion 一类的工具，也不在终端里停下等作者选择。
- 需要确认、拿不准、要拍板的事，写进任务单"状态"或请求文件并通知主会话（Astra、Sol 会话在 `notes/opus/` 新建来信，格式见 WF-COMMS §4；子代理交给派它的一方转达）。
- 主会话能据项目信息判断的直接定；只有属于作者的决定才转问作者。只有主会话转达"作者已定"的，才算作者的决定。

## 3 不预判时间

模型凭推理感知时间，误差很大：不估"已经用了多久""还要多久"，回报、评审和流水里不写预计完成时间，只写做到哪一步。
- 要用时间时以真实读数为准：命令输出、文件时间戳、额度读数；时长用两次真实读数相减。手边没有真实时间就只写日期，不凭推理填，也不为写时间戳频繁读时钟。
- 任务单按 D-184 写的预计工作量只用来定单子大小，不当作完成时间的预告。

## 4 不短轮询、不干等、不重复复核

- **等命令**：能前台一次跑完的前台跑（单次最长 10 分钟）；必须放后台的，隔几分钟查一次日志或进程，进程没了就直接读结果往下做，不等完成通知，通知可能送不到。轮询间隔不短于 2 分钟，不连续反复读同一份日志。
- **每次被叫醒只读与这次事件有关的文件**，不重读已完成的任务单。
- **不重复复核**：已推送、已复核通过的事项，没有新输入（新提交、新基线、新条件）就不再复核，也不再回"已核"；收到提醒时先看有没有新输入，没有就一行写"无新输入，沿用 <时间> 的结论"。门禁同一组合只跑一次（ENG-GATES §1）。

## 5 来信

给主会话的来信一条一个新文件，开头标【需定】【待审】【知会】之一，一件事、5 行以内；格式与收件箱见 WF-COMMS §4。

## 6 文件操作

对所有会话和子代理都适用（D-149–D-152）：
1. **下载**：需要的引擎、导出模板、SDK、素材、文档直接下载，不必请示；只用官方或可信来源，下完说明下了什么、多大、放在哪。第三方代码与插件、音频素材的许可与登记见 OPS-RELEASE §7。
2. **临时文件**：放会话临时目录或不进 git 的 `output/`，不放进源码和文档目录。
3. **删除**：能不删就不删；要删只用绝对路径、只删具体文件，不用通配符或相对路径，不写 `cd X; … rm …`（`cd` 失败后删除会落到当前目录）。复制文件时复制来的 `.uid` 也按绝对路径逐个删。
4. **路径与格式**：一律用绝对路径，命令行参数里的也一样；新建文本文件用 UTF-8 和 LF，保持原有换行风格。
5. **只改分派给自己的文件**：别的代理正在改的不碰。
6. **向 `.collab` 追加含 Windows 路径的中文文本**：先用 Write 写到临时文件，再 `cat 临时文件 >> 目标` 追加，不用 python heredoc 或 printf 带反斜杠；追加后用 grep 核一下确实落进去了。

## 7 git 与直接改主线（D-211）

- **只在主检出 `main` 上改**：`E:\Project\UESTC_RPG`，不另开目录、工作树和本地分支。
- **只提交自己的文件**：`git add <自己改的文件>`，不用 `-A` 和 `.`；提交带路径 `git commit -- <路径>`，以免带走别人暂存的东西；碰到 `index.lock` 就等几秒重试。
- **编译与快检通过才推送**：施工子代理默认只写不编译、不提交，由指挥统一编译、跑快检（碰启动、行走、存档加核心专项，§9）后提交并 `git push origin main`（WF-FLOW §3.1）；只提交编译通过的东西，失败项只是一般或轻微的 bug 时照样先推送（§14）。提交首行写 `WP-xx: <一句话>` 或 `文档：<一句话>`，结尾 `Co-Authored-By` 写实际执行的模型。
- **不动别人的文件**：要改邻居的文件，先停下报派单方（WF-FLOW §2.1）。
- **回滚只用 `git revert <提交>`**：不用 `reset --hard`、`checkout .`、`clean`，也不用 `git stash`，它们会毁掉或卷走别人还没提交的改动；历史不线性没关系。
- **推送被拒就停下**，报派单方；不强推，不改写历史。
- **远端**：`origin` 是 GitHub 上的 `Wendystar0628/UESTC_RPG`，只有 `main` 和里程碑标签；不开 PR，不推别的分支。`override.cfg` 和 Debug 编译改写的 `packages.lock.json` 不提交。

## 8 主线优先（D-168）

- 主线的定义见 CORE-INDEX §2。主线闸口（ENG-WP §1）通过之前，每个包只交主线版：能接进主线、跑得通、不崩、不挡路。
- **主线版可以**：用简化几何或体块、默认参数、占位贴图与占位声音；只做默认状态和最常见的组合；跳过边角情况。
- **主线版不可以**：改动或绕开契约、数据格式和目录归属；留临时接口；违反 CORE-INDEX §0 里关于画风、精度、禁区和世界预算的几条。
- **不为细节阻塞推送**：细节问题写进回报，留到主线闸口之后统一处理；核心体验（主线流程、行走、存档、画面没有明显卡顿）的问题优先修。

## 9 测试最小（D-167）

- **只做认为最有必要的测试**：时间花在实现上，不按上架游戏的标准测。经常跑、几乎从不失败的检查不该每次跑；不为一批改动堆测试。
- 推送前由指挥统一编译后跑几分钟的快检（WF-FLOW §3.1）；改动碰到启动、行走、存档时加跑对应的核心专项；其余测试全部留到大量开发之后集中测一次，由主会话发起。构建、import、烘焙、门禁和截图一次只跑一个，等锁不绕过（WF-BUILD §4）。判据与命令见 ENG-GATES §1。
- **不重跑**：同一个包上次门禁全过、之后没改相关文件，不再原样重跑；施工不用 `-NoCache`。
- 开发中用 `--pose` 截图看效果不算门禁；只改文档的不跑门禁，跑 `check_docs.py`。测试代码怎么写见 ENG-CODE §6。

## 10 少和别人打架（D-199）

大家在同一个主检出上写，碰的公共文件越多，互相覆盖和返工越多。
- **开工和被恢复时先看谁动了什么**：先 `git status`、`git log -5`，再读简报里的邻居栏；之后每开始下一步之前，别人动了你要碰的文件就先停下问。
- **只往自己的文件里加**：多包共用的数据只加本包条目，覆盖层按包分片（写法见 CORE-CONVENTIONS）；改动尽量落在本包独占目录。
- **测试只锁本包自己的输出**，以及"原有条目的字节与顺序不变"；不锁别的包会合法增减的全局集合与指纹。
- **改架构或实现新设计时，一次迁完、不留旧的（D-209）**：改的一方在同一批改动里把所有使用方迁到新设计，删掉旧设计、旧代码、旧测试和旧文档，禁止新旧多套并存；推送前跑全仓 G2，回报里列出迁了哪些使用方。只有下游文件正由另一个子代理在改、一次改不完时，允许一层过渡兼容，它活不过这张单结案，任务单里写明删除条件；牵涉下游包归属的先找 Astra 定迁移方案。已冻结的契约组按 WF-BUILD §3 申请。
- **小步交付**：小步提交，测完就推；一块能独立成立的先推，不攒大批。
- **评审定下的通用规则以规范文档为准**：开工时按文档做；决策编号（D-nnn）由主会话统一分配，需要新决策在回报里提。

## 11 拿不准就问

- 会改动契约、数据格式或目录归属的，停下来问主会话；不影响这些的，按最保守的理解做，并在回报里写明假设。
- 文档之间冲突，或文档与 CORE-DECISIONS 不一致：按 WF-DOC §6 的层级判定；判定不了的报主会话，不自己改文档。

## 12 写文档与记忆

- 只写对后续开发有用的现行规则，不超出这份文档的作用范围，能一句说清不写一段。
- 已在代码或数据里实现的（契约、接口签名、参数表、归属表、预算数值）不在文档里抄，写一句以哪处为准；文档写结构、规则和导向，不写实现做法（WF-DOC §4）。
- 同一条信息只留一份权威，别处只给指向；推送流水与状态历史交给 git，文档只记现在。
- 写文档也费输出额度：先列要点，再展开。
- 记忆文件同理：只留偏好与原因和指向，不抄规则。文档的具体写法见 WF-DOC。

## 13 一次性产物（D-221）

- **用完就删**：日志、测试输出、临时脚本、调试截图都是一次性产物；回报要引用的留到评审结束，其余在交回前删掉自己的。
- **放对地方**：临时脚本和中间结果放系统临时目录（Claude 用会话的 scratchpad），不放仓库；必须落在仓库里的生成物只进 `output/`。
- **长期保留的只有**：构建锁 `output/.locks/`、烘焙缓存 `output/cache/`、固定机位截图 `output/shots/`、门禁复用记录 `output/build/gates/*-cache.json`、管线安装包 `output/pipeline-wheels/`。
- **定期清理**：`python -I -X utf8 scripts/build/clean_output.py` 列出之后主线上已有 20 次提交的一次性产物（按提交轮次算，不开发就不过期），加 `--delete` 删除；主会话和 Astra 每个任务结束时跑一次。

## 14 按严重程度修 bug（D-223）

- **先分级**：
  - **阻断**：挡住启动、进出、行走、存档等核心体验，或破坏核心架构与数据（契约、存档格式、确定性）；当场修，修好再推送。
  - **一般**：局部出错、少数位置表现不对、非核心功能不可用；先提交推送，回报里写明，由指挥登记待修，另派子代理或排到后面。
  - **轻微**：观感小瑕疵、罕见的边界情况；只登记，集中测试时一起修。
- **不让小 bug 挡住大家**：一批改动只差一般或轻微的 bug 时先提交推送，提交信息和回报里写明已知问题；编译不过和阻断的不在此列。
- **修不收敛就停**：同一个问题试了两轮还没修好，就停下写清现象和试过的办法；阻断的交派单方，非阻断的登记后去做别的。指挥和子代理都一样。

## 15 数值按数量级判断（D-225）

- **主观设定的数值看数量级**：预算百分比、面数与绘制调用、形状与实例数量、绝对精度与容差、项目自己定的上限常量，都是设定出来的目标，不是要逐位达到的数。实测和阈值在同一个数量级（相差不到 10 倍）、又不挡核心体验，就算合理：照常推送，必要时把阈值调到实测附近，回报里写一句；不为压到某个具体数字另做优化。
- **硬约束照真实上限办**：格式或接口的真实容量、引擎限制、存档与契约的版本、确定性要求的逐字节一致、对外的体积上限，不适用数量级判断。
- **体验优先**：差在同一量级内却明显影响玩家体验（卡顿、穿模、加载等待），按 §14 的 bug 处理。
