# WF-MODEL · 模型、子代理与额度

> **范围**：本文规定每张单按什么选施工模型与推理强度，Opus 与 Sonnet 怎么分，机械活交谁，各方怎么开子代理，子代理什么时候恢复、什么时候新开，派工简报与"接续"段的写法，额度口径、子代理开多少、Codex 账号与额度见底时的冻结，以及两家模型的易犯行为与对应做法。
> **不在本文**：各模型的长处与"GPT 不做审美"：WF-ROLE §2、§3；队列平衡：WF-STATUS §2；派工、拆单与评审流程：WF-FLOW。
> **查阅**：先读 §0；七问看 §1；Opus 与 Sonnet 的分界看 §2；机械活看 §3；推理强度看 §4；升级、派单与直接做看 §5；开子代理看 §6；恢复还是新开看 §7；简报模板与接续看 §8；额度、并发与冻结看 §9；两家模型的易犯行为与对应做法看 §10。

## 0 结论

1. **按七问选够用的施工模型**（§1）：先分清未定判断与已定实现；审美相关的不交 GPT。
2. **Opus 只用在观感还没定的地方**（§2，DECISION-193）：观感已由评审或已批样子定下的可见活交 Sonnet。
3. **机械活交便宜模型**（§3）：不需要判断的量大、重复的活，GPT 侧交 Codex 主线开的 gpt-6-luna 子代理（medium），Claude 侧用 Sonnet medium。
4. **推理强度按难度选**（§4）：够用就停，Sonnet 只用 medium 与 high，不用 max。
5. **开多少按任务量定，额度只做刹车**（§9.1，DECISION-226）：有几路互不冲突、按目录分得开的活就开几个，不设固定个数上限；派工前读用量，照现在的速度会在重置前用完，就少开或改派便宜模型。
6. **临近重置还剩得多就用足**（§9.2，DECISION-196）；作者说"加快"或"慢慢用"时以作者的话为准。
7. **Codex 额度要省**（§9.3，DECISION-249）：Codex 子代理按难度选模型，困难艰深的派 gpt-6-astra，其余派 gpt-6.1-sol（WF-ROLE §6）；GPT 侧一律普通速度；主账号剩余约 1% 时冻结，停止派新活，由作者手动切换账号（§9.4）。
8. **简单少量的活由拿到信息的一方直接做**，不转手（§5）。
9. **子代理一律新开，靠任务单的"接续"段交接；单子在上下文约 40 万 token 或 150 次请求前交回**（§7，DECISION-191）。
10. **两家模型各有易犯的行为**（扩范围、多问就停、测过头、加校验、写长）：写简报时按 §10 的做法预防。

### 0.1 接入要点

- **写派工简报**：用 §8 的模板，只填本次任务特有的信息；入口、守则、回报写在 WF-ENTRY、WF-RULE、WF-COMMS，不抄。
- **交回时**：在任务单末尾写"接续"段（§8.2）。
- **开子代理**：按 §6；施工位置按 WF-FLOW §3.1，简报里必须写明邻居（§8.1）。
- **派单、选 Opus 还是 Sonnet、决定开几个之前**：先看最近一次用量读数，读数超过 15 分钟就重读；开几个按任务量定，额度紧时少开（§9.1）。
- **主账号剩余约 1%**：停止派新活（§9.4）。

## 1 按七问选施工模型

依次看还缺什么判断、结果能否验收、错误会传播多远。混合任务先分清未定判断与已定实现。

| 问题 | 倾向：模型与档位 |
| --- | --- |
| 1. 要定造型、风格、声音、玩家可见参数或内容取舍，或制作可见构件吗？ | 需要审美判断的（造型、风格、观感取值，地标与重点构件，质感移植）由 Opus 子代理施工，主会话定案；只缺判断时主会话直接定。规格、尺寸、色名都已给全的可见活（简单部件、按已定预设填数据、小修）交 Sonnet。审美相关的活不交 GPT，非可见部分可拆出继续问 |
| 2. 必须读图或依赖中文语感判断吗？ | 按检查单读图初筛、中文改写交 Sonnet；可程序测出的数据与截图采集交 gpt-6.1-sol。涉及审美回第 1 问；改变原意或含内容取舍时交主会话 |
| 3. 目标、规格和通过条件仍有歧义吗？ | 工程歧义交 Codex 主线，设计与内容歧义交 Opus，定清再派实现；不靠增加推理替代决定 |
| 4. 错误会跨接口、线程、资源寿命或存档扩散吗？ | Codex 主线定方案、边界与验收条目，施工按难度交 Codex 主线名下的子代理：困难艰深的派 gpt-6-astra，其余派 gpt-6.1-sol（默认 high，根因不明才 xhigh）；sol 两次做不对时改派 astra（WF-ROLE §6） |
| 5. 数学或几何很难，但能由不变量、参考结果验证吗？ | 非审美实现由 Codex 主线名下的 gpt-6.1-sol 子代理施工；前提不清或全局耦合，先由 Codex 主线定清前提。可见构件回第 1 问 |
| 6. 是大量明确执行或事实整理吗？ | GPT 侧由 Codex 主线开 gpt-6-luna 或 gpt-6.1-sol 子代理；确需语言加工时再用 Sonnet |
| 7. 是剩余明确的非审美实现吗？ | 默认 gpt-6.1-sol 实现，由相应负责方派单 |

## 2 Opus 与 Sonnet 的分界（DECISION-193）

Opus 贵，只用在观感还没定的地方。

| 默认交 | 活 |
| --- | --- |
| Opus（high；地标与质感移植 xhigh） | 一类内容或构件第一次造型，还没有已批的样子可照；地标与重点构件；质感移植与新的画面机制；评审里标明"要定""拿不准"的观感取舍 |
| Sonnet high | 调研（同类主流游戏的做法加本项目建议，WF-STATUS §4）；评审已写明怎么改的跟进单；照已批的样子铺到同类；摆放规则、数据与世界文件登记、树种与预设键；截图采集与重拍；素材收集；文档撰写 |
| Sonnet medium | 按条目填数据、按确切文字打文档补丁 |

- 一张单里混着未定的观感和已定的实现时，把已定的拆出来交 Sonnet，Opus 只做未定的那块。
- Sonnet 的成果在观感上两次评审不过，改派 Opus，不先升推理档。换模型就是新开子代理（§7）。

## 3 机械活交谁

只做照清单执行、结果能机械核对、出错也不会扩散的活，不做任何判断。Claude 侧不用 Haiku。

- **交谁**：量大、重复、照清单的活（成批替换引用、全仓数据核对与盘点、成批截图与拼图、成批状态整理、按确切文字打文档补丁、重跑 `gen-index.py` 与 `check-docs.py`、按给定参数跑门禁并汇总结果），交 gpt-6-luna 子代理（medium），由 Codex 主线 `spawn_agent` 开；主会话手上的这类活写成旁路单交 Codex 主线去开（WF-COMMS §5，DECISION-249）。Claude 侧要做的交 Sonnet medium。
- **边界**：不判断依赖是否"算满足"，不改写措辞、不补内容，不修代码、不判断失败原因，不评价观感，不改数据只报结果；拿不准就留原样。
- **谁开**：拿到这件杂活的一方直接开（DECISION-190），不转手。GPT 侧的新活一律交 Codex 主线，在它里面开子代理，不另开会话（DECISION-249）。
- **怎么选**：一次做不对就改派 gpt-6.1-sol medium 或 Sonnet medium，不在原档上重试。等待、轮询、定时重跑交脚本，不占模型。

## 4 推理强度按难度选

每张单按难度选一档，写进派单；每升一档费用和用时都明显上涨，提升越来越小，够用就停。

| 难度 | 例子 | Opus | Sonnet | gpt-6.1-sol |
| --- | --- | --- | --- | --- |
| 简单 | 规格已给全，能按条目验收：填数据、按已定预设接线、单文件小修、查资料与整理、打文档补丁 | 不派 | medium | medium |
| 一般 | 要自己规划实现，能按条目验收：常规部件与建模、普通接线与单测、截图采集 | high（需审美判断的可见构件） | high | high |
| 难 | 判断重，或错误会扩散：地标与重点构件的造型、质感移植、跨模块根因，确定性、并发、资源寿命、存档方案，契约方案 | xhigh | 不派，改派 Opus | high；根因不明或跨模块的诊断才 xhigh |

- 要 Sonnet 开 xhigh 才做得好的活，改派 Opus high。不用 max，施工不用 low。
- **难也先用 high（DECISION-232）**：日常整合和统一编译用 high，xhigh 只给诊断类（根因不明、跨模块）；一两处小错指挥自己改，不单开子代理。单张子单按范围拆（WF-FLOW §2）。
- 返工沿用原档；同一档两次做不对，先按 §5 查原因，确实是难度不够才升一档。
- 固定长期会话：主会话 xhigh；Codex 主线（gpt-6.1-sol）日常用 high，诊断时临时升 xhigh；GPT 侧都是普通速度。

## 5 升级、派单与直接做

- **升级先找失败原因**：已明确条目漏做，由原施工者补；接口或生命周期无解交 Codex 主线定边界；观感和内容争议交 Opus；超量或后半段质量下降按 DECISION-184 拆单（WF-FLOW §2），不用升级模型代替拆单。
- **派单最少写**：目标与验收条目、定案与未定项、独占路径、模型/推理档、必要复核人、升级信号。实现路径由施工者规划，只给目标、约束（主线优先、依赖、契约、目录归属、预算）和交付标准，不规定步骤。
- **复核只在需要时叠**：gpt-6.1-sol 实现 → Codex 主线核工程风险；程序采集 → Sonnet 读图初筛 → Opus 定观感。每张单只列具体风险和对应复核人，小修与纯接线默认不叠。
- **简单少量的活，拿到信息的一方直接做**：每转一次手都要花额度（写简报、对方重读上下文、再回报）；只有量大、要并行、要换模型能力，或归属不在自己手里时才转派。

## 6 怎么开子代理

**各方都适用**：一张施工任务单一个子代理；同一时刻一个文件只有一个代理在写，简报写明邻居（WF-FLOW §2.1）；简报按 §8 模板写，入口由钩子注入（WF-ENTRY §2）；构建、import、烘焙、门禁和截图排队，一次一个（WF-BUILD §4）。

**Claude 侧**（主会话开）：用 Agent 工具在后台开，指定 `model: "opus"` 或 `"sonnet"`，`description` 的格式见 STD-CONVENTIONS §3.8，观察台按它把子代理对到在做的工作上；子代理的最终回复就是回报。开几个按任务量定，额度紧时少开（§9.1）。

**Codex 侧**（Codex 主线）：用 `spawn_agent`（`task_name` 用小写类别、下划线、三位数与主题（如 `game_031_grass_puddles`、`tool_116_xxx`、`batch_007_xxx`），`message` 写完整简报）、`wait_agent`、`list_agents`、`send_input`。开几个按任务量定（§9.1）；`~/.codex/config.toml` 里的上限是软件自身的硬限制，照它办。模型在开的时候指定：默认 gpt-6.1-sol，机械活 gpt-6-luna，临时审计 gpt-6-astra（WF-ROLE §6）。写游戏 C# 的 Codex 子代理在独立临时工作树（WF-FLOW §3.1），其余与 Codex 主线共用主检出；简报里必须写明：只改点名的文件，读写用绝对路径，不碰邻居的文件，提交推送同 WF-RULE §7。

## 7 子代理的生命周期：默认新开，靠任务单交接

每次请求都要重读整段上下文，恢复一个已经很长的子代理去接新活，每一轮都在为旧历史付费，通常比新开一个只读这次需要的文档更贵。

- **默认新开**：同一组目录的下一张子单、新一阶段、无关的活一律新开；交接写在任务单"接续"段（§8.2）。子代理交回就结束，不待命，不占并发名额。
- **返工也新开**：任务单写明改什么、改哪里。唯一例外是交回几分钟内、原子代理上下文在约 8 万 token 以内的几处小改。
- **上下文封顶**：做到上下文约 40 万 token 或 150 次请求时，把已完成的部分提交推送，余下写进"接续"交回，由新子代理接着做；派单时按这个量拆单。
- **恢复以后先对齐现状**：`git status`、`git log -5`，再核对任务涉及的契约、数据与相关模块的新提交，不以记得的旧版本为准。
- **记录**：任务单"派出"行写子代理的名字和类型；回报最后一行的 token 数是交回时的上下文大小。

## 8 简报模板与"接续"段

### 8.1 简报模板

只替换尖括号里的内容，只写本次任务特有的信息；入口与必守在 WF-ENTRY，守则在 WF-RULE，回报在 WF-COMMS §3.4。

```
你是《电光年华》的子代理，负责 <施工队列行号与标题>。你向 <派你的一方> 回报。
任务单：<绝对路径>；写在：<主检出或临时工作树的绝对路径>；允许改：<路径>。
新文件：<进项目结构的新文件放哪、归哪个目录或文档、为什么；没有写"无">（只在这里列出的路径新建，WF-RULE §16）。
同时在干活的邻居：<名字：在做什么：改哪些路径>（没有写"无"；来源是施工队列的目录与谁两列和巡逻的"正被改着的目录"）。碰到共用边界先发消息问邻居，要改它的文件先停下报派单方。
<本轮的特别说明，可空>
完成后按 WF-ENTRY §2 收尾，回报交指挥。
```

允许改的路径以简报为准，目录来自施工队列行的"目录"列。

### 8.2 "接续"段

交回时在任务单末尾的"接续"段里写，只填对下一张子单有用的几行：
- **源与状态**：源提交，已推送还是进行中，沿用了哪些已定约束（评审时间）；
- **接合**：部件装到宿主的哪个面、基点和安装方式；入口接哪一层；唯一的生产方和消费方；
- **重建**：从哪个生成入口、哪份参数或数据重建；有没有本机生成或缓存；
- **截图**：在哪个位姿拍的，是不是沙盒或替身；
- **未完**：下一张子单要补的事，需要哪一方配合；
- **文字载体**：有牌面、题字、门牌的部件或楼，写明写什么字、批准留白的原因、在等什么。

## 9 额度与并发

### 9.1 口径、开多少与刹车

订阅容量与扣额估计只用于本项目排程，以作者实数和项目经验为准，不作 API 报价。

- **按任务量开**：先按目录把活分成互不冲突的几路（WF-FLOW §2.1），有几路就开几个子代理；同一批文件同一时间只有一个写者。截图与重 CPU 任务照样排构建锁（WF-BUILD §4）。
- **省额度靠选模型**：能交 Sonnet 的不交 Opus，机械活交 Sonnet medium 或 gpt-6-luna；子代理默认新开、靠任务单交接，长上下文接新活每一轮都在为旧历史付费（§7）。
- **刹车**：派工前用 `get_usage` 读 5 小时与每周两个窗口的用量和恢复时间，读数超过 15 分钟就重读。照现在的速度会在恢复前用完，就少开新的或改派便宜模型，在跑的不中断。

### 9.2 节奏（DECISION-196）

- 离重置还早时不赶，按任务量正常开。
- 临近重置还剩得多就用足：每周额度离重置不到 24 小时、或 5 小时窗口离重置不到 1 小时而每周额度宽裕时，照现在的速度到重置还会剩 10% 以上，就多开、两难的活用 Opus；剩余低于约 20% 时少开新的。
- 作者说"加快"或"慢慢用"时以作者的话为准；周额度由作者自己调节，不加"用量快于时间进度就降并发"之类的兜底。

### 9.3 Codex 账号

- **额度要省**（DECISION-249）：Codex 子代理按难度选模型，只有困难艰深的派 gpt-6-astra，其余派 gpt-6.1-sol；主线模型由作者在应用里定，不带动子代理选型（WF-ROLE §6）。重置时机由作者自己决定，套餐额度用完会自动使用账户余额。
- **速度**：GPT 侧一律用普通速度（DECISION-197），不开快速模式。

### 9.4 额度见底时冻结

主会话每次处理事件时查一次本账号的额度（`get_usage`）。主账号的任一额度窗口（5 小时或每周）剩余约 1% 时冻结：停止派一切新活，等在跑的做完，由作者手动切换账号。冻结时主会话在 `HANDOVER.md` 更新"进行中的事"，供切换后的会话接着做（WF-STATUS §3）。换账号后来信监视要重开，做法见 `.collab/tools/README.md`。

## 10 两家模型的易犯行为与对应做法

写简报和任务单时按下表预防；模型换代时核对一次。

| 模型 | 易犯 | 对应做法 |
| --- | --- | --- |
