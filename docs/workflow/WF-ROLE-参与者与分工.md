# WF-ROLE · 参与者与分工

> **范围**：本文规定协作有哪些角色、各向谁汇报，各模型擅长什么，谁决定谁执行，GPT 模型不做审美，总指挥只做什么，Codex 主线怎么当指挥。
> **不在本文**：各角色的入口与必守：WF-ENTRY；按难度选模型、开子代理：WF-MODEL；包的归属：ENG-WP-LIST §1；额度与并发：WF-MODEL §9。
> **查阅**：先读 §0；角色与运行方式看 §1；模型长短板看 §2；GPT 不做审美看 §3；决定权与事归谁看 §4；总指挥看 §5；Codex 主线看 §6。

## 0 结论

1. **主代理只有一个，就是主会话**（§5，D-166）：只做判断；施工子代理只写不编译，由指挥统一编译后提交推送（§4，D-219）。
2. **视觉风格只由 Opus 侧做，GPT 模型不做任何审美工作**（§3）：玩家看得见、听得见的结果，参数和取舍由主会话评审定值。
3. **按模型长处分工**（§2）：Opus 管审美、判断与变通；Sonnet 做语言、看图和已定的活；Codex 主线管架构与工程指挥；gpt-6.1-sol 是 Codex 主线和工程施工的模型，gpt-6-astra 只做临时审计（D-249）。
4. **Claude 侧子代理都开在主会话下**（§1）；**Codex 主线是工程指挥官与重要决策者，施工交 gpt-6.1-sol 子代理**（§6）。

### 0.1 接入要点

- **画面、配色、质感、构图、造型、界面观感、参数取值、截图评审的决定**：只能是 Opus 侧；Codex 主线与它的子代理等 GPT 执行者不做（§3）。
- **Codex 主线的包有可见或可听的结果**：只交机制和集中的可调参数，观感问题写评审请求交主会话（§3、WF-FLOW §4）。
- **Opus 侧的包里有重工程问题**（性能结构、线程、确定性、契约）：请 Codex 主线评审（§4）。

## 1 角色与运行方式

协作由一位作者和下表的会话组成。评审里的"Opus"指主会话，"Opus 侧"指主会话和它开的 Claude 侧施工。各角色的必守与开工动作见 WF-ENTRY；会话号与调用命令见 `.collab/tools/README.md`。

| 角色 | 模型与运行方式 | 汇报给 |
| --- | --- | --- |
| 主会话 | Claude Opus 5.5，Claude Code 交互会话 | 作者 |
| 主会话的子代理 | Claude Opus 或 Sonnet，Agent 工具后台开，按包取名 | 主会话 |
| Codex 主线 | gpt-6.1-sol（日常 high，诊断 xhigh），Codex 应用里唯一的会话 | 主会话 |
| Codex 主线的子代理 | 默认 gpt-6.1-sol，机械活 gpt-6-luna（medium），`spawn_agent` 开；gpt-6-astra 只做临时审计（§6） | Codex 主线 |

- **Claude 侧只有一个账号**，不另设中间会话；额度见底见 WF-MODEL §9.4。
- **Codex 侧只有 Codex 主线一个会话**，开在 Codex 应用里，作者能看到全过程；要用 GPT 就在它里面开子代理，不另开会话（D-249）；派活与通信见 WF-COMMS §5。GPT 侧一律普通速度（D-197）。

## 2 模型的长处与短板

| 模型 | 长处 | 短板与限制 |
| --- | --- | --- |
| Claude Opus 5.5 | 审美、判断、变通：画面、风格、内容，跨系统取舍，需要 Opus 的文档撰写 | 额度最贵，能交 Sonnet 的不交 Opus（WF-MODEL §9.1） |
| Claude Sonnet | 价格约为 Opus 的一半：规格已给全的简单部件，按已定预设填数据，覆盖层与数据改动，测试与小修，中文文档改写、文案、看图初筛 | 不定风格，画面与风格的定值归主会话 |
| gpt-6-astra | 最强的 GPT 档：跨包根因、并发、确定性、资源寿命、存档迁移这类重大问题的诊断与审计 | 单价约为 gpt-6.1-sol 的五倍，只开成临时审计子代理（§6）；不做审美 |
| gpt-6.1-sol | 能力接近 gpt-6-astra，价格低，可高并发：Codex 主线本身和工程施工的模型，复杂的用 high 或 xhigh | 不做审美；子代理不自行改契约和共享工程文件（Codex 主线授权后可施工）；设计文档只按确切文字打补丁 |

## 3 GPT 模型不做审美工作

- **视觉风格只由 Opus 侧做**：着色、调色、描线与后期，材质与造型的观感，按参考场景移植质感（ART-STYLE）；参考场景里没有对应物的内容，也按同一套质感做法由 Opus 侧统一处理。
- **作者最终决定**：玩家看得见、听得见的观感，最终由作者决定；首版按 Opus 的主见直接做，主会话定可见参数的初值，看截图只挑明显出错，作者看了再改。
- **GPT 一律不做**：Codex 主线和它的子代理，不对画面、配色、质感、构图、造型、界面观感、参数取值和截图评审做决定与调整。
- **GPT 不做视觉核验**：不看截图挑细节，不做像素比对，也不为此专门跑截图。截图由主会话跑、主会话看；施工方碰了画面只在回报里注明（ENG-GATES §1）。

## 4 决定权与事归谁

- **主会话决定**：派工与分工；评审后留下还是回滚；施工状态的内容；`docs/` 改什么；设计、审美、内容取舍、可见参数、优先级；与作者沟通。
- **Codex 主线决定**：工程、契约、共享工程文件及高传播风险的方案（WF-BUILD §3）。
- **指挥统一编译后提交推送**：施工子代理只写不编译（WF-FLOW §3.1、WF-RULE §7）。设计文档的撰写可以派出去：需要 Opus 的交 Opus 子代理，GPT 只在任务单给出确切文字时按文打补丁。
- **谁施工**按 WF-MODEL §1 的七问判断；包归属（ENG-WP-LIST §1）与目录写权限不因施工模型改变。
- **可见构件一律由 Opus 施工**，哪怕已给全尺寸和截面；GPT 可承担其非可见部分，如碰撞、数据、接线和单测。
- **有可见结果的 Codex 主线包**（启动雾幕、镜头手感、跳转、行走手感、过场、介质）：Codex 主线交机制和参数表，主会话定参数值；**有重工程的 Opus 侧包**（建筑生成器规则、描线的计算着色器、材质库）：请 Codex 主线评审；画面相关的契约见 WF-FLOW §4。

## 5 总指挥只做什么

主会话的注意力只花在要判断的事上：
- **评审与定值**：画面与风格的评审和定值，质感移植（实现交子代理）。
- **设计定案与裁决**：设计定案、跨系统取舍、文档冲突裁决（WF-DOC §6）；决策编号 D-nnn 由它统一分配。
- **派工与分工**：派工、排优先级、按独占目录分工；推送后评审，不合格回滚或派返工单（WF-FLOW §2、§4）。
- **宣布与审批**：宣布契约冻结（WF-BUILD §3）；审批契约变更、开放室内清单的增删（D-164）、预算余量（D-161）。
- **集中测试与文档状态**：大量开发之后安排一次集中测试（ENG-GATES §1）；维护 `docs/` 和施工状态（WF-STATUS）；与作者沟通。
- **元规则**：作者提出明显不合理或代价过高的要求时，先指出来，再按作者的决定执行。

其余随时派出去，简单又量少、手上已有全部信息的活例外（WF-MODEL §5）；量大的机械活写成旁路单交 Codex 主线开便宜子代理（WF-STATUS §4.1），Opus 侧的施工写成任务单开子代理（WF-FLOW §2）。

**不等 GPT 侧**（D-234）：工程施工默认归 Codex 主线，但主会话能派 Claude 子代理做完的活就自己派，不排队等 Codex 主线：挑和 Codex 主线在跑的路不冲突的目录，写信告诉它接了哪几路；契约与共享工程文件仍只由 Codex 主线改；统一编译、快检和提交由主会话做（WF-FLOW §3.1）。

## 6 Codex 主线当指挥，施工默认交 gpt-6.1-sol 子代理

**Codex 主线是工程指挥官与重要决策者**：管契约、工程配置、归属表与门禁入口，还负责制定并演进工程架构（模块边界、依赖方向、数据流、线程与生命周期、确定性与资源管理）。发现明显不好的架构，不绕过也不打补丁糊过去，而是写清该怎么改（问题、改法、影响哪些包、怎么迁移），再派子代理修掉；改别人在用的接口照 WF-RULE §10，牵涉观感取舍的交主会话。

**Codex 主线只当指挥官和项目管理者**（D-234）：推进项目是子代理的事，指挥官不亲自施工。
- 做：控制子代理（拆单、派工、写简报、审交回的方案与代码、统一编译提交），契约与共享工程文件定案，跨包集成，和主会话通信。
- 不做：亲自写实现、亲自跑长时间的测试与排查；一处小错除外。
- 派出子代理后用 `wait_agent` 等，超时约 10 分钟；醒来先看主会话的消息和来信，把到达的消息和结果一次处理完再接着等；等待时不自己接着干活，也不用 sleep 轮询，sleep 期间收不到消息。这样既能及时收到通信，也不白耗额度。

**施工默认用 gpt-6.1-sol 子代理**：Codex 主线名下所有包的施工，包括内核、确定性、契约与存档迁移相关的包，用 `spawn_agent` 开 gpt-6.1-sol，复杂的用 high 或 xhigh。包的归属与审查权不变。

**gpt-6-astra 只做临时审计**（D-249）：单价约为 gpt-6.1-sol 的五倍。重大问题 gpt-6.1-sol 两次解决不了时（跨包根因查不出，确定性、并发、资源寿命或存档迁移的方案定不下），Codex 主线才临时开一个 gpt-6-astra 子代理（xhigh）审计：只读，交回根因与改法即结束，施工仍交 gpt-6.1-sol；主会话要审计就写信请 Codex 主线开。其余一律用 gpt-6.1-sol。
