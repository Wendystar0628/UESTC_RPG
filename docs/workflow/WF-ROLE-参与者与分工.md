# WF-ROLE · 参与者与分工

> **范围**：本文规定协作有哪些角色、各向谁汇报，各模型擅长什么，谁决定谁执行，GPT 模型不做审美，总指挥只做什么，Codex 主线怎么当指挥。型号的现行取值以 §1 的表为准。
> **不在本文**：各角色的入口与必守：WF-ENTRY；按难度选模型、开子代理：WF-MODEL；路径归属：各文档文件头的 paths；额度与并发：WF-MODEL §9。
> **查阅**：先读 §0；角色与运行方式看 §1；模型长处看 §2；GPT 不做审美看 §3；决定权与事归谁看 §4；总指挥看 §5；Codex 主线看 §6。

## 0 结论

1. **总指挥只有一个，就是主会话**（§5）：只做判断；施工子代理只写不编译，由指挥统一编译后提交推送（§4，DECISION-219）。
2. **视觉风格只由 Claude 侧做，GPT 模型不做任何审美工作**（§3）：玩家看得见、听得见的结果，参数和取舍由主会话评审定值。
3. **按模型长处分工**（§2）：Opus 管审美、判断与变通；Sonnet 做语言、看图和已定的活；Codex 主线管架构与工程指挥；gpt-6.1-sol 是 Codex 主线和工程施工的模型，gpt-6-astra 只做临时审计（DECISION-249）。
4. **Claude 侧子代理都开在主会话下**（§1）；**Codex 主线是工程指挥官与重要决策者，施工交 gpt-6.1-sol 子代理**（§6）。

### 0.1 接入要点

- **画面、配色、质感、构图、造型、界面观感、参数取值、截图评审的决定**：只能是 Claude 侧；Codex 主线与它的子代理等 GPT 执行者不做（§3）。
- **Codex 主线的包有可见或可听的结果**：只交机制和集中的可调参数，观感问题写评审请求交主会话（§3、WF-FLOW §4）。
- **Claude 侧的活里有重工程问题**（性能结构、线程、确定性、契约）：请 Codex 主线评审（§4）。

## 1 角色与运行方式

协作由一位作者和下表的会话组成。Claude 侧指主会话和它开的子代理，Codex 侧指 Codex 主线和它开的子代理。各角色的必守与开工动作见 WF-ENTRY；会话号与调用命令见 `.collab/tools/README.md`。

| 角色 | 模型与运行方式 | 汇报给 |
| --- | --- | --- |
| 主会话 | Claude Opus 5.5，Claude Code 交互会话 | 作者 |
| 主会话的子代理 | Claude Opus 或 Sonnet，Agent 工具后台开，按施工队列行号取名 | 主会话 |
| Codex 主线 | gpt-6.1-sol（日常 high，诊断 xhigh），Codex 应用里唯一的会话 | 主会话 |
| Codex 主线的子代理 | 默认 gpt-6.1-sol，机械活 gpt-6-luna（medium），`spawn_agent` 开；gpt-6-astra 只做重难审计（§6） | Codex 主线 |

- **Claude 侧只有一个账号**，不另设中间会话；额度见底见 WF-MODEL §9.4。
- **Codex 侧只有 Codex 主线一个会话**，开在 Codex 应用里，作者能看到全过程；要用 GPT 就在它里面开子代理，不另开会话（DECISION-249）；派活与通信见 WF-COMMS §5。GPT 侧一律普通速度（DECISION-197）。

## 2 模型的长处与短板

| 模型 | 长处 | 短板与限制 |
| --- | --- | --- |
| Claude Opus 5.5 | 审美、判断、变通：画面、风格、内容，跨系统取舍，需要 Opus 的文档撰写 | 用量最贵，能交 Sonnet 的不交 Opus（WF-MODEL §2） |
| Claude Sonnet | 规格已给全的简单部件，按已定预设填数据，世界文件与数据改动，测试与小修，中文文档改写、文案、看图初筛 | 不定风格，画面与风格的定值归主会话 |
| gpt-6-astra | 最强的 GPT 档：跨模块根因、并发、确定性、资源寿命、存档迁移这类重大问题的诊断与审计 | 只开成临时审计子代理（§6）；不做审美 |
| gpt-6.1-sol | 能力接近 gpt-6-astra，可高并发：Codex 主线本身和工程施工的模型，复杂的用 high 或 xhigh | 不做审美；子代理不自行改契约和共享工程文件（Codex 主线授权后可施工）；设计文档只按确切文字打补丁 |

选哪个模型施工见 WF-MODEL §1–§4；两家模型各自易犯的行为与对应做法见 WF-MODEL §10。

## 3 GPT 模型不做审美工作

- **视觉风格只由 Claude 侧做**：着色、调色、描线与后期，材质与造型的观感，按参考场景移植质感（ART-STYLE）；参考场景里没有对应物的内容，也按同一套质感做法由 Claude 侧统一处理。
- **作者最终决定**：玩家看得见、听得见的观感，最终由作者决定；按 Opus 的主见直接做，主会话定可见参数的初值，看截图只挑明显出错，作者看了再改。
- **GPT 一律不做**：Codex 主线和它的子代理，不对画面、配色、质感、构图、造型、界面观感、参数取值和截图评审做决定与调整。
- **界面层只由 Claude 侧做**（DECISION-287）：游戏界面 `game/hud/**`（HUD、开始页与菜单、设置、地图页、加载界面、文字与本地化）、界面主题与令牌 `game/style/palette/ext/ui.json` 和界面着色器，以及观察台前端 `dashboard/app`，都只由 Claude 侧改；GPT 只提供界面读取的服务、契约与后端数据（`game/contracts`、内核服务、`.collab/tools/monitor`、`dashboard/tools`）。一行活前后端都要改的，拆成后端行归 Codex、界面行归 Claude，界面行以后端契约为前置；门禁、改名、清理这类横切的机械活碰到界面层文件，那几处交 Claude 侧改。
- **GPT 不做视觉核验**：不看截图挑细节，不做像素比对，也不为此专门跑截图。截图由主会话跑、主会话看；施工方碰了画面只在回报里注明（ENG-GATES §1）。

## 4 决定权与事归谁

- **主会话决定**：派工与分工；评审后留下还是返工；施工状态的内容；`docs/` 改什么；设计、审美、内容取舍、可见参数、优先级；与作者沟通。内容开发的节奏由作者安排：内容行在作者提出时开，指挥不自行排内容批次（DECISION-292）。
- **Codex 主线决定**：工程、契约、共享工程文件及高传播风险的方案（WF-BUILD §3）。
- **对作者的要求提出反对**（DECISION-277）：主会话认为作者的要求违背硬约束、损害架构或数据权威、或代价与收益明显失衡时，在动手之前当轮提出反对，写清三件事：哪里不合理、照做的代价、更好的做法；不先照做再补说，也不为了不打扰而默默改成别的做法。作者听过仍坚持，就按作者的决定执行，同批落实到队列和文档。审美取向同样可以提意见，最终以作者为准（DECISION-252）。
- **指挥统一编译后提交推送**（WF-FLOW §3.1）。设计文档的撰写可以派出去：需要 Opus 的交 Opus 子代理，GPT 只在任务单给出确切文字时按文打补丁。
- **谁施工**按 WF-MODEL §1 的七问判断；可见构件交 Opus 还是 Sonnet 见 WF-MODEL §1–§2，GPT 只承担其非可见部分，如碰撞、数据、接线和单测；路径归属（各文档文件头的 paths）与目录写权限不因施工模型改变。
- **有可见结果的 Codex 主线包**（开始页与加载界面、镜头手感、跳转、行走手感、介质）：Codex 主线交机制和参数表，主会话定参数值；**有重工程的 Claude 侧包**（建筑生成器规则、描线的计算着色器、材质库）：请 Codex 主线评审；画面相关的契约见 WF-FLOW §4。

## 5 总指挥只做什么

主会话的注意力只花在要判断的事上：
- **评审与定值**：画面与风格的评审和定值，质感移植（实现交子代理）。
- **设计定案与裁决**：设计定案、跨系统取舍、文档冲突裁决（STD-DOC §6）；决策编号 DECISION-nnn 由它统一分配。
- **派工与分工**：派工、排优先级、按独占目录分工；推送后评审，不合格派返工单向前修（WF-FLOW §2、§4）。
- **宣布与审批**：宣布契约冻结（WF-BUILD §3）；审批契约变更、开放室内清单的增删（DECISION-164）、预算余量（DECISION-161）。
- **集中测试与文档状态**：大量开发之后安排一次集中测试（ENG-GATES §1）；维护 `docs/` 和施工状态（WF-STATUS）；与作者沟通。

其余随时派出去，简单又量少、手上已有全部信息的活例外（WF-MODEL §5）；量大的机械活写成旁路单交 Codex 主线开便宜子代理（WF-STATUS §4.1），Claude 侧的施工写成任务单开子代理（WF-FLOW §2）。

**不等 GPT 侧**（DECISION-234）：工程施工默认归 Codex 主线，但主会话能派 Claude 子代理做完的活就自己派，不排队等 Codex 主线：挑和 Codex 主线在跑的路不冲突的目录，写信告诉它接了哪几路；契约与共享工程文件仍只由 Codex 主线改；统一编译、快检和提交由主会话做（WF-FLOW §3.1）。

## 6 Codex 主线当指挥，施工默认交 gpt-6.1-sol 子代理

**Codex 主线是工程指挥官与重要决策者**：管契约、工程配置、文档文件头的 paths 与门禁入口，还负责制定并演进工程架构（模块边界、依赖方向、数据流、线程与生命周期、确定性与资源管理）。发现明显不好的架构，写清该怎么改（问题、改法、影响哪些模块、怎么迁移），再派子代理修掉；改别人在用的接口照 WF-RULE §10，牵涉观感取舍的交主会话。

**Codex 主线派工为主、自己不干等**（DECISION-234）：成段施工交子代理并行做，指挥官自己做控制与集成，也做小单。
- 做：控制子代理（拆单、派工、写简报、审交回的方案与代码、统一编译提交），契约与共享工程文件定案，跨模块集成与集成修错，小单，和主会话通信。
- 子代理在跑时不干等：主会话的消息和来信到了即时处理，手上的事接着做；不用 sleep，sleep 期间收不到消息。

**施工默认用 gpt-6.1-sol 子代理**：Codex 主线名下所有任务的施工，包括内核、确定性、契约与存档迁移相关的任务，用 `spawn_agent` 开 gpt-6.1-sol，复杂的用 high 或 xhigh。任务的归属与审查权不变。

**gpt-6-astra 只做重难审计**（DECISION-249、DECISION-306）：Codex 侧的审查默认交 gpt-6.1-sol，收口结构审计也一样；只有重难的审查——跨模块根因、确定性、并发、资源寿命或存档迁移这类，或重大问题 gpt-6.1-sol 两次解决不了——Codex 主线才临时开一个 gpt-6-astra 子代理（xhigh）审计：只读，交回根因与改法即结束，施工仍交 gpt-6.1-sol。主会话要审计就写信请 Codex 主线开，信里写明是不是重难审查。其余一律用 gpt-6.1-sol。
