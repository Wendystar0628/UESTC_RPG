# WF-STATUS · 施工状态、队列与调研入队

> **范围**：本文规定施工状态文件怎么填、待派工队列怎么管、队列怎么平衡，交接单，以及作者给出新任务时的调研入队流水线与旁路单。
> **不在本文**：状态文件的实际内容（它在 git 之外）；工作包的划分与交付：ENG-WP；git 与推送：WF-RULE §7；派工、拆单与评审：WF-FLOW；额度与并发：WF-MODEL §9。
> **查阅**：先读 §0；状态文件怎么填看 §1；待派工队列与队列平衡看 §2；交接单看 §3；调研入队流水线与旁路单看 §4。

## 0 结论

1. **施工状态只记现在，放在 git 之外**（§1）：文件是 `E:\Project\UESTC_RPG\.collab\status\施工状态.md`，推送流水看 git，不记在里面。
2. **内容由主会话决定并维护，在派工和推送后更新**（§1）。
3. **"回报完成"不等于"已集成"**：推送到 `main` 才算集成（§1）。
4. **待派工队列**（§2）：审计采纳或新决定带来的工作先排队，依赖满足改"可派"，只有主会话派工。
5. **派工看整条流水线的队列平衡**，不只看额度（§2）。
6. **调研走入队流水线**（§4，D-224）：主会话派 Sonnet 子代理调研 → 审计 → 并入工作包 → 分配 → 入队；Sol 会话只接旁路单。

### 0.1 接入要点

- **想知道自己的包或别的包在施工表里的状态**：只读状态文件，不改；进度、阻塞和完成都经回报交派你的一方（§1）。
- **想知道某组契约能不能改**：看状态文件的"已冻结的契约组"；列在那里的组只增不改（§1）。
- **想知道一项新工作排到哪了、能不能开工**：看队列；只有主会话从"可派"条目里派工，子代理不自己领（§2）。
- **作者给出新任务、要先弄清怎么做**：主会话走调研入队流水线，每条建议先审计再入队（§4）。

## 1 施工状态文件怎么填

- **内容**：当前 `main` 的短号和提交首行；最近可运行入口（能启动并走通主线的那条命令和对应提交，还没有写"尚无"）；已冻结的契约组（逐组列出并记冻结时的提交，还没有写"尚无"）；已知问题；活跃工作包表；待派工队列表。
- **何时更新**：派工、推送、交接、冻结契约这四个时刻；其余时候不必改。派工加一行，状态写"已派工"；推送后改 `main` 和相关行，删掉做完的包，还要继续的包把最近提交换成新的；交接时把每一行改成此刻的实情；冻结契约时在"已冻结的契约组"里加这一组和提交。
- **活跃工作包表**同时是防打架的"谁在改什么"清单（WF-FLOW §2.1），简报的邻居栏从这里取。每列写什么：

| 列 | 写什么 |
| --- | --- |
| 包 | 编号，子包写到子包（`WP-35b`） |
| 目标 | 本轮要交的东西，一句话，引用 ENG-WP 的条目，不复述 |
| 执行者 | 子代理的名字和类型 |
| 改动路径 | 它正在改的独占目录或文件 |
| 最近提交 | 最近一次推送的短号；还没有写"—" |
| 状态 | 已派工、施工中、待评审（已推送并回报）、阻塞，四选一 |
| 阻塞 | 卡在什么上、等谁；没有写"—" |
| 下一步 | 下一个动作和由谁做 |

- **谁写**：主会话；文件在 git 之外，不跑 `gen_index.py`、不提交。
- **接手时**：先读状态文件，再用 `git status`、`git log --oneline -5` 核对；对不上以 Git 为准并改文件。工作区里有、但没写进状态文件的改动，接手人先问清楚再处理，不删。
- **不写**：推送流水、日报周报、讨论过程和评审意见；这些在 git 和会话里（WF-RULE §12）。

## 2 待派工队列与队列平衡

待派工队列是调研入队流水线的出口（§4）：审计采纳或新决定带来的工作先在这里排队，依赖满足后由主会话按优先级派工。队列表在状态文件里。

**规则**：
- **加条目**：审计完成、采纳的工作写进 ENG-WP 并分配了两侧任务后再加行；每侧各一行，"派往"写 Astra 或 Opus 侧，不写"待定"。编号 Q-nnn，三位递增；状态先写"排队"。
- **改"可派"**：依赖满足就改成"可派"，由主会话在推送和评审时顺带检查。
- **派工**：主会话按任务量、额度（WF-MODEL §9.1）与优先级，从"可派"条目里派工，建模包排在系统新功能之前（D-183）；派出后状态写"已派 → <任务单号>"。
- **移除**：条目完成后从表里删掉，历史交给 Git。
- **列**：编号、事项（一句话）、来源（审计或决定）、落到（包）、依赖、派往、优先级（高中低）、状态（排队、可派、已派 → 任务单号）。

**队列平衡：不让一类活积压**。开发是几道工序串起来的：待派（主会话）→ 在施工（子代理）→ 待评审（主会话）；另有等契约、接线与工程验收的（Astra）。某一条堆得太多，上游再快也只是在排队，还会让改同一批文件的单越积越多、互相等待。每次派工前看一眼各队列（任务单"状态"和施工状态活表）：
- **同一个上游压着 2 张以上下游**（一份契约、一次接线）：不再开依赖它的新单，把这个上游排到最前，必要时催一句。
- **待评审超过 3 条**：主会话先评审，不开新单。
- **某一方空着、它的输入在另一方手里**：把能解开它的那一件排到最前，例如 Astra 等 Opus 侧的验收就先审它。

### 2.1 施工队列与拆分

- **施工队列**是状态文件里的一张表，列现在要做的每一件活：号、做什么、目录、状态、谁、前置。一行一件，只碰一组目录，一般一小时内做完（WF-FLOW §2）。
- **重的活拆开**：要碰多组目录或要做很久的，按目录拆成带字母的几行（C-50a、C-50b），互不冲突的同时标"可派"；拆不开的在"做什么"里写明为什么。
- **状态**只用可派、进行中、待编译、等前置（前置列写号）、暂停五种；谁在做谁改，做完删行，历史交给 Git。
- **派活**：主会话和 Astra 都从这张表挑"可派"的行；主会话能派 Claude 子代理做的就接，"谁"写 Claude（D-234）。巡逻列出可派的行、前置已删可改可派的行，以及建议拆的重活。

## 3 交接单

- **交接单** `.collab/HANDOVER.md`：主会话写，只留进行中的事和现行模式；额度冻结与换账号时更新（WF-MODEL §9.4）。

## 4 调研入队流水线

作者给出新任务、要先弄清怎么做时走这条流水线：调研 → 主会话审计 → 更新或新增工作包 → 分配任务 → 入队（§2），再派子代理施工（D-224）。不经调研、由新决定带来的工作从第 3 步进入。

| 步 | 谁做 | 产出与落点 |
| --- | --- | --- |
| 1 调研 | 主会话按方向派 Sonnet 子代理（high），一个方向一个；每个方向既查业界的成熟做法，也结合本项目现状给建议 | `research/<日期>-r<nnn>-<主题>/` 下各方向报告与 `00-总览.md`（按优先级去重的建议表）；`research/INDEX.md` 标"待审" |
| 2 审计 | 主会话 | 每条建议标采纳（并入 WP-xx 或新增）、暂缓或不采纳，写在总览末尾"Opus 审计"和 INDEX 对应列 |
| 3 更新或新增工作包 | 主会话；大段撰写可派子代理 | 写进 ENG-WP：按归属逻辑定归属（ENG-WP §1.1），排波次 |
| 4 分配任务 | 主会话（审计时一并定） | 拆成两侧任务：Astra 侧管契约、共享接口、引擎与工程机制；Opus 侧管画面、风格、内容、建模与文档；每项写做什么、落哪个包、预计工作量（D-184）、依赖 |
| 5 入队 | 主会话 | 每侧各入一条或一组 Q-nnn，状态"排队"，派往写 Astra 或 Opus 侧，不写"待定" |

入队以后：Astra 侧条目由主会话写进 `notes/astra/` 通知排期，Opus 侧条目按 WF-FLOW §2 派工；依赖满足后改"可派"，派出后写任务单号，完成后移除。

### 4.1 调研与旁路单

- **调研**：主会话直接派 Sonnet 子代理（high），按方向分，一个方向一个，同时跑。简报写背景、方向（每个写为什么现在值得查）和输出目录；派之前先读 `research/INDEX.md` 去重。每个方向的报告都要有两部分：业界的成熟做法（带出处），以及结合本项目现状的建议（归哪个包或建议新包、主线版还是细节阶段、工作量、依赖）。总览写完把 INDEX 标"待审"。
- **用完就删**：调研目录不归档。不采纳的审计完就删；采纳的，等引用它的任务单都结案再删，巡逻会列出可删的。每个调研目录在 INDEX 都有一行，删时这行留着：总览列写"已删"，审计列写结论落在哪（D 编号、文档或工作包），新调研前照旧读 INDEX 去重。
- **三个视角**：制作完整度（内容量、系统与管线覆盖、测试、性能与稳定、存档稳健、本地化、无障碍）；优越性（与同类作品比的长短处、差异化、让人记住的时刻）；玩家体验（上手、节奏、舒适度、操作摩擦、加载等待、手感反馈、重玩理由）。
- **不调研**：本项目是个人实验作品（D-181），不查商店页、上架、宣传、成就、云存档、平台集成；"发布完整度"只看按 OPS-RELEASE 在 GitHub 发整包时的完整与稳健。调研只给建议，观感取舍由主会话定。
- **旁路单** `side/cards/s<nnn>-<主题>.md`：某件事不在主线关键路径上却会占主线时间，或要大量补信息、批量核对数据时，由主会话写，发进 Sol 会话（WF-COMMS §5）；写明在哪做、交付什么、能改什么、不许做什么。Sol 会话做完在末尾"状态"写结果。
