# WF-STATUS · 施工状态、队列与调研入队

> **范围**：本文规定施工状态文件怎么填、施工队列的格式与即时维护、队列怎么平衡，交接单，以及作者给出新任务时的调研入队流水线与旁路单。
> **不在本文**：状态文件的实际内容（它在 git 之外）；工作包的划分与交付：ENG-WP；git 与推送：WF-RULE §7；派工、拆单与评审：WF-FLOW；额度与并发：WF-MODEL §9。
> **查阅**：先读 §0；状态文件怎么填看 §1；施工队列与队列平衡看 §2；交接单看 §3；调研入队流水线与旁路单看 §4。

## 0 结论

1. **施工状态只记现在，放在 git 之外**（§1）：文件是 `E:\Project\UESTC_RPG\.collab\status\施工状态.md`，推送流水看 git，不记在里面。
2. **内容由主会话决定并维护，在派工和推送后更新**（§1）。
3. **"回报完成"不等于"已集成"**：推送到 `main` 才算集成（§1）。
4. **施工队列**（§2，D-235）：要做的活都在一张表里，一行一件、只碰一组目录；派单前加行，接活改进行中，交回改待编译，提交后删行，钩子和巡逻盯着。
5. **派工看整条流水线的队列平衡**，不只看额度（§2）。
6. **调研走入队流水线**（§4，D-224）：主会话派 Sonnet 子代理调研 → 审计 → 并入工作包 → 分配 → 入队；旁路单交 Codex 主线开子代理做。

### 0.1 接入要点

- **想知道自己的包或别的包在施工表里的状态**：只读状态文件，不改；进度、阻塞和完成都经回报交派你的一方（§1）。
- **想知道某组契约能不能改**：看状态文件的"已冻结的契约组"；列在那里的组只增不改（§1）。
- **想知道一项活排到哪了、能不能开工**：看施工队列；子代理不自己领活、不改队列，由派它的指挥改（§2）。
- **作者给出新任务、要先弄清怎么做**：主会话走调研入队流水线，每条建议先审计再入队（§4）。

## 1 施工状态文件怎么填

- **内容**：当前 `main` 的短号和提交首行；最近可运行入口（能启动并走通主线的那条命令和对应提交，还没有写"尚无"）；已冻结的契约组（逐组列出并记冻结时的提交，还没有写"尚无"）；已知问题；各类单号的下一个号；施工队列（§2）。
- **何时更新**：派工、推送、交接、冻结契约这四个时刻；其余时候不必改。派工前在施工队列加行；推送后改 `main` 和相关行，做完的行删掉；交接时把每一行改成此刻的实情；冻结契约时在"已冻结的契约组"里加这一组和提交。
- **谁写**：主会话；文件在 git 之外，不跑 `gen_index.py`、不提交。
- **接手时**：先读状态文件，再用 `git status`、`git log --oneline -5` 核对；对不上以 Git 为准并改文件。工作区里有、但没写进状态文件的改动，接手人先问清楚再处理，不删。
- **不写**：推送流水、日报周报、讨论过程和评审意见；这些在 git 和会话里（WF-RULE §12）。

## 2 施工队列与队列平衡

要做的活都在状态文件的"施工队列"这一张表里，暂停的也在（D-235）。任务单和 ENG-WP 放细节，队列只记谁在做什么、做到哪；状态只在这里，任务单不写状态（WF-COMMS §3.1）。

**格式**：表头固定为 `| 号 | 做什么 | 目录 | 状态 | 谁 | 前置 |`。

- **号**：前缀字母加数字，同表唯一，接着同前缀的最大号往下编；拆出的子行在号后加小写字母（C-30a）；旁路单用 S 加旁路单号（S-007）。
- **做什么**：一句话，指向任务单或 ENG-WP 条目，不抄细节；拆不开的重活写明原因。
- **目录**：要改的目录；还没定到目录的写工作包号。
- **状态**：只用可派、进行中、待编译、等前置、暂停。
- **谁**：Codex 或 Claude（Codex 指 Codex 主线和它的子代理，Claude 指主会话和它的子代理）；空着表示没人接。
- **前置**：要先做完的行号；等主会话拍板的写"需定"，内容在【需定】来信里（WF-COMMS §4）。
- 越靠上越先做。

**一行一件**：一行只碰一组目录，一般一小时内做完（WF-FLOW §2）。要碰多组目录或做很久的，按目录拆成能并行的子行。

**即时维护**：谁动谁改；钩子在建任务单、派子代理、提交时提醒，巡逻核对。

- **加行**：派单方在建任务单或开子代理之前加行；审计采纳的新活也这时加（§4）。
- **接活**：状态改进行中，"谁"写上；主会话能派 Claude 子代理做的就接（D-234）。
- **交回**：指挥收到子代理交回改待编译。
- **做完**：提交推送后删行，提交说明首行带行号（WF-RULE §7），历史交给 Git。
- **前置做完**：前置的行删了，依赖它的行改可派。
- 子代理不改队列，由派它的指挥改。

**队列平衡：不让一类活积压**。可派的活堆着没人接、某一方的输入压在另一方手里，上游再快也只是在排队。每次派工前看一眼队列：
- **同一个上游压着 2 行以上下游**（一份契约、一次接线）：把这个上游排到最前，必要时催一句。
- **某一方空着、它的输入在另一方手里**：把能解开它的那一行排到最前。

## 3 交接单

- **交接单** `.collab/HANDOVER.md`：主会话写，只留进行中的事和现行模式；额度冻结与换账号时更新（WF-MODEL §9.4）。

## 4 调研入队流水线

作者给出新任务、要先弄清怎么做时走这条流水线：调研 → 主会话审计 → 更新或新增工作包 → 分配任务 → 入队（§2），再派子代理施工（D-224）。不经调研、由新决定带来的工作从第 3 步进入。

| 步 | 谁做 | 产出与落点 |
| --- | --- | --- |
| 1 调研 | 主会话按方向派 Sonnet 子代理（high），一个方向一个；每个方向既查业界的成熟做法，也结合本项目现状给建议 | `research/<日期>-r<nnn>-<主题>/` 下各方向报告与 `00-总览.md`（按优先级去重的建议表）；`research/INDEX.md` 标"待审" |
| 2 审计 | 主会话 | 每条建议标采纳（并入 WP-xx 或新增）、暂缓或不采纳，写在总览末尾"Opus 审计"和 INDEX 对应列 |
| 3 更新或新增工作包 | 主会话；大段撰写可派子代理 | 写进 ENG-WP：按归属逻辑定归属（ENG-WP §1.1），排波次 |
| 4 分配任务 | 主会话（审计时一并定） | 拆成两侧任务：Codex 侧管契约、共享接口、引擎与工程机制；Opus 侧管画面、风格、内容、建模与文档；每项写做什么、落哪个包、预计工作量（D-184）、依赖 |
| 5 入队 | 主会话 | 按 §2 加进施工队列，一行一件，"谁"写 Codex 主线或 Claude，前置写行号 |

入队以后：Codex 主线的行由主会话写信知会，Claude 的行按 WF-FLOW §2 派工；之后照 §2 维护。

### 4.1 调研与旁路单

- **调研**：主会话直接派 Sonnet 子代理（high），按方向分，一个方向一个，同时跑。简报写背景、方向（每个写为什么现在值得查）和输出目录；派之前先读 `research/INDEX.md` 去重。每个方向的报告都要有两部分：业界的成熟做法（带出处），以及结合本项目现状的建议（归哪个包或建议新包、主线版还是细节阶段、工作量、依赖）。总览写完把 INDEX 标"待审"。
- **用完就删**：调研目录不归档。不采纳的审计完就删；采纳的，等引用它的任务单都结案再删；不用每轮都清，巡逻攒到 3 个以上才提醒，主会话在收尾时一起删。每个调研目录在 INDEX 都有一行，删时这行留着：总览列写"已删"，审计列写结论落在哪（D 编号、文档或工作包），新调研前照旧读 INDEX 去重。
- **三个视角**：制作完整度（内容量、系统与管线覆盖、测试、性能与稳定、存档稳健、本地化、无障碍）；优越性（与同类作品比的长短处、差异化、让人记住的时刻）；玩家体验（上手、节奏、舒适度、操作摩擦、加载等待、手感反馈、重玩理由）。
- **不调研**：本项目是个人实验作品（D-181），不查商店页、上架、宣传、成就、云存档、平台集成；"发布完整度"只看按 OPS-RELEASE 在 GitHub 发整包时的完整与稳健。调研只给建议，观感取舍由主会话定。
- **旁路单** `side/cards/s<nnn>-<主题>.md`：某件事不在主线关键路径上却会占主线时间，或要大量补信息、批量核对数据时，由主会话写，交 Codex 主线开子代理做（WF-COMMS §5）；写明在哪做、交付什么、能改什么、不许做什么。做完由子代理在末尾"结果"写结果；做到哪看施工队列的 S 行（§2）。
