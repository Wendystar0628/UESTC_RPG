# WF-QUOTA · 账号与额度

> **范围**：本文规定额度怎么用：口径，子代理开多少（按任务量，额度只做刹车），临近重置时的节奏，Codex 账号与速度层，主账号额度见底时怎么办。
> **不在本文**：按难度选模型与推理档：WF-MODEL；队列平衡：WF-STATUS §2；子代理恢复还是新开：WF-MODEL §7。
> **查阅**：先读 WF-QUOTA §0；口径看 WF-QUOTA §1；开多少与刹车看 WF-QUOTA §2；节奏看 WF-QUOTA §3；Codex 账号看 WF-QUOTA §4；冻结看 WF-QUOTA §5。

## 0 结论

1. **开多少按任务量定**（WF-QUOTA §2，D-226）：有几路互不冲突、按目录分得开的活就开几个，不设固定个数上限；Claude 与 Codex 两侧都一样。
2. **额度只做刹车**（WF-QUOTA §2）：派工前读用量；照现在的速度会在重置前用完，就少开或改派便宜模型，在跑的不中断。
3. **临近重置还剩得多就用足**（WF-QUOTA §3，D-196）：作者说"加快"或"慢慢用"时以作者的话为准。
4. **Codex 账号额度充足、不监控**（WF-QUOTA §4）：杂活默认先派 Sol；GPT 侧一律普通速度（D-197）。
5. **主账号剩余约 1% 时冻结**（WF-QUOTA §5）：停止派一切新活，等在跑的做完，由作者手动切换账号。

### 0.1 接入要点

- **派单、选 Opus 还是 Sonnet、决定开几个之前**：先看最近一次用量读数，读数超过 15 分钟就重读；开几个按任务量定，额度紧时少开（WF-QUOTA §2）。
- **主账号剩余约 1%**：停止派新活（WF-QUOTA §5）。

## 1 口径

本文的订阅容量与扣额估计只用于本项目排程，以作者实数和项目经验为准，不作 API 报价。

## 2 开多少与刹车

- **按任务量开**：先按目录把活分成互不冲突的几路（WF-FLOW §2.1），有几路就开几个子代理；同一批文件同一时间只有一个写者。截图与重 CPU 任务照样排构建锁（ENG-ARCH §6）。
- **省额度靠选模型**：能交 Sonnet 的不交 Opus，机械活交 Sonnet medium 或 gpt-6-luna（WF-MODEL）；子代理默认新开、靠任务单交接，长上下文接新活每一轮都在为旧历史付费（WF-MODEL §7）。
- **刹车**：派工前用 `get_usage` 读 5 小时与每周两个窗口的用量和恢复时间，读数超过 15 分钟就重读。照现在的速度会在恢复前用完，就少开新的或改派便宜模型，在跑的不中断。粗估：5 小时窗口约够 30 个 Opus 子代理小时，Sonnet 一小时约合四分之一个 Opus 小时。

## 3 节奏（D-196）

- 离重置还早时不赶，按任务量正常开。
- 临近重置还剩得多就用足：每周额度离重置不到 24 小时、或 5 小时窗口离重置不到 1 小时而每周额度宽裕时，照现在的速度到重置还会剩 10% 以上，就多开、两难的活用 Opus；剩余低于约 20% 时少开新的。
- 作者说"加快"或"慢慢用"时以作者的话为准；周额度由作者自己调节，不加"用量快于时间进度就降并发"之类的兜底。

## 4 Codex 账号（Astra 与 Sol）

- **额度充足、不监控**：杂活默认先派 Sol；重置时机由作者自己决定，套餐额度用完会自动使用账户余额。
- **速度**：GPT 侧一律用普通速度（D-197）；快速模式（`service_tier="priority"`，约 2 倍速、2.5 倍额度）本项目不用。

## 5 额度见底时冻结

主会话每次处理事件时查一次本账号的额度（`get_usage`）。主账号的任一额度窗口（5 小时或每周）剩余约 1% 时冻结：停止派一切新活，等在跑的做完，由作者手动切换账号。冻结时主会话在 `HANDOVER.md` 更新"进行中的事"，供切换后的会话接着做（WF-STATUS §3）。换账号时原会话开的 来信监视 inbox_wait 会随它一起停掉，接续的会话先查进程再重开，同一时刻只能有一个在跑。
