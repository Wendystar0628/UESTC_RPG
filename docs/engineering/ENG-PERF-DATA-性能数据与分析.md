# ENG-PERF-DATA · 性能数据与分析

> **范围**：性能记录的四层与写入方、记录开关与会话（§1），原始流与时间基（§2），指标口径与非稳态帧（§3），测量范围（§4），判定归属（§5），比较、索引与保留（§6），开销目标（§7）。
> **不在本文**：怎么采集、诊断与调优（ENG-PERF-MEASURE）；预算与目标数值（ENG-BUDGET）；自适应与帧节奏（ENG-PERF-ADAPT）；画面页的界面（UI-NAV）；失败登记（ENG-FAILS）；观察台性能页（`dashboard/README.md`）。
> **查阅**：先读 §0；四层、开关与会话看 §1；原始流看 §2；指标口径看 §3；测量范围看 §4；判定归属看 §5；比较、索引与保留看 §6；开销看 §7

## 0 结论

1. **四层单向，每层一个写入方**：帧统计写逐帧样本，记录服务写原始数据，`scripts/perf` 分析器写指标、派生与索引，观察台与 `perf.py` 只读（§1，DECISION-325）。
2. **记录开关只管记不记**：默认关、即时生效，不是画质项；基础计时常开，与开关无关；AI 用 `--perf-out`，不读写作者设置（§1.2，DECISION-326）。
3. **作者与 AI 写同一套六件**：只差清单来源与 AI 的 `run.json`；字段与格式以 `perf-fields.json` 为准，未知与丢失留 null（§2，DECISION-327、DECISION-328）。
4. **口径只有一处**：本文写定义与取哪些帧，实现只在 `scripts/perf`；原始带 `schema`、派生带 `calc`，只认当前，`calc` 变了重算（§2.2、§3，DECISION-329）。
5. **阈值不进文档**：预算线与痛点阈值见 `budgets.json`（`deviceTargets`、`perfAnomalies`、`waits`），其余见 `perf-fields.json`、`KernelBudgets` 与分析器常量（§3）。
6. **五段只作关联阶段**：回调边界 B0–B4 之间的墙钟区间，不当纯 CPU 成本；主线程周期只记原始增量（§3.2，DECISION-330）。
7. **隔离桌面只判成本**：体验字段只来自作者开着记录的交互桌面会话（§4，DECISION-331）。
8. **分析器只出数，不下判定**：游戏内只做卡死看门狗与离散事件；分析器出指标、与上一次的差和预算对照，不判异常、不判运行有效与否、不自动登记失败（§5，DECISION-332）。
9. **低 GPU 占用只作背景**：占用率、归一负载与频率变化不据以判瓶颈（§3.1，DECISION-333）。
10. **作者根按条数与容量修剪，AI 根不自动删**（§6，DECISION-337）。

### 0.1 接入要点

- **读性能数据或引用性能数**：只经 `perf.py`，不打开逐帧原始文件；先按 ENG-PERF-MEASURE §3 取最新数据（§2）。
- **增删或改原始字段**：先改 `perf-fields.json` 并把 `schema` 加 1，记录服务与分析器同批改；物理量带单位后缀，比例 0–1，缺值 null（§2.2）。
- **改指标定义**：先改本文 §3，再改分析器，`calc` 加 1，现存原始数据下次分析时按新口径重算（§2.2）。
- **新增转场、加载或会改画面设置的流程**：按 §3 判断它是否产生非稳态帧，是就登记进 `perf-fields.json` 的非稳态规则（§3）。
- **新增要计 GPU 时间的视口**：经帧统计契约登记为受测视口，每帧报告本轮是否绘制，关闭或卸载时注销（§3.2）。
- **在游戏里读写性能记录或加性能判定**：不做；只有记录服务读写性能记录，别处只发离散事件（§1、§5）。

## 1 四层与写入方

### 1.1 四层

- **采样**：帧统计（`Kernel.Frame`）是视口计时与逐帧样本的唯一写入方，计时常开；性能条与记录服务只读它的样本与显示窗。
- **记录**：记录服务（`Kernel.Inspect`）是原始数据的唯一写入方：会话、帧环、事件、慢采样、硬件样本与卡死看门狗都经它落盘；游戏内只有它读写性能记录，仓库脚本只读作者根。
- **分析**：`scripts/perf` 的分析器是指标、派生与索引的唯一写入方，原始数据只读。
- **展示**：观察台性能页与 `perf.py` 只读分析器的产出，不自算口径、不另存历史。
- **分析触发**：作者会话由启动入口在游戏退出后分析；AI 会话由 `run.ps1` 一批跑完后分析；观察台只读、不补跑。两处共用 `output/perf/.lock` 串行化，输入（原始文件、`calc`、字段字典与 `budgets.json`）没变的会话不重算；会话目录仍被写入锁占用时跳过它。

### 1.2 记录开关与会话

- **开关**：画面页"性能信息"组的"记录性能数据"，与"显示性能信息"各管各。默认关；即时生效，开即起新会话，关即停接并后台排空。
- **记录意图**：一个设置键，由记录服务经设置存储登记与唯一读写，存 `settings.json` 的 `ui` 节、跨启动保持；不是画质项，不随预设与恢复默认变，界面不经设置界面行写它。
- **关着记录**：不建数据文件、不起写盘线程、不开硬件会话；不做关记录时的黑匣子。
- **AI**：`--perf-out=<绝对路径>` 隐含开记录，不读写作者设置。
- **会话是应用级的**：回标题与再次入场不断会话，地图相关订阅随作用域解除、重接；快速开关串行处理。
- **五态**：Off、Starting、Recording、Stopping、Faulted，状态变化发事件；真正开始写入才进 Recording，排空完才回 Off。故障原因用契约的故障码，界面按码取文案，不转写异常文字。
- **停止、退出与失败走同一路径**：停接 → 停止并回收生产者 → 写盘排空 → 关文件 → 最后发布清单；退出经应用退出参与者走这条路。写盘失败时会话进 Faulted，原异常保留在记录服务的结束结果里并经 `IDiagnosticLog` 输出，已写数据保留，游戏照常运行；未排空完不标已关闭。

### 1.3 线程分工

- **帧环只有主线程一个生产者**：记录服务订阅帧统计的样本发布通知，在主线程入队，不另设轮询采样步。
- **唯一写盘线程**：硬件线程与卡死看门狗各自把值数据交给它；它只用线程安全的单调时钟与捕获的值，不读场景树与服务。
- **卡死看门狗独立循环**：不与写盘、NVML 查询共用执行循环；读段号、采集帧号与单调时刻取一致快照。
- **主线程不等磁盘**：帧环满了丢行并记 gap（累计丢失条数与首末序号），会话标不完整；不覆盖未消费的数据。

## 2 原始流与时间基

### 2.1 六件与存放

每个会话一个目录，作者与 AI 写同一套六件（DECISION-328）：

- `manifest.json` 会话清单：构建、软硬件、显示与窗口、所在桌面、帧节奏、画质请求值与生效值、启动参数、运行时预算与字段字典快照、时钟锚点，条目以 `perf-fields.json` 为准；中途变化记事件，会话结束最后原子发布。构建身份（提交、是否有未提交改动、程序集 MVID）取自原生构建成功时写下的旁文件；AI 采样段开始时另记当时的显示、渲染尺寸、画质与帧节奏条件；取不到的条目写缺失原因（DECISION-353）。
- `frames.csv`：逐帧样本，每个采集帧一行。
- `samples.csv`：2 Hz 慢采样（位姿、模式、世界、内存与进程 CPU）。
- `hw.csv`：1 Hz 硬件样本；能耗与限频时间记区间增量，各限频时间可重叠、不相加。
- `hwfast.csv`：NVML 驱动样本缓冲，只作背景趋势，不保证捕获单次短卡顿。
- `events.jsonl`：离散事件，见下条。

**玩家行为**只订阅现有权威服务（应用流程、地图与到达、观者与镜头、行走、界面表面、世界、画质、存档）与视口尺寸信号，记请求与实际完成；加载与传送记等待起止与真实就绪；不截获输入、不另造监听层；所在格与最近点位由分析器推出。

**来源差别**：清单的 `origin` 区分作者与 AI；AI 运行另有 `run.json`，不另起格式；诊断产物不进记录（ENG-PERF-MEASURE §4）。

**存放**：作者根 `%APPDATA%\UESTC\perf\`，含 `latest.json` 与各会话目录，写入期间会话目录持 `.lock`，只由记录服务读写与修剪；AI 根是主检出的 `output/perf/runs/<来源名>/<场景>/<会话>/`；派生在 `output/perf/derived/<会话>/`（摘要），另有 `output/perf/index.json`，只由分析器写。

**根级状态 `latest.json`**：每个输出根一份，只由记录服务原子替换。真正写出会话开始与时钟锚点之后才发布"记录中"；关闭时先原子发布正式 `manifest.json`，再改为"已关闭"。会话是否完成只认正式清单加可独占的锁，不另设完成标记；只剩 `manifest.pending.json` 且锁能独占的按已结束的不完整会话处理。观察台判"正在记录"只读 `latest.json`，不读逐帧文件。

### 2.2 字段、版本与时间基

- **字段**：原始字段的名称、列序、类型、单位与含义以 `game/data/perf-fields.json` 为准，启动时核对、快照进清单；派生字段的字典在 `scripts/perf`。命名用 ASCII camelCase，物理量带单位后缀，比例 0–1（展示时再乘 100），容量写 MiB。
- **缺值**：未知与丢失按字段、按区间留 null，不用 0 补；硬件样本缺只使硬件字段缺失。
- **版本**：原始流带格式号 `schema`，增删字段或改含义就加 1；派生带口径版本 `calc`，指标定义一改就加 1，并重算仍在的原始数据；分析器按每份原始数据自带的字段字典快照解析，当前口径要的字段语义都在就按当前口径重算，不写按 `schema` 的分支、不改旧原始数据（DECISION-355）；索引的 `calc` 与当前不符时，`perf.py` 与 G10 要求先重跑分析。
- **时间基**：逐帧与事件用单调时钟；采集帧号取 `Engine.GetProcessFrames()`，不是 GPU 完成序号；事件按自己的单调时刻按区间关联到帧。
- **挂钟**：记录服务可读系统挂钟，只用于会话 ID、开始时刻与定时锚点（G4 例外，DECISION-338）；会话 ID 写 `yyyyMMdd-HHmmss-play|ai`，同秒冲突追加序号。

## 3 指标口径

口径定义在本文，计算只在分析器。

- **记号**：Δt 为帧间隔，第 f 行的 Δt 覆盖上一个 B1 到本行 B1。T 为生效上限对应的目标帧时，开垂直同步时与刷新率取小；不限帧时为 null，依赖 T 的指标也为 null。
- **采样段**：AI 会话只取 `run.json` 指定的采样段 Begin 到 End 之间的行，帧要整帧落在段内；作者会话取整场。等待从整场事件取，不受采样段裁剪。
- **摘要两份**：全体与稳态，稳态去掉非稳态帧与上下文不完整的帧。
- **非稳态帧**：不进稳态摘要，不触发自动调节降级（ENG-PERF-ADAPT §1.1）；原始帧照记，由上下文位标出。包括：转场（快进、换季、跳转、传送、切图、模式切换）、读档、新游戏、画面设置生效与窗口尺寸或模式变化的期间及之后的稳定时长（DECISION-345）；存档抓缩略图的那一帧；Title、Entering、Leaving 全部帧。换天气的过渡是慢变化，不算。判定规则与稳定时长在 `perf-fields.json` 的非稳态规则。
- **分布**：每项给样本数、均值、p50、p95、p99、p99.9 与最大值，分位取升序第 ⌈q·N⌉ 个（最近秩）；缺测不进样本。
- **场景指标**：稳态的主视口 GPU、视口 CPU 渲染、帧准备 CPU 与五段各自的 p95，已确认的受测视口 GPU 合计 p95，全体的工作集与引擎显存记账 p95，以及 `run.json` 里的手动存档耗时与关闭耗时。
- **预算对照**：主视口 GPU、视口 CPU 渲染、帧准备 CPU 三项的 p95 对 `deviceTargets` 开发机项的上沿，给差值与出处，不判达标（ENG-BUDGET §2）。
- **与上一次的差**：同场景的 AI 会话按结束时刻取最近两次，每个场景指标给上次值、差值与变化比例。
- **等待**：加载、进场、传送、回标题与退出各取请求到真实就绪的墙钟秒数，并列 `budgets.json` 的 `waits` 上限；端点缺测写原因。启动三项从 `run.ps1` 的脚本入口起算，还没有双击起点，只作参考（DECISION-331）。

### 3.1 体验口径

只在交互桌面会话出（§4）。

- **帧率**：平均帧率 = 1000·N / ΣΔt；跨 gap 与 Δt 无效的帧不进 N。
- **帧时分位**：Δt 的分布，同 §3 的分位取法。
- **1% / 0.1% low**：取最慢 k = ⌈0.01N⌉ / ⌈0.001N⌉ 帧，值为 1000·k / 这 k 帧的 ΣΔt；N 不足 100 / 1000 记 null；同时给尾样本数，不声称与外部工具逐值一致。
- **掉帧**：Δt 超过 T 的掉帧倍数即掉帧；掉帧率 = 掉帧数 / N，掉帧时间占比 = 掉帧的 ΣΔt / 总 ΣΔt。
- **卡顿**：Δt 超过重卡线的帧数折成每分钟，另计超过严重线的帧数；两条线在 `perfAnomalies`。
- **帧节奏**：原时间线上相邻、都有效且都稳态的两帧 |Δtᵢ − Δtᵢ₋₁| 的 p95，不跨 gap。
- **GPU 忙比**：受测视口 GPU 合计 / ΣΔt，只覆盖受测视口，不是全进程 GPU 忙时。
- **占用率与归一负载**：占用率是渲染适配器 NVML 样本均值（整卡、采样窗内有内核在跑的时间比、相对当前频率）；归一负载 = 占用 × 当前频率 / 最高频率，可大于 1，只提示可能的调频影响；两者与频率变化只作背景，不据以判瓶颈（DECISION-333）。

### 3.2 成本口径

两类会话都出。`deviceTargets` 开发机项的 GPU p95 对主视口 GPU，CPU p95 对视口 CPU 渲染，帧准备另有一项，各分上沿与停线（ENG-BUDGET §2）。

- **五段**：物理、逻辑、延迟、绘制、尾段是回调边界之间的墙钟区间，边界为 B0 物理帧信号、B1 FadeClock 步、B2 Stage 采样点、B3 绘制前信号、B4 绘制后信号。physMs = 本轮 B1 − B0（0 个物理步时 B0 = B1、为 0；多步只记首步并累计步数）；procMs、lateMs、drawMs 取上一轮的 B2 − B1、B3 − B2、B4 − B3；tailMs = 本轮 B0 − 上一轮 B4。边界齐全且有序时五段之和等于本行 Δt；边界缺失、次序不符或线程模型不是 Safe 时本行分段标不可用，不复用旧边界。段名只定位阶段，不据段名断言在等什么，也不当纯 CPU 成本。
- **主线程周期**：mainCycles、drawCycles 是整帧与绘制段的线程周期原始增量，不换算毫秒，分析器不用。
- **GPU 渲染**：主视口每帧绘制，其引擎计时读数约晚两次绘制，按近似对齐（±2 帧）记为成本样本，不用于逐帧尖峰归因；本帧未绘制或窗口不能绘制时写 null，恢复绘制后的头几帧按 §3 的非稳态规则剔除。按需绘制的视口（倒影等）各一列，来源与新鲜度未确认的写 null；受测视口 GPU 合计只合已确认的视口，有未确认的就为 null（DECISION-342）。
- **CPU 渲染**：帧准备 CPU（本轮写入）与各视口 CPU（延迟回读，主视口同样按近似对齐记）分列，不默认同帧；视口 CPU 是墙钟跨度，含等待与抢占，不是线程 CPU 时间。
- **其余成本量**：可见与阴影的调用和图元、五类管线编译与 JIT 的增量合计、GC 停顿与各代次数、分配字节、流式挂载与积压、内存与显存、渲染适配器的硬件样本；GC 与分配是全进程量，不算某个函数的成本。
- **不判瓶颈**：成本口径只列各成本量与预算对照。

## 4 测量范围与 `scope`

隔离桌面只出成本口径；会话的 `scope` 取 `cost` 或 `full`，由清单里的桌面事实定（DECISION-331）。

- **桌面事实**：清单记所在桌面（交互或隔离）与窗口的可见、焦点；`scope` 只按它定，不按来源定。
- **`full`**：交互桌面且是当前输入桌面，§3.1 与 §3.2 都出。
- **`cost`**：其余情况只出 §3.2；§3.1 各项写 null 并注原因（隔离桌面不测，或桌面事实未确认），展示时写原因、不画 0。

## 5 判定归属

游戏内只做卡死看门狗与离散事件，不做性能判定；分析器只出 §3 的数，不判异常、不判运行有效与否、不自动登记失败（DECISION-332）。

- **越线与痛点**：由读数的一方按 `budgets.json` 的线判（ENG-PERF-MEASURE §6）；是否登记为失败按 ENG-FAILS §0 第 2 条判。
- **卡死**：卡死看门狗的事件留在原始流，分析器不汇总；看门狗可能迟报或漏报，进程挂起或突然退出时不保证有末尾事件。

## 6 比较、索引与保留

- **比较**：只比同场景、同来源的会话；分析器不核两次的条件与构建身份，画质、分辨率或构建配置不同的差值不下结论（条件在各自清单里）。
- **索引**：`index.json` 有 `calc`、`sessions`（每个会话的 ID、来源、场景、`scope`、结束时刻、场景指标与预算对照）、`scenes`（每个场景最近一次 AI 会话的 `id`、上一次的 `previousId`、`metrics`、`delta`、`budgets`）与 `errors`（分析失败的会话与原因）；会话不分状态，不另存历史。观察台、`perf.py` 与 G10 只读它与派生。
- **作者根**：由记录服务在开新会话时修剪，保留最近若干次，且已关闭会话合计不超过容量上限（`KernelBudgets`）；不限单次录制长度。只删已关闭、锁可独占的整会话，不碰存档、设置与日志（DECISION-337）。
- **AI 根与派生**：分析器不删；旧来源按需整批删，下次分析时从索引里去掉。
- **清理工具**：`output/perf` 在 `clean-artifacts.py` 的保留名单里。

## 7 开销目标

记录开着时主线程的采样与入队有每帧耗时目标且零托管分配，首次完整链闭环时实测核对；性能记录开着时启动测量照常计时（DECISION-256）。

- **主线程**：只做采样与入队；零托管分配只在采样调用前后核主线程分配，全进程分配计数不作证据；核对在引擎内测试宿主里离线做，零分配由回归测试守，耗时按数量级记（DECISION-351）。
- **写盘与硬件**：写盘、硬件采样与卡死看门狗都在主线程之外；帧环按约定的秒数留容量，不保证跨过任意长的写停顿，跟不上就丢行记 gap（§1.3）。
- **体积**：按实测行长核算，总量由 §6 的保留控制。
- **核对口径**：开销与体积按数量级判断，在数量级内即放行（WF-RULE §15）。
