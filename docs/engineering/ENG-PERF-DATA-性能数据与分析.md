# ENG-PERF-DATA · 性能数据与分析

> **范围**：性能记录的四层与写入方、记录开关与会话（§1），原始流与时间基（§2），指标口径与非稳态帧（§3），测量范围（§4），异常（§5），比较键、状态与保留（§6），开销目标（§7）。
> **不在本文**：怎么采集、诊断与调优（ENG-PERF-MEASURE）；预算与目标数值（ENG-BUDGET）；自适应与帧节奏（ENG-PERF-ADAPT）；画面页的界面（UI-NAV）；失败登记（ENG-FAILS）；观察台性能页（`dashboard/README.md`）。
> **查阅**：先读 §0；四层、开关与会话看 §1；原始流看 §2；指标口径看 §3；测量范围看 §4；异常看 §5；比较键与保留看 §6；开销看 §7

## 0 结论

1. **四层单向，每层一个写入方**：帧统计写逐帧样本，记录服务写原始数据，`scripts/perf` 分析器写指标、异常、派生与历史，观察台与 `perf.py` 只读（§1，DECISION-325）。
2. **记录开关只管记不记**：默认关、即时生效，不是画质项；基础计时常开，与开关无关；AI 用 `--perf-out`，不读写作者设置（§1.2，DECISION-326）。
3. **作者与 AI 写同一套六件**：只差清单来源与 AI 的 `run.json`；字段与格式以 `perf-fields.json` 为准，未知与丢失留 null（§2，DECISION-327、DECISION-328）。
4. **口径只有一处**：本文写定义与取哪些帧，实现只在 `scripts/perf`；原始带 `schema`、派生带 `calc`，只认当前，`calc` 变了重算（§2.2、§3，DECISION-329）。
5. **判据的数不进文档**：倍数、窗口、帧数、合并间隔与保留数见 `budgets.json` 的 `perfAnomalies`、`perf-fields.json`、`KernelBudgets` 与分析器常量（§3）。
6. **五段只作关联阶段**：回调边界 B0–B4 之间的墙钟区间，不当纯 CPU 成本；主线程周期只记原始增量，不进判据（§3.2，DECISION-330）。
7. **隔离桌面只判成本**：体验字段只来自作者开着记录的交互桌面会话；加载墙钟与主线程长停两条单边判例外（§4，DECISION-331）。
8. **判定全在分析器**：游戏内只做卡死看门狗、离散事件与测量自检；分析器不自动登记失败（§5，DECISION-332）。
9. **低 GPU 占用只作背景**：GPU 空等类异常只记候选窗口，瓶颈保留"不定"（§3.1、§5，DECISION-333）。
10. **保留按条数不按日历**（§6，DECISION-337）。

### 0.1 接入要点

- **读性能数据或引用性能数**：只经 `perf.py`，不打开逐帧原始文件；先按 ENG-PERF-MEASURE §3 取最新数据（§2）。
- **增删或改原始字段**：先改 `perf-fields.json` 并把 `schema` 加 1，记录服务与分析器同批改；物理量带单位后缀，比例 0–1，缺值 null（§2.2）。
- **改指标定义或异常判据**：先改本文 §3、§5，再改分析器，`calc` 加 1 并重算现存原始数据（§2.2）。
- **新增转场、加载或会改画面设置的流程**：按 §3 判断它是否产生非稳态帧，是就登记进 `perf-fields.json` 的非稳态规则（§3）。
- **新增要计 GPU 时间的视口**：经帧统计契约登记为受测视口，每帧报告本轮是否绘制，关闭或卸载时注销（§3.2）。
- **在游戏里读写性能记录或加性能判定**：不做；只有记录服务读写性能记录，别处只发离散事件，判定交分析器（§1、§5）。

## 1 四层与写入方

### 1.1 四层

- **采样**：帧统计（`Kernel.Frame`）是视口计时与逐帧样本的唯一写入方，计时常开；性能条与记录服务只读它的样本与显示窗。
- **记录**：记录服务（`Kernel.Inspect`）是原始数据的唯一写入方：会话、帧环、事件、慢采样、硬件样本与卡死看门狗都经它落盘；游戏内只有它读写性能记录，仓库脚本只读作者根。
- **分析**：`scripts/perf` 的分析器是指标、异常、派生、索引与历史的唯一写入方，并修剪 AI 根、诊断附件与派生。
- **展示**：观察台性能页与 `perf.py` 只读分析器的产出，不自算口径、不另存历史。
- **分析触发**：作者会话由启动入口在游戏退出后分析；AI 会话由 `run.ps1` 每跑完一次分析；观察台采集发现未分析的会话时兜底补跑。三处共用 `output/perf/.lock` 串行化索引、历史与修剪，取锁后复查会话与 `calc`，已分析的不重复追加；会话目录仍被写入锁占用时跳过它。

### 1.2 记录开关与会话

- **开关**：画面页"性能信息"组的"记录性能数据"，与"显示性能信息"各管各。默认关；即时生效，开即起新会话，关即停接并后台排空。
- **记录意图**：一个设置键，由记录服务经设置存储登记与唯一读写，存 `settings.json` 的 `ui` 节、跨启动保持；不是画质项，不随预设与恢复默认变，界面不经设置界面行写它。
- **关着记录**：不建数据文件、不起写盘线程、不开硬件会话；不做关记录时的黑匣子。
- **AI**：`--perf-out=<绝对路径>` 隐含开记录，不读写作者设置。
- **会话是应用级的**：回标题与再次入场不断会话，地图相关订阅随作用域解除、重接；快速开关串行处理。
- **五态**：Off、Starting、Recording、Stopping、Faulted，状态变化发事件；真正开始写入才进 Recording，排空完才回 Off。故障原因用契约的故障码，界面按码取文案，不转写异常文字。
- **停止、退出与失败走同一路径**：停接 → 停止并回收生产者 → 写盘排空 → 关文件 → 最后发布清单；退出经应用退出参与者走这条路。写盘失败时会话进 Faulted，原异常保留在记录服务的结束结果里并经 `IDiagnosticLog` 输出，已写数据保留，游戏照常运行；未排空完不标已关闭。

### 1.3 线程分工

- **帧环只有主线程一个生产者**：记录服务订阅帧统计的样本发布通知，在主线程入队，不另设轮询采样步。
- **唯一写盘线程**：硬件线程与卡死看门狗各自把值数据交给它；它只用线程安全的单调时钟与捕获的值，不读场景树与服务。
- **卡死看门狗独立循环**：不与写盘、NVML 查询共用执行循环；读段号、采集帧号与单调时刻取一致快照。
- **主线程不等磁盘**：帧环满了丢行并记 gap（累计丢失条数与首末序号），会话标不完整；不覆盖未消费的数据。

## 2 原始流与时间基

### 2.1 六件与存放

每个会话一个目录，作者与 AI 写同一套六件（DECISION-328）：

- `manifest.json` 会话清单：构建、软硬件、显示与窗口、所在桌面、帧节奏、画质请求值与生效值、启动参数、运行时预算与字段字典快照、时钟锚点，条目以 `perf-fields.json` 为准；中途变化记事件，会话结束最后原子发布。
- `frames.csv`：逐帧样本，每个采集帧一行。
- `samples.csv`：2 Hz 慢采样（位姿、模式、世界、内存与进程 CPU）。
- `hw.csv`：1 Hz 硬件样本；能耗与限频时间记区间增量，各限频时间可重叠、不相加。
- `hwfast.csv`：NVML 驱动样本缓冲，只作背景趋势，不保证捕获单次短卡顿。
- `events.jsonl`：离散事件，见下条。

**玩家行为**只订阅现有权威服务（应用流程、地图与到达、观者与镜头、行走、界面表面、世界、画质、存档）与视口尺寸信号，记请求与实际完成；加载与传送记等待起止与真实就绪；不截获输入、不另造监听层；所在格与最近点位由分析器推出。

**来源差别**：清单的 `origin` 区分作者与 AI；AI 运行另有 `run.json` 与诊断附件，不另起格式。

**存放**：作者根 `%APPDATA%\UESTC\perf\`，含 `latest.json` 与各会话目录，写入期间会话目录持 `.lock`，只由记录服务读写与修剪；AI 根 `output/perf/runs/<批次>/<运行>/<会话>/`；派生在 `output/perf/derived/<会话>/`，另有 `output/perf/index.json` 与 `output/perf/history.jsonl`，只由分析器写。

**根级状态 `latest.json`**：每个输出根一份，只由记录服务原子替换。真正写出会话开始与时钟锚点之后才发布"记录中"；关闭时先原子发布正式 `manifest.json`，再改为"已关闭"。会话是否完成只认正式清单加可独占的锁，不另设完成标记；只剩 `manifest.pending.json` 且锁能独占的按已结束的不完整会话处理。观察台判"正在记录"只读 `latest.json`，不读逐帧文件。

### 2.2 字段、版本与时间基

- **字段**：原始字段的名称、列序、类型、单位与含义以 `game/data/perf-fields.json` 为准，启动时核对、快照进清单；派生字段的字典在 `scripts/perf`。命名用 ASCII camelCase，物理量带单位后缀，比例 0–1（展示时再乘 100），容量写 MiB。
- **缺值**：未知与丢失按字段、按区间留 null，不用 0 补；硬件样本缺只使硬件字段缺失。
- **版本**：原始流带格式号 `schema`，增删字段或改含义就加 1；派生带口径版本 `calc`，指标定义一改就加 1，并重算仍在的原始数据；只认当前版本，不写迁移；只在同一 `calc` 内比较。
- **时间基**：逐帧与事件用单调时钟；采集帧号取 `Engine.GetProcessFrames()`，不是 GPU 完成序号；事件按自己的单调时刻按区间关联到帧。
- **挂钟**：记录服务可读系统挂钟，只用于会话 ID、开始时刻与定时锚点（G4 例外，DECISION-338）；会话 ID 写 `yyyyMMdd-HHmmss-play|ai`，同秒冲突追加序号。

## 3 指标口径

口径定义在本文，计算只在分析器。

- **记号**：Δt 为帧间隔，第 f 行的 Δt 覆盖上一个 B1 到本行 B1。T 为生效上限对应的目标帧时，开垂直同步时与刷新率取小，只用于体验判据，不限帧时相对目标的判据跳过。M 为同一指标在此前同场景有效窗口里的滚动中位数：窗口按帧计，只排除缺测、口径变化与非稳态帧，不因数值高或已判异常而删样，判当前帧只用此前的窗口；窗口帧数不足时相对判据不出，绝对预算、编译与 GC 判据照出。
- **关联窗口**：渲染计时是延迟回读，比较尖峰时前后几帧只作关联窗口，不叫精确对齐。
- **摘要两份**：全体与稳态，稳态去掉非稳态帧。
- **非稳态帧**：不进稳态摘要与 M，不触发自动调节降级（ENG-PERF-ADAPT §1.1）；原始帧照记，由上下文位标出；未被加载界面遮住的照判 §3.2 的成本卡顿绝对线。包括：转场（快进、换季、跳转、传送、切图、模式切换）、读档、新游戏、画面设置生效与窗口尺寸或模式变化的期间及之后的稳定时长（DECISION-345）；存档抓缩略图的那一帧；Title、Entering、Leaving 全部帧。换天气的过渡是慢变化，不算。判定规则与稳定时长在 `perf-fields.json` 的非稳态规则。

### 3.1 体验口径

只在交互桌面会话出（§4）。

- **帧率**：平均帧率 = 1000·N / ΣΔt；实时帧率按 1 s 窗。
- **帧时分位**：升序取第 ⌈q·N⌉ 个（最近秩），给 p50、p95、p99、p99.9；跨 gap 的间隔不进完整窗。
- **1% / 0.1% low**：取最慢 k = ⌈0.01N⌉ / ⌈0.001N⌉ 帧，值为 1000·k / 这 k 帧的 ΣΔt；N 不足 100 / 1000 记 null；同时给 N 与尾样本数，不声称与外部工具逐值一致。
- **掉帧**：Δt 超过 T 的掉帧倍数即掉帧；掉帧率 = 掉帧数 / N，掉帧时间占比 = 掉帧的 ΣΔt / 总 ΣΔt。
- **卡顿分级**：轻卡、重卡、严重、冻结四级，轻卡要同时超过 M 与 T 各自的倍数，其余按毫秒边界；边界一律取"超过"。卡死 = 心跳停滞达到 `KernelBudgets` 的卡死看门狗秒数。
- **每分钟卡顿**：超过重卡边界的帧数 ÷ 总时长（分钟），另计超过严重边界的帧数；对 `frameStutter`，它只是 F1 的体验判据，成本口径的轻级另有键（§3.2）。
- **帧节奏**：原时间线上相邻且都有效的两帧 |Δtᵢ − Δtᵢ₋₁| 的 p95，不跨 gap、不跨非稳态帧。
- **GPU 忙比**：受测视口 GPU 合计 / ΣΔt，只覆盖受测视口，不是全进程 GPU 忙时。
- **占用率与归一负载**：占用率是 NVML 样本均值（整卡、采样窗内有内核在跑的时间比、相对当前频率）；归一负载 = 占用 × 当前频率 / 最高频率，可大于 1，只提示可能的调频影响，不据它排除原因。低占用与频率变化只作背景，本身不进异常。
- **瓶颈**：按 1 s 窗依次判限帧（帧间隔中位贴近 T，主视口 GPU 中位明显低于帧间隔）→ GPU（主视口 GPU 中位占帧间隔的大部分）→ 其余记"不定"，带滞回；"不定"保留，不硬判 CPU。

### 3.2 成本口径

两类会话都出。`deviceTargets` 开发机项的 GPU p95 对主视口 GPU，CPU p95 对视口 CPU 渲染，帧准备另有一项，各分上沿与停线（ENG-BUDGET §2）。

- **五段**：物理、逻辑、延迟、绘制、尾段是回调边界之间的墙钟区间，边界为 B0 物理帧信号、B1 FadeClock 步、B2 Stage 采样点、B3 绘制前信号、B4 绘制后信号。physMs = 本轮 B1 − B0（0 个物理步时 B0 = B1、为 0；多步只记首步并累计步数）；procMs、lateMs、drawMs 取上一轮的 B2 − B1、B3 − B2、B4 − B3；tailMs = 本轮 B0 − 上一轮 B4。边界齐全且有序时五段之和等于本行 Δt；边界缺失、次序不符或线程模型不是 Safe 时本行分段标不可用，不复用旧边界。段名只定位阶段，不据段名断言在等什么，也不当纯 CPU 成本。
- **主线程周期**：mainCycles、drawCycles 是整帧与绘制段的线程周期原始增量，不换算毫秒，不进自动定性与达标判据。
- **GPU 渲染**：主视口每帧绘制，其引擎计时读数约晚两次绘制，按近似对齐（±2 帧）记为成本样本，不用于逐帧尖峰归因；本帧未绘制或窗口不能绘制时写 null，恢复绘制后的头几帧按 §3 的非稳态规则剔除。按需绘制的视口（倒影等）各一列，来源与新鲜度未确认的写 null；受测视口 GPU 合计只合已确认的视口，有未确认的就为 null（DECISION-342）。
- **CPU 渲染**：帧准备 CPU（本轮写入）与各视口 CPU（延迟回读，主视口同样按近似对齐记）分列，不默认同帧；视口 CPU 是墙钟跨度，含等待与抢占，不是线程 CPU 时间。
- **其余成本量**：调用与图元、五类管线编译、GC 停顿与次数、分配字节、挂载、显存；GC 与分配是全进程量，不算某个函数的成本。
- **成本尖峰**：主视口 GPU、视口 CPU、帧准备 CPU 与挂载逐项判（主视口两项的候选只落到 ±2 帧的窗口）：值超过 M 的尖峰倍数，且达到该指标的成本底线，记候选；底线引用 `deviceTargets` 的上沿或现有预算，来源写在 `perfAnomalies`，不取显示器刷新率；尚无分档的先为提示；预算越线另判。
- **成本卡顿**：帧准备 CPU 按自己的时刻逐帧对 `perfAnomalies` 的重、严重、冻结三条绝对线判，不要求先攒 M；主视口 GPU 与视口 CPU 渲染按 ±2 帧的关联窗口判，窗口内遮挡状态一致才分类，边界不确定记候选（DECISION-342）。轻级：超过 M 的倍数且超过轻级线，按帧计次。手动存档抓缩略图那一帧单设键。
- **逻辑段停顿**：物理、逻辑、延迟三段墙钟之和按同一组绝对线判；第 0 轮核过隔离桌面被钉住的等待不落在这三段才启用（ENG-PERF-MEASURE §6.1）。
- **主线程长停**：隔离桌面上帧间隔超过严重线记严重，被钉住的节奏抬不到这么高；第 0 轮核过静置时这类帧为 0 才启用（DECISION-331）。
- **不判瓶颈**：成本口径只列各成本指标对预算的占比。

## 4 测量范围与 `scope`

隔离桌面只出成本口径；会话的 `scope` 取 `cost` 或 `full`，由清单里的桌面事实定（DECISION-331）。

- **桌面事实**：清单记所在桌面（交互或隔离）与窗口的可见、焦点；`scope` 只按它定，不按来源定。
- **`full`**：§3.1 与 §3.2 都出。
- **`cost`**：只出 §3.2；§3.1 各项写 null 并注"隔离桌面不测"，展示时写原因、不画 0；加载时长按 §5.1 单边判。

## 5 异常

游戏内只做卡死看门狗、离散事件与测量自检，异常判定全在分析器，会话分析完即自动标注；异常是否登记为失败，按 ENG-FAILS §0 第 2 条判，分析器不自动登记（DECISION-332）。

- **四级**：提示、轻、重、严重。
- **每条带**：类型与级别、判据与阈值出处、关联阶段、候选原因、持续时间与现场的帧区间。
- **深挖**：反复出现、无事件原因的异常由分析器写 `deepen` 条目（ENG-PERF-MEASURE §4）。

### 5.1 体验类

掉帧、卡顿、冻结、持续掉帧、限帧失效、加载界面卡顿与 GPU 空等候选只在交互桌面会话判（DECISION-333）。

- **掉帧**：只作统计量；会话条件与预算条件一致时才对 `deviceTargets`、`frameStutter`，否则记"不适用"。
- **卡顿与冻结**：按 §3.1 分级定级，冻结为严重。
- **卡死**：两类会话都判，严重；带停在哪一段与段内时长。卡死看门狗可能迟报或漏报，进程挂起或突然退出时不保证有末尾事件。
- **持续掉帧**：窗帧间隔中位持续高于 T，连续若干窗才进出；超出更多升为重。
- **限帧失效**：窗帧率高于生效上限。
- **加载界面卡顿**：遮挡期内的长帧，按毫秒边界分轻、重。
- **加载与传送时长**：从整场事件取，对 `budgets.json` 的 `waits` 判；有可见进度时超过上限的痛点倍数、或连续无可见进展超过停滞线为痛点，后者不是全程上限（DECISION-348）。隔离桌面只单边判：不超过上限记本次观测达标，超过记未判，成本分解只用来排序与定位；冷启动与驱动管线缓存为空只看作者会话（DECISION-331）。
- **帧节奏抖动**：§3.1 的帧节奏越线，提示。
- **GPU 空等候选**：帧已判掉帧或卡顿，而关联窗口内已确认的受测视口 GPU 合计远小于 Δt；按五段写关联阶段，不分忙与等、不归责。来源帧不明或数据有效性已标不定时不出。
- **持续空等候选**：窗帧率低于上限、GPU 忙比低、不是限帧，连续若干窗进出；关联阶段写进原因。
- **瓶颈**：§3.1 的判定（含"不定"）不单列，作为上下文挂到每条异常。

### 5.2 成本与数据类

数据有效性最先判，只禁用受影响字段的结论；预算越线、成本尖峰、成本卡顿、管线编译、GC 与分配、挂载与缓存类按成本口径判，阈值见 `perfAnomalies`。

- **数据有效性**：计时缺测（合法跳过的视口与无绘制不算）、五段边界不全、硬件样本缺、丢行与没收尾、`scope` 与桌面事实不符。窗帧间隔中位贴在 T 的整数倍上且 GPU 很闲时，只提示外部节奏或错过呈现，不排除交互会话的低帧统计。
- **预算越线**：成本指标越过 `deviceTargets` 的上沿或现有预算，重；条件不一致时记"不适用"；越线排进调优，不算痛点。
- **成本卡顿、逻辑段停顿与主线程长停**：按 §3.2 定级，超过重线记重，超过严重线或冻结线记严重；轻级只计次，每分钟上限见 `perfAnomalies`，分母为路线套与传送套的稳态时长；痛点次数按原始命中帧，两套全部运行合计、列最差场景，固定机位套只作对照（DECISION-348）。
- **成本尖峰**：按 §3.2，提示。
- **管线编译**：游玩中出现 Draw 编译增量为重；未遮挡时的 Surface、Canvas 编译为轻，同帧有卡顿或尖峰时升重；Mesh、Specialization 编译为提示；作废只用于固定机位套，路线套与传送套里的编译记为发现、照常定级（ENG-PERF-MEASURE §2，DECISION-349）。
- **GC 与分配**：单帧停顿越过 GC 底线、窗内合计越线、分配风暴、游玩中出现 gen2，轻至严重。
- **挂载与缓存**：挂载跳闸或远超预算（预算取清单里的运行时预算快照）、同格短时间内反复挂卸、游玩中缓存未命中（边玩边补烘）、积压持续不降，轻至严重。
- **物理追帧**：物理步数达到上限。
- **其余**：显存逼近、降频、内存持续增长、占用读数波动、周期性起伏、呈现模式不符，提示至严重，判定细节在分析器。

### 5.3 归因与合并

每条异常在关联窗口内按事件写候选原因、按五段写关联阶段，不据段名断言原因；同类就近合并，合并间隔与每类条数见分析器常量。

- **候选原因**：在关联窗口内按编译、GC、挂载、缓存未命中、同步读回、物理、转身（逐帧朝向的角速度）、存档、设置、焦点、降频逐项查；事件按自己的单调时刻按区间关联。全局 GC 与分配增量不算某个函数的成本。
- **关联阶段**：五段各算超出本段滚动中位数的量，最大的一段为关联阶段；分段不可用的行不写。
- **合并**：同类的帧级异常与状态级异常各按合并间隔并成一条；持续掉帧里的轻卡只计数。
- **排序**：摘要每类条数有上限，按超额毫秒排，数据有效性排最前。
- **现场**：按帧区间引用原始流；重级以上另切 `hotframes.csv`，供逐帧查看。

## 6 比较键、状态与保留

摘要带比较键、`calc` 与状态，只比同键同口径；保留按条数不按日历，作者根由记录服务在开新会话时修剪，AI 根、诊断附件与派生由分析器修剪，保留数见 `KernelBudgets` 与分析器常量（DECISION-337）。

- **比较键**：场景、机器、构建配置、预设与各项画面设置、输出分辨率、渲染精度、帧节奏（垂直同步与上限）与图形接口合成，另配中文标签。驱动、系统与引擎版本不进键，变了就把基线标 `stale`。键不同的差异不下结论。
- **状态**：分析器每次重建索引时重算：
  - `current`：同键下最新的有效 AI 运行；前提是干净构建、提交在主线上、覆盖达到场景要求。
  - `stale`：是 `current`，但其后 `game/` 有改动，或驱动、系统、引擎版本与本机不同；附原因。
  - `superseded`：同键下已有更新的有效运行。
  - `partial`：未完成：截断、丢行、覆盖不足、非零退出或超时强杀。
  - `invalid`：作废：采集前提不满足或读回不符（ENG-PERF-MEASURE §2）。
  - `unsupported`：`schema` 不是当前版本，不再分析。
  - `evidence`：作者会话的固定状态，只定位问题，不当基线。
  - 带未提交改动的实验运行永不成为 `current`。
- **索引与历史**：`index.json` 列全部会话及其状态；`history.jsonl` 每次分析的会话一行摘要，供其他历史展示读；观察台的性能趋势只读 `index.json` 里各批次组的阶段中位，不从历史自算。
- **作者根**：保留最近若干次，且已关闭会话合计不超过容量上限；不限单次录制长度。只删已关闭、锁可独占的整会话，不碰存档、设置与日志；锁已释放却仍标 open 的会话标 `partial` 后照常过期。
- **AI 根与派生**：AI 根留最近若干批次与含 `current` 基线的批次，诊断附件另有总量上限；原始删了，派生跟着删，历史行保留；历史按比较组与作者各留若干行。由分析器在每次分析末尾修剪。
- **清理工具**：`output/perf` 在 `clean-artifacts.py` 的保留名单里。

## 7 开销目标

记录开着时主线程的采样与入队有每帧耗时目标且零托管分配，首次完整链闭环时实测核对；性能记录开着时启动测量照常计时（DECISION-256）。

- **主线程**：只做采样与入队；零托管分配只在采样调用前后核主线程分配，全进程分配计数不作证据。
- **写盘与硬件**：写盘、硬件采样与卡死看门狗都在主线程之外；帧环按约定的秒数留容量，不保证跨过任意长的写停顿，跟不上就丢行记 gap（§1.3）。
- **体积**：按实测行长核算，总量由 §6 的保留控制。
- **核对口径**：开销与体积按数量级判断，在数量级内即放行（WF-RULE §15）。
