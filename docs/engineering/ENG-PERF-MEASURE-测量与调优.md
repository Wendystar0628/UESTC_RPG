# ENG-PERF-MEASURE · 测量与调优

> **范围**：性能怎么测与怎么调：机器与剖析权限（§1）、AI 采集批次（§2）、以最新数据为准（§3）、诊断（§4）、不采用的工具（§5）、调优规则与判停（§6）。
> **不在本文**：数据格式、指标口径、异常判据与保留（ENG-PERF-DATA）；预算与目标数值（ENG-BUDGET）；门禁判据与命令行（ENG-GATES、ENG-GATES-SHOTS）；自适应与帧节奏（ENG-PERF-ADAPT）。
> **查阅**：先读 §0；机器与权限看 §1；AI 批次看 §2；引用数据看 §3；诊断看 §4；不采用的工具看 §5；调优看 §6

## 0 结论

1. **引用性能数前先取最新**：先跑 `perf.py latest`，只用同比较键、同口径、有效且不过时的数据；作者游玩数据不作比较基线（§3，DECISION-336）。
2. **AI 只经一个入口采集**：`scripts/perf/run.ps1`，在隔离桌面里跑固定机位套、路线套、传送套；不建吞吐模式（§2，DECISION-334）。
3. **隔离桌面只判成本**：体验类只来自作者自己开着记录的游玩会话，不排作者录制；例外是加载墙钟与主线程长停两条单边判（§2，DECISION-331）。
4. **准备与采样分开**：就绪后先做采样前稳定，每轮每场景采一遍、与上一轮记录比，读回不符即作废（§2，DECISION-354）。
5. **诊断按需用现成工具**：根因不明时跑一个场景加一种工具查出处，不登记、不比基线（§4，DECISION-359）。
6. **调优有计划、轮次有限**：第 0 轮基线与诊断后至多 3 轮，每轮至多 3 行，痛点优先；按达标、无收益、轮数三种原因结束，分开写（§6，DECISION-339、DECISION-348）。
7. **剖析不提权**（§1，DECISION-323）。

### 0.1 接入要点

- **引用性能数或定调优方向**：先跑 `python -I -X utf8 scripts/perf/perf.py latest`；只经 `perf.py` 读性能数据，不打开逐帧原始文件；引用写会话 ID（§3）。
- **为性能采集写脚本或加场景**：只经 `run.ps1` 与它的场景计划，不另起采集入口与数据格式（§2）。
- **比较改动前后**：和上一轮记录比，同场景同指标改善不到 5% 算没变化；不拿作者会话当基线（§2、§3）。
- **在隔离桌面里看到帧率、帧间隔或卡顿**：不据此判体验，只判成本与 §2 的两条单边判（§2）。
- **查根因**：根因不明才用 `run.ps1 -Scene <场景> -DiagnosticTool <工具>`，结果只用来定改法（§4）。

## 1 机器与剖析权限

成本、回归与份额核算在开发机上测，剖析在普通权限的后台进程里做，不提权（DECISION-323）。

- **机器**：开发机（RTX 4080），`--gpu-index` 选卡；不设中档参考机（ENG-BUDGET §4）。
- **剖析权限**：开发机的 GPU 性能计数器对所有用户开放，Nsight 逐绘制抓帧与硬件计数器在普通权限的后台进程里跑，不以管理员身份启动代理会话；上屏帧率与帧间隔（PresentMon）要另给权限，只在体感卡而帧时正常、或验收稳帧时由作者手动开，不进体系。
- **运行条件**：从项目运行、窗口模式；命令行与截图默认串以 ENG-GATES-SHOTS §1 为准，画质只由命令行决定、不读 `user://`（ENG-GATES-SHOTS §1.1）；AI 采集的固定机位套与路线套按 DECISION-318 的条件开 3840×2160，不沿用那里的默认尺寸；测量时自动调节关闭；叠加层与录屏关掉，因为它们改变帧时序。
- **构建配置**：作者启动与测量用 Debug 程序集，CPU 数偏悲观；不同构建配置的数不互比（比较键见 ENG-PERF-DATA §6）。

## 2 AI 批次

- **隔离桌面**：`run.ps1` 在已登录会话里另建的不可见桌面上起游戏，不操作作者桌面。那里的帧间隔被外部节奏钉住、GPU 占用偏低，所以帧率、帧间隔分位、low、掉帧、卡顿、帧节奏与 GPU 占用都不判体验，只判成本口径（ENG-PERF-DATA §3.2、§4）；不追帧间隔被钉住的成因。例外是两条单边判：加载墙钟不超过 `budgets.json` 的 `waits` 上限记本次观测达标，超过记未判（ENG-PERF-DATA §5.1）；帧间隔超过严重卡顿线记主线程长停，第 0 轮核过静置时这类帧为 0 才启用（ENG-PERF-DATA §3.2，DECISION-331）。
- **入口**：`scripts/perf/run.ps1` 是 AI 采集的唯一入口，复用构建锁、独立 profile、隔离桌面与正式退出；冻结本批条件，`--perf-out` 指向 `output/perf/runs/<行号-主题>/`，每个会话关闭后把 `run.json` 写进 `<perf-out>/<会话>/`，跑完调分析器。不建吞吐模式：成本口径不需要它。
- **场景套**（场景计划在 `scripts/perf`，只引地图数据的编号）：
  - 固定机位套：几个固定点位的默认状态与夏夜雷雨，流逝暂停、静置采样；另含开放室内门厅朝外、行走贴地与新游戏落地位姿（ENG-BUDGET §2、§4）。回答渲染成本与回归。
  - 路线套：行走与旁观各一条多段路线，各不短于判卡顿所需的时长、跨多个流式格与细节环，行走那条进一栋开放楼；起点经一次实走确认后冻结。回答移动中的挂载、GC、编译与渲染 CPU 尖峰。
  - 传送套：`travel-sequence` 的少量已验证点，含远距离与进室内各一段，分有预取与直接下令两种。回答到达尖峰、挂载与等待边界。
- **与预算条件一致**：隔离桌面上以无边框全屏（非独占）渲染到预算分辨率，只经命令行参数设置；成本按真实渲染尺寸判，与预算条件不一致的不判；清单记真实的构建提交与改动状态，取不到标未完成（DECISION-353）。
- **采样前稳定**：准备与采样分开；真实就绪、流式排空、管线编译计数连续若干帧不增、进入实时满规定时长、GPU 处于最高性能状态（NVML P0）后才起录；帧数与时长见 `run.ps1` 的常量。
- **采集期间不提交**：一轮从冻结到登记完成，冻结的是整个提交，主检出不提交、不推送任何改动（含文档），要改的等这一轮登记后再推。
- **一轮一遍**：每轮每场景采 1 次，采完记为本轮记录，下一轮直接与它比，改善不到 5% 算没变化；结果离上沿或停线不到 5%、或痛点只出现一次的，只重采该场景一次，按两次中较差的判（DECISION-354）。
- **作废**：请求起点与实际落点、模式、轨迹不符的运行作废；固定机位套采样中出现管线编译增量的运行作废重跑，路线套与传送套里的编译记为发现、不作废，因为玩家每次开游戏都会遇到（DECISION-349）；协议不完整的不进比较。作废的原始数据与原因都保留。
- **未完成与污染**：非零退出与超时强杀的运行保留原始数据，标未完成；采样前与采样中别的进程的 GPU 占用（Windows PDH GPU Engine，同一引擎上其他进程合计取各引擎最大值）超出 `run.ps1` 的阈值，该次运行标污染，原始数据保留、不进比较；正式实测作废重跑，功能短跑照常走完全链只标污染；来源读不到时标未完成，不当作无污染（DECISION-344）。
- **启动测量**：启动目标的体验测量不带诊断工具（EventPipe、`--gpu-profile`、Nsight）；性能记录开着时照常计时（DECISION-256，开销目标见 ENG-PERF-DATA §7）。

## 3 以最新为准

- **先取最新**：引用性能数或定调优方向前，先跑 `perf.py latest`；只用同比较键、同 `calc`、同口径、状态有效且不过时的当前数据（比较键与状态见 ENG-PERF-DATA §6）；过时的先重测。
- **只经 `perf.py` 读**：用它的 `latest`、`show`、`compare`、`slice`、`anomalies`，不打开逐帧原始文件；比较键不同的差异不下结论。
- **基线**：作者游玩数据用来定位问题、作体验证据，不作 A/B 基线；A/B 的基线是同批 A 运行。
- **引用**：写会话 ID，文档不抄测得的数；新数据推翻旧结论时，旧结论当场作废。

## 4 诊断

采集回答哪里慢、慢多少；诊断只在要定改法而根因不明时，用现成工具查是哪段代码或哪个渲染步骤（DECISION-359）。开不开、用哪个，由 AI 看距离表与痛点定，分析器不生成诊断条目。

- **入口**：`run.ps1 -Scene <场景> -DiagnosticTool <gpu-profile|EventPipe|Nsight>`，跑一个场景加一种工具，产物放诊断目录并打印摘要；不登记、不进记录与轮次、不和基线比、不判有效、不去重。
- **`--gpu-profile`**：游戏内逐步骤 GPU 耗时，用来排序哪个渲染步骤贵，不当绝对值。
- **EventPipe**：本机 `dotnet-trace` 附着游戏进程，解析与 `scripts/build/startup-cpu` 共用；收集器要在游戏还活着时停下，方法名才解析得出，所以游戏在样段结束后等收集器停完再退出；样本是墙钟栈采样，占比不写成 CPU 利用率。
- **Nsight**：普通权限（§1）抓 GPU 帧，只看相对占比。
- **结果**：看得懂就用；不完整（比如方法名没解析出来）就换工具或重跑，不为它建判据。
- **不常开**：常规批次、门禁与启动目标的体验测量都不带诊断工具（§2）。

## 5 不采用的工具

不往游戏里接进程内剖析器与逐系统打点，不做关记录时的黑匣子；PresentMon 不用（作者定）。

- **Tracy、Perfetto**：要自己编引擎，锁定的官方二进制用不上。
- **Optick**：只支持 C++。
- **`Performance.AddCustomMonitor`、`EngineProfiler`**：只在连着调试器时生效，且走 Variant，不适合常驻记录。
- **GPU 引擎计数器加密轮询**：每读一次就是毫秒级，逐帧 GPU 计时与 NVML 驱动样本已经覆盖。
- **`GetThreadTimes`**：分辨率远粗于一帧。
- **逐帧 `QueryProcessCycleTime`**：线程多时每次调用超出逐帧开销目标，进程 CPU 只按慢采样记。
- **ETW 与 WPR 环形会话**：要管理员，与 §1 冲突。
- **逐系统打点**：要在各属主处逐个加计时，EventPipe 的栈采样不改代码就能定位到方法。
- **进程内 `EventListener`**：在派发线程上持续分配，帧级精度已经够用。
- **黑匣子**（记录关着时常开内存环、卡顿时落盘）：违背记录开关只管记不记的语义（ENG-PERF-DATA §1.2）。
- **PresentMon**：要另给权限，只按 §1 由作者手动用。

## 6 调优规则与判停

调优由作者派任务开始，先建计划、轮次有限：第 0 轮基线与诊断，再至多 3 轮，任一结束条件成立就停，不加第 4 轮；合理区间、停线与痛点的线以 `budgets.json` 为准，在第 0 轮前冻结（DECISION-339、DECISION-348）。

### 6.1 第 0 轮

第 0 轮不改游戏代码。

- **0a 冻结**：判停要用的分析、记录字段与采集场景落地后，字段版本、分析器口径、场景集与 `budgets.json` 的线一起冻结；本次调优中途不再升 `schema`。
- **0b 基线**：不改代码采一遍全套，记为第 0 轮记录；另在测试宿主里离线核记录开销（ENG-PERF-DATA §7）；按这一遍的数据核物理、逻辑、延迟三段与静置帧间隔的分布，逻辑段停顿与主线程长停据此启用（ENG-PERF-DATA §3.2）。
- **0c 体验候选**：有作者自开记录的会话就看一眼、列体验候选，没有不等。
- **0d 距离表**：分析器出距离表（测值、上沿、停线、比值、档位），结合已知根因得出主要问题清单。
- **0e 诊断**（不计轮次）：根因不明的主要问题按 §4 查出处，定出改法；查不出的项出局登记（§6.3）。

### 6.2 第 1–3 轮

- **挑项**：每轮先按 §3 取最新，旧轮的结论与候选不沿用；次序为痛点（按严重度、再按次数）＞越过上沿（按测值÷上沿）＞已入选但还没到停线的项；从没越过上沿的项不挑。同一根因并成一行，每轮至多 3 行。
- **合入**：本轮的行合成一个候选构建采一遍，和上一轮记录比；目标指标改善 5% 以上、没新出痛点、没有项被推出上沿或停线的行才合入。
- **碰画面的行**：由主会话跑固定机位截图评审，画质不降才合入，因为 DECISION-318 不靠降画质达标。
- **轮末**：合入后的那一遍记为本轮记录，出新距离表；有行没合入的，按合入的版本重采一遍再记录。体验指标只在有适用的作者会话时附列，调优不等它。

### 6.3 判停与收尾

- **结束**（任一成立即停，结束原因分开写）：
  1. 达标结束：必判集全部已判，全部进入合理区间（越线入选的项到停线），且没有痛点。必判集是帧成本（只算固定机位套与路线套，传送套不判帧成本）、成本卡顿、逻辑段停顿、主线程长停、轻级卡顿（按批次合计）、Draw 编译、GC、显存逼近与卡死；其中出现"不适用"或缺测的，该次运行按不完整重跑，不记未判。
  2. 无收益结束：一轮里有改动的行，没有一行的目标指标比上一轮记录改善 5% 以上。
  3. 轮数结束：第 3 轮跑完。
- **按项出局**：一项连修两轮仍不在区间、且第二轮比上一轮记录改善不到 5%，这一项出局登记，其余继续；候选清空即按第 1 条判。
- **未判**：调优中途才接通的判据本次一律记未判，不进第 1 条；必判集以外没判的类别（加载超限、启动三项、湖边受测视口合计在来源确认前、流式检测、读档与回标题等场景、存档卡）在结论里逐项写"未判"，不写"总体无痛点"。
- **剩余项**：开队列行，写判据、会话 ID、比值、试过的修法与不收敛原因；只有超出判据一个数量级的才按 ENG-FAILS 登记失败。
- **定稿**：按实测在 `budgets.json` 或 `KernelBudgets.cs` 定稿初值，主会话删去 ENG-BUDGET §5 对应条目；文档只写会话 ID，不抄测得的数（§3）。
- **转常规**：之后集中测试先按当前代码采一轮，G10 只读这一轮的结论；作者自行开关记录；下一次攻关按开发节点，或 G10 查出越线、新痛点时再开。
