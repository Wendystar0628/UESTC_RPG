# ENG-ARCH · 工程架构

> **范围**：本文说明当前的工程架构（技术栈、分层、生产链与数据流），架构层面的准则（边界、确定性、契约、烘焙、桩），以及后续设计的导向。只写结构、规则和方向。
> **不在本文**：类型签名、目录明细、文件格式、参数与清单以代码和数据为准；写代码的结构规矩见 ENG-CODE；命名与目录约定见 CORE-CONVENTIONS §3、§5；性能与预算见 ENG-PERF、ENG-BUDGET；门禁见 ENG-GATES；工作包分工见 ENG-WP；RPG 路线见 ENG-ROADMAP。
> **查阅**：先读 §0；当前架构看 §1；边界与确定性看 §2；契约看 §3；资源与烘焙看 §4；桩看 §5；架构导向看 §6；RPG 扩展方式看 §7；待验证看 §8

## 0 结论

1. **四层，依赖只朝下**：契约 → 世界与公共几何 → 内容生成 → 运行时；同层的内容包互不引用；程序集只有约 4–5 个，层间与包间的边界由命名空间规则（G4）守（§1、§2，D-232）。
2. **生成是纯 .NET 的纯函数**：契约与生成层不引用 Godot；`Build()` 只读冻结的地图输入，不读运行时状态、画面设置和时间（§2）。
3. **一条生产链**：正式运行由 `KernelStage` 装配；每类状态一个写入方；原生资源只由所属的内核服务创建（§1、§2）。
4. **打特性即接入**：模块、部件、服务、节点、存档段靠特性自动发现，不改共享文件；Autoload 只有 `Boot` 和 `Kernel`（§2）。
5. **确定性**：随机和哈希只用契约的 `Rng`、`StableHash`；同一台机器上同一输入烘出同样的字节，不要求本机与别的机器逐字节一致（§2，D-232）。
6. **契约以源码为准**：签名只在 `game/contracts/`；改动先申请，与全部使用方同批迁移（§3）。
7. **几何本机烘焙**：几何由代码生成，在玩家机器上首次需要时烘进本机缓存；每格只在它用到的输入改了时重烘；不做几何启动集（§4）。
8. **一个主检出，构建排队**：所有代理在 `main` 上只改自己的文件；构建、导入、烘焙、门禁、截图一次只跑一个（WF-BUILD §4，D-211）。
9. **往哪走**：边界交给命名空间规则，整图流程面向全部模块，用公共层和数据代替复制，大类按职责拆（§6）。

### 0.1 接入要点

- **新建或修改文件**：只改 `ownership.json` 划给本包的路径；`project.godot`、csproj、`Directory.*.props`、契约、`ownership.json`、`docs/` 这些共享文件向 Astra 申请（WF-BUILD §1）。
- **写契约、生成层或烘焙子任务**：不引用 GodotSharp，不读文件路径和运行时状态，不引用其他内容包的命名空间（§2）。
- **要显示、用材质或出声**：显示经 `IRenderHost`，材质经 `ToonSpec`，声音经音频服务；不自己创建网格实例、`ShaderMaterial` 和音频播放器（§2）。
- **接入新模块、节点、服务或存档段**：打对应的特性，不加 Autoload，不改 `main.tscn`（§2）。
- **写随机、计时或哈希**：用契约的 `Rng`、`StableHash`，遍历字典先排序；禁用写法以仓库根的 `BannedSymbols.txt` 和 G4 为准（§2）。
- **读写 `user://`**：每个文件只有一个读写方；任何代码都不用 `ResourceLoader`、`ResourceSaver` 读写 `user://`（§2）。
- **用到契约**：签名看 `game/contracts/` 源码；会追加值的枚举写穷举 `switch`；JSON 用 `ContractJson.Options`（§3）。
- **要改契约，或加着色器全局参数、着色器文件、项目引用、NuGet 包**：向 Astra 申请（§3）。
- **依赖的能力还没交付**：照显式桩开发，真实实现接入时同批删桩（§5）。

## 1 当前架构

### 技术栈

引擎锁定 Godot 4.7.2-stable .NET 版，目标框架 net10.0（D-177）；只做 PC（Windows），渲染器 Forward+，默认 D3D12。代码全部用 C#，着色器用 Godot 着色语言，计算着色器用 GLSL；Godot API 以 本地签名库 `docs/godot-api/` 为准。升级引擎前单独评估。

### 分层

| 层 | 程序集（约 4–5 个） | 责任 |
| --- | --- | --- |
| 契约 | `Campus.Contracts` | 数据、命令、只读状态与确定性工具；只引用基础类库 |
| 世界与公共几何 | `Campus.Gen`（世界、几何、部件内核等通用生成） | 解释冻结的地图输入（地形、路网、覆盖层、室内索引），提供权威查询和共享几何 |
| 内容生成 | 通用内容包在 `Campus.Gen`（建筑、地面、植被、水、碰撞、可行走、外围、声学等）；每张图一个 `Campus.Gen.Maps.<图>`（各区）；`Campus.Pipeline`（地图与行走管线） | 按格生成几何、碰撞与声明数据；纯函数，命名空间互不引用 |
| 运行时 | 主程序集 `Campus`（kernel、stage、flow、camera、medium、systems、style、audio、hud、gates） | 装配、烘焙与流式、世界状态、表现与界面 |

- 程序集与目录的对应、归属以仓库本身和 `ownership.json` 为准。程序集只按"契约 / 通用生成 / 每图一个 / 管线 / 运行时"划分，包与包、层与层之间的边界靠命名空间规则（§2）。
- 各包的测试放在自己目录的 `tests/`，分别编进 `Campus.Gen.Tests` 和 `Campus.Tests`。

### 生产链

1. `Boot` 解析命令行；`KernelStage` 是唯一的组合根，装配已注册的服务与节点。
2. 地图服务加载当前图的冻结输入，发布一份世界模型。
3. 烘焙服务按格调用内容模块的 `Build()`，产物进本机缓存；流式与 LOD 把格包经 `IRenderHost` 挂上。
4. 运行时系统（时间、天气、植被、水、灯、动物）读世界状态驱动表现；行走读碰撞与可行走烘焙；界面只读服务发布的展示数据。
5. 启动、换图、读档、退出都由正式编排入口（应用流程、地图服务、存档服务）驱动，走同一条链。

### 数据流

`pipeline/` 离线生成按图数据 → `game/data/maps/<图>/` 的 JSON 与覆盖层 → 世界模型 → 生成 → 本机缓存 → 挂载。远景、遮挡体、灯表这类派生数据同样在本机烘焙（§4）。

## 2 边界与确定性

### 依赖方向

- 上层可以引用下层，反过来不行；同层的内容包、归属不同地图的命名空间互不引用（SYS-MAPS §6）。程序集并少之后，这些边界由 `scripts/gates/arch/` 的命名空间架构规则（G4）挡，不靠多建程序集；增删规则要 Astra 批准。
- **生成层看不到运行时**：`BuildContext` 里没有世界状态、画面设置和规则集。随时间、季节和天气变化的东西，只能通过调色板、灯光通道、变体掩码和全局着色器参数表达（ENG-BUDGET-RULES §1）。
- **运行时内部**：各命名空间之间只经契约和 Kernel 服务交互；界面除 GodotSharp 外只依赖契约和 `Kernel.Get<T>()`，不用其他包的内部类型。
- **原生资源各有唯一创建方**：网格与渲染实例只由内核创建，其他包经 `IRenderHost` 申请并按包记账；`ShaderMaterial` 只由 Style 按白名单创建，其余经 `ToonSpec` 取；音频播放器与总线只由 Audio 创建；计时只出现在内核的帧、画质、巡检、存档和门禁里。
- **`user://` 每个文件一个读写方**：存档只由内核存档服务读写，本机烘焙缓存只由烘焙服务读写。任何代码都不用 `ResourceLoader`、`ResourceSaver` 读写 `user://`，因为 Resource 能嵌入脚本、读入即执行。

### 确定性与禁用写法

禁用写法由 BannedApiAnalyzers（仓库根一份 `BannedSymbols.txt`）和 G4 的架构规则挡住，清单以它们为准。背后的原则：

- 随机只用契约的带种子 `Rng`；种子由 `StableHash` 把世界种子与 ID、用途组合起来，与生成顺序无关。
- 不读系统时钟，不用进程间不稳定的哈希。
- 只保证同一台机器上同一输入同一输出；不要求本机与别的机器逐字节一致，不设专门的数学库，数学照常用标准库（D-232）。
- 遍历字典、集合前先排序；一个 `Build()` 内部不做并行浮点归约，并行只在格与格之间，由内核调度。
- 材质只经 `ToonSpec`，颜色只用色名，着色器用全局的 `anim_time` 而不用 `TIME`；不写 GDScript，不手写 `uid://`，`main.tscn` 以外不放共享的 `.tscn`、`.tres`。

由此保证：同一台机器上同一输入烘出同样的字节，缓存判鲜才可靠；运行时同一钟点、同一种子、同一串输入得到同样的画面；读档是换一个世界实例，续跑等价（SYS-SAVE-FLOW §2.3）。例外只有登记过的几处（新游戏取一次熵作天气种子、存档读一次系统时钟用于显示），以 G4 的登记为准。

### 自动发现与模块接入

- 内核按构建时生成的程序集清单逐个加载，反射扫描特性，按 ID 排序注册，ID 重复报错。特性的种类与参数以 `game/kernel/registry` 的源码为准：内容模块、部件、室内提供者、发声器来源在生成层；介质呈现、内核节点、内核服务、画质响应、存档段在主程序集。
- 加载一张图时只启用"通用 + 当前图"的内容模块、室内提供者和发声器来源；服务、部件和存档段是全局的（SYS-MAPS §6）。
- Autoload 只有 `Boot` 和 `Kernel`；新的全局对象一律注册成 Kernel 服务。
- 生成与挂载分开：`Build()` 在工作线程上跑；挂载和会动的物体只在主线程，由内核节点负责（SYS-MOTION）。

### 仓库脚本自成一体

`scripts/` 不引用 `.collab/`；本机协作工具可以调用仓库脚本，反过来不行。别人克隆仓库也要用的工具（构建、检查、清理、截图）放 `scripts/`。

### 生命周期与发布

- **一次读取、一次发布**：地图加载发布同一版本的上下文，消费者显式接收，不各自重读同一份文件。
- **可写与冻结**：构建阶段可写，进入共享缓存或跨线程发布时冻结；后台任务只持纯数据，主线程接收时核对地图与任务的代际。
- **谁开谁关**：应用、地图、节点与一次操作各自拥有自己的资源、订阅和异步工作；卸图或退树时终止等待、解除订阅，迟到的结果不再发布。
- 不另建平行的状态机或全局事件通道；服务可以拆成职责明确的内部组件。

## 3 契约

- 契约在 `game/contracts/`（`Campus.Contracts`）；签名、注释和 JSON 格式（`schemas/`）以源码为准，文档不抄签名。
- 改契约，或加着色器全局参数、着色器文件、程序集引用、NuGet 包，向 Astra 申请（WF-BUILD §1、WF-BUILD §3）；改动与全部使用方、数据和文档同批迁移，不保留旧接口（WF-RULE §10，D-209、D-214）。
- 画面相关的契约（`ToonSpec`、调色板、着色器全局参数、界面令牌、过场 JSON）由主会话确认字段够用、命名与美术文档一致。
- **枚举纪律**：枚举只在末尾追加值，JSON 按字符串存；会追加值的枚举，消费方写穷举 `switch`，`default` 分支拒绝或报错，不写二值判断；读到不认识的字符串按不合法处理（SYS-SAVE-FORMAT §1.3）。
- JSON 一律用 `ContractJson.Options`；存读档用 System.Text.Json 源生成（SYS-SAVE-FORMAT §4）。
- 契约用 `System.Numerics`，Godot 侧用引擎的向量与变换，两边转换只用内核的一组扩展方法（CORE-CONVENTIONS §1）。

## 4 资源与烘焙

- **几何由代码生成**：全部几何由生成层的 `Build()` 产出。确需外部模型（如雕像）时先经主会话批准，作为英雄资产放 `game/assets/hero/`。
- **本机烘焙**（D-165）：格包、碰撞、室内包、平面底图，以及远景、遮挡体、灯表、导航图、声学这些派生数据，在玩家机器上首次需要时，由烘焙服务调用与开发烘焙器同一个 `Build()` 生成并写进本机缓存。不做几何启动集 `boot_<图>.pck` 与 `bake.manifest.json`，随包只发原始数据和必要的小索引（D-232）。
- **格式**：缓存用自定义的 `.tbin`，不用 Godot 资源格式；解析逐段做边界检查，读坏了就删掉重烘一次，仍不行就报失败。
- **判鲜**（D-229）：每格只看它用到的输入（数据和生成代码）改没改，改了只重烘这一格，没改的直接用；用最省事的判断办法，说明文字不算输入，不叠多层哈希；生成代码一侧读程序集自带的标识（MVID），编译时不再给全部源码算哈希。玩家侧游戏版本一变就清缓存重烘。不出整图的行走产物。
- **查找顺序**：本机缓存 → 本机烘焙。玩家的缓存在 `user://cache/bake/`；开发与 CI 用 `UESTC_BAKE_CACHE` 指向的共享缓存，默认位置以 `BakeOptions` 源码为准。缓存上限、淘汰、烘焙排队与首次运行目标见 ENG-PERF-STREAM §1、ENG-BUDGET §3。
- **管线输入**：`pipeline/` 离线生成按图数据。同一份已提交输入重建，输出逐字节相同；快照日期取自随快照提交的元数据；刷新快照须显式执行，并与元数据一并提交；Python 依赖按 `pipeline/requirements.lock` 锁定。
- **贴图与字体**：PNG 源图加 Godot 导入；区域包不自带大于 512² 的贴图，向 WP-04 申请图集槽位或数组层；数据纹理在运行时创建；字体只用开源许可并只截取用到的字（UI-VISUAL-COMPONENTS §1）。音频素材见 SYS-AUDIO §9、§10。
- **登记与版本**：资源的许可与来源登记、版本号与构建信息、导出内容见 OPS-RELEASE；版本号只有 `version.txt` 一个来源。

## 5 未交付能力的占位边界

正式运行统一经 `KernelStage` 装配已交付的服务与节点。尚未交付的能力可以用显式桩，桩的注册、行为与默认值以 `game/kernel/stubs/` 源码为准。

- 依赖方按正式契约接线；桩只提供声明过的占位行为，桩的就绪、成功返回或截图不算该能力通过核心验收。
- 真实实现接入时，同批撤掉对应的生产桩、旧执行入口和旧断言，不留两套生产路径（WF-RULE §10）；测试替身不带运行时注册。
- 能力未实现或正式检查缺失时如实标为未交付，不以占位结果代签。
- 部件按 ID 编目先行：共享部件的 ID 与参数在 `game/contracts/Parts/`；区域包按 ID 放置部件，特有部件建在自己目录、ID 加区名前缀，证明能复用再申请提升为共享部件。

## 6 架构导向

后续设计朝这几个方向走；现有不符合的地方按整治计划逐步改掉，新代码直接按这里写（写法见 ENG-CODE）。

- **边界交给命名空间规则**：生成层不引用运行时命名空间，内核不引用系统层，由 G4 的架构规则挡，不再维护"哪些类型不许用"的名单；系统要读的数据类型放契约。
- **整图流程面向全部模块**：烘焙、碰撞、行走、注册这类面向整张图的流程，经 `IContentModule` 遍历全部模块，不点名某一个区。
- **公共层代替复制**：分区施工底座、几何底座、平面几何、用户配置落盘各只有一份，各区只留本区专用的内容选择与组合。
- **数据驱动内容**：实体 ID、坐标、尺寸、名称进按图数据，代码只留规则；规则值（行走与碰撞、建筑默认值、预算）各在一处定义。
- **按职责拆**：观者相机拆出输入路由、输入锁、键位、位姿校验和视图存档；超大的页面、布局与规划类按页、按步骤拆。
- **程序集少而大**：只留契约、通用生成、每图一个、管线、运行时这几个；没有独立依赖边界的过碎程序集并入相邻的，部件包合成一个。
- **测试跟着契约走**：契约的假实现集中成共用夹具，测试测行为不钉实现（ENG-CODE §6）。

## 7 扩展点（RPG）

现在只做观光模式；扩展路线、子系统挂点和预算见 ENG-ROADMAP。观光模式下的现行规则（不出现人物、没有可点选的东西、偶发事件全片唯一）照旧。扩展的方式：

1. 枚举只在末尾追加值，JSON 一律按字符串存，旧数据和旧存档照读；消费方写穷举 `switch`（§3）。
2. record 只加 init 属性，不动位置参数。
3. 接口加成员一律带默认实现，或者另开新接口；已有实现不用改。
4. 新系统一律是新的 Kernel 服务、新的存档段和新的契约块，不加 Autoload（§2）。
5. 需要新的帧步骤时只追加 `FramePriority` 常量，值不与现有步骤相同。
6. 观光和 RPG 是两个规则集，存档记下所用的规则集；观光构建的行为和门禁不变。
7. 不许做的：改已有签名或枚举序号；让 `Build()` 读运行时状态；为剧情改烘焙产物或烘焙碰撞。剧情带来的世界变化一律放在运行时层：显隐掩码、物体差分、运行时门体、导航覆盖。
