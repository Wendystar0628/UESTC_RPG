# ENG-CODE · 代码结构准则

> **范围**：本文规定写代码时的结构规矩：依赖方向怎么落地、规则值与数据各留一份、先复用再新写、不留死代码、控制文件规模、测试代码怎么写。
> **不在本文**：分层、依赖方向、禁用写法与架构导向见 ENG-ARCH §1、§2、§6；测多少、什么时候跑见 WF-RULE §9 与 ENG-GATES §1；命名与目录见 CORE-CONVENTIONS §3、§5。
> **查阅**：先读 §0；依赖看 §1；规则值与数据看 §2；复用看 §3；死代码看 §4；规模看 §5；测试代码看 §6。

## 0 结论

1. 依赖只朝一个方向：运行时只读契约里的数据，全局流程遍历所有内容模块，不点名某一个（§1）。
2. 同一含义的数只定义一次，别处引用；坐标、实体 ID、尺寸、名称写数据，Tune 只放规则值（§2）。
3. 写之前先找现成的：引擎内建、成熟的开源库、仓库公共层，有就用，不手写一套；出现第二份相同代码就收进公共层（§3，D-237）。
4. 被取代的代码同批删；不为测试开单实现接口；不吞错、不留过时兜底（§4）。
5. 文件、方法、构造参数超限就拆；多人常改的清单文件拆小，能生成的不手写（§5）。
6. 测试测行为、不钉实现；契约的假实现共用一份夹具（§6）。

### 0.1 接入要点

- **加 `using` 或项目引用时**：照 ENG-ARCH §2 的依赖方向；运行时代码不用生成层的实现类，内核不用系统层（§1）。
- **要用碰撞顶、台阶、门高、层高、预算这类规则数时**：找到它的定义处引用；没有就加进对应的规则类，不写字面量（§2）。
- **要写坐标、实体 ID、尺寸、名称时**：写进按图的数据或覆盖层，不写进 Tune 或 Site 代码（§2）。
- **要写算法或基础设施前**（三角剖分、多边形裁剪、噪声、序列化、空间索引、寻路、网格简化之类）：先查引擎内建和成熟的开源库，再查公共层，有就用（§3）。
- **写测试前**：先读 §6，测多少见 WF-RULE §9。
- **注释或数据里提到文档时**：只写文档编码，不写节号（WF-DOC §3）。
- **提交后钩子提示测试过多或文件过大时**：推送前按 §5、§6 精简或拆分。

## 1 依赖方向

依赖方向以 ENG-ARCH §2 为准，本节只列落地时常犯的写法和改法：

- **内核引用系统层**：kernel 不用 systems 的类型。系统要在启动时参与，就实现内核给的接口，接口和数据类型放 Contracts。
- **运行时用生成层的实现类**：systems、style、camera 只读 Contracts 里的数据类型，不用 Planner、Params 这类生成层内部类；生成层改实现不应连带运行时。
- **全局流程点名某个模块**：烘焙、碰撞、发现这类面向整张图的流程，经 `IContentModule` 遍历全部模块，不 `new` 某一个区的模块。
- **命名空间成环**：两个命名空间互相引用时，把共用的常量或类型挪到被依赖的一方。

## 2 规则值与数据各一份

- **规则值**：同一含义的数只定义一次，其他地方引用它，不复制字面量。
  - 行走与碰撞的规则值（碰撞顶、台阶、胶囊半径、默认门高、梯段最大升高，数值见 SYS-WALK）收在生成层公共的行走规则类里，碰撞生成、行走烘焙和运行时的行走调参都读它。
  - 建筑的通用默认值（层高、窗台、女儿墙、勒脚、小屋尺寸）放建筑生成的默认规则，各区只写与默认不同的项。
  - 预算常量在代码里只留一处，各模块按名字读。
- **数据**：坐标、实体 ID、尺寸、朝向、中文名写在按图的数据或覆盖层（CORE-CONVENTIONS §5）；Tune 只放规则值和风格参数。同一个 ID 只在一处出现，代码按 ID 读数据，不在 Tune、Site 和覆盖层各写一份。
- **派生值不手写**：缓存是否过期从输入本身判断，规则值从定义处读，不手写版本串、改规则时再手动加一。

## 3 先用现成，再复用，不复制

- **先用现成**（D-237）：引擎内建（Godot 节点与服务器、Jolt、导航、本地化、Image 等）或成熟的开源库（.NET 标准库、仍在维护的 NuGet 包）能做的，就用它，不自己手写一套。只有现成的满足不了硬约束（生成层是纯 .NET、同机同输入同输出、许可）或接入代价明显更大时才手写，在类注释里一句话写明理由。
- **引入库**：许可只收 MIT、Apache、BSD、ISC、OFL，并登记（OPS-RELEASE）；NuGet 包和程序集引用按 WF-BUILD §3 申请；生成层只用纯 .NET 的库。
- 新写类或工具函数前，先查公共层：几何底座 `gen/parts/core`、平面几何 `gen/geometry`（世界要素的立面与轮廓在 `gen/world`）、各生成包的公共层。
- 第二份相同或只差参数的代码出现时就收进公共层，原处改引用；不复制整个模块或框架类再改。
- 各区的差异写成数据或参数，不靠每区一套同构的类来表达。

## 4 不留死代码

- 桩或旧实现被真实实现取代时，同一批删掉，连同只为它存在的测试（D-209）。
- 临时诊断用完就删，包括环境变量开关、日志前缀和诊断类；要长期保留的诊断参数写进 ENG-GATES-SHOTS §1。
- 只有一个生产实现的接口不为测试而开，测试用真实对象加临时目录；真要换实现时再抽接口。
- 不吞异常，不写"拿不到就用旧值"的兜底：失败就报错。确实可缺的服务在调用处明确按可缺处理。

## 5 规模

- 单个文件超过约 600 行、方法超过约 80 行、构造参数超过 8 个，就按职责拆开；拆分本身不改行为。
- 多人常改的清单文件（登记表、调参表）按程序集或按区拆开；能从代码生成的不手写。
- 不足约 1000 行、又没有独立依赖边界的程序集，并进相邻程序集；边界靠依赖规则立，不靠多建程序集。

## 6 测试代码怎么写

测多少、什么时候跑见 WF-RULE §9，本节只管写法。

- **按 demo 阶段测**：容差取厘米、帧这一量级，样本几十个够，不撒上千个，一个专项几分钟内跑完；确定性要求逐位一致的除外（WF-RULE §15）。
- **测性质，不钉实现**：断言"同一输入两次结果一致、不重叠、不出界、走得到"这类性质；不钉布局哈希、指纹和内容数量，内容一调就红的断言不写。
- **假实现只有一份**：`IWorldModel`、`IMapService`、`IRuleset` 这类契约的假实现放共用测试夹具，带默认实现，测试只覆盖要改的成员；不在每个测试文件各写一份。
- **夹具不是第二套系统**：不在测试里重写整套世界或天气；要真实行为就用真实实现。
- **跟着代码走**：被测代码删了，测试同批删；行为改了就改断言，不另加一份并存。
- **一个测试文件过 300 行**：先看是不是在测实现细节或重复搭场景，能删就删。
