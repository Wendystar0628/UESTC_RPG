# SYS-SAVE-FORMAT · 格式、损坏处理与安全

> **范围**：本文规定存档容器与序列化约定、格式号与段版本、存档损坏的处理、唯一的设置文件 `settings.json`、禁止用 Resource 与 ConfigFile 存读档的安全原则。
> **不在本文**：存档位模型与各段存什么（SYS-SAVE）；保存时机、读档流程与一致性（SYS-SAVE-FLOW）；文件布局、DTO、写盘步骤（`game/kernel/save/format/`）；契约签名（`game/contracts/Runtime/Save/`）；命令行与 G4、G20（ENG-GATES）。
> **查阅**：先读 §0；格式与版本看 §1；坏档看 §2；设置文件看 §3；安全看 §4

## 0 结论

1. **每次保存写新文件，保留 3 代，不覆盖**；容器是定长头、可单独读的 meta、压缩的分段 JSON、缩略图（§1）。
2. **版本只有两层**：一个格式号 `format` 加每段的 `v`；字段增减升段版本，demo 阶段不写迁移，版本对不上按坏档处理（§1.3、§1.4，D-232）。
3. **坏档从最新一代往旧代退**，全坏只能开新游戏，坏文件不自动删除（§2）。
4. **设置只有一个文件 `settings.json`**，界面、输入、画面、声音各占一节（§3）。
5. **读档的输入不可信**：读档最多把世界摆成合法状态，不执行代码、不创建任意对象；禁止用 Godot Resource、ConfigFile、`StrToVar` 一类能创建对象的方式存读档（§4）。

### 0.1 接入要点

- **段的数据**：只放基础类型、向量、契约枚举和 ID，不放 `object`、Godot 类型或开放多态（§1.3）
- **段的字段有任何增减**（哪怕只加一个可选字段）：段版本加 1；不写迁移，旧版本的段读档时按坏段处理（§1.4、§2）
- **存档里引用别的数据**：只存 ID，不存文件路径；ID 不复用（§1.4、§4）
- **读写设置**：只经设置存储读写 `settings.json`，不自己读写 `user://`；加一项设置先在对应的节里登记键、类型和默认值（§3）

## 1 格式与版本

### 1.1 容器

布局与写盘步骤以 `game/kernel/save/format/` 为准。规则：

- 一个文件依次是定长头、未压缩的 meta JSON、压缩的分段 JSON 正文、WebP 缩略图。**meta 可单独读**：存档卡只读它；读档仍校验整个文件的哈希。
- meta 记存档位、代号、世界线号、游玩时长、地图、世界时间、季节、天气、模式、位姿与空间、规则集、保存原因、系统时钟时间。**系统时钟时间只用于显示，从不进入世界状态**（SYS-SAVE-FLOW §3）。
- 哈希只发现损坏，不防修改，不加密：观光作品里改存档不算作弊。
- **不用"临时文件 + 改名"**：每代都是新建的文件，写了一半就断电，这一代校验失败，读档退到上一代。
- 未知段原样保留，写回时照抄；缺段用 `CreateDefault` 补。

### 1.2 缩略图

WebP 缩略图（尺寸以 `game/kernel/save/format/` 为准）。只在退出、返回标题、新游戏交还控制时抓新图（经游戏内统一拍摄服务抓帧，抓帧时隐藏界面，ENG-GATES-SHOTS §1.2），其余保存沿用上一代；缩放编码放后台；抓不到图不阻断存档。

### 1.3 序列化约定

- 每个包用源生成的序列化上下文，约定同契约的 `ContractJson.Options`。
- 每段一个只读 `sealed record`，只放基础类型、向量、契约枚举和 ID。
- 缺字段、未知字段、不认识的枚举字符串都按"这一段不合法"处理（§2）；快照里出现 NaN 与 ∞ 是 bug。只用带 `JsonTypeInfo` 的重载（G4）。

### 1.4 版本

- **段版本**：一段的字段有任何增减都升 `v`，纪律同契约的"只增不改"。
- **不写迁移**（D-232）：`format` 或某段的 `v` 与本构建不同，不论旧还是新，都按坏档处理（§2）：核心段对不上整代作废，其余段换成默认值。
- **往返测试**：只留当前格式一份往返读写测试（G20）；没有金档，发布之后再按需加旧格式的样本。序列化与解码往返保持数据一致。
- **持久化 ID**（STD-CONVENTIONS §3.7）：ID 不复用，改名不改身份；真正删除的对象，读档时按 SYS-SAVE-FLOW §2.6 修复。

## 2 存档损坏

读一个存档位时，从最新一代往旧代依次试，第一份通过全部检查（魔数与长度、哈希、JSON 解析、核心段反序列化、格式号与段版本不新于本构建）的就用它。回退只在同一条世界线内进行：一代读不出时，只有当前的解码还能读出它的元信息、确认与上一代同属一条世界线，才退到上一代；身份读不出的这一代按坏档处理、文件保留，不猜它属于哪条世界线，不为此另做预扫描或加新锚点（TOOL-233）。

| 情况 | 处理 |
| --- | --- |
| 最新一代坏了，旧代可读 | 改用最新的可读代，不另分状态 |
| 全部代都读不了（包括来自更新版本的） | 存档卡显示"存档无法读取"；文件不动，观者可在这个存档位开新游戏，覆盖前二次确认 |
| 某一段不合法 | `maps`、`world`、`weather` 这三类核心段不合法，整代视为不可读，退到上一代；其余段换成默认并记一次修复 |
| 另一个进程占着锁 | 只读，不保存（SYS-SAVE §1） |

- 不可读的文件不会被自动删除，观者明确确认开新游戏之后才覆盖。

## 3 设置文件：唯一的 `settings.json`

界面、输入、画面、声音的设置合成**一个**档案级文件 `user://settings.json`，不进存档，换存档位不变；门禁和基准不读任何 `user://` 文件。这一节是设置文件的权威，SYS-GRAPHICS §6、SYS-AUDIO §7、UI-NAV §3.5 只写各自那一节存什么。

- **结构**：顶层按 `ui`、`input`、`graphics`、`audio` 分节，各节的键、类型、范围和默认值由对应的包登记。`input` 节存物理键码和鼠标键号，不存 `InputEvent` 对象；向量、颜色拆成几个数字。
- **一个存储**：只有一个设置存储读写它，各系统经它取自己那一节，不自己读写 `user://`。音频要比界面更早拿到音量，所以启动最早期就读入整份，音量先应用。
- **解析**：用 System.Text.Json 源生成读入，JSON 不会按文件内容创建对象，所以不需要先查文本。类型不对或越界的键用默认值，未知的键忽略，缺的节补默认。
- **写盘**：替换覆盖并留 `.bak`；读不了就退到 `.bak`，`.bak` 也不行就用全部默认值并写日志；写不了就放弃这次写盘，内存里的设置照常生效。
- 图形接口与显卡选择所需的 `engine_override.cfg` 在主线之后（SYS-GRAPHICS §3）；它由引擎在任何 C# 代码之前读取，到时仍是独立的文件，且只写登记过的几个键。

## 4 安全：为什么禁止用 Resource 和 ConfigFile 存读档

**威胁模型**：读档的输入不可信，哪怕只是存档被误改或损坏。嵌了 GDScript 的 `.tres` 被加载时代码会执行，`ConfigFile`、`StrToVar` 会按文件内容创建对象。所以：

1. **存读档与设置只经 System.Text.Json 源生成**：反序列化到登记过的 DTO；未知段只在容器层按原始字节保留。
2. **G4 禁止的写法**：全工程用 `ResourceLoader`、`ResourceSaver` 读写 `user://`；存档与设置代码里用 ConfigFile、`StrToVar`、`BytesToVar*`、`GetVar`、Godot 的 `Json`，以及不带 `JsonTypeInfo` 的序列化重载。
3. **各段在 `Restore` 里核对内容**：数组长度；数值有限且在合法范围。
4. **存档里只存 ID，不存文件路径**：读档不加载外部文件，也不联网。
5. **一票否决**：丢档；读档时执行了存档里的代码或创建了存档指定的对象；存档被覆盖或删除导致无法回退；来自更新版本的存档被旧构建覆盖。
