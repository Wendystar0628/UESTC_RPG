# SYS-SAVE-FORMAT · 格式、迁移、损坏处理与安全：容器、段版本、坏档、设置文件

> **范围**：本文规定存档容器与序列化约定、段版本与迁移、金档、存档损坏与版本不兼容的处理、设置类文件只接受基本类型、禁止用 Resource 与 ConfigFile 存档的安全原则。
> **不在本文**：存档位模型与各段存什么（SYS-SAVE）；保存时机、读档流程与一致性（SYS-SAVE-FLOW）；文件布局、DTO、写盘步骤（`game/kernel/save/format/`）；契约签名（`game/contracts/Save/`）；命令行与 G4、G20（ENG-GATES）。
> **查阅**：先读 §0；格式与迁移看 §1；损坏与版本不兼容看 §2；设置文件看 §3；安全看 §4

## 0 结论

1. **每次保存写新文件，保留 3 代，不覆盖**；容器是定长头、可单独读的 meta、压缩的分段 JSON、缩略图（§1）。
2. **段的数据只放基础类型**，字段增减升段版本并写纯函数迁移；新于本构建的存档只读（§1.3、§1.4）。
3. **坏档从最新一代往旧代退**，三代全坏只能开新游戏，坏文件不自动删除（§2）。
4. **存档会被玩家互相分享**：读档最多把世界摆成合法状态，不执行代码、不创建任意对象；禁止用 Godot Resource、ConfigFile、`StrToVar` 一类能创建对象的方式存读档（§3、§4）。

### 0.1 接入要点

- **段的数据**：只放基础类型、向量、契约枚举和 ID，不放 `object`、Godot 类型或开放多态（§1.3）
- **段的字段有任何增减**（哪怕只加一个可选字段）：段版本加 1，并写迁移函数；迁移是纯函数，不碰 Godot、不读服务状态（§1.4）
- **存档里引用别的数据**：只存 ID，不存文件路径；ID 不复用，确需换 ID 时提交 ID 迁移表并升段版本（§1.4、§4）
- **读写档案级设置文件**：先查文本有无 `Object(` 等写法再解析，只接受基本类型，写入走临时文件加替换（§3）

## 1 格式与迁移

### 1.1 容器

布局与写盘步骤以 `game/kernel/save/format/` 为准。规则：

- 一个文件依次是定长头、未压缩的 meta JSON、压缩的分段 JSON 正文、WebP 缩略图。**meta 可单独读**：存档卡只读它；读档仍校验整个文件的哈希。
- meta 记存档位、代号、世界线号、游玩时长、地图、世界时间、季节、天气、模式、位姿与空间、规则集、保存原因、系统时钟时间。**系统时钟时间只用于显示，从不进入世界状态**（SYS-SAVE-FLOW §3）。
- 哈希（SHA-256）只发现损坏，不防修改，不加密：观光作品里改存档不算作弊。
- **不用"临时文件 + 改名"**：每代都是新建的文件，写了一半就断电，这一代校验失败，读档退到上一代。
- 未知段原样保留，写回时照抄；缺段用 `CreateDefault` 补。
- 版本两层：一个格式版本 `format` 加每段的 `v`。

### 1.2 缩略图

384×216 的 WebP。只在退出、返回标题、新游戏交还控制时抓新图（抓帧前隐藏界面），其余保存沿用上一代；缩放编码放后台。

### 1.3 序列化约定

- 每个包用源生成的序列化上下文，约定同契约的 `ContractJson.Options`：camelCase，枚举按字符串写，向量写成数组，ID 写成字符串。
- 每段一个只读 `sealed record`，只放基础类型、向量、契约枚举和 ID。
- 缺字段、未知字段、不认识的枚举字符串都按"这一段不合法"处理（§2）；快照里出现 NaN 与 ∞ 是 bug。只用带 `JsonTypeInfo` 的重载（G4）。

### 1.4 版本与迁移

- **段版本**：一段的字段有任何增减都升 `v`，纪律同契约的"只增不改"，旧构建遇到新档时只会只读，不会丢字段再写回去。
- **迁移**：每段自带逐版本的纯函数 `Migrate(v) → v + 1`，读档时在后台线程按链迁到当前版本；迁移后不立即写回，等下一次正常保存。
- **新于本构建**：`format` 或任一已登记段的 `v` 比本构建新，整个存档位就是 `NewerBuild`：只读，不读档，不自动写（§2）。
- **往返测试**：只留当前格式一份往返读写测试（G20）；发布之后再按需加旧格式的金档。
- **持久化 ID 换名**（CORE-CONVENTIONS §3.7）：ID 不复用，改名不改身份，平时不需要迁移。确需换 ID 时，负责数据的包提交旧 ID → 新 ID 的映射 `id-remap.json`，引用它的段各升一次 `v`；真正删除的对象不给映射，读档时按 SYS-SAVE-FLOW §2.6 修复。

## 2 存档损坏与版本不兼容

读一个存档位时，从最新一代往旧代依次试，第一份通过全部检查（魔数与长度、哈希、JSON 解析、核心段反序列化）的就用它。

| 情况 | 处理 |
| --- | --- |
| 最新一代坏了，旧代可读 | 改用最新的可读代，记为 `RecoveredOlderGen` |
| 三代全坏 | 记为 `Corrupt`；文件不动，存档卡显示"存档已损坏"，观者可在这个存档位开新游戏 |
| 来自更新的版本 | 记为 `NewerBuild`：只读，不读档，不自动写；开新游戏要二次确认 |
| 某一段不合法 | `maps`、`world`、`weather`、各图天气这四类核心段不合法，整代视为损坏，退到上一代；其余段换成默认并记一次修复 |
| 另一个进程占着锁 | 只读，不保存，提示"另一个窗口正在运行 · 本窗口不保存" |

- 坏档和新版本的档不会被自动覆盖或删除，观者明确确认之后才覆盖。

## 3 设置类文件只接受基本类型

适用于 `settings.cfg`、`input.cfg`、`graphics.cfg`、`audio.cfg`。它们是档案级文件，仍用 ConfigFile 格式；音量要比界面更早拿到，所以 `audio.cfg` 独立成文件。门禁和基准不读任何 `user://` 文件。

ConfigFile 的解析器支持 `Object(类名, 属性…)` 写法，**在 `Load` 或 `Parse` 返回之前就已经按文件内容创建了对象**，读出来再查类型挡不住。所以：

1. **先查文本**：含 `Object(`、`Resource(`、`SubResource(`、`ExtResource(` 任一写法，整份不用，退到 `.bak`，`.bak` 也不行就用默认值并写日志。
2. **再解析**：每个键按登记表只接受 bool、int、float、String；类型不对或越界用默认值，未知的键忽略。
3. **只存基本类型**：向量、颜色拆成几个数字存；`input.cfg` 存物理键码和鼠标键号，不存 `InputEvent` 对象。
4. **写盘**：写临时文件、落盘、用替换覆盖并留 `.bak`；仍失败就放弃这次写盘，内存里的设置照常生效。
5. **`engine_override.cfg`**：引擎在任何 C# 代码运行之前就读它，没法先查文本，所以只写登记过的几个键。

## 4 安全：为什么禁止用 Resource 和 ConfigFile 存档

**威胁模型**：存档会被玩家互相分享，读档的输入不可信。实测：嵌了 GDScript 的 `.tres` 被加载时代码会执行；`ConfigFile`、`StrToVar` 会按文件内容创建对象。所以：

1. **存读档只经存档包**：正文只用 System.Text.Json 源生成，反序列化到登记过的 DTO；未知段只在容器层按原始字节保留。
2. **G4 禁止的写法**：全工程用 `ResourceLoader`、`ResourceSaver` 读写 `user://`；存档代码里用 ConfigFile、`StrToVar`、`BytesToVar*`、`GetVar`、Godot 的 `Json`，以及不带 `JsonTypeInfo` 的序列化重载。
3. **各段在 `Restore` 里核对内容**：数组长度（标记 ≤ 50、安全点环正好 16 槽、天气队列有上限）；数值有限且在合法范围。
4. **存档里只存 ID，不存文件路径**：读档不加载外部文件，也不联网。
5. **一票否决**（ENG-GATES-VETO §1）：丢档；读档时执行了存档里的代码或创建了存档指定的对象；存档被覆盖或删除导致无法回退；来自更新版本的存档被旧构建覆盖。
