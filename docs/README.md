# CORE-INDEX · 《电光年华》开发总纲

> **范围**：本文是全项目唯一的顶层，只放每次开发都要掌握的全局：项目与约束、信息地图，以及全员共守的工作原则、协作与分工、文档规范、代码规范与运行时可靠性。
> **不在本文**：具体内容（作品取舍、规则细则、设计、数值、清单）都在下层文档，按 §1 查找；作品与范围在 PRD-SCOPE；不变量全文在 PRD-INVARIANTS；角色入口在 WF-ENTRY。
> **查阅**：开工时钩子整节注入本文各节与本角色的入口卡；信息在哪、仓库目录与文档地图看 §1

## 0 项目与约束

- **项目**：《电光年华》，校园题材的独立 RPG，本阶段只做观光规则集；Godot 4.7.2 .NET（C#），只做 PC；作者的个人作品，处于 demo 阶段（PRD-SCOPE）。
- **硬约束**：INV（PRD-INVARIANTS）与作者明确禁止的事项。成品只守 INV——画风、精度底线、不出现人物、场景文字、日式边界、不是地图复刻、世界规则——具体设计按需查各域；地图只改项目的世界文件，不从 OSM 等外部地图取数据。
- **优先级**：冲突时依次服从作者、硬约束、主线不中断；硬约束以外都是默认做法，按判断取用；审美以作者为准（DECISION-252）。
- **本文的规则**：§0、§1 以外各节每条一句结论，括号里是细则所在；引用时写节名与条目标题，不写条号。

### 0.1 接入要点

- **派单、写简报**：不抄本文的规则，写"顶层规则见 CORE-INDEX"。
- **改一条规则**：先改它指向的细则，再改本文那一句。
- **往本文加内容**：只加每次开发都要的全局，放进内容所属的那一节；具体内容写进下层，这里至多一个标题或一句话加指向（STD-DOC §1）。一节快到 STD-DOC §5 的上限时先压缩，压不下就按主题拆出新的一节，不加"续"节。
- **新开一个域、改仓库顶层目录或某类信息的存放位置**：同批改 §1；新增主题文档登记在它的域总纲，不登在这里（STD-DOC §7）。

## 1 信息地图

每类信息只在一处；先在这里查到位置，再按需读。

**信息在哪**：
- **钩子注入**：开工时送来本文各节与自己的入口卡（WF-ENTRY），之后随作者消息、定时与来信整套重送；写文件之前、读改某个路径、派工、看截图时送来管它的文档的接入要点；时机与节流见 `.collab/tools/README.md`，没送到就手动读。
- **钩子与脚本**：钩子在 `.collab/tools/hooks/`（Claude 登记在 `~/.claude/settings.json`，Codex 在 `~/.codex/hooks.json`），协作与巡逻工具在 `.collab/tools/`，两者的作用与用法见 `.collab/tools/README.md`；工程脚本在 `scripts/`，观察台采集在 `dashboard/tools/`，全部脚本的作用与用法列在观察台资料页的脚本目录，谁调用、读写什么在体系页。

- **实现**：代码，签名与契约以源码为准。
- **数值、坐标、ID 与清单**：数据文件（按图数据在 `game/data/`）。
- **为什么这样定、是否生效**：REG-DECISIONS，按决策号 DECISION-nnn 查。

- **作者看的全局**：观察台 `dashboard/`（WF-COMMS §6）。

**仓库目录**：
- `game/`：Godot 工程，C# 代码、着色器、契约与按图数据。

## 2 工作原则

1. **按需查阅**：本文只给全局；在 §1 找到域总纲，按标题找到文档，读它的 §0 与接入要点；要细节时 grep `docs/SECTIONS.md` 按行号只读那一节，不整份通读（STD-DOC §1）。
2. **精度按 demo 阶段把握**：精度、样本量、测试与验收按 demo 阶段定，看不出差别的不追，不要求全局高精度：精度处理从简，看不见的部分和走不到处的碰撞极简处理（一个平面、一道空气墙也行），建模细节不简化，外面看着没问题就不管内部形态，数值按数量级判断，不预设包体与内容规模上限；画面质量与架构底座不降；先接进主线跑通，缺陷按严重程度修，修不收敛就停（WF-RULE §8、§14、§15，DECISION-290）。
3. **最小实现，先用现成**：能用 Godot 原生与现成库的不自写（§5「先用原生，不重复造轮子」）；只做本单要求的，做完即停，多出的想法写在回报末尾；不为假想的扩展加抽象、配置和开关，不写校验和与 proof 报告，不自加门禁和测试脚手架；一次性产物用完即删（WF-RULE §1、§13）。
4. **最小测试，快检通过即推送**：默认只跑快检，涉及启动、行走、存档再加几分钟内的核心专项；通过即推送，没有新改动或新失败不复测；阻断项先修，其余登记、不挡推送；测试写法见 §5「测试读权威、测行为」；测量与验证在后台运行，不操作作者桌面（WF-RULE §4、§9）。
5. **根因修复，同批清旧**：先参考相关同类主流游戏的做法，再查别处有没有同类问题、同批修齐；在架构的根上改，不加没有设计依据的特例、兜底、开关或绕过（设计要的默认、降级与回退写进管它的文档，代码处标出处）；撞到架构问题先治理，量大就停下本行、拆单排在它前面，规模大不是打补丁或推迟的理由；可以带着登记过的缺陷推送，不能带着掩盖它的代码推送；改设计时同批迁完所有使用方，删净旧代码、测试与文档，不留兼容层；补丁由 G4 与另一方的收口审计拦（WF-RULE §10、§14，STD-CODE §4，WF-FLOW §3.1）。
6. **改文件即维护体系**：新建项目文件或加内容前，先按结构图找到归属（文档看文档树，代码看模块分层与文档文件头的 `paths`）；有归属就写进去，先复用再新写，不另开平行文件；找不到归属先改结构并报主会话，不随手找路径；改完同批登记进索引与文档文件头的 paths，被取代和重复的删除或合并（WF-RULE §16）。
7. **顺手清掉死代码与旧设计**：工作中看到没有使用方的代码、测试、数据与文档段落，或已被取代的旧设计、旧路径、旧说法，以及重复和放错层的东西，量小当批删掉并同批改引用，量大开队列行；删前确认真没有使用方，别人正在改的目录写信给负责方，不视而不见（WF-RULE §16）。
8. **先判轻重缓急，不向作者出选项**：需要拍板的写给主会话；架构、实现、流程与工程排期由两位指挥定，内容开发的节奏与审美取向归作者，挂给作者的事先按主会话的判断做、不挡推进，作者看过再调；新需求先判插队、排在当前批次之后还是按轻重插入，影响在做或排着的活就同批改它们的描述；不预估工期，定期事项按开发节点触发；高层信息有变当场更新观察台（WF-STATUS §2，WF-RULE §2、§3，WF-COMMS §6）。
9. **作者的要求不合理就提出反对**：主会话认为作者的要求违背硬约束、损害架构或数据权威、或代价与收益明显失衡时，先说清理由、代价和更好的做法，不照单执行；作者听过仍坚持就照办（WF-ROLE §4）。
10. **游戏本体的失败先登记再继续，同类反复就整类排查**：交回或集成之后抓到的游戏失败（编译、门禁、运行报错、预烘、截图评审、性能、存档、收口审计查实），先按根因类别用 `.collab/tools/fail.py add` 登记，再接着修；没有合适类别当场新增候选；同一子类自上次整类排查以来在最近一段提交内累计到 3 条，主会话就停止逐条修，开一行整类排查，在根上补缺口并扫清同类残留（ENG-FAILS §0，DECISION-285、DECISION-296）。

## 3 协作与分工

1. **施工流程**：活进施工队列 → 指挥按队列派子代理，简报写明模型、推理强度和同时在改的邻居 → 子代理只在派工简报允许的路径写，不编译、不提交，共享文件与契约走申请 → 指挥统一编译、修错、快检，一行一提交、只带自己的路径，首行"行号 领域词：一句话"，推送前确认没有别人未推的提交，推到 `main` → 涉及画面的由主会话跑固定机位截图评审；出了问题一律开行插队、在最新版本上改，不回滚（WF-FLOW，WF-RULE §7，WF-BUILD §1）。
2. **双指挥分工与沟通**：主会话（Claude）是总指挥，负责画面、文档与评审；Codex 主线（GPT）负责工程；任务与状态只以施工队列为准；给对方发话先写来信，一信一事，标【需定】【待审】【知会】，不超过 5 行，对方空闲时再叫醒（WF-COMMS §4，WF-ROLE）。
3. **模型与子代理**：观感未定的审美工作交 Opus，Claude 侧其余工作交 Sonnet，GPT 不做审美、不碰任何界面层（游戏界面与观察台前端，DECISION-287）；Codex 侧日常用 gpt-6.1-sol，机械活用 luna，astra 只做临时只读审计；子代理一律新开，名字以队列行号或"调研""核查"开头，派单用参数传模型与推理强度（WF-MODEL，WF-ROLE §1）。
4. **动可能撞车的事先看对方**：改施工队列、共享文件与契约，在主检出提交、推送、变基或合并，跑预烘、截图、门禁这类重活，起停后台进程，删文件与工作树之前，先看一眼对方最近的来信、在做的行、未提交与未推送的改动和构建锁；撞上了先写信约定先后，不抢先动手（WF-RULE §10）。
5. **能同时写就同时写**：前置只写真正的依赖——要用那一行的结果，或改同一批文件、会干扰正在跑的测量和截图；执行方正忙、同在一个大目录、交接要多写几句都不算前置。Codex 主线在干活时，就绪的行照样写信交给它开子代理并行做；编译、快检与提交由指挥统一收口，小活不排长队（WF-STATUS §2，DECISION-286）。

## 4 文档规范

1. **单一权威，同批改齐**：同一信息只在一处，别处给指向；改规则、编号或标题前，用文档索引和 grep 查出讲它、引用它的所有地方（含 `CLAUDE.md`、`AGENTS.md`、钩子与记忆），同批改到一致、不留旧名；冲突按 STD-DOC §6 判（STD-DOC §3、§4.2）。
2. **写给按字面执行的模型**：只写删了会出错的规则、适用范围和完成标准；默认做法附一句理由，例外至多一个出口；"必须""禁止"与加码措辞只给硬约束；不写铺垫、例子堆、日期与进度（STD-DOC §4.2）。
3. **分层存放，指针一层到底**：文档只写结构、规则、设计目标和导向，按 §1 放，顶层只放全局；跨文档写"编码 §小节"，代码与数据只写编码，会增长的一组节写组名、不写区间；超上限先删，再按子主题拆，压不下才放宽（STD-DOC §3、§4.1、§5）。

## 5 代码规范

1. **先用原生，不重复造轮子**：写功能前先判断 Godot 原生（节点、服务器、资源与内建工具类，签名查 `docs/godot-api/signatures.txt`）能不能做，原生做得到且更简单就用原生；其次 .NET 自带与已引用的成熟库；只在原生做不到，或违反生成层纯 .NET、确定性、画风底线时才自写，并在代码处写明理由；改到已有的自写实现时同样先判能否换成原生（STD-CODE §3，DECISION-297）。
2. **依赖只朝下，模块经契约接上**：契约 → 世界与公共几何 → 内容生成 → 运行时，同层内容模块互不引用，生成层是纯 .NET、不读运行时状态；模块之间只经契约与 Kernel 服务取用，不按节点名、字符串键或强转去找别的模块的内部类型（ENG-ARCH §2，STD-CODE §1）。
3. **每类状态一个写入方，每类资源一个创建方**：模式、位姿、流程阶段、就绪这类状态只由持有者改写并发布，别处申请或订阅；显示、材质、声音、存档、设置各经自己的服务，材质只经 `ToonSpec` 与白名单着色器，`user://` 每个文件一个读写方（ENG-ARCH §2、§6）。
4. **规则值、数据与机制各一份**：同一含义的数只定义一次，别处引用；坐标、ID、尺寸、名称写进按图数据，不写字面量、不按 ID 特判；同一机制（失败聚合、判码、转角政策这类）出现第二份就收进公共层（STD-CODE §2、§3）。
5. **按职责拆，不按行数切**：类型约 600 行、方法约 80 行、构造参数 8 个即到上限，超了按职责拆成独立类型；不用 partial 分摊，不压行凑数；Godot 宿主节点只做生命周期与编排（STD-CODE §5）。
6. **契约同批迁完**：签名以 `game/contracts/` 源码为准；改动与全部使用方（含组合根与测试替身）同批迁移、删掉旧接口，冻结组只追加；数据与存档只认当前版本，不写迁移（ENG-ARCH §3，SYS-SAVE-FORMAT §1.4）。
7. **同机同输入同输出**：随机只用 `Rng`、`StableHash`，不读系统时钟，遍历字典先排序（ENG-ARCH §2）。
8. **测试读权威、测行为**：测试只守契约、核心体验与回归，标明 `Contract`、`Smoke` 或 `Regression`；期望值从数据与规则常量读，异常只断言类型，不钉实现、不写永远为真或静默跳过的断言（STD-CODE §6）。

## 6 运行时与可靠性

1. **进出只走一条正式链**：新游戏、继续、换图、读档、回标题与退出只经应用流程、地图服务与存档服务编排，系统按应用状态启停；改流程同批删旧入口，不另开平行路径（ENG-ARCH §1，SYS-TITLE §3）。
2. **谁开谁关，先停再排空后释放**：后台任务、订阅与原生资源创建时就挂到所属作用域（应用、地图、格、节点、一次操作）；失败、回标题与退出走同一条路：停接新工作 → 取消 → 等排空 → 逆序释放，关闭期间不新建、不取服务；取消只是请求，清理完才算完成，按令牌或所有者状态识别取消，不看异常文字（ENG-ARCH §2「生命周期与发布」）。
3. **失败带原异常交到底**：失败要么抛出，要么沿结果载体交给文档写明的接收方；包装与聚合保留原异常，失败码在产生处定一次、下游不重判；只打日志、只转文字、返回空或默认值、改报取消、留无人读取的故障任务都算吞（STD-CODE §4）。
4. **异步有主，跨线程只交数据**：每个 Task 都有持有者等它或交给失败通道，不写 `async void`、不丢弃任务，迟到的结果核对代际后丢弃；工作线程只做纯计算与缓存读写，场景树、物理与渲染对象只在主线程碰（STD-CODE §7，ENG-BUDGET-RULES §1）。
5. **就绪看真实状态，等待有出口**：就绪由状态持有者按实际结果发布，不用代理标志或提前完成；每个等待写明在等谁、有失败出口，按连续无进展判停滞、不按总时长；就绪前不撤遮挡、不放输入（ENG-ARCH §2「就绪与等待」）。
6. **构建期能做的不留到运行时**：编译、生成、判鲜在构建期或收口预烘完成，启动只读现成结果、只比输入标识；碰渲染、逐帧代码、烘焙、存档先读 ENG-BUDGET-RULES §0.1，主线程按帧限额挂载，逐帧路径不做托管分配（ENG-ARCH §4）。
7. **存档只存落定状态**：跨读档的状态只经存档段；`Capture` 任何时刻给出落定值、不做 I/O，`Restore` 立即生效；字段增减升段版本，写盘在后台，失败不动旧代（SYS-SAVE-FLOW §0.1、§1.3，SYS-SAVE-FORMAT §0.1）。
