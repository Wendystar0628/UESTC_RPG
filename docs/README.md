# CORE-INDEX · 《电光年华》开发总纲

> **范围**：本文是全项目唯一的顶层，只放每次开发都要掌握的全局：项目与约束、信息地图，以及全员共守的工作原则、协作与分工、文档规范与代码规范。
> **不在本文**：具体内容（作品取舍、规则细则、设计、数值、清单）都在下层文档，按 §1 查找；作品与范围在 PRD-SCOPE；不变量全文在 PRD-INVARIANTS；角色入口在 WF-ENTRY。
> **查阅**：开工时钩子整节注入 §0、§2–§5、§1 与本角色的入口卡；信息在哪、仓库目录与文档地图看 §1

## 0 项目与约束

- **项目**：《电光年华》，校园题材的独立 RPG，本阶段只做观光规则集；Godot 4.7.2 .NET（C#），只做 PC；作者的个人作品，处于 demo 阶段（PRD-SCOPE）。
- **硬约束**：INV（PRD-INVARIANTS）与作者明确禁止的事项。成品只守 INV——画风、精度底线、不出现人物、场景文字、日式边界、不是地图复刻、世界规则——具体设计按需查各域；地图只改项目的世界文件，不从 OSM 等外部地图取数据。
- **优先级**：冲突时依次服从作者、硬约束、主线不中断；硬约束以外都是默认做法，按判断取用；审美以作者为准（D-252）。
- **本文的规则**：§2–§5 每条一句结论，括号里是细则所在；引用时写节名与条目标题，不写条号。

### 0.1 接入要点

- **派单、写简报**：不抄本文的规则，写"顶层规则见 CORE-INDEX"。
- **改一条规则**：先改它指向的细则，再改本文那一句。
- **往本文加内容**：只加每次开发都要的全局，放进内容所属的那一节；具体内容写进下层，这里至多一个标题或一句话加指向（STD-DOC §1）。一节快到 STD-DOC §5 的上限时先压缩，压不下就按主题拆出新的一节，不加"续"节。
- **新开一个域、改仓库顶层目录或某类信息的存放位置**：同批改 §1；新增主题文档登记在它的域总纲，不登在这里（STD-DOC §7）。

## 1 信息地图

每类信息只在一处；先在这里查到位置，再按需读。

**信息在哪**：
- **钩子注入**：开工时送来本文 §0、§2–§5、本节和自己的入口卡（WF-ENTRY），作者每条消息再送一遍 §0、§2–§5；读改某个路径、派工、看截图时送来管它的文档的接入要点；没送到就手动读。
- **钩子与脚本**：钩子在 `.collab/tools/hooks/`（Claude 登记在 `~/.claude/settings.json`，Codex 在 `~/.codex/hooks.json`），协作与巡逻工具在 `.collab/tools/`，两者的作用与用法见 `.collab/tools/README.md`；工程脚本在 `scripts/`，观察台采集在 `dashboard/tools/`，全部脚本的作用与用法列在观察台的脚本页。
- **规则、设计目标与导向**：`docs/`，按下面的域找到域总纲，小节用 `docs/SECTIONS.md` 定位。
- **实现**：代码，签名与契约以源码为准。
- **数值、坐标、ID 与清单**：数据文件（按图数据在 `game/data/`）。
- **为什么这样定、是否生效**：REG-DECISIONS，按 D 编号查。
- **要做的活和状态**：施工队列 `.collab/status/施工状态.md`。
- **双方的沟通**：来信在 `.collab/notes/<收件方>/`；任务单、请求、调研与交回也在 `.collab/`（WF-COMMS §1）。
- **过程与历史**：git。
- **作者看的全局**：观察台 `dashboard/`（WF-COMMS §6）。

**仓库目录**：
- `game/`：Godot 工程，C# 代码、着色器、契约与按图数据。
- `pipeline/`：音频等离线脚本；参与 .NET 构建的烘焙输入装配在 `game/gen/bakeinput/`。
- `scripts/`：构建、门禁、截图、文档索引与清理脚本。
- `docs/`：规则与设计文档。
- `.collab/`：协作目录（队列、来信、任务单、调研、协作工具），不进 git。
- `dashboard/`：作者观察台。
- `tools/`：锁定的 Godot 版本号。
- `output/`、`build/`：构建、测试、截图、缓存与导出产物，不进 git，可删可重建。

**文档分层**：本文 → 域总纲（每个文件夹一份，写本域通用原则和文档树）→ 主题文档 → 子文档。先读域总纲找到主题，再按需往下读。

**作品**（`product/`）：PRD-INDEX 作品总纲。作品是什么、做什么不做什么、硬约束。

**画面**（`art/`）：ART-INDEX 画面总纲。画成什么样的视觉语言。

**世界**（`world/`）：WLD-INDEX 世界总纲。不分图的世界内容规则。

**清水河**（`maps/qingshuihe/`）：MAP-QSH-INDEX 清水河总纲。第一张图的具体内容。

**系统**（`systems/`）：SYS-INDEX 系统总纲。运行时各系统怎么工作。

**界面**（`ui/`）：UI-INDEX 界面总纲。界面有什么、长什么样。

**工程**（`engineering/`）：ENG-INDEX 工程总纲。架构、性能、验收、发布与开发工具（内容预览）。

**计划**（`plan/`）：PLAN-INDEX 计划总纲。工作包与阶段。

**协作**（`workflow/`）：WF-INDEX 协作总纲。两个指挥和子代理怎么干活。

**规范**（`standards/`）：STD-INDEX 规范总纲。写文档、写代码与命名。

## 2 工作原则

1. **按需查阅**：本文只给全局；在 §1 找到域总纲，按标题找到文档，读它的 §0 与接入要点；要细节时 grep `docs/SECTIONS.md` 按行号只读那一节，不整份通读（STD-DOC §1）。
2. **精度按 demo 阶段把握**：精度、样本量、测试与验收按 demo 阶段定，看不出差别的不追，数值按数量级判断，不预设包体与内容规模上限；画面质量与架构底座不降；先接进主线跑通，缺陷按严重程度修，修不收敛就停（WF-RULE §8、§14、§15）。
3. **最小实现，优先复用**：引擎内建或成熟开源库能做的就用它；只做本单要求的，做完即停，多出的想法写在回报末尾；不为假想的扩展加抽象、配置和开关，不写校验和与 proof 报告，不自加门禁和测试脚手架；一次性产物用完即删（WF-RULE §1、§13）。
4. **最小测试，快检通过即推送**：默认只跑快检，涉及启动、行走、存档再加几分钟内的核心专项；通过即推送，没有新改动或新失败不复测；阻断项先修，其余登记、不挡推送；测试守契约、主线与回归，验证行为而不钉死实现；测量与验证在后台运行，不操作作者桌面（WF-RULE §4、§9）。
5. **根因修复，同批清旧**：先参考相关同类主流游戏的做法，再查别处有没有同类问题、同批修齐；在架构的根上改，不加特例、兜底、开关或绕过；撞到架构问题先治理，量大就停下本行、拆单排在它前面，规模大不是打补丁或推迟的理由；可以带着登记过的缺陷推送，不能带着掩盖它的代码推送；改设计时同批迁完所有使用方，删净旧代码、测试与文档，不留兼容层；补丁由 G4 与另一方的收口审计拦（WF-RULE §10、§14，STD-CODE §4，WF-FLOW §3.1）。
6. **改文件即维护体系**：新建项目文件或加内容前，先按结构图找到归属（文档看文档树，代码看模块分层与 `ownership.json`）；有归属就写进去，先复用再新写，不另开平行文件；找不到归属先改结构并报主会话，不随手找路径；改完同批登记进索引或归属表，被取代和重复的删除或合并，看到的明显混乱当批处理或进队列（WF-RULE §16）。
7. **先判轻重缓急，不向作者出选项**：需要拍板的写给主会话；新需求先判插队、排在当前批次之后还是按轻重插入，影响在做或排着的活就同批改它们的描述；不预估工期，定期事项按开发节点触发；高层信息有变当场更新观察台（WF-STATUS §2，WF-RULE §3）。

## 3 协作与分工

1. **施工流程**：活进施工队列 → 指挥按队列派子代理，简报写明模型、推理强度和同时在改的邻居 → 子代理只在本包独占目录写，不编译、不提交，共享文件与契约走申请 → 指挥统一编译、修错、快检，一行一提交、只带自己的路径，首行"行号 领域词：一句话"，推送前确认没有别人未推的提交，推到 `main` → 涉及画面的由主会话跑固定机位截图评审，不合格就 `git revert` 或返工（WF-FLOW，WF-RULE §7，WF-BUILD §1）。
2. **双指挥分工与沟通**：主会话（Claude）是总指挥，负责画面、文档与评审；Codex 主线（GPT）负责工程；任务与状态只以施工队列为准；给对方发话先写来信，一信一事，标【需定】【待审】【知会】，不超过 5 行，对方空闲时再叫醒（WF-COMMS §4，WF-ROLE）。
3. **模型与子代理**：观感未定的审美工作交 Opus，Claude 侧其余工作交 Sonnet，GPT 不做审美；Codex 侧日常用 gpt-6.1-sol，机械活用 luna，astra 只做临时只读审计；子代理一律新开，名字以队列行号或"调研""核查"开头，派单用参数传模型与推理强度（WF-MODEL，WF-ROLE §1）。

## 4 文档规范

1. **单一权威，同批一致**：同一信息只在一处，别处给指向；改一条规则先按文档索引（域总纲 → 主题文档 §0 → SECTIONS）查出讲同一主题的文档，同批改到一致；文档冲突按 STD-DOC §6 判（STD-DOC §4.2，WF-RULE §12）。
2. **面向旗舰模型写作**：读者按字面执行：写规则本身、适用范围和完成标准；默认做法附一句理由，例外至多一个出口；"必须""禁止"只用于硬约束；不写铺垫、成堆的例子和会过期的日期、进度（STD-DOC §4.2）。
3. **分层存放，写得精简**：文档只写结构、规则、设计目标和导向，各类信息按 §1 的位置存放；顶层只放全局，具体内容下放；指针一层到底，写到"编码 §小节"；超出上限按 STD-DOC §5 压缩、放宽或拆分；改名、改结构全量改到最新，不留旧名（STD-DOC §3、§4、§5）。

## 5 代码规范

1. **依赖与数据**：依赖只朝下，生成层是纯 .NET；规则值与数据各一份：规则数引用定义处，坐标、ID、尺寸写进按图数据，不写字面量；不留死代码；文件超过约 600 行就拆（ENG-ARCH §2，STD-CODE §2、§3）。
2. **边界与确定性**：显示、材质、声音各经自己的服务，材质只经 `ToonSpec` 与白名单着色器；随机只用 `Rng`、`StableHash`，遍历字典先排序，同机同输入同输出；改契约同批迁完所有使用方；Godot API 先查 `docs/godot-api/signatures.txt`（ENG-ARCH §2、§3，STD-CODE §0.1）。
3. **失败即报错，构建期能做的不留到运行时**：不吞异常，不写"拿不到就用旧值"的兜底；编译、生成、判鲜等构建期能完成的不放到运行时，启动只读现成结果；涉及渲染、逐帧代码、烘焙、存档先读 ENG-BUDGET-RULES 的接入要点（STD-CODE §4，ENG-ARCH §4）。
